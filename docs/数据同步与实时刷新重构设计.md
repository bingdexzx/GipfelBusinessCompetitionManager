# 数据同步与实时刷新机制（已实现版）

> 状态：已落地实现，与代码一致
> 代码基线：`client/src/api/cache.ts`、`client/src/api/request.ts`、`client/src/realtime/socket.ts`、`client/src/realtime/resource-changed.ts`、`client/src/realtime/useResourceChanged.ts`、`server/src/common/sync.ts`、`server/src/realtime/realtime.gateway.ts`、`server/src/realtime/realtime.service.ts`
> 本文档覆盖「本地存储 / 增量同步 / 实时推送 / 前端刷新」四件事的实际实现。

---

## 1. 实现总览

当前系统已实现完整的四层数据同步与刷新机制：

1. **IndexedDB 本地缓存层**：按「服务器身份 realm + 账号」分库，存全量副本 + 增量基线；
2. **HTTP 增量查询层**：`?updatedAfter=<ISO>` 服务端按 `updatedAt` 过滤，返回 `existingIds` 做删除对账；
3. **WebSocket 实时推送层**：Socket.IO 房间广播，Prisma 写钩子自动触发；
4. **前端组件刷新层**：Vue Composable 精确订阅资源类型，收到事件后自动失效并重拉。

四层机制协同，目标是：**平时靠增量降带宽、变更靠实时即刷新、断线靠重连补回放、离线靠副本可读**。

## 2. 本地缓存（IndexedDB）实现

### 2.1 库名隔离

代码位置：`client/src/api/cache.ts:17-24`

```typescript
// 按「服务器身份 realm + 账号」分库
function currentDbName(): string {
  const realm = getServerRealm();              // 区分不同后端实例
  const id = getActiveUserId();                // 区分不同登录账号
  return id == null
    ? `${BASE_DB_NAME}-${realm}-anon`
    : `${BASE_DB_NAME}-${realm}-u${id}`;
}
```

- **物理隔离**：不同账号、不同服务器的副本各自在独立的 IndexedDB 数据库，完全不串档；
- **账号切换自动重开库**：`openDB()` 检测库名变化时丢弃旧连接，重新 `indexedDB.open()`；
- **旧库清理**：`deleteOldAccountDbs()` 在启动时删除升级前的旧格式库（无 realm 段的 `gipfel-client-cache-u<id>`）。

### 2.2 存储键格式

```

META|baseline|<集合键>                该集合上次增量同步基线（ISO 时间）
META|fullSyncAt|<集合键>              该集合上次全量同步时间戳
```

## 3. HTTP 增量查询实现

### 3.1 服务端工具（`server/src/common/sync.ts`）

```typescript
// 解析 updatedAfter 并构造查询条件
export function applyUpdatedAfter(baseWhere: any, updatedAfter?: string): IncrementalContext {
  const baseline = parseBaseline(updatedAfter);
  if (!baseline) {
    return { where: baseWhere, incremental: false, baseline: null };
  }
  return {
    where: { ...baseWhere, updatedAt: { gt: baseline } },  // 只取更新晚于基线的行
    incremental: true,
    baseline,
  };
}

// 增量响应包装
export function buildIncrementalResult(
  changedItems: any[],
  existingIds: number[],
  total?: number,
): IncrementalListResult {
  return {
    items: changedItems,          // 变更行（增量）
    total: total ?? changedItems.length,
    existingIds,                  // 当前全量 id 集合 → 前端 diff 删除
    serverTime: serverNowIso(),   // 下次同步基线
    incremental: true,
  };
}
```

**服务端使用模式**（各 Service 列表方法）：

```typescript
async findAll(competitionId: number, updatedAfter?: string) {
  const { where, incremental } = applyUpdatedAfter(
    { competitionId },
    updatedAfter,
  );
  const [items, allIds] = await Promise.all([
    this.prisma.material.findMany({ where }),
    incremental
      ? this.prisma.material.findMany({ where: { competitionId }, select: { id: true } })
          .then(rows => rows.map(r => r.id))
      : Promise.resolve(null),
  ]);
  if (!incremental) return items;
  return buildIncrementalResult(items, allIds!);
}
```

### 3.2 客户端请求流程（`request.ts` 的 `_cachedGet`）

```
请求到达
  │
  ├─ ① 查内存 memo（15s 新鲜度窗口）
  │     · 命中且在窗口内 + 无后续事件 → 直接返回内存值
  │     · 键格式：`uid|cid|GET url params`（已加入账户+比赛维度）
  │
  ├─ ② 查 IndexedDB 副本
  │     · 有副本且未失效 → 携带 ?updatedAfter=<baseline> 发增量请求
  │     · 无副本或被写失效 → 不带 updatedAfter 发全量请求（大 pageSize）
  │
  ├─ ③ 网络请求
  │     · 成功 → 写入 IDB：全量 storeAndReturn / 增量 patchFullItems
  │              → 写入 memo
  │     · 失败（离线）→ 返回 IDB 本地副本降级（保证可读）
  │
  └─ ④ 返回结果
```

关键实现细节（`cache.ts`）：

- **增量合并**：`patchFullItems()` 按 id 合并 `items` 到本地全量副本；
- **删除对账**：对比 `existingIds` 与本地副本 id，diff 出被删行并删除；
- **基线单调推进**：仅接受新的 `serverTime ≥ 旧 baseline`，禁止回退；
- **写失效**：POST/PUT/PATCH/DELETE 成功后，调用 `invalidateResource(resourceName)` 清空该资源所有集合的本地副本与 memo；下次请求自动走全量同步。

## 4. 实时推送（WebSocket）实现

### 4.1 连接与鉴权（`server/src/realtime/realtime.gateway.ts`）

```
客户端 socket.io 连接
  │
  ├─ 握手鉴权：handshake.auth.token
  │     · JWT 校验 issuer/audience（与 HTTP 侧一致）
  │     · 查用户：若账号已被删除 → 立即 disconnect
  │     · 若 mustChangePassword=true → 断开并提示先改密
  │     · 通过 → 写入 client.data: { userId, role, competitionId }
  │
  ├─ 自动加入私有房间
  │     · socket.join(`user-${userId}`) → 用户定向推送（消息/权限变更）
  │
  ├─ 客户端主动发送 subscribe { competitionId }
  │     · 房间归属校验：非超管只能订阅自身 competitionId
  │     · 通过 → socket.join(`comp-${cid}`) → 只收该比赛广播
  │
  └─ 断线重连
        · socket.io 内置自动重连（无限次，2s 起步延迟）
        · 重连成功 → 客户端发 sync:replay { afterSeq } → 服务端补发遗漏事件
```

### 4.2 事件清单（服务端广播）

| 事件名 | 触发时机 | 载荷 | 目标房间 |
|--------|---------|------|---------|
| `resource:changed` | Prisma `$allOperations` 写钩子（create/update/delete） | `{ resource, competitionId, ids, action }` | `comp-{cid}` |
| `message:new` | 发布站内消息 | 消息对象 + 收件人信息 | `user-{recipientId}` |
| `company-field:changed` | 产业字段值变更/合同改写 | `{ companyId, competitionId }` | `comp-{cid}` |
| `contract:changed` | 合同执行/状态变更 | 合同对象 + competitionId | `comp-{cid}` |
| `competition:changed` / `fiscal-year:changed` | 比赛/财年配置变更 | 实体对象 | 对应房间 |
| `stock:round-advanced` | 股票推进轮次完成 | 轮次摘要 | `comp-{cid}` |
| `permissions:changed` | 用户角色/权限/范围被修改 | `{ userId }` | `user-{userId}` |

### 4.3 Prisma 写钩子自动广播

```typescript
// prisma.service.ts: $allOperations 中间件
prisma.$use(async (params, next) => {
  const result = await next(params);
  const resource = MODEL_TO_RESOURCE[params.model];
  if (resource && ['create', 'update', 'delete', 'updateMany', 'deleteMany'].includes(params.action)) {
    // 提取 competitionId（关联比赛）
    const competitionId = extractCompetitionId(params, result);
    const ids = extractAffectedIds(params, result);
    this.realtime.broadcastResourceChanged(competitionId, resource, ids, params.action);
  }
  return result;
});
```

**效果**：任何 Service 通过 Prisma 写入（增删改），都会自动广播对应 `resource:changed` 事件 → 所有在线客户端实时刷新，无需每个 Service 手工调广播方法。

## 5. 前端组件刷新实现

### 5.1 事件分发（`resource-changed.ts`）

```typescript
// 中心分发：socket 收到 resource:changed 后，按 resourceType 做三件事：
//  1) 失效该资源的本地缓存 + memo
//  2) 删除/更新 IDB 中的受影响条目（若事件带精确 ids）
//  3) window.dispatchEvent 自定义事件，通知 Vue 组件
export function handleResourceChanged(payload: {
  resource: string; competitionId?: number; ids?: number[]; action?: string;
}) {
  const { resource } = payload;
  // ① 写失效：下次 GET 走全量
  invalidateResource(resource);
  // ② 精确删本地行（若有 ids）
  if (payload.ids?.length) {
    if (payload.action === 'delete') {
      removeFullItemByResource(resource, payload.ids);
    } else {
      markDirtyByResource(resource, payload.ids);
    }
  }
  // ③ 派发全局事件 → useResourceChanged() hook 捕获
  window.dispatchEvent(new CustomEvent('resource:changed:' + resource, { detail: payload }));
}
```

### 5.2 组件级 Hook（`useResourceChanged.ts`）

```vue
<script setup lang="ts">
// 在任何需要"该资源变更就自动刷新"的组件中：
import { useResourceChanged } from "@/realtime/useResourceChanged";

// 订阅 material 资源 → 只要有任意原料写操作，就重新拉 materialsApi.list()
useResourceChanged(['material'], async () => {
  materials.value = (await materialsApi.list()).items;
});
</script>
```

**Hook 内部逻辑**：
1. `onMounted` 时，为每个资源名添加 `window.addEventListener('resource:changed:' + resource)`；
2. 事件触发 → 执行用户传入的 reload 回调；
3. `onUnmounted` 时移除监听，避免内存泄漏。

### 5.3 特殊刷新点

| 场景 | 实现 |
|------|------|
| 断线重连 | socket.io `reconnect` 事件 → `onReconnectHandler` → 重新 `subscribeCompetition()` + 对当前页所有资源发增量对账请求 + 回调结束后派发 `sync:reconciled` |
| 切换比赛 | `useCompetitionReload` → 切命名空间 → 对目标比赛所有集合执行一次增量对账 |
| 权限变更 | 客户端监听 `permissions:changed`（`user-{id}` 房间）→ auth store 重新拉 `/auth/me` → 刷新菜单/按钮状态 |
| 消息到达 | 监听 `message:new` → `useMessageStore` 未读计数 +1 + 弹窗 toast |

## 6. 竞态与冲突防护

### 6.1 写入-增量竞态防护

1. **内存 memo 失效优先**：写操作成功后先 `_resetMemo`，任何窗口内返回都被阻断；
2. **generation 标记**：每个集合维护 `generation` 计数器，写操作成功自增；在途增量请求返回时若 `generation` 已变 → 丢弃本次 patch（数据由下一次全量同步兜底）；
3. **基线单调**：`setBaseline(newTime)` 仅接受 `newTime >= oldBaseline`；服务端返回的 `serverTime` 为唯一真值来源。

### 6.2 版本封锁期间隔离

- `versionBlocked.value === true` → `connectRealtime()` 立即 disconnect 返回 null；
- 保证版本硬封锁期间：WebSocket 不保留后台通道、HTTP 所有 API 返回 426 强制升级。

## 7. 故障与离线降级策略

| 情况 | 行为 |
|------|------|
| HTTP 网络失败 | 有 IDB 副本 → 返回副本（控制台告警）；无副本 → 抛错到 UI 显示网络错误 |
| WebSocket 断连 | socket.io 自动重连（2s→4s→…指数退避，无限次） |
| 事件丢失 | ① 5 分钟全量对账轮询（`FULL_SYNC_INTERVAL_MS`）；② 重连后 `sync:replay` 按序号回放 |
| IndexedDB 不可用（隐私模式） | 自动跳过缓存层，所有请求直接走 HTTP，不影响功能 |
| 版本不匹配 | 所有 API 响应拦截器检测 426 → `versionBlocked = true` → 弹窗强制升级并封锁 |

## 8. 调优与扩展点

- **内存 memo 窗口**：当前 15s（`request.ts` 中 `MEMO_TTL_MS`）。若后端写入频率很高可缩短；若只读为主可延长。
- **全量对账周期**：当前 5 分钟。若比赛参与人数多、写操作频繁，可缩短到 2 分钟。
- **新增资源类型接入增量同步**：
  1. 在 `cache.ts` 的 `SEG_TO_RESOURCE` 增加映射；
  2. 服务端该资源列表方法接入 `applyUpdatedAfter` + `buildIncrementalResult`；
  3. 服务端 Prisma `MODEL_TO_RESOURCE` 增加对应模型映射（自动广播）。
