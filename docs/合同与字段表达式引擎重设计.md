## 1. 两套引擎体系总览

系统内存在两套可视化配置 + 一套文本表达式体系，背后共用**同一套跨端共享 DSL**（`shared/engine-dsl/`）与**同一套 OP 运算定义**（`server/src/common/engine-ops.ts`）：

| 维度 | 合同类型配置 | 产业计算字段配置 |
|---|---|---|
| **配置对象** | `ContractType`（含 partyRoles / inputSchema / effects / conditions / graph） | `IndustryField`（含 config / calcGraph / formula / timerValue） |
| **存储形态** | JSON 字符串列，写入前经 JSON Schema 校验 | JSON 字符串列（calcGraph），写入前经 JSON Schema 校验 |
| **服务端引擎** | `contract-engine.service.ts` + `contracts/engine/{values,effects,conditions,compute}.ts` | `industry-calc-engine.service.ts` |
| **客户端编辑器** | `ContractTypeGraphEditor.vue`（图编辑器） | `IndustryFieldGraphEditor.vue`（图编辑器） |
| **值源抽象** | `ValueSpec`（CONST / INPUT / FIELD / ENTITY / FORMULA / OP / VAR / ROUTE / INDUSTRY_IS） | `ValueSpec` 子集（FIELD / CONST / FORMULA / OP / VAR / CONSUMER_DEMAND） |
| **控制流** | IF / FOREACH / ASSIGN 嵌套效果树 | 无控制流，纯 DAG（VAR 依赖拓扑排序 → output 汇点） |
| **共享 OP 运算** | 44 个（列表 14 + 字典 14 + 通用 3 + 算术 13） | 同左，直接 import common/engine-ops |
| **公式执行** | FORMULA 值源走 safe-expression 白名单求值 | 同左 |
| **单测覆盖** | 拆分后 engine/ 子目录可单测（计划补） | industry-calc-engine.service.spec.ts ✅ 已覆盖 |

**核心统一事实**：两套体系的 OP_ARG_SPECS、JSON Schema、值源类型定义均**从单一源（shared/engine-dsl + common/engine-ops）提供**，不再前后端手抄多份。

## 2. 配置语义模型（共享 DSL）

所有「可计算配置」（合同 effects/conditions、产业 calcGraph、FORMULA 文本表达式）最终都收敛到一套统一的 DSL 类型：

### 2.1 值源（ValueSource）

```ts
// 所有能"产出一个值"的节点统一抽象
type ValueSource =
  | { type: "CONST"; value: string | number | boolean | any[] | Record<string, any> }
  | { type: "INPUT"; key: string; aggregate?: AggregateEndpoint }     // 合同：输入项引用（可接聚合端点）
  | { type: "FIELD"; party?: PartyRef; fieldKey: string }             // 合同/产业：某方产业字段
  | { type: "ENTITY"; entityType: EntityType; entityRef?: string; attribute: string; multiplyByInput?: string }
  | { type: "INDUSTRY_IS"; party?: PartyRef; industryTypeId?: number }
  | { type: "VAR"; name: string }                                     // FOREACH/ASSIGN 引入的临时变量
  | { type: "FORMULA"; expr: string }                                 // 文本表达式（走 safe-expression）
  | { type: "OP"; op: OpName; args: (ValueSource | Literal)[] }       // 44 个运算节点
  | { type: "ROUTE"; routeRef?: string; nodeIds?: number[]; pathTypeIds?: number[]; aggregate?: string };
```

**注意**：产业计算引擎不会出现 INPUT / ENTITY / ROUTE / INDUSTRY_IS；`CONSUMER_DEMAND` 是产业侧专用扩展（走 DB 聚合端点，不在共享 ValueSpecSchema enum 中）。

### 2.2 合同效果树（EffectSpec）

```ts
type EffectSpec =
  | { kind: "FIELD";  party: PartyRef; fieldKey: string; op: "ADD" | "SUB" | "SET"; value: ValueSource }
  | { kind: "IF";     cond: ValueSource; then: EffectSpec[]; else?: EffectSpec[] }
  | { kind: "FOREACH"; items: ValueSource; var: string; body: EffectSpec[] }
  | { kind: "ASSIGN"; name: string; value: ValueSource };
```

- `FIELD`：直接操作某参与方的产业字段
- `IF`：条件分支，**cond 为假时 then 内效果不执行；同时 then 内的 inputSchema 输入项在 UI 上会被隐藏（显隐+分支语义共用同一个节点）**
- `FOREACH`：遍历 items，每次迭代把当前元素赋给 `var`，body 可引用 `{type:"VAR", name}`
- `ASSIGN`：引入一个作用域内临时变量，后续 VALUE/VAR 可引用

### 2.3 合同条件检查（ConditionSpec）

```ts
type CondKind = "FIELD_COMPARE" | "VALUE_COMPARE" | "INDUSTRY_IS"
              | "DICT_COMPARE"  | "LIST_COMPARE";
type CompareOp = "GTE" | "LTE" | "GT" | "LT" | "EQ"
               | "CONTAINS" | "HAS_KEY"
               | "LEN_GTE" | "LEN_LTE" | "LEN_EQ" | "ELEMENT_EQ";

type ConditionSpec = {
  id: string; label: string; errorMessage: string;
  kind: CondKind;
  party?: PartyRef; fieldKey?: string;        // FIELD_COMPARE / INDUSTRY_IS
  op: CompareOp;
  left: ValueSource; right: ValueSource;      // VALUE_COMPARE / DICT / LIST
};
```

执行：`runAllConditions()` 顺序检查，全部通过 → 继续执行效果；任何一条失败 → 收集所有失败的 `errorMessage` 抛给前端展示。

### 2.4 产业字段计算图（calcGraph = GGraph，output 为汇点）

产业侧无控制流，是一个 DAG：
- 节点类型：`output`（汇点，1 个） + `value`（6 种 kind：FIELD / CONST / FORMULA / OP / VAR / CONSUMER_DEMAND） + `if`（条件选择） + `assign`（变量绑定）
- 求值：`evaluate(graph, fieldScope, ctx)`：
  1. 扫描所有 VAR 引用，构建依赖图
  2. 拓扑排序确定执行顺序（无环则报错）
  3. 依次计算每个 value → 最终 output 值

### 2.5 OP 运算全集（44 个，common/engine-ops.ts 单一事实源）

| 分组 | OP 名 | 参数（count / labels / types） |
|---|---|---|
| **列表（14）** | LIST_APPEND / LIST_CONCAT / LIST_LEN / LIST_CONTAINS / LIST_INDEX_OF / LIST_UNIQUE / LIST_FLATTEN / LIST_SUM_OF / LIST_JOIN / LIST_SLICE / LIST_REVERSE / LIST_SORT / LIST_RANGE / LIST_ADD / LIST_SUB | 1~3 个参数，types 全部声明为 list/number/any |
| **字典（14）** | DICT_GET / DICT_KEYS / DICT_VALUES / DICT_ENTRIES / DICT_HAS_KEY / DICT_MERGE / DICT_FROM_PAIRS / DICT_FROM_KEYS / DICT_INVERT / DICT_ADD / DICT_SUB / DICT_APPEND / DICT_SUM | 1~3 个参数，DICT_GET 支持默认值兜底 |
| **通用（3）** | LEN / CONTAINS / SUM_OF | 通用集合操作 |
| **算术（13）** | ADD / SUB / MUL / DIV / EXP / LOG / MIN / MAX / ABS / ROUND / CEIL / FLOOR / SQRT / POW / CLAMP | 2 参数运算居多；算术 OP 支持字面量回退 argLiterals（端口没连就取面板填的值） |

每个 OP 的参数规格由 `OP_ARG_SPECS[op]` 定义，编辑器据此渲染端口数量与提示，服务端据此校验 args 数量匹配——**一份定义三处消费**（客户端端口渲染 + 服务端写入校验 + 服务端执行器分支）。

## 3. 三层校验闭环（坏配置不出编辑器 / 不进库 / 不炸引擎）

```
用户在图编辑器上拖节点
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ L1 客户端结构校验（保存按钮触发）                      │
│  • 效果必填 value 节点是否填写                         │
│  • 端口连线类型匹配（合同 edgeTypeCheck 钩子）          │
│  • FORMULA 表达式语法预扫（括号 / 引号配对）            │
└──────────────────────────────────────────────────────┘
    │  通过
    ▼  写入请求（POST/PUT ContractType / IndustryField）
┌──────────────────────────────────────────────────────┐
│ L2 服务端写入校验（json-schema.ts + shared/engine-dsl）│
│  • ValueSpecSchema：每个值源必填字段齐全 + type 合法     │
│  • EffectSchema：effect kind / op 合法 + 递归结构      │
│  • ConditionSpecSchema：condKind + compareOp 合法      │
│  • OP 节点 args 数量 == OP_ARG_SPECS[op].count         │
│  任何不通过 → 400 {message: "合同配置校验失败", errors} │
└──────────────────────────────────────────────────────┘
    │  通过
    ▼  DB 内 JSON 字符串 + 正常响应
┌──────────────────────────────────────────────────────┐
│ L3 执行期容错（引擎层）                                │
│  • evalValueSpec：坏字段引用 → 0 / "" / []（按类型兜底）│
│  • safe-expression：白名单沙箱，越权访问一律抛 Error    │
│  • OP 执行：参数类型不符 → toNumber / toString 柔型转换 │
│  捕获的错误 → 写入 Contract.executionLog                │
└──────────────────────────────────────────────────────┘
```

**L2 校验器单测**：`json-schema.spec.ts` 覆盖「合法样例 / 必填缺失 / type 非法 / OP args 不匹配 / 效果递归嵌套」等路径。

## 4. 服务端执行引擎

### 4.1 合同引擎（拆分后结构）

```
contract-engine.service.ts（编排层，~700 行）
  ├─ execute(contractId, inputs, operator)     # 主入口：事务 + 前置检查 + 效果执行 + 日志
  ├─ precheck(ctx)                             # 条件检查：runAllConditions()
  ├─ revertContract(contractExecutionId)       # 回滚：反向重放效果 + 写回滚日志
  └─ 依赖 engine/ 子模块（纯函数）

engine/
  ├─ values.ts        evalValueSpec(spec, ctx): any     # 9 种值源 + FORMULA + OP
  ├─ effects.ts       applyEffect(effect, ctx): FieldEffect[]  # FIELD / IF / FOREACH / ASSIGN
  │                   revertEffect(effect, snapshot): void     # 反向应用
  ├─ conditions.ts    checkCondition(cond, ctx): {ok,msg}
  │                   runAllConditions(conditions, ctx): string[]
  ├─ compute.ts       20+ computeXxx(ctx, partyRef): number    # 聚合端点（给 INPUT 聚合用）
  └─ index.ts         汇总导出
```

**关键机制**：
- **上下文对象 ctx**：`{ prisma, competitionId, parties: {roleKey -> companyId}, inputs: {key->value}, vars: Map, snapshotBefore, effectsApplied }`
- **效果快照回滚**：每个 FIELD 操作前读旧值 → 追加到 `snapshotBefore` → 回滚时反向 `SET`
- **IF 的隐式语义**：IF cond == false → 跳过 then 内效果；同时 UI 层（contract-editor）会把 then 内绑定的 input 项隐藏

### 4.2 产业字段计算引擎（industry-calc-engine.service.ts）

```
evaluate(graph: GGraph, fieldScope: {companyId, industryTypeId, [fieldKey]: value}, ctx): {result, order}
  1. 扫描所有 VAR 节点 → 构 buildDepGraph(n, edges)
  2. Kahn 拓扑排序（检测循环依赖 → 抛错 "循环依赖：A -> B -> A"）
  3. 按拓扑序依次算每个中间节点 value（写入 computedVars）
  4. 计算 output 节点 → 返回结果 + 计算顺序（用于诊断面板高亮）

  支持 6 种 value.kind：
    • FIELD            → fieldScope[fieldKey]
    • CONST            → 字面量
    • FORMULA          → safeEvaluate(expr, fieldScope ∪ computedVars)
    • OP               → applyOp(op, args.map(evalArg))，通过 common/engine-ops
    • VAR              → computedVars[name]
    • CONSUMER_DEMAND  → ctx.prisma.consumerDemand 聚合查询（region + productId 匹配）
```

**级联刷新**：当 CompanyField 某条值被写入后，`company-fields.service.ts` 调用 `IndustryCalcEngine.recalcDownstream(changedFieldKeys)` 按反依赖拓扑重新计算所有被影响的计算字段值 → 写回 DB → 广播刷新。

**单测覆盖**：`industry-calc-engine.service.spec.ts` 验证拓扑排序、循环依赖报错、FORMULA 求值、CONSUMER_DEMAND 聚合 mock。

### 4.3 白名单表达式求值器（safe-expression.ts，FORMULA 值源）

| 能力 | 支持 / 不支持 |
|---|---|
| **支持运算符** | `+ - * / % ^`，`== != > >= < <=`，`&& || !`，三元 `? :`，括号 |
| **支持函数** | round / floor / ceil / abs / sqrt / pow / log / exp / min / max / sum / avg / len / contains / concat |
| **支持符号** | FORMULA 值源 scope 中的字段键、临时变量名、数字字面量、字符串字面量（单/双引号）、布尔 |
| **不支持** | 函数定义、对象字面量方法调用、属性赋值、`new`、`eval`、`Function`、原型链访问、`import`/`require`、正则 `.`、无限循环（超时中断） |
| **沙箱机制** | AST 遍历拦截 + mathjs 限制 scope 为白名单对象；Function 构造器重写为抛错 |

**单测覆盖**：`safe-expression.spec.ts` 覆盖合法运算、属性访问阻断、沙箱逃逸尝试（`constructor.constructor`、`__proto__` 等 20+ 种攻击 payload）。

## 5. 客户端编辑器现状

### 5.1 共享图模型（graph-model.ts）

- **基础类型**：`GNode<TData>` / `GEdge` / `GGraph`（位置、尺寸、输入/输出端口 handleId）
- **序列化**：
  - 合同侧：`graphToFlat(graph) → FlatContract{partyRoles, inputSchema, effects, conditions}`；反向 `flatToGraph(flat) → GGraph`（用 `colW=240 / rowH=130` 硬排）
  - 产业侧：`calcGraph` 原样序列化为 JSON 字符串（GGraph 直接写 IndustryField.calcGraph 列）
- **节点库 / 端口**：合同侧与产业侧分别通过 `NODE_PORTS / NODE_META` 常量声明端口数和标签，`edgeTypeCheck` 钩子做连线时类型校验

### 5.2 ContractTypeGraphEditor.vue（合同类型编辑器）

- **三栏布局**：左侧节点库（分组：参与方 / 输入 / 值源 / 效果 / 控制流 / 运算 / 列表 / 字典）→ 中间手动画布（绝对定位 div + SVG path 连线）→ 右侧属性面板（按节点类型 v-if 分支渲染表单）
- **value 节点属性面板**：7 种 valueType 各一套子表单，每个节点标题摘要 `nodeSummary` 用一行文字概述「这个值来自哪里」
- **效果属性面板**：FIELD_OPS（ADD / SUB / SET）+ VALUE_OPS（CONST / 各种引用）
- **条件属性面板**：5 种 condKind，每种参数面板不同
- **工具栏**：撤销 / 重做 / 自动对齐 / 源码 JSON 切换 / 保存（触发 L1 校验，通过后写库）

### 5.3 IndustryFieldGraphEditor.vue（产业字段编辑器）

- **复用三栏布局**，但节点库规模更小：`output / value(6 kind) / if / assign`
- **OP 节点双重输入**：端口连线优先；端口未连时取面板上 `argLiterals[i]` 的字面量（UI 上用灰色提示 "未连接，使用字面量"）
- **集成方式**：从 IndustryTypeManageView.vue 字段对话框内「打开编辑器」按钮全屏进入；对话框底部仍保留 calcGraph 原始 JSON 折叠预览（只读）

## 6. 后续优化方向（界面复杂度治理）

> 以下为**尚未实施**的持续优化项，按对"界面乱、不清晰"的改善效果排序。

### P1 图编辑器工程化导航能力（投入 3~4 天，高收益）

- **缩放/平移**：鼠标滚轮缩放 + 空白处拖拽平移画布，左上角百分比按钮复位
- **缩略图 / 鸟瞰**：右下角小面板显示全图，可快速拖到目标区域
- **搜索/定位**：Ctrl+F 弹出搜索框，输入节点摘要 / fieldKey / varName → 匹配节点高亮居中
- **自动布局**：替换 `flatToGraph` 的硬排逻辑为「层次化布局（Sugiyama 算法简化版）」，嵌套效果树每层间距自适应
- **分组折叠**：IF / FOREACH 节点头部加折叠按钮，折叠后整棵子树收为一个徽章（显示内部节点数）

### P2 简单模式（向导式 / 表格）覆盖 80% 常见配置（投入 5 天）

新增**两种可选编辑模式**，与图编辑器并存并可双向切换：
- **合同简单模式**：把常见的「XX 方付 Y 元 / 交付 N 个货 / 必须是某产业」拆成表格行，每行 = 一个 FIELD 效果或 FIELD_COMPARE 条件。向导步骤：① 选参与方角色 → ② 拖输入项 → ③ 表格填效果 + 条件 → ④ 生成图（用户也可再切回专家模式微调）
- **产业简单模式**：把计算字段拆成「公式文本」一行（优先走 FORMULA 节点），复杂 OP 节点才切图编辑器

### P3 FORMULA 编辑器体验升级（投入 2 天）

- 废弃孤儿的 `FormulaPanel.vue`，统一 FORMULA 节点内编辑体验
- FORMULA 节点点击编辑弹出**多行编辑器**，带：
  - 词法高亮（关键字 / 函数 / 数字 / 字符串不同色）
  - 自动补全（当前 scope 内可用字段键、函数名 + 参数提示）
  - 实时校验（输入时跑 safe-expression，错误下划线 + 提示）
  - 试算按钮（选一家示例公司 → 现场算结果显示在编辑器底部）

### P4 运行时试算与诊断面板（投入 2~3 天）

编辑器工具栏新增「诊断」按钮：
- **合同侧**：选示例参与方（公司）+ 填输入项 → 现场跑一遍 `contract-engine.execute` → 在图上高亮：
  - 条件通过 / 失败（绿色勾 / 红色叉 + 错误消息）
  - 效果应用值（节点角标显示 +X / -Y / =Z）
  - 失败节点闪烁（定位到具体节点 ID）
- **产业侧**：选示例公司 → 按拓扑序逐节点显示中间值，output 显示最终计算结果

### P5 状态裸字符串枚举化 + JSON 列剩余校验（P3，长期）

见 [后端重构设计.md §3-B1](./后端重构设计.md) 的持续治理项。
