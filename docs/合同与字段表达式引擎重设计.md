## 1. 背景与目标

用户反馈：**「合同逻辑复杂或者字段公式复杂时，整个界面很乱，不清晰。」**

这不是单个 bug，而是「配置模型 + 编辑交互」两层叠加的结构性问题。系统目前有两套并行的可视化配置体系，共用同一套底层图类型（`graph-model.ts` 的 `GNode/GEdge/GGraph`），但语义、节点库、端口、序列化目标完全不同；同时还有第三套文本公式编辑体验（`FormulaPanel.vue`）。配置常量在客户端与服务端多处复制，JSON 字符串存储没有模式校验，画布没有自动布局与工程化导航能力。

本次重设计目标（按优先级）：

- **G1 统一配置心智模型**：把「值源 / 运算 / 规则 / 检查」收敛为一份跨端共享的单一事实源（DSL 类型 + JSON Schema），消除客户端/服务端双份维护与三套编辑体验的割裂；
- **G2 分级编辑体验**：新增「简单模式」（表格 / 向导式，覆盖 80% 常见配置），保留并升级「专家模式」（可视化图编辑器，覆盖复杂嵌套逻辑），让复杂配置不再要求用户一次性理解整张图；
- **G3 图编辑器工程化**：自动布局、缩放平移、缩略图、折叠、搜索、校验徽章、试算反馈——复杂图可读、可导航、可验证；
- **G4 校验前置**：保存时结构校验、服务端写入时校验、执行前校验三层闭环，坏配置在配置界面就被拦住并定位，而不是等到运行期爆炸；
- **G5 治理不破坏兼容**：旧 JSON 数据兼容读取，迁移平滑，`FlatContract` 四个 JSON 的服务端执行契约不变。

> 与后端重构蓝图的关系：本文的 E 系列方案落地依赖 `docs/后端重构设计.md` 的 R3（JSON 三级结构化 + 校验器）与 R1（contract-engine 上帝模块拆分）作为服务端地基；本文只做「编辑器与配置模型」侧的设计。

## 2. 现状全景

### 2.1 两套图编辑器 + 一套文本公式面板

|---|---|---|---|---|

| 产业计算字段可视化编辑 | `IndustryFieldGraphEditor.vue` | 984 行 | `output/value/if/assign`（`value.kind ∈ FIELD/CONST/FORMULA/OP/VAR/CONSUMER_DEMAND`） | `calcGraph`（GGraph JSON 字符串，`output` 为汇点） |

### 2.2 合同图编辑器（`ContractTypeGraphEditor.vue`）

- **交互模型**：左侧节点库（分组：参与方/输入/计算/控制流等）→ 点击添加到中间手动画布；节点以绝对定位 div 渲染 + SVG path 画连线；右侧属性面板按节点类型 `v-if/v-else-if` 分支渲染表单。
- **属性面板分支规模**（模板内）：
  - `value` 节点（368–501 行）：7 种 `valueType`（`ENTITY / FIELD / INDUSTRY_IS / INPUT / CONST / FORMULA / VAR`），每种一套表单 + 提示；
  - `effect` 节点（504–554 行）：`op ∈ FIELD_OPS` + `valueOp ∈ VALUE_OPS`；
  - `condition` 节点（557 行起）：5 种 `condKind`（`INDUSTRY_IS / VALUE_COMPARE / DICT_COMPARE / LIST_COMPARE / FIELD_COMPARE`），每种不同参数表单；
  - `if/foreach/assign/calc/list-op/dict-op` 各自分支。
- **保存校验**：`onSave` 仅校验「效果值缺失」一类问题；端口类型、孤立节点、必填属性、跨节点引用完整性均不校验。
- **源码视图**：工具栏「源码 JSON」切换，把整棵图序列化后原样展示/编辑。

### 2.3 产业字段图编辑器（`IndustryFieldGraphEditor.vue`）

- 复用同一 `GGraph` 类型与「节点库 + 画布 + 属性面板」布局，但节点库、端口逻辑（`indInputHandles/indOutputHandles`）、`value.kind` 分支（140–282 行，6 种 kind）与合同侧完全不同。

## 3. 问题清单（Q 系列）

> Q 系列聚焦「界面乱、不清晰」的直接来源；与后端重构 B 系列（上帝模块/数据模型）互补不冲突。

### Q1 value 节点是「万能节点」，属性面板巨型分支
- 合同侧 `value` 7 种 `valueType`、产业侧 6 种 `kind`，每种来源一套表单 + 提示，面板靠 `v-if/v-else-if` 堆叠（合同 368–501 行、产业 140–282 行）。
- 一个节点的完整含义被拆到**三处**：属性面板（来源类型与参数）、画布端口连线（依赖关系）、节点标题摘要（`nodeSummary` 的一行文字）。复杂配置时用户无法从任何单一视图看到「这个值到底怎么算出来的」。

### Q2 两套图系统语义分裂，共享同一类型系统
- 合同图与产业图共用 `GNode/GEdge/GGraph`，但 `NODE_PORTS / NODE_META / 端口语义 / 序列化目标`完全不同，且 `value` 节点的类型字段在合同侧叫 `valueType`、产业侧叫 `kind`——同一概念两套命名。
- 维护者改 `graph-model.ts` 会影响两个编辑器，但语义约束（哪些端口可连、哪些 type 合法）完全靠各编辑器自己的 `edgeTypeCheck / 端口枚举`，没有共享的类型级约束。

### Q3 一个合同的配置被拆成 4 个并列 JSON，图上无聚合视图
- `FlatContract = partyRoles + inputSchema + effects + conditions` 四个并列结构（`graphToFlat`，graph-model.ts 1456 行）。
- 效果树支持 `IF/FOREACH/ASSIGN` 嵌套（`effectSpec` 递归，1506–1556 行），条件与输入还可以挂在 IF 分支下（`resolveControlBranch`，1440–1449 行）——「输入项显隐 + 检查短路 + 效果分支」三套分支语义共用同一个 IF 节点，图上一旦嵌套两层以上就极难阅读。

### Q4 文本公式与图形配置双轨，函数词表不一致
- 同一功能有「拖图形」（OP 节点）与「写文本」（FORMULA 节点 textarea / FormulaPanel）两种心智模式；FORMULA 节点只给一个 2 行 textarea，无补全、无校验、无试算。
- `FormulaPanel.vue` 的 12 个函数徽章（round/max/min/abs/ceil/floor/sqrt/pow/log/sum/avg）与 `safe-expression.ts` 实际内置词表不同源——用户照着面板写，运行期可能不存在该函数。
- `FormulaPanel` 是孤儿组件，进一步证明「公式 UI」处于未收敛状态。

### Q5 配置常量双份/三份维护
- `OP_ARG_SPECS` 客户端（graph-model.ts）与服务端（industry-calc-engine.service.ts 48–93 行）手抄两份；`EXPR_HELPERS` 跨模块 import（产业引擎依赖合同引擎内部实现）。
- 改一个 op 的参数端口定义，需同步 2–3 个文件；漏改则出现「前端能连、后端报错」或反之，且错误发生在运行期。

### Q6 JSON 字符串无模式校验，坏配置运行期才爆炸
- 保存时只有「效果值缺失」一个校验点；`calcGraph / effects / conditions` 写入无 Schema 校验。
- `IndustryTypeManageView` 直接把 `calcGraph` 原始 JSON dump 给用户看（`<pre class="fb-json">`，397 行）——「界面乱」的最直接样本。

### Q7 手动画布缺工程化能力
- 无自动布局：`flatToGraph` 反序列化用固定 `colW=240 / rowH=130 / PORT_GAP=22` 硬排（graph-model.ts 1629–1665 行），复杂图节点互相重叠；保存后再打开，节点坐标来自上次手工拖动，新加的节点插在固定行列，容易遮住已有内容。
- 无缩放/平移、无缩略图/鸟瞰、无分组折叠、无搜索定位；效果树横向 240px/层、纵向 130px/项，嵌套 3 层即可溢出视口。

### Q8 无运行时洞察与试算能力
- 配置保存后看不到「在真实/示例数据上求值的结果」；合同执行失败只有执行日志，无法在图上高亮出错的节点与链路。
- 复杂合同/计算图的验证只能靠「保存 → 运行 → 看日志 → 回来改」的慢循环。

## 4. 重设计方案（E 系列）

### E1 统一配置模型：一份跨端共享的「引擎 DSL」（单一事实源）（✅ CE2-A 已确认）

把两套图 + 公式面板背后的配置语义收敛为一份**共享 DSL 类型 + JSON Schema**，双端引用同一份定义：

```ts
// shared/engine-dsl/  （新目录，client 与 server 通过相对路径或构建别名共享）

// 值源：一个「能产出值的东西」的统一抽象（合同 value 节点 / 产业 value 节点 / 公式里的一个操作数）
type ValueSource =
  | { type: "CONST"; value: string | number | boolean | any[] | Record<string, any> }
  | { type: "INPUT"; key: string; aggregate?: AggregateEndpoint }   // 合同：输入项引用（含聚合端点）
  | { type: "FIELD"; party?: PartyRef; fieldKey: string }           // 合同/产业：某方产业字段
  | { type: "ENTITY"; entityType: EntityType; attribute: string }   // 合同：实体属性
  | { type: "INDUSTRY_IS"; party?: PartyRef; industryTypeId?: string }
  | { type: "VAR"; name: string }
  | { type: "FORMULA"; expr: string }                               // 受限表达式（safe-expression）
  | { type: "OP"; op: OpName; args: (ValueSource | Literal)[] };    // 44 个 op 统一收敛

// 规则（合同效果）：IF / FOREACH / ASSIGN / FIELD 统一
type Rule =
  | { kind: "IF"; cond: ValueSource; then: Rule[]; else: Rule[] }
  | { kind: "FOREACH"; items: ValueSource; var: string; body: Rule[] }
  | { kind: "ASSIGN"; name: string; value: ValueSource }
  | { kind: "FIELD"; party?: PartyRef; fieldKey: string; op: FieldOp; value: ValueSource; value2?: ValueSource; valueOp?: ValueOp };

// 检查（合同 conditions）与计算图输出声明
type Check = { kind: CondKind; label: string; errorMessage: string; branch?: BranchRef; /* …按 kind 展开 */ };
```

配套动作：

1. **生成 `engine.schema.json`**（从 DSL 类型生成 JSON Schema），双端共用；服务端校验、客户端表单校验同一份规则；
2. **`OP_ARG_SPECS / ENTITY_TYPES / FIELD_OPS / VALUE_OPS / COND_KINDS / COMPARE_OPS / EXPR_HELPERS` 全部移入该共享包**，删除客户端/服务端各自副本；
3. **`FormulaPanel` 的函数徽章词表改为从共享包的「safe-expression 实际实现词表」生成**（或直接废弃 FormulaPanel，并入 E2 简单模式公式编辑器）；
4. 合同侧 `valueType` 与产业侧 `kind` 统一为同一个 `ValueSource.type` 枚举命名。

> 依赖：`后端重构设计.md` R3（JSON 三级结构化）为服务端落地点；E1 的共享包是 R3 校验器的输入。

### E2 分级编辑体验：简单模式（默认）+ 专家模式（图编辑器）（✅ CE1-B / CE6-A 已确认）

**简单模式（默认入口，覆盖常见配置）**——表格/向导式，无需理解图：

- **合同类型**：三段式表单——
  1. **参与方表格**：行 = 角色编码/显示名/主办方/可选/限定产业；
  2. **输入项表格**：行 = 字段键/显示名/类型/必填/默认值/所属分支；
  3. **规则编辑器**：条件行（检查清单，每行一条「INDUSTRY_IS / 数值比较…」）+ 效果行（「当…则 对 某方.fieldKey 执行 ADD 值」），支持简单缩进表达 IF/FOREACH 嵌套，复杂嵌套自动降级提示「去专家模式」。
- **产业计算字段**：公式输入框（E2 升级版：字段键补全、函数补全、实时校验、试算预览）+「计算步骤」列表（可选步骤式：读取 A → 求和 → 存入 B）。

**专家模式（保留并升级现有图编辑器）**：作为高级入口，进入条件 = 简单模式「更多选项」或配置复杂度超出表格表达能力时自动推荐。升级内容见 E3/E4/E5。

> 两种模式编辑的是**同一份 DSL 数据**（简单模式表单 ↔ 图编辑器 ↔ DSL 三向同步），不存在第二份存储。

### E3 图编辑器工程化（复杂度治理）（✅ CE4-C 已确认）

对两个图编辑器（合同 + 产业）统一增强：

1. **自动布局**：引入分层布局（dagre 或自研分层算法），「自动整理布局」按钮 + 新建/反序列化时默认自动排列；用户手工拖动后坐标保留，但提供「一键重排」；
2. **画布导航**：滚轮缩放 + 拖拽平移 + 视口自适应 + 缩略图/鸟瞰（右下角小地图，可拖拽视口）；
3. **折叠与聚合**：效果树可按「IF 分支 / FOREACH 体」折叠为摘要卡片（显示「IF: 条件摘要 → N 条效果」），展开时才铺开子节点——控制复杂图的可视规模；
4. **搜索定位**：按节点标题/字段键/角色搜索，命中高亮 + 视口跳到目标；
5. **端口可读性**：端口按语义着色（数据流/控制流/参与方），连线可显示运算标注（如 `ADD` / `GTE`）；`edgeTypeCheck` 不合法的连线**禁止建立**而非画红；
6. **节点库改进**：分组 + 搜索 + 「示例模板」（预设常用子图：如「读 A 方字段与 B 方比较」「对列表 FOREACH 累加」）一键插入。

### E4 三层校验闭环（保存前 / 写入时 / 执行前）（✅ CE3-C 已确认）

1. **编辑器内（保存前）**：结构校验（必填属性、孤立节点、端口类型、跨节点引用完整性、IF 分支归属），错误在**图上定位到具体节点**并标红；校验不过禁止保存；

## 附录：合同会签状态机设计

> 状态：已确认（按默认方案实施）｜2026-08-18
> 关联：在现有 `DRAFT | EXECUTED | TERMINATED` 基础上引入会签流程与 `PENDING_EXEC` 中间态；权限模型复用 `server/src/permissions/catalog.ts` 的三档角色。
>
> 最终决策（用户确认，2026-08-18）：
> 1. 执行兜底——保留 `contract:execute`/`contract:manage`/超管 可执任意合同最后一步；仅 `contract:audit` 公司级管理员限为"最后一方参与公司"。
> 2. 创建放宽——`contract:execute`（比赛级）/`contract:manage`（超管/合同管理员）可任意创建，不强制发起方必须是 parties[0] 公司管理员。
> 3. `setStatus` 禁止绕过 execute——仅允许置 `TERMINATED`，禁止置 `EXECUTED` 或回退 `DRAFT/PENDING_EXEC`。

### 1. 背景与目标

当前合同状态机由权限角色触发执行（`contract:execute` 比赛级 / `contract:audit` 按公司范围），参与方编号由管理员分步补全，但"谁执行"与"参与方顺序"在业务上无关联。

新需求（用户确认）：
- 创建放宽：**办赛管理员（`contract:execute` 比赛级 / `contract:manage` 超管）可任意创建合同**，约定的 `parties[0]` 即发起方（甲方），但不强制发起方公司管理员才能建；
- 各方编号分步补全（保留现状：管理员可改任意方）；
- 所有非主办方编号齐备后，由**最后一个参与方（乙方/丙方）对应公司的管理员**点击执行落账（仅最后一方，中间方只能填自己编号）；
- **参赛选手（PLAYER）没有任何执行/创建权**；
- 引入**待执行（PENDING_EXEC）**中间态，明确区分"会签中 / 待执行 / 已执行"。

### 2. 状态定义

| 状态 | 含义 | 字段效果 |
|------|------|----------|
| DRAFT | 草稿 / 会签中（编号尚未齐备） | 无 |
| PENDING_EXEC | 待执行（编号已齐备，等待最后一方执行） | 无 |
| EXECUTED | 已执行 / 落账 | 引擎改写产业字段 |
| TERMINATED | 已终止（标记态） | 同 EXECUTED，已落账 |

> SQLite 不支持原生 enum，状态以 `String` 存储；`schema.prisma` 注释更新为 `ContractStatus: DRAFT | PENDING_EXEC | EXECUTED | TERMINATED`。

### 3. 参与方顺序约定（关键）

`parties` 为 JSON 数组，元素结构 `{ role, companyId, isHost, contractNumber }`，其中 `isHost` 为比赛主办方（无编号、不参与会签）。

- **发起方（甲方）** = `selectableParties[0]`（第一个非主办方参与方）
- **执行方（最后一方）** = `selectableParties[selectableParties.length - 1]`（最后一个非主办方参与方）

两方合同时执行方即乙方；三方合同时执行方即丙方。前端创建时必须按"甲方 → 乙方 → 丙方"顺序传入 `parties`，此顺序即会签顺序。

### 4. 状态转换规则

| 起点 | 触发动作 | 终点 | 权限要求 | 前置条件 |
|------|----------|------|----------|----------|
| — | `create` | DRAFT | 办赛管理员（`contract:execute`/`contract:manage`/超管），非 PLAYER | 约定 parties[0]=甲方 |
| DRAFT | `updatePartyNumbers`（编号齐备） | PENDING_EXEC | 保留现状（管理员可改任意方） | 所有非主办方 `contractNumber` 非空 |
| PENDING_EXEC | `updatePartyNumbers`（某编号被清空） | DRAFT | 同上 | 出现空编号则回退 |
| PENDING_EXEC | `execute` | EXECUTED | 能管理执行方公司的管理员（非 PLAYER） | 编号齐备 |
| EXECUTED / TERMINATED / DRAFT / PENDING_EXEC | `setStatus` | TERMINATED | 管理员 | 仅允许置 TERMINATED（标记态）；禁止置 EXECUTED 或回退 DRAFT/PENDING_EXEC |
| DRAFT / PENDING_EXEC | `remove` | 删除 | 能查看/管理 | 未落账，直接删 |
| EXECUTED / TERMINATED | `remove` | 删除 | 能查看/管理 | 已落账，复原字段后删 |

> `setStatus` 严格受限：会签模型下状态转换由 `execute` / `remove` / `updatePartyNumbers` 驱动，本接口仅保留"标记终止（TERMINATED）"这一无害动作，禁止绕过 execute 直接置 `EXECUTED` 或回退 `DRAFT/PENDING_EXEC`（修复账实不一致隐患）。

### 5. 权限判定

复用现有 `hasPermission` 与三档角色（SUPER_ADMIN / COMPETITION_ADMIN / PLAYER），新增两个辅助判定：

```
// 返回该用户可管理的公司范围：
//   null = 全局（超管 / 比赛级管理员）
//   []   = 无管理权（PLAYER）
//   数组 = 公司级范围（仅 contract:audit 者按其 companyScopes）
getManagedCompanyScopes(user):
  if SUPER_ADMIN: return null
  if hasPermission(contract:execute) || hasPermission(contract:manage): return null
  if hasPermission(contract:audit): return user.companyScopes || []
  return []

// 当前用户能否管理某公司的合同（发起/执行）
canManageCompany(user, companyId):
  scopes = getManagedCompanyScopes(user)
  if scopes === null: return true            // 全局管理员 / 超管
  return scopes.includes(companyId)
```

- **发起方校验（create，已放宽）**：不再强制发起方公司管理员；入口守卫用 `ContractReviewGuard`（`hasPermission(contract:execute)`，含 `contract:manage`/超管），PLAYER 与 `contract:audit` 公司级管理员均无创建权。
- **执行方校验（execute）**：`assertExecuteScope`——`contract:execute`/`contract:manage`/超管 直接放行（兜底，可执任意合同最后一步）；仅 `contract:audit` 公司级管理员须 `canManageCompany(user, lastParty.companyId)`（最后一方在其 `companyScopes` 内），否则 403「仅最后一方参与公司管理员可执行」。
- **PLAYER**：`getManagedCompanyScopes` 返回 `[]`，对任何公司 `canManageCompany` 均为 false，天然无创建/执行权。

### 6. 后端改造清单（server/src/modules/contracts/contract.service.ts）

1. 新增辅助方法：`getLastSignatoryCompanyId(contract)`（取最后一个非主办方 companyId）、`assertExecuteScope(user, contract)`。
2. `create`：入口守卫由 `@RequirePermissions("contract:manage")` 改为 `@UseGuards(ContractReviewGuard)`（`hasPermission(contract:execute)`，含 `contract:manage`/超管），放宽创建权；不强制发起方公司管理员；`status: "DRAFT"`。
3. `updatePartyNumbers`：写回编号后，若当前为 DRAFT/PENDING_EXEC，按 `isAllNumbersFilled` 自动升降 `PENDING_EXEC`↔`DRAFT`；广播 `contract:changed`。
4. `execute`：
   - 入口守卫由 `ContractReviewGuard` 改为 `ContractEditGuard`（允许 execute/audit/manage 进入）；
   - 用 `assertExecuteScope` 替代 `assertAuditScope`：execute/manage/超管 兜底放行；仅 audit 须最后一方公司在其 `companyScopes` 内；
   - 保留"所有编号齐备"校验；落账后 `status: "EXECUTED"`，并广播 `contract:changed`/`company-field:changed`。
5. `remove`：复原判定改为基于 `contractFieldEffect.count`（`effectCount > 0` 即曾落账），不再依赖当前 `status`，彻底修复"EXECUTED→TERMINATED→删"不复原的账实不一致。
6. `setStatus`：仅允许置 `TERMINATED`；置 `EXECUTED` 或回退 `DRAFT/PENDING_EXEC` 一律 400。

### 7. DTO 与 schema

- `dto/contract.dto.ts`：`UpdateContractStatusDto.status` 的 `@IsIn` 收紧为仅 `["TERMINATED"]`（会签模型下 setStatus 仅用于标记终止，禁止绕过 execute）。
- `prisma/schema.prisma`：注释 `ContractStatus: DRAFT | PENDING_EXEC | EXECUTED | TERMINATED`。

### 8. 前端改造（client/src/views/data-management/ContractManageView.vue）

1. 状态标签/颜色映射增加 `PENDING_EXEC: "待执行"`（warning/amber），与 DRAFT/EXECUTED/TERMINATED 并列。
2. `executeBtnState(row)` 改为（与后端 `assertExecuteScope` 对齐）：
   - 无 `contract:execute`/`contract:audit` 权限 → 禁用「无执行权限」；
   - `EXECUTED`/`TERMINATED` → 禁用（状态原因）；
   - `DRAFT`/`PENDING_EXEC`：不因病态禁用（落账前的任意会签态均可点，编号齐备由后端执行时统一校验）；
   - 权限：`contract:execute`/`contract:manage`/超管 → 直接可执行（兜底）；仅 `contract:audit` → 取 `lastParty = selectableParties[last]`，若 `authStore.canAuditCompany(lastParty.companyId)` 为真则可执行，否则禁用「仅最后一方(乙方/丙方)管理员可执行」；
   - PLAYER 因无执行/审核权限且无公司管理范围，自然禁用。
   - 提示文案：PENDING_EXEC 显示「所有参与方编号已齐全，等待最后一方(乙方/丙方)执行」；DRAFT 显示「编号齐备后可执行」。
3. 创建流程：约定 `parties[0]` 为甲方（发起方），UI 保持现有顺序选择即可；无需新增"发起方"字段。
4. 编号补全 UI：保留现状（管理员可改任意方）。

### 9. 默认假设（需评审）

- A. `parties` 数组顺序即会签顺序：index0=甲方（发起），最后一个非 isHost=执行方。
- B. "管理员" = 持有 `contract:execute`/`contract:manage` 的比赛管理员或超管；"参赛选手" = PLAYER（无 `contract:*`）。
- C. 全局比赛管理员（companyScopes 空）仍可作任意合同的发起方/执行方（兜底/运维）；有公司范围的管理员仅在 firstParty/lastParty 属自己范围时可发起/执行。
- D. PENDING_EXEC 由 `updatePartyNumbers` 自动升降，无需额外按钮。
- E. 已落账的合同（EXECUTED/TERMINATED）删除均复原字段。

### 10. 开放点（已决）

1. **保留全局管理员兜底**（不严格限制）——`contract:execute`/`contract:manage`/超管 可执任意合同最后一步（已采纳 §9-C 默认）。
2. **放宽创建权限**——`contract:execute`（比赛级）/`contract:manage`（超管/合同管理员）可任意创建，不强制发起方必须是 parties[0] 公司管理员（已采纳"办赛管理员任意建"）。
3. **禁止 setStatus 绕过 execute**——`setStatus` 仅允许置 `TERMINATED`，禁止置 `EXECUTED` 或回退 `DRAFT/PENDING_EXEC`（修复账实不一致隐患，已采纳默认）。
