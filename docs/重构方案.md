## 3. 统一依赖拓扑（跨蓝图）

> 六份蓝图不是并行的六条线，而是「地基 → 同步 → 前端 → 引擎」的依赖树。核心依赖边如下：

```
后端 R4（UserRole 枚举） ──► 权限 T7（目录端点）
后端 R5（[competitionId,updatedAt] 索引） ──► 同步 S 系列（增量查询性能）
后端 R8（增量分页化） ──► 同步 S3/S11（memo 维度化/防冲突）
后端 R9（合并窗/seq/定向房间） ──► 同步 S1/S6（事件标准化/集合精确删除）
后端 R1（引擎拆分） ──► 合同 E6（engine-ops 提取）、股票 T1/T2（纯函数化）
后端 R3（JSON 校验器） ──► 合同 E4/E7（三层校验/schemaVersion）、同步 S10（关联比赛）
同步 S7（权限推送服务端） ──► 前端 F4（账号状态实时刷新）、权限 T7/T9
同步 S2/S3/S4/S5/S9 ──► 前端 F1/F2/F3/F8/F7（承接）
权限 T8（范围对象化迁移） ◄──► 同步 S8（本地存储隔离，同一批 schema 改动）
股票 T6（Competition.stockConfig） ──► 股票 T8/T9（前端配置界面）
```

**关键洞察**：后端重构（R 系列）是全部蓝图的地基；数据同步（S 系列）是前后端的中枢；权限与前端刷新都依赖同步的事件机制；合同与股票引擎的拆分共用后端 R1 的纯函数化路径。**任何蓝图单独实施都会踩到未加固的地基（无索引、无校验、无单测）。**
