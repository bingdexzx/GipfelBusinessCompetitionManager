# 接口规范性与合理性审查报告

> 审查日期：2026-08-15
> 审查范围：全部 29 个控制器、~130 个 API 端点

---

## 审查维度

| 维度 | 说明 |
|------|------|
| 路由命名 | kebab-case / 复数 / 一致性 |
| HTTP 方法 | GET/POST/PATCH/DELETE 使用是否正确 |
| 权限守卫 | 类级 vs 方法级 @RequirePermissions 一致性 |
| 分页支持 | page/pageSize 参数是否统一 |
| 增量同步 | updatedAfter / requireExistingIds 支持 |
| 资源归属 | @Ownership / @NoCompetitionScope 使用 |
| 查询参数 | competitionId 处理一致性 |
| 端点完整性 | CRUD 是否齐全 |
| 响应格式 | 统一 { code, message, data } |

---

## 缺陷列表

### 🔴 高优先级（3 个）

#### D1: MapNodeController 缺少类级 `@RequirePermissions`

**位置**：`server/src/modules/maps/map-node.controller.ts`

| 端点 | 类级权限 | 方法级权限 | 实际效果 |
|------|---------|-----------|---------|
| `GET /api/map-nodes` | ❌ 无 | ❌ 无 | **任何已登录用户可列出所有地图节点** |
| `GET /api/map-nodes/:id` | ❌ 无 | ✅ `data:map:view` | 正常 |
| `POST /api/map-nodes` | ❌ 无 | ✅ `data:map:edit` | 正常 |

**对比**：同级控制器 `MapEdgeController`、`MapNodeTypeController`、`PathTypeController` 均有类级 `@RequirePermissions("data:map:view")`。

**影响**：`GET /api/map-nodes` 端点无权限校验，任何已登录用户（包括无任何权限的 PLAYER）可列出全部地图节点数据。

**建议**：在 `MapNodeController` 类上添加 `@RequirePermissions("data:map:view")`。

---

#### D2: ConsumerDemandController 的 `@Ownership` 仅在 update 方法上，DELETE 无保护

**位置**：`server/src/modules/consumer-demands/consumer-demand.controller.ts`

```typescript
@Patch(":id")
@Ownership({ model: "consumerDemand" })  // ← 仅 update 有
async update(...) {}

@Delete(":id")
// ← 无 @Ownership
async remove(@Query("competitionId") competitionId?: string) {}
```

**影响**：用户可通过 `DELETE /api/consumer-demands/:id` 删除其他比赛的消费者需求记录（若知道 id）。

**建议**：将 `@Ownership({ model: "consumerDemand" })` 移至类级。

---

#### D3: StockController 缺少 `@Ownership`，detail 端点存在 BOLA 风险

**位置**：`server/src/modules/stock/stock.controller.ts`

以下端点无 `@Ownership` 保护：

| 端点 | 风险 |
|------|------|
| `GET /api/stocks/:id` | 可枚举其他比赛的股票详情 |
| `GET /api/stocks/accounts/:id` | 可枚举其他比赛的资金账户 |
| `GET /api/stocks/accounts/:id/holdings` | 可查看其他比赛的持仓 |
| `GET /api/stocks/orders/list` | 按 competitionId 过滤但无归属校验 |

**对比**：所有其他业务控制器（material、part、product、vehicle 等）均有类级 `@Ownership`。

**建议**：在 `StockController` 类上添加 `@Ownership({ model: "stock" })`，或在 service 层增加归属校验。

### 🟠 中优先级（7 个）

#### D4: 分页支持不一致

| 控制器 | 列表端点 | 分页 | 默认 pageSize |
|--------|---------|------|--------------|
| MaterialController | `GET /materials` | ✅ | 50 |
| PartController | `GET /parts` | ✅ | 50 |
| ProductController | `GET /products` | ✅ | 50 |
| MapNodeController | `GET /map-nodes` | ✅ | 50 |
| MapEdgeController | `GET /map-edges` | ✅ | 50 |
| MapNodeTypeController | `GET /map-node-types` | ✅ | 50 |
| PathTypeController | `GET /path-types` | ✅ | 50 |
| InfrastructureController | `GET /infrastructures` | ✅ | 50 |
| TechTreeController | `GET /tech-nodes` | ✅ | 50 |
| FuelController | `GET /fuels` | ✅ | 50 |
| VehicleController | `GET /vehicles` | ✅ | 50 |
| **WarehouseController** | `GET /warehouses` | ❌ | — |
| **ProductionLineController** | `GET /production-lines` | ❌ | — |
| **CompanyController** | `GET /companies` | ❌ | — |
| **ConsumerDemandController** | `GET /consumer-demands` | ❌ | — |
| ContractController | `GET /contracts` | ✅ | 50 |
| StockController | `GET /stocks` | ✅ | 50 |
| UsersController | `GET /users` | ✅ | **20** |

**问题**：
1. 4 个控制器的列表端点不支持分页
2. UsersController 默认 pageSize 为 20，其余为 50

**影响**：数据量增长后，无分页端点可能返回大量数据；pageSize 不一致导致客户端缓存行为不统一。

#### D5: `updatedAfter` 增量同步支持不一致

以下列表端点**不支持** `updatedAfter`：

| 端点 | 说明 |
|------|------|
| `GET /consumer-demands` | 业务数据，应支持 |
| `GET /stocks/accounts/list` | 业务数据，应支持 |
| `GET /stocks/orders/list` | 业务数据，应支持 |
| `GET /stocks/holdings/list` | 业务数据，应支持 |
| `GET /competitions/:id/fiscal-years` | 子资源，可不支持 |
| `GET /industry-types/:id/fields` | 子资源，可不支持 |
| `GET /regions/map-overview` | 聚合端点，可不支持 |
| `GET /regions/:id/companies` | 子资源，可不支持 |
| `GET /regions/:id/overview` | 聚合端点，可不支持 |
| `GET /messages/inbox` | 用户维度，可不支持 |
| `GET /messages/sent` | 用户维度，可不支持 |

**影响**：consumer-demands 和 stock 子资源不支持增量同步，客户端每次读取全量数据。

#### D6: ConsumerDemandController 缺少类级守卫和权限

**位置**：`server/src/modules/consumer-demands/consumer-demand.controller.ts`

```typescript
@Controller("consumer-demands")
@UseGuards(JwtAuthGuard)  // ← 仅 JwtAuthGuard，无 PermissionsGuard
export class ConsumerDemandController {
  @Get()
  @UseGuards(PermissionsGuard)  // ← 每个方法单独加
  @RequirePermissions("data:region:view")
  async findAll(...) {}
}
```

**对比**：所有其他控制器在类级 `@UseGuards(JwtAuthGuard, PermissionsGuard)` + 类级 `@RequirePermissions("domain:view")`。

**影响**：代码风格不一致，增加维护成本。

---

#### D7: RegionController 的 create/delete 与 update 使用不同权限域

**位置**：`server/src/modules/regions/region.controller.ts`

| 操作 | 权限 | 域 |
|------|------|-----|
| `POST /regions` | `data:map:edit` | 地图 |
| `PATCH /regions/:id` | `data:region:edit` | 区域 |
| `DELETE /regions/:id` | `data:map:edit` | 地图 |

**问题**：用户有 `data:region:edit` 可以更新区域但不能创建/删除；有 `data:map:edit` 可以创建/删除但不能更新。

**影响**：权限配置困惑，需同时授予两个域的编辑权限才能完整管理区域。

**建议**：统一为 `data:region:edit`，或在文档中明确说明权限拆分的原因。

---

#### D8: ContractController 使用 `@Req()` 而非 `@CurrentUser()`

**位置**：`server/src/modules/contracts/contract.controller.ts`

```typescript
@Get()
async findAll(@Query(...) ..., @Req() req?: any) {
  return this.service.findAll(..., req?.user);
}
```

**对比**：所有其他控制器使用 `@CurrentUser()` 装饰器。

**影响**：类型不安全，代码风格不一致。

---

#### D9: StockController `advance` 端点抛出原生 `Error`

**位置**：`server/src/modules/stock/stock.controller.ts:176`

```typescript
if (!cid) throw new Error("缺少比赛上下文");
```

**对比**：所有其他端点使用 NestJS HTTP 异常（`BadRequestException` 等）。

**影响**：原生 `Error` 绕过 `HttpExceptionFilter`，返回未格式化的 500 响应。

**建议**：改为 `throw new BadRequestException("缺少比赛上下文")`。

#### D10: CompetitionController 财年路由嵌套不一致

**位置**：`server/src/modules/competitions/competition.controller.ts`

| 端点 | 路径 | 嵌套 |
|------|------|------|
| `GET` | `/competitions/:id/fiscal-years` | ✅ 在比赛下 |
| `POST` | `/competitions/:id/fiscal-years` | ✅ 在比赛下 |
| `PATCH` | `/competitions/fiscal-years/:fyId` | ❌ 不在比赛下 |
| `DELETE` | `/competitions/fiscal-years/:fyId` | ❌ 不在比赛下 |

**影响**：GET/POST 需要比赛 id，但 PATCH/DELETE 不需要。URL 风格不一致。

#### D13: StockController 多个端点有 `user.competitionId` 回退逻辑

```typescript
const cid = competitionId ? parseInt(competitionId) : user.competitionId ?? undefined;
```

此模式在 StockController 中出现 6 次，但其他控制器均不使用（依赖 `CompetitionScopeGuard` 自动注入）。

**影响**：双重注入可能掩盖 bug。

---

#### D14: 方法级 `@UseGuards(PermissionsGuard)` 冗余

当类级已有 `@UseGuards(JwtAuthGuard, PermissionsGuard)` 时，方法级再加 `@UseGuards(PermissionsGuard)` 是冗余的。此模式出现在几乎所有控制器的写操作上。

**影响**：代码噪音，不影响功能。

## 路由命名规范性

### ✅ 全部符合规范

| 规范 | 状态 |
|------|------|
| kebab-case | ✅ 全部使用（`map-nodes`、`tech-nodes`、`production-lines`） |
| 复数名词 | ✅ 全部使用（`materials`、`companies`、`contracts`） |
| RESTful 动词 | ✅ GET=读取、POST=创建、PATCH=更新、DELETE=删除 |
| 子资源嵌套 | ✅ 除财年路由外全部一致 |

## 权限守卫规范性

### 守卫使用统计

| 模式 | 控制器数 | 说明 |
|------|---------|------|
| 类级 JwtAuthGuard + PermissionsGuard + RequirePermissions | 16 | 标准模式 |
| 类级 JwtAuthGuard + 方法级 PermissionsGuard | 2 | competition, consumer-demand |
| 类级 JwtAuthGuard only | 1 | message |
| @NoCompetitionScope + 类级守卫 | 5 | competition, contract-type, industry-type, message, files |

### @Ownership 使用统计

| 状态 | 控制器 |
|------|--------|
| ✅ 类级 @Ownership | material, part, product, map-node, map-edge, map-node-type, path-type, infrastructure, tech-tree, fuel, vehicle, warehouse, production-line, company, region, contract, users |
| ⚠️ 方法级 @Ownership | company-fields (viaCompany), consumer-demand (仅 update) |
| ❌ 无 @Ownership | stock, message, files, competition, contract-type, industry-type |
