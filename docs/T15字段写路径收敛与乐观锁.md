# T15 字段写路径收敛 + version 乐观锁（R11 一致性治理）

> 隶属：后端重构设计 R11。本文件是 T15 的实施定稿，R11 段仅保留结论指针。
> 提交：见 `docs/重构进度报告.md` M8 段 T15 行。

## 1. 问题（B11 复述）

`CompanyFieldValue`（公司产业字段值）存在 **三套独立写路径 + 两套外部直写**，彼此不感知：

| 写路径 | 位置 | 触发源 |
|---|---|---|
| ① 手动编辑 | `company-fields.service.ts` `setValues` (L284) | 管理员编辑公司资料 |
| ② 财年定时器 | `company-fields.service.ts` `applyFiscalYearTimer` (L493) | 财年开始/结束触发 |
| ③ 计算图级联重算 | `company-fields.service.ts` `recomputeCalculatedFields` (L651) | 基础字段写后级联 |
| ④ 合同引擎直写 | `contract-engine.service.ts` L1660 (`tx.upsert`) / L1796 (`prisma.upsert`) | 合同执行 / 复原重放 |
| ⑤ 股票引擎直写 | `stock.service.ts` L1167 (`tx.updateMany`) | 股票推进写现金绑定字段 |

风险：同一字段并发写（如合同执行与手动编辑重叠）时后写覆盖先写；级联重算与基础字段写可能交错产生中间态；股票写绕过单入口，审计/广播语义不一致。

## 2. 方案

### 2.1 单写入口（写路径收敛）

`CompanyFieldsService` 新增 **事务感知** 的统一写方法：

```ts
async writeFieldValueInTx(
  tx: Prisma.TransactionClient,        // 复用调用方事务；也可传 PrismaService 本身
  companyId: number,
  industryFieldId: number,
  value: string,
): Promise<void>
```

语义：
- 行不存在 → `create({ companyId, industryFieldId, value, version: 0 })`；
- 行已存在 → `updateMany({ where: { id, version }, data: { value, version: { increment: 1 } } })`；
- 并发创建触发 `P2002` → 重试（下一轮命中已存在分支）；
- `updateMany.count !== 1`（version 被其他写入抢占）→ 重试，耗尽抛 `FieldWriteConflictException`（409）。

**所有 5 个写点改用此方法**：
- ①②③ 内部三处 `prisma.companyFieldValue.upsert/.updateMany` 替换为 `writeFieldValueInTx(tx, ...)`；
- ④ `ContractEngineService` 注入 `CompanyFieldsService`，两处直写改为 `this.fields.writeFieldValueInTx(...)`；
- ⑤ `StockService` 注入 `CompanyFieldsService`，现金绑定字段写改为 `this.fields.writeFieldValueInTx(...)`。

模块接线：`StockModule` 增加 `imports: [CompanyFieldsModule]`（contracts 模块已含）。

### 2.2 version 乐观锁

`schema.prisma` 的 `CompanyFieldValue` 增加：

```prisma
version Int @default(0)
```

落库：`prisma generate` + `db push --skip-generate`（存量行默认 0）。写入时以 `where: { id, version }` 条件更新并 `version: { increment: 1 }` 实现乐观锁；跨进程/重叠事务的写冲突被检测为重试或 409。

### 2.3 级联重算串行化（进程内 per-company 互斥）

`CompanyFieldsService` 新增进程内按公司串行队列：

```ts
private serializeCompany<T>(companyId: number, fn: () => Promise<T>): Promise<T>
```

- 对**同一 companyId** 的 `setValues` / `applyFiscalYearTimer`（每公司段）/ `recomputeCalculatedFieldsForCompany` 入队串行，消除进程内读-改-写竞态；
- 仅公共入口加锁；内部一律调用**私有** `recomputeCalculatedFields`（不加锁），避免同公司重入死锁；
- 队列头 settle 后清理 `Map` 条目，无内存泄漏。

### 2.4 删除影响自动化（删除字段时的引用清理）

`IndustryField` 删除入口 `industry-type.service.ts` `removeField`（已要求 fieldValues 为空才允许删，数据级联安全）增加**兄弟字段引用清理**：

新增 `common/field-ref-cleanup.ts`：

```ts
async function cleanupFieldReferences(prisma, industryTypeId, deletedFieldKey)
```

- 扫描同产业类型其余 `IndustryField`：
  - `timerValue === "field:<deletedFieldKey>"` → 置空（避免定时器引用已删字段静默跳过）；
  - `calcGraph` 中 `type:"value"` 且 `data.fieldKey === deletedFieldKey` 的节点 → 移除该节点及相关边（避免计算图悬空引用导致重算异常）。
- 不注入 `CompanyFieldsService`（避免 industry-types ↔ company-fields 循环依赖），直接走 `prisma`。

### 2.5 删除影响清单审计结论（Cascade 覆盖核对）

为收口 R11「`getDeleteImpact` 覆盖所有 `onDelete: Cascade` 关联」要求，对照 `schema.prisma` 全部 47 处 `onDelete: Cascade` 关系，逐个核对 14 个 `getDeleteImpact`/`getXxxImpact` 实现。结论：**既有实现已 100% 覆盖各自的级联子表，无需改代码**。

| 模块（被删模型） | schema 中指向它的 Cascade 子表 | 实现是否覆盖 |
|---|---|---|
| Material | PartMaterial(materialId) | ✅ 报 partMaterialCount |
| Product | ProductPart(productId)、ProductTechRequirement(productId) | ✅ 两项均报 |
| Part | PartMaterial(partId)、ProductPart(partId)、PartTechRequirement(partId) | ✅ 三项均报 |
| TechNode | PartTechRequirement(techNodeId)、ProductTechRequirement(techNodeId)、TechPrerequisite(nodeId)、TechPrerequisite(prerequisiteNodeId) | ✅ 四项均报 |
| Contract | ContractFieldEffect(contractId) | ✅ 报 effectCount |
| Vehicle | VehiclePathType(vehicleId) | ✅ 报 pathTypeCount |
| MapNodeType | MapNode(nodeTypeId)、MapEdge(fromNodeId/toNodeId，经节点级联) | ✅ 报节点数 + 边数 |
| PathType | MapEdge(pathTypeId)、VehiclePathType(pathTypeId) | ✅ 两项均报 |
| MapNode | MapEdge(fromNodeId)、MapEdge(toNodeId) | ✅ 报 edgeCount |
| Company | CompanyFieldValue(companyId) | ✅ 报 fieldCount |
| MapEdge / Warehouse / ProductionLine / Infrastructure / Fuel | 无（叶子 / 无任何 Cascade 子表指向它们） | ✅ 空 children 正确 |

**Fuel 的 Restrict 情形已妥善处理**：`Vehicle.fuelId` 未声明 `onDelete`（迁移为 RESTRICT，非 Cascade），删除燃料不会级联删载具、反会被外键阻止。`fuel.service.ts` 的 `remove()` 已有前置校验（`vehicle.count({where:{fuelId:id}})`），若被引用则抛 `ConflictException` 清晰提示；`getFuelImpact` 返回空 children（无级联子数据），前端 `deleteConfirm.ts` 仅在 children 非空时才展示「级联删除」警告——行为一致、无盲点。

### 2.6 仍属广义治理的后续项（超出本次手写补全范围）

以下**根模型**本身可删除、且拥有 `onDelete: Cascade` 子表，但当前**没有**对应的 `getDeleteImpact` 端点（属 R11 提到的「更广义删除影响治理」，非本次 14 模块手写补全范围）：

- `Competition`（根，级联约 20 类子表：FiscalYear/Material/Part/Product/TechNode/地图/Region/Company/Contract/Stock 等）——删除比赛影响面极大，建议补端点并强提醒；
- `IndustryType`（级联 IndustryField）、`Stock`（级联 StockHolding/StockOrder/StockCandle）、`StockFundsAccount`（级联 StockHolding/StockOrder）、`Message`（级联 MessageRecipient）。

这些需新增 service 方法 + controller 路由 + 前端在对应删除入口接入 `confirmDeleteWithImpact`，建议作为独立任务推进。
