### 1.3 请求管线（5 级守卫 + 3 级拦截/过滤）

```
HTTP 请求
  │
  ▼
┌─────────────────────────────────────────────────────────────┐
│ 守卫链（按序）                                                │
│  ① JwtAuthGuard             JWT + @Public 豁免 + tokenVersion│
│  ② MustChangePasswordGuard   未改密仅放行改密/资料接口         │
│  ③ CompetitionScopeGuard    BOLA 防护：注入本人 competitionId │
│  ④ OwnershipGuard           @Ownership 接口按 ID 直查归属      │
│  ⑤ PermissionsGuard         @RequirePermissions + actionRank │
└─────────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────────┐
│ 控制器方法                                                    │
│  └─→ service 业务编排 → Prisma 模型操作                        │
│          └─→ PrismaService.$allOperations 扩展                 │
│               ├─ 拦截写操作 → 构造审计日志 writeAuditLog()      │
│               └─→ 拦截写操作 → RealtimeService.emit... 广播     │
└─────────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────────┐
│ 响应后处理                                                    │
│  ResponseInterceptor  → 统一包装 {code,message,data,requestId}│
│  LoggingInterceptor   → Winston 记录请求/响应/耗时/操作人     │
│  HttpExceptionFilter  → 异常统一格式 + 错误审计落库 + requestId│
└─────────────────────────────────────────────────────────────┘
  │
  ▼
HTTP 响应（CORS 白名单 + helmet 安全响应头）
```

### 1.4 数据模型（schema.prisma 现状）

- **模型规模**：30+ 模型，核心业务实体均带 `competitionId` 实现多租户隔离
- **主键**：`Int` 自增；名称唯一性通过 `@@unique([competitionId, name])` 覆盖多数模型
- **金额/数值**：`Float`
- **状态字段**：仍以 `String` 存储（代码内通过枚举字面量 + Zod/class-validator 校验约束）
- **结构化字段**：部分保留 JSON 字符串列，但**合同 / 产业字段配置类 JSON 已接入 shared/engine-dsl 的 JSON Schema 三层校验**
- **审计表**：`AuditLog`（数据库写操作 + 错误上下文，支持 requestId 串联排查）

## 2. 已完成的重构项

### R1 上帝模块拆分（合同引擎 + OP 运算）

| 原文件 | 拆分后 | 说明 |
|---|---|---|
| `contract-engine.service.ts`（~2500 行） | `contracts/engine/` 子目录 + 编排层 | ✅ 已完成 |
| 其中纯函数（值求值 / 应用效果 / 条件判定 / 聚合计算） | `contracts/engine/values.ts` | 值源全类型求值：CONST / INPUT / FIELD / ENTITY / FORMULA / INDUSTRY_IS / OP / VAR / ROUTE |
|  | `contracts/engine/effects.ts` | applyOp / FIELD_OPS 效果应用（ADD / SUB / SET）+ IF / FOREACH / ASSIGN 控制流递归 |
|  | `contracts/engine/conditions.ts` | 5 种条件检查执行与错误消息构造 |
|  | `contracts/engine/compute.ts` | 20+ 聚合端点（公司字段求和 / 原材料消耗 / 库存统计 等） |
|  | `contracts/engine/index.ts` | 汇总导出 |
| 编排逻辑（事务 / 回滚 / 前置检查 / 执行日志） | `contract-engine.service.ts`（瘦身到 ~700 行） | 依赖拆分后的 engine 子模块，含 Prisma 事务编排 |
| 跨模块共享 OP 运算 + OP_ARG_SPECS | `common/engine-ops.ts` | ✅ 已从 contract-engine 独立抽出，供产业计算引擎直接 import |

**可测试性收益**：`engine/` 子目录与 `common/engine-ops.ts` 均为纯函数，不依赖 Prisma，可脱离数据库 Jest 单测。

### R2 跨端共享配置 DSL（单一事实源）

新增 `shared/engine-dsl/` 独立 TypeScript 包，**服务端 package.json 的 build/start 脚本均先编译此包**：

```json
"build": "tsc -p ../shared/engine-dsl/tsconfig.json && nest build",
"start": "tsc -p ../shared/engine-dsl/tsconfig.json && nest start",
```

共享内容：
- `schema.ts`：`ValueSpecSchema` / `EffectSchema` / `ConditionSpecSchema` 三套 JSON Schema 定义
- `index.ts`：DSL 类型声明
- 客户端（通过相对路径 alias）和服务端均可引用同一套定义，**消除 OP_ARG_SPECS / 类型常量的手抄双份漂移风险**

### R3 JSON 结构化校验（三层闭环）

| 层级 | 位置 | 实现 |
|---|---|---|
| ① 保存前结构校验 | 客户端编辑器 | graph-model.ts 类型约束 + 保存前校验 |
| ② 服务端写入校验 | `common/validators/json-schema.ts` | 使用 shared/engine-dsl 的 schema 对 ContractType.{effects/conditions/partyRoles/inputSchema}、IndustryField.{calcGraph,config} 做写入前校验，不合格直接 400 |
| ③ 执行前容错 | 服务端引擎 | safe-expression 白名单 + evalValueSpec 边界值处理，坏数据不炸整条链路 |

校验器覆盖：
- 值源 type 枚举合法
- 每个 valueType 的必填字段齐全
- 效果节点 op / kind 合法
- 条件检查 condKind / compareOp 合法
- OP 节点 args 数量匹配 OP_ARG_SPECS

`json-schema.spec.ts` ✅ 有单测覆盖正常/异常路径。

### R4 审计落库（取代仅进日志）

新增 `common/logging/audit.ts`，审计写统一走 `writeAuditLog()`：

```
写操作（Prisma $allOperations 扩展）
   ├─ before：读取旧值（仅 update/delete）
   ├─ after：读取新值
   ├─ 构造 changes JSON（diff 前后）
   └─ writeAuditLog({kind:"write", action, operatorId, model, recordId, competitionId, changes, ip, requestId})
       │
       └─ AsyncLocalStorage 标记「审计写上下文」
       └─ 使用原始 PrismaClient（非 $extends 版本）写入 AuditLog 表
           （天然避免「审计写又被 $allOperations 拦截 → 再审计」的无限递归）
```

**错误上下文审计**：HttpExceptionFilter 捕获异常时同样调用 `writeAuditLog({kind:"error"})`，关联 `requestId`、`statusCode`、`errorSummary`。

**排障流程**：给出一个 requestId → AuditLog 表按 requestId 查询 → 一次性看到「请求链路全部写操作 + 最终异常堆栈」。

### R5 错误排查能力（requestId 串联）

- `operator.context.ts`：AsyncLocalStorage 存储 `{operatorId, competitionId, requestId, ip}`
- 请求进入 LoggingInterceptor 生成 requestId，写入 ALS
- ResponseInterceptor：响应体追加 `requestId`
- HttpExceptionFilter：异常响应追加 `requestId`，Winston 日志全部携带 requestId 字段
- 审计落库每条携带 `requestId`

### R6 登录限流外置可观测

`common/security/login-throttle.ts`：
- 策略：同 IP 15 分钟内失败 5 次 → 临时封禁；同账户 15 分钟内失败 10 次 → 临时封禁
- 存储：进程内存 Map（单体够用；如需多实例迁移可替换为 Redis 适配器，接口已抽象 `get/set/del/increment`）
- 失败计数器：`attemptsKey = login:ip:${ip}` / `login:user:${username}`

### R8 Prisma 扩展合并（审计 + 实时广播一条链路）

`PrismaService.$extends({ query: { $allOperations } })`：
- 仅拦截 mutate 类（create / update / upsert / delete / createMany / updateMany / deleteMany / executeRaw 白名单）
- before：读旧值 → after：读新值 → 计算 changes
- 顺序：`writeAuditLog(...)` → `RealtimeService.emitResourceChanged(...)`
- 房间策略：有 `competitionId` 发 `comp-${cid}`，无则全体广播

## 3. 现状问题清单（仍需持续治理）

### B1 数据模型加固（部分解决，仍存缺口）

| 问题 | 现状 | 建议 |
|---|---|---|
| `competitionId` 可空泛滥（23 个模型） | 仍保留；靠 CompetitionScopeGuard + service 自觉兜底 | 短期：schema 注释显式标注「允许全局模板」的模型白名单；中期：新设计把模板与实例拆表（MaterialTemplate vs Material） |
| 状态字段裸字符串 | 仍保留；代码内用字面量 | 先引入 Zod DTO 枚举校验，再逐步替换为 Prisma enum |
| 部分 JSON 字符串列无校验 | Material.nodePrices / Region.overviewCards / Message.targetUserIds / Stock.carbonFieldRef 等未接 Schema | 按业务紧迫度逐个接入 Zod 校验 + 可选拆表 |
| `updatedAt` 无索引 | 增量查询每次全表扫描 | SQLite 下 `@@index([competitionId, updatedAt])` 加到所有走增量同步的模型（低风险，收益高） |

### B2 同步/实时链路（高频场景待优化）

| 问题 | 现状 | 建议 |
|---|---|---|
| `existingIds` 每次全量查 | 增量接口仍返回满足 baseWhere 的全部 id 集 | 改为 cursor 分页 + "deletedIds" 增量差集 |
| 实时广播无去重合并 | 股票推进等批量场景逐条 emit，产生事件风暴 | RealtimeService 引入 50ms 微批：同 resource + 同 action 合并为一条 multi-{ids} |
| 无补偿 | 连接断开的客户端靠下次 HTTP 增量自愈 | 网关新增 `missedUpdates` 通道：客户端重连传 lastEventId，回放窗口内事件 |

### B3 安全 / 可观测性

| 问题 | 现状 | 建议 |
|---|---|---|
| 登录限流进程内存 | 单实例够用；多实例/重启失效 | 保留现有接口抽象，新增 RedisThrottleStore 适配器 |
| Winston 日志仅本地文件 | 无集中化 | 可选接入 Datadog / Loki 远程上报（保留本地轮转作兜底） |
| 健康探针无深度 | `/health` 仅 200 文本 | 扩展 Prisma ping + 磁盘空间 + 登录限流统计 |

### B4 工程化

| 问题 | 现状 | 建议 |
|---|---|---|
| 0 CI | 无 GitHub Actions / GitLab CI | 增加 `.github/workflows`: lint → build → test |
| 环境配置无校验 | `.env` 缺失字段时启动抛模糊错误 | 启动时 Zod 校验 process.env，缺失即 exit(1) 并打印缺失项 |
| 纯函数覆盖度刚起步（7 份） | 合同引擎 `engine/` 拆分后还没补 spec | 补 `contracts/engine/*.spec.ts`（纯函数，成本低收益高） |
