## 1. 背景与目标

后端自项目启动以来经历了多轮功能叠加（合同引擎、股票系统、消息中心、实时广播、增量同步、权限分级），单体规模已经膨胀到需要系统性治理的程度。审查发现的问题可分为五类：

1. **服务层上帝模块**：`contract-engine.service.ts`（2590 行）、`stock.service.ts`（1189 行）等单文件职责过重，且引擎纯函数与编排逻辑混在同一文件，无法独立测试；
2. **数据模型脆弱**：23 个模型 `competitionId` 可空、15+ 个字段用 JSON 字符串存结构化数据、状态全部用裸字符串、增量同步依赖的 `updatedAt` 无索引——数据层约束基本靠 service 代码「自觉」；
3. **同步/实时链路粗放**：增量契约每次全量查 `existingIds`、实时广播无去重/合并/补偿，股票推进等高频场景会产生事件风暴；
4. **安全与可观测性短板**：登录限流是进程内存实现、审计只进日志不落库、错误细节被统一屏蔽导致排障困难；
5. **工程化缺失**：0 个测试文件、无 CI、无环境配置校验。

本次重构目标（按优先级）：

- **G1 消除上帝模块**：合同引擎与股票服务按「纯函数库 + 编排层」拆分，每个文件职责单一、可单测；
- **G2 数据模型加固**：`competitionId` 归属策略明确化、JSON 字符串结构化、状态枚举化、索引补全，让约束回到 schema 而不是代码；
- **G3 同步/实时链路可控**：增量查询不再全表扫描、实时广播可合并可补偿，杜绝事件风暴；
- **G4 安全与可观测性达标**：审计落库、限流可外置、日志可串联、错误可排查；
- **G5 测试与 CI 从零到一**：先保引擎纯函数单测，再补 e2e 冒烟。

> 与权限/数据同步/前端刷新/股票四份蓝图的关系：本文的 R 系列是「后端地基」，其余四份的落地都依赖这里的数据模型与模块边界先理清。**建议按本文 D 系列决策确认 → R2/R3/R4 数据层先行 → R1 服务拆分 → R7 测试兜底 → 再推进其余蓝图实施**。

### 2.1 目录与规模

```

├── users/                     # 账户管理

### 2.2 守卫链（认证 → 授权五级）

```
JwtAuthGuard → MustChangePasswordGuard → CompetitionScopeGuard → OwnershipGuard → PermissionsGuard
```

| 守卫 | 职责 | 关键机制 |
|---|---|---|
| JwtAuthGuard | 登录态 | `@Public` 豁免；JWT 载荷 `tv` 与库内 `tokenVersion` 比对（单设备踢出） |
| MustChangePasswordGuard | 强制改密 | 未改密仅放行 `/auth/change-password`、`/auth/me` |
| CompetitionScopeGuard | 比赛作用域（防 BOLA） | 非超管写接口强制覆盖 `body.competitionId`；列表接口注入本人 `competitionId`；`@NoCompetitionScope` 豁免全局模板 |
| OwnershipGuard | 按 ID 直查归属（防 BOLA） | 仅 `@Ownership` 标注接口生效；查实体 `competitionId` 与请求者归属比对 |
| PermissionsGuard | 功能权限 | `@RequirePermissions`；SUPER_ADMIN 隐式全放行；同域蕴含（manage⊇edit⊇view） |

守卫链本身设计较完整（BOLA 修复到位），本文不再重复。

### 2.3 数据模型概览（schema.prisma 689 行）

- 约 30 个模型；核心业务实体 22+ 个带 `competitionId`；
- 存储形态：`Int` 主键自增、`Float` 金额、**状态一律 `String`**、**结构化数据一律 JSON 字符串**；
- 索引：名称唯一 `@@unique([competitionId, name])` 覆盖较全；**`updatedAt` 无任何索引**。

### 2.4 实时与增量链路

```
写操作（Prisma $extends $allOperations）
  ├─→ logger.info("数据库写操作", {audit, model, action, before/after/changes})   # 审计仅进日志
  └─→ emitResourceChange() → RealtimeService.emitResourceChanged()                # 广播 {resource,id,action}
         ├─ competitionId != null → comp-{cid} 房间
         └─ competitionId == null → 全体广播（全局模板）
读操作（增量同步）
  列表接口 ?updatedAfter=ISO → applyUpdatedAfter() → 查 updatedAt>baseline 的记录
       + existingIds（满足 baseWhere 的全部 id 集合）→ 前端 diff 删除本地副本
```

## 3. 问题清单（B 系列）

### B1 服务层上帝模块（高优先）

| 文件 | 行数 | 混合职责 |
|---|---|---|
| `contract-engine.service.ts` | 2590 | 引擎纯函数（20+ 个 `computeXxx`）+ `evalValueSpec` 值规范求值 + 执行编排 `execute` + 回滚 `revertContract` + 前置检查 `runConditions`/`precheck` + 列表过滤校验 `validateInfraListFilters` 等，全部堆在一个文件 |
| `stock.service.ts` | 1189 | 撮合/定价（实际在 engine.ts）+ 做市商生成 + 推进轮次编排 + PE 联动/随机 + 账户权限范围 + 绑定解析 + 诊断 |
| `company-fields.service.ts` | 727 | 字段值 CRUD + 计算图级联重算 + 定时器 + 范围过滤 |
| `contract.service.ts` | 470 | 合同 CRUD + 状态机 + 审批流 |
| `industry-type.service.ts` | 431 | 产业类型 CRUD + 字段 CRUD + 计算图维护（另有 `industry-calc-engine.service.ts` 352 行） |

后果：
- 引擎纯函数与 Prisma 编排耦合，**无法脱离数据库做单元测试**；
- 一个文件改一行就要全文回归，review diff 巨大；
- `contract-engine.service.ts` 头部 1800 行是模块级函数，类型全靠 `any`，无导出边界。

### B2 数据模型：`competitionId` 可空泛滥（高优先）

23 个模型 `competitionId Int?`：User、Material、Part、Product、TechNode、MapNodeType、PathType、MapNode、MapEdge、Infrastructure、Warehouse、ProductionLine、Fuel、Vehicle、Region、ConsumerDemand、Company、Stock、StockFundsAccount、StockHolding、StockOrder、StockCandle、Message。

问题：
1. **「全局模板」与「比赛数据」混存同一张表**：`Material` 既可属比赛也可作为全局模板（`competitionId=null`），读接口 `where: {competitionId}` 天然漏掉模板行，写接口漏传即造出「孤儿全局行」；
2. **归属语义靠注释约定**：哪些模型允许全局模板、哪些必须比赛级，schema 无法表达，全靠 service 自觉 + CompetitionScopeGuard 兜底；
3. `CompetitionScopeGuard` 把非超管写请求的 `body.competitionId` 强制覆盖为本人归属——这只堵住了越权写，**没有解决「超管创建比赛数据时漏传」的脏数据面**；
4. 跨比赛删除依赖 `assertSameCompetition` 逐点调用，漏一处即洞（已由 CompetitionScopeGuard 全局兜底，但删除接口仍双轨校验，规则分散）。

### B3 JSON 字符串字段泛滥（高优先）

| 字段 | 用途 | 问题 |
|---|---|---|
| `Material.nodePrices` | 节点价格字典 | 无法 `where` 过滤、无类型校验 |
| `Region.overviewCards` | 总览卡片数组 | 同上；前端要整体读出再解析 |
| `ContractType.partyRoles/inputSchema/effects/conditions/graph` | 合同类型配置 | 合同系统的**核心配置**无 schema 校验，错误配置到执行期才炸 |
| `Contract.parties/inputs/executionLog/executionResult` | 合同实例数据 | 审计与结果快照不可查询 |
| `ContractFieldEffect.valueRaw/beforeRaw/afterRaw` | 效果明细 | 回滚重放依赖它，但字符串解析散落多处 |
| `Message.targetUserIds/images` | 收件人/附件 | 收件人无法 SQL 反查「某人收到哪些消息」 |
| `Stock.carbonFieldRef/happinessFieldRef/industryAvgCarbonRefs` | 字段绑定引用 | 绑定关系不可查询 |
| `IndustryField.config/calcGraph/formula/timerValue` | 字段配置/计算图 | calcGraph 是图结构 JSON，无校验 |

后果：**校验、查询、迁移三类能力全部缺失**；解析点分散（`safeParse` 在各 service 各写一份，`catalog.ts` 里也有一份）；坏数据只有运行时才暴露。

### B4 状态/类型全部裸字符串（中优先）

`User.role`、`FiscalYear.status`、`Competition.status`、`Material.type`、`Company.status`、`IndustryField.fieldType`、`Contract.status`、`ContractFieldEffect.op`、`StockFundsAccount.ownerType`、`StockOrder.side/status` 等全部 `String` + 注释枚举。

后果：拼写错误无编译期拦截、无效值可入库、`@default` 与代码里的默认值可能不一致、重构枚举名靠全局搜索。

### B5 索引缺失（高优先，直接影响同步）

- **全模型 `updatedAt` 无索引**：增量同步 `where: {updatedAt: {gt: baseline}, competitionId}` 走全表扫描，数据量上来后每次同步都 O(n)；
- `Company.competitionId / industryTypeId / regionId`、`Stock.companyId`、`StockFundsAccount.userId / companyId`、`MapEdge.fromNodeId / toNodeId`、`TechNode.tier` 等外键/高频过滤列无索引；
- 好消息：`StockOrder` 有 `@@index([competitionId, stockId, round, status])`、`StockCandle` 有 `@@unique([stockId, round])`、`ConsumerDemand` 有 `@@index([competitionId, region])`、`Message` 有 `@@index([competitionId])`、`ContractFieldEffect` 有 `@@index([contractId])` 与 `@@index([companyId, industryFieldId])`——命名唯一索引覆盖也基本齐全。

### B6 非空约束 / 默认值缺失（中优先）

- `Stock.totalShares / initNetProfit / industryPE / currentCarbon / industryAvgCarbon / happiness / initPrice / currentPrice` 无 `@default`，创建 DTO 校验不足时会产生半成品股票行；
- `IndustryField.calcGraph` 为 `isCalculated` 的必填项但可空；
- `ContractType.partyRoles / inputSchema / effects` 无默认值（`conditions` 有 `@default("[]")`），新建类型漏填即执行期报错。

### B7 无测试、无 CI（高优先）

- `server/` 下 **0 个 `.spec.ts` / `.e2e-spec.ts`**；
- 自研 500 行表达式求值器 `safe-expression.ts`、2590 行合同引擎、股票撮合/定价/K 线全是纯函数，**是最适合也最需要单测的代码**，却一行测试都没有；
- 无 CI 流水线：合并即上线，回归全靠手工。

### B8 增量同步契约粗糙（中优先）

`common/sync.ts` 的 `buildIncrementalResult` 每次增量请求都要：
1. 查 `updatedAt > baseline` 的记录（无索引 → 全表扫）；
2. **再查一次满足 `baseWhere` 的全部 id 集合**（`existingIds`）——数据量 O(n)，与增量初衷相悖；
3. 增量与分页互斥（`Material.findAll` 增量分支直接 `findMany` 不分页，增量期间数据超量会拖垮响应）。

与《数据同步与实时机制重构设计》S 系列衔接点：S 系列已定「按比赛/账户隔离分库 + 统一 `updatedAfter` 契约」，本文 R8 负责把服务端查询侧做到「索引 + 分页 + 游标」三件事。

### B9 实时广播粗放（中优先）

`RealtimeService.emitResourceChanged` 只推 `{resource, id, action}`，无：
- **去重/合并**：股票推进一轮 = N 只股票 × 每只多实体变更（Stock/Order/Holding/Candle）→ 单轮可推 4N+ 个事件，前端 `resource:changed` 处理风暴；
- **ACK / 重连补偿**：断线期间的变更不补发，靠前端下次增量同步兜底（能自愈但延迟不可控）；
- **房间粒度**：只有 `comp-{cid}` 比赛房间和 `user-{id}` 私有房间两级，无法按「资源 + 操作者」定向（如「仅给合同审核员推待审事件」）。

### B10 安全纵深不足（中优先）

- **登录限流是进程内存 Map**（`login-throttle.ts`）：多实例部署即失效；`setInterval` 清理依赖 `unref()`，Electron 打包单进程场景可用，但不可水平扩展；
- **审计只进 Winston 日志**（`logger.info("数据库写操作", ...)`）：日志轮转/清理后审计即丢失，无法回答「谁在何时改了什么」；
- **DTO 校验覆盖不全**：`common/validators` 只有密码强度一个校验器；大量 service 方法签名是 `dto: any` 或直接收 `unknown`，依赖全局 `ValidationPipe` + 手写 `safeParse`；
- `http-exception.filter` 统一屏蔽 Prisma/约束错误原文（安全正确），但**不落库错误上下文**，排障只能翻日志。

### B11 事务与一致性风险（中优先）

- 合同执行 `execute()` 用 `$transaction`（正确），但**计算字段级联重算**（`industry-calc-engine`）与合同写字段、财年定时器写字段是**三套独立写路径**，彼此不感知，同一字段并发写时后写覆盖先写；
- `company-fields.service.ts` 的 `computePbData` 等每次创建/更新都重新查库计算，存在 **N+1 查询**（列表页加载所有公司字段值时逐公司计算）；
- 删除级联（`onDelete: Cascade`）依赖 Prisma 定义，但**删除影响预估**（`getDeleteImpact` 系列）逐模块手写，漏一个关联表就会静默级联删错。

### B12 可观测性短板（低优先）

- 日志有 `operator.context`（AsyncLocalStorage 操作员上下文）+ 脱敏，方向正确；
- 缺：**requestId 贯穿**（无链路追踪）、**慢查询日志**（logging.interceptor 有 500ms 告警但无 SQL 级）、**指标暴露**（无 Prometheus / 健康详情）、**错误上下文落库**。

### B13 配置管理散乱（低优先）

- 环境变量散落读取（`process.env.JWT_SECRET` 在 JwtStrategy、`CORS_ORIGIN` 在 main.ts、`WS_ALLOWED_ORIGINS` 在 realtime.gateway 各读一遍）；
- 无 `ConfigModule` 校验：必填项缺失启动不报错（如忘配 `JWT_SECRET` 时用默认值静默降级）。

### B14 单例与模块耦合 hack（低优先）

- `PrismaService` 构造函数 `return this.$extends(...)` 用 Proxy 替换 `this`——注释已说明依赖 Proxy 转发 `onModuleInit/onModuleDestroy`，脆弱且难懂；
- `RealtimeService` 用模块级 `_singleton` + `getRealtimeService()` 全局取单例（为避免与 PrismaModule 循环依赖）——绕开了 Nest 依赖注入，测试注入困难。

## 4. 重构方案（R 系列）

> 原则：
> - **先数据层、后服务层、再工程化**（R2–R6 → R1 → R7–R9 → R10–R14）；
> - 每个 R 都必须**向后兼容**（旧数据可迁移、旧接口可用），SQLite 迁移用 Prisma migrate，不做破坏式改表；
> - 纯函数与编排分离后，**引擎代码先行补测试**再动拆分，防止拆分引入回归。

### R1 服务层拆分：引擎纯函数库 + 编排层

**合同引擎**（`contract-engine.service.ts` 2590 行 → 拆 5 文件）：

```
modules/contracts/
├── engine/
│   ├── values.ts          # evalValueSpec 值规范求值 + 类型强制（从 325 行区域抽出）
│   ├── compute.ts         # 20+ 个 computeXxx 纯函数（物料/零件/产品/基建/载具/燃料/仓库/科技树/路径）
│   ├── effects.ts         # 效果应用逻辑（applyEffect / applyLeaf / ADD|SUB|SET）
│   ├── conditions.ts      # runConditions 前置检查（FIELD_COMPARE / INDUSTRY_IS）
│   └── graph.ts           # 最短路 Dijkstra、路由距离/路径类型计算
├── contract-engine.service.ts   # 只剩 execute / revertContract / precheck 编排（<500 行）
└── contract-engine.module.ts    # 导出引擎服务
```

关键动作：`compute.ts` 等纯函数文件**不 import Prisma**——数据通过参数传入（`loadContext()` 统一在编排层做一次查询，把「公司字段值/产业配置/合同类型」打包成上下文对象传给纯函数），彻底脱离数据库可单测。

**股票服务**（`stock.service.ts` 1189 行 → 拆 4 文件）：

```
modules/stock/
├── engine.ts             # 已有纯函数（computeInitPrice/Match/Price/buildCandle）——保持

### R2 数据模型：`competitionId` 归属策略显式化（✅ D1/D2 已确认）

### R3 JSON 字符串 → 结构化（✅ D3/D5 已确认）

分三级处理（按成本递增）：

1. **低级：加校验器**（不动表结构）。为 `ContractType.partyRoles/inputSchema/effects/conditions/graph`、`IndustryField.calcGraph/config`、`Region.overviewCards` 建立**schema 校验函数**（`common/validators/json-schema.ts`，用 TS 手写守卫或引入 zod），在创建/更新 DTO 处统一校验，坏数据拒绝入库；
2. **中级：Prisma `Json` 类型**（`String` → `Json`，迁移时 `JSON.parse` 存量）。适用：`Contract.parties/inputs/executionLog/executionResult`、`Message.targetUserIds/images`、`Stock.*FieldRef`、`IndustryField.timerValue`——读写路径从 `JSON.parse/stringify` 收敛到 Prisma 自动序列化，`Prisma.JsonNull` 语义清晰；
3. **高级：拆表**（只对查询刚需的做）。`ContractFieldEffect` 的 `valueRaw/beforeRaw/afterRaw` 拆为数值列（`value/before/after` + `op` 枚举），回滚重放不再字符串解析；`Region.overviewCards` 拆 `RegionCard` 子表（`regionId, displayName, companyId, industryFieldId`），支持按公司反查；`ContractType` 的 `effects` 拆 `ContractTypeEffect` 子表（外键到 IndustryField，`op` 枚举，`value` 数值）。

验收标准：所有 `JSON.parse` 只出现在 `json.util.ts` 一个文件；新增/修改配置类数据 100% 过校验；拆表后相关查询走 Prisma 关系而非字符串过滤。
