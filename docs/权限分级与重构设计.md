# 权限分级与重构设计

> 版本：v2（决策已确认）
> 状态：设计定稿，进入重构实施阶段
> 已确认决策（2026-08-17）：D1-A 合同域等级蕴含 / D2-A 越权拒绝 / D3-B 范围作用域对象化 / D4-A 开放扩展集
> 关联代码基线：`server/src/permissions/catalog.ts`（后端权威）、`client/src/permissions/catalog.ts`（前端镜像）、`client/src/stores/auth.ts`、`client/src/views/account-management/AccountManagementView.vue`
> 阅读对象：本系统维护者。本文档是「细化权限分级、优化权限系统」的蓝图，重构验收以本文档第 6 节任务清单与第 7 节兼容策略为准。

---

## 1. 背景与目标

当前权限系统已具备 RBAC + 范围约束 + 多租户隔离的骨架，但存在**动作层级不统一、角色权限无后端权威模板、范围空值语义相反、前后端权限目录双份硬编码**等问题。本次优化目标是：

1. **统一动作分级模型**：用「动作偏序表」取代硬编码蕴含判断，把 `view / edit / manage / execute / audit` 纳入可声明的等级体系；
2. **后端权威化角色模板**：三角色的默认权限集合与「授予上限」由后端定义并强制校验，杜绝前端派生权限被越权放大；
3. **范围作用域对象化**：4 个范围字段升级为作用域对象（`mode` + `companyIds`），根治「空值含义相反」陷阱；
4. **单一事实源**：前端权限目录不再手工镜像后端，改为运行时拉取；
5. **可验收**：给出端点-权限矩阵基线（111 处守卫使用）与重构任务清单。

### 2.4 当前蕴含规则（`hasPermission`，硬编码）

```
view    ← 持有该域任意动作（view/edit/manage/execute/audit 任一）即满足
edit    ← 持有该域 manage 即满足
manage  ← 需精确持有
execute ← 需精确持有（不向下蕴含）
audit   ← 需精确持有（不向下蕴含）
```

| 角色 | 权限派生（前端 `derivePermissions` 硬编码） | 四个范围 |
|------|--------------------------------------------|---------|
| SUPER_ADMIN | 空数组（隐式全放行） | 全空 |
| COMPETITION_ADMIN | baseView(17) + `contract:manage` + `contract:audit` + `contract:execute` + `stock:edit` = **21 key** | 全部 = 所选公司 |
| PLAYER | baseView(17) | `companyScopes=[]`；其余 = 所选公司 |

范围字段与权限的绑定关系（后端 `canReadCompanyAllFields` / `filterByScope` / `assertAuditScope` 等实现）：

| 字段 | 生效权限 | 空值（null/[]）语义 |
|------|---------|--------------------|

## 3. 现状问题分析（问题清单）

### P1（高）动作层级不统一，蕴含规则硬编码

- `manage / execute / audit` 三个动作在 `hasPermission` 中都是「精确持有」，但**相互之间及与 `edit` 之间没有声明式关系**；
- `contract:manage` 与 `contract:execute` 无蕴含关系，导致「能删除合同的管理员却不能执行合同」的语义断层（见 P5）；
- 未来新增动作（如 `export`、`approve`）必须手改 `hasPermission` 的 if-else，易漏。

### P2（高）后端无角色权限模板，授予完全信任前端派生 → 越权提升风险

- `users.service.sanitize()` 只校验**权限 key 是否合法**（`isValidPermissions`），**不校验该角色是否允许持有该 key**；
- 权限集合完全由前端 `derivePermissions` 生成后 POST 给后端；一个被攻破/篡改的客户端可把 `account:manage`、`competition:manage`、`stock:manage` 写入任意 COMPETITION_ADMIN 账号 → **横向/纵向越权**；
- 角色提升的唯一防线是 `role` 字段本身（仅超管可改角色），但权限数组没有同等防线。

### P3（中）前后端权限目录双份硬编码，易漂移

- `client/src/permissions/catalog.ts` 与 `server/src/permissions/catalog.ts` 结构重复；历史上已出现口径漂移（文档曾写 18 域，实际 19 域）；
- 新增权限 key 时若漏同步前端，会导致前端无法勾选/展示，或后端拒绝前端提交。

### P4（中）范围字段空值语义相反

- `companyScopes` 空 = 严格无（看不到任何合同）；`viewCompanyScopes` / `contractViewCompanyScopes` 空 = 不限制；
- 同一「空值」在不同字段下含义相反，且与直觉（空 = 不限）冲突，极易造成配置事故；
- 前端简化界面「公司多选框为空」时，四个范围全部被置空 → 管理员反而**看不到任何合同**（`companyScopes=[]`），与「管理员」直觉严重不符。

### P5（中）contract:manage 在守卫层与 service 层语义不一致

- `ContractReviewGuard`：`contract:manage` **不能**通过（需精确 `execute` 或 `audit`）；
- `contract.service.assertAuditScope` / `filterByScope`：`contract:manage` 视为**全放行**（不受公司范围限制）；
- 结果：仅持 `contract:manage` 的用户列表可见全部合同、但点击执行必 403；权限模型对「manage 是否蕴含执行」自相矛盾。

### P6（低）域动作组合随意，缺少元数据

- 同为管理域：`competition`/`account` 只有 `manage`；`contractType`/`industryType`/`company`/`message` 是 `view+manage`；`data:*` 是 `view+edit`；`contract` 是 `view+execute+audit+manage`；`stock` 是 `view+edit+manage`；
- 没有「该域支持哪些动作、动作间偏序」的声明式元数据，前端无法据此渲染分级勾选。

### P7（低）前后端蕴含实现双份

- `client/src/stores/auth.ts` 的 `can()` / `canAny()` 与后端 `hasPermission` 逻辑重复实现，行为依赖手工保持一致；
- `canAuditCompany()` 使用 `owned.includes("contract:execute")` 精确匹配，若未来蕴含规则变化（如 manage ⊇ execute），前端会先于后端判定不一致。

### P8（低）文档口径漂移

- README / 软件文档 / 设计文档对权限域数量、权限 key 数量的表述不一致（18 域 vs 19 域、31 key vs 39 key）。

## 4. 目标设计：细化权限分级模型

### 4.1 动作分级模型（Action Rank）

**原则**：每个域声明一组动作，每个动作带一个整数等级（rank）；`hasPermission(domain:actionX)` 满足 ⟺ 用户持有该域任一动作 `actionZ` 且 `rank(Z) ≥ rank(X)`。

**全局标准动作等级（默认）**：

| 动作 | rank | 含义 |
|------|------|------|
| `view` | 10 | 只读 |
| `edit` | 20 | 数据写（增删改） |
| `manage` | 30 | 管理（含增删改、配置、删除等全部写） |

**合同域自定义动作等级（D1 已确认）**：

| 动作 | rank | 含义 |
|------|------|------|
| `view` | 10 | 查看合同 |
| `audit` | 20 | 公司级执行（仅 `companyScopes` 内公司参与的合同） |
| `execute` | 30 | 比赛级执行（本比赛内任意草稿合同） |
| `manage` | 40 | 全权管理（新建/删除/执行/任意改） |

> 推荐理由：能删除合同（manage）者必然能执行合同（execute）；能全局执行（execute）者自然能局部执行（audit）。该偏序让 P5 的语义矛盾自动消解：`manage ⊇ execute` 后，`ContractReviewGuard` 只需校验 `contract:execute` 即同时覆盖 manage 持有者。

**影响对照（新规则 vs 现状）**：

| 判定 | 现状 | 新规则（D1） | 变化 |
|------|------|-------------|------|
| `manage` → `execute` | ✗ 不蕴含 | ✓ 蕴含 | 变宽（合理：能删合同者能执行） |
| `execute` → `audit` | ✗ 不蕴含 | ✓ 蕴含 | 变宽（合理：全局执行涵盖局部执行） |
| `audit` → `view` | ✓ 已蕴含 | ✓ 蕴含 | 不变 |
| `edit` → `view` | ✓ 已蕴含 | ✓ 蕴含 | 不变 |
| `view` 由任意同域动作满足 | ✓ | ✓（rank ≥ 10 即满足） | 不变 |

**实现建议（重构 T1/T2）**：在 `PermissionDomain` 上增加可选 `actionRank?: Record<string, number>`（缺省用全局表），`hasPermission` 改为查表判定。废弃 key 继续按「精确持有即满足」兼容。

### 4.2 角色权限模板（Role Templates）与授予上限（Grant Ceiling）

**后端权威定义**（新增 `server/src/permissions/role-templates.ts`，重构 T3）：

| 角色 | 模板权限（默认） | 范围默认值 | 授予上限（默认 = 模板本身） |
|------|-----------------|-----------|---------------------------|
| `SUPER_ADMIN` | `[]`（隐式全放行） | 全空 | 任意（不受限） |
| `COMPETITION_ADMIN` | baseView(17) + `contract:manage` + `contract:audit` + `contract:execute` + `stock:edit` = 21 key | 四个范围 = 所选公司 | 模板 ∪ 可选扩展集（默认不开放） |
| `PLAYER` | baseView(17) | `companyScopes=[]`；其余 = 所选公司 | 模板本身 |

**可选扩展集（`GRANT_EXTRAS`，默认不开放，超管可按需放开）**：

- `COMPETITION_ADMIN` 可扩展：`message:manage`、`contractType:manage`、`industryType:manage`、`company:manage`、`data:region:edit`
- **超管专属（任何非超管角色禁止持有）**：`competition:manage`、`account:manage`、`stock:manage`、`data:*:edit`（除扩展集显式允许外）

**校验规则（重构 T4）**：

```
assertGrantAllowed(actorRole, targetRole, permissions):
  - actor 非 SUPER_ADMIN → 直接拒绝（仅超管可写权限）
  - targetRole = SUPER_ADMIN → 仅允许空数组（超管权限不落库）
  - 否则要求 permissions ⊆ GRANT_CEILINGS[targetRole]，越权 key 记审计日志并拒绝/裁剪
```

> ✅ D2 已确认：越权处理采用**拒绝**（403 + 审计日志）；裁剪会静默丢失授权导致难排查。

### 4.3 范围作用域规范化（Scope Model）

**已确认方案（D3-B）**：把 4 个 JSON 数组字段**升级为作用域对象**，用显式 `mode` 取代隐式空值语义，彻底消除「空值含义相反」陷阱。**列名保持不变**（避免无谓的列重命名风险），仅变更 JSON 值结构：

| 字段（列名不变） | 新结构 | 语义 |
|-----------------|--------|------|
| `companyScopes` | `{ mode: "none" \| "company", companyIds: number[] }` | 合同审核范围：`company` 仅限所列公司参与的合同；`none` 无可审核合同（原空数组的安全默认） |
| `viewCompanyScopes` | `{ mode: "all" \| "company", companyIds: number[] }` | 全量字段读取范围：`all` 不限制（兼容原空=不限）；`company` 仅限所列公司 |
| `contractViewCompanyScopes` | `{ mode: "all" \| "company", companyIds: number[] }` | 合同查看范围：语义同上 |
| `stockCompanyScopes` | `{ mode: "none" \| "company" \| "all", companyIds: number[] }` | 资金账户管理范围：`none` 仅自身 USER 账户；`company` 限所列公司；`all` 全量 |

**迁移要点（重构 T8 内）**：
- 字段保持现有列类型（JSON 文本存储），仅前后端序列化结构变更，**不强制列迁移**；
- 存量数据转换脚本：非空数组 → `{ mode: "company", companyIds: [...] }`；空数组 → 各字段安全默认（`companyScopes`/`stockCompanyScopes` → `none`，两个 view 字段 → `all`）；
- 接口 DTO 按新结构校验；转换脚本运行后旧结构（裸数组）不再接受。

> 对照：v1 曾提议「保持 JSON 数组 + 语义表显式化」，经决策点 D3 确认改为对象化方案（D3-B），从结构层面根治空值语义反相问题。

### 4.4 前后端单一事实源

**目标**：删除前端镜像目录，运行时拉取。

1. 后端新增只读端点 `GET /api/permissions/catalog`（登录即可，无需业务权限），返回 `{ domains, groups, actionRank, roleTemplates, grantExtras }`；
2. 前端 `authStore` 启动时拉取并缓存到 Pinia（登录态失效即清空）；`PERMISSION_CATALOG` 等前端镜像常量删除；
3. `derivePermissions` 逻辑**移入后端**（与 `ROLE_TEMPLATES` 合并）：前端账号管理页只回传「role + 所选公司 id」，由后端派生权限与范围并落库（范围按 §4.3 作用域对象结构）；前端仅做展示与提示；
4. 前端 `can()` 改为使用后端模板 + 动作等级表本地复算（一份共享实现，可抽 `shared/permissions.ts` 或由后端下发的等级表驱动），消除双实现漂移（P7）。

## 5. 端点-权限矩阵（重构验收基线）

以下为按控制器归纳的守卫矩阵；重构后每个单元格的放行集合必须与「动作等级表」推导结果一致（或按 D1 变宽且符合预期）。

### 5.1 数据域控制器（material/part/product/map/tech/fuel/vehicle/warehouse/infrastructure/productionLine）

| 端点类别 | 所需权限 | 备注 |
|---------|---------|------|
| 列表/详情（读） | `data:<x>:view`（或同域更强） | 类级或方法级 |
| 增删改（写） | `data:<x>:edit` | 全量写；蕴含模型下 `view` 不满足 `edit` |

### 5.2 合同域

| 端点 | 所需权限 | 守卫 | 现状行为 |
|------|---------|------|---------|
| `GET /contracts`、`GET /contracts/:id` | `contract:view` | PermissionsGuard | 读接口 |
| `POST /contracts` | `contract:manage` | PermissionsGuard | 仅建草稿 |
| `POST /contracts/:id/execute`、`POST /contracts/:id/precheck` | `contract:execute` 或 `contract:audit` | ContractReviewGuard | 重构后 `contract:execute`（manage 蕴含自动覆盖） |
| `PATCH /contracts/:id/party-numbers` | ContractEditGuard | 单独守卫 | 见 §3.5，重构后并入 execute/manage 语义 |
| `PATCH /contracts/:id/status`、`DELETE /contracts/:id` | `contract:manage` | PermissionsGuard | 管理操作 |

### 5.3 其他域（摘要）

| 控制器 | 读 | 写 |
|--------|----|----|
| competitions | 公开/登录 | `competition:manage` |
| companies / company-fields | `company:view`（范围：viewCompanyScopes） | `company:manage` |
| contract-types | `contractType:view` | `contractType:manage` |
| industry-types | `industryType:view` | `industryType:manage` |
| messages | `message:view` | `message:manage` |
| stocks | `stock:view` | `stock:edit`（低级）/ `stock:manage`（高级、推进轮次） |
| regions | `data:region:view` | `data:region:edit` |
| users（账号） | — | `account:manage` |
| files | 各业务权限 | 各业务权限 |

> 完整 111 处清单以代码为准；重构验收时用脚本对比「改动前后每个端点的放行集合」产出差异报告，人工确认差异全部落在 D1 允许的变宽范围内。

## 7. 兼容与迁移策略

1. **数据库迁移（仅范围字段一次，D3-B）**：4 个范围字段由 JSON 数组升级为作用域对象（列名不变），配套存量数据转换脚本（T8）；其余表结构不动。执行顺序：备份 `dev.db` → `db push` → 跑转换脚本 → 回归；
2. **既有账号权限数组无需重写**：新蕴含规则全部是**变宽方向**（manage ⊇ execute、execute ⊇ audit），不会让现有授权失效；
3. **T4 只约束「之后」的写入**：历史账号若已持有超管专属权限（理论上不存在，因前端从未派发），T4 上线时扫描一次并告警清单；
4. **灰度顺序**：T1–T2（后端蕴含）→ T5–T6（合同对齐）→ T3–T4（模板校验）→ T8（范围对象化迁移 + 派生后端化）→ T7（目录端点）→ T9（前端同构）→ T10（文档）；
5. **回滚**：T1–T6 改动集中在 catalog/guard/service，可整文件 revert；T7 依赖新端点，需与前端同时发布（客户端 build+重启）；T8 迁移前备份 `dev.db`，异常时还原备份即可回退。
