## 1. 实现概览

当前权限系统已完成以下改造并全部落地：

1. **动作分级模型（Action Rank）已实现**：`catalog.ts` 中的 `PermissionDomain.actionRank` + `hasPermission()` 查表判定，取代旧硬编码 if-else。
2. **后端权威角色模板已实现**：`role-templates.ts` 定义三角色默认权限、授予上限、可选扩展集；`users.service.sanitize()` 调用 `assertGrantAllowed()` 做授予上限校验。
3. **范围字段统一语义**：空范围（null/[]）统一为「不限制」（向后兼容）；但 `companyScopes`（合同审核范围）仍保持空=无范围的严格语义（见 §4.3 说明）。
4. **前后端权限目录**：后端权威目录已结构化，前端为同结构镜像副本；暂未实现运行时拉取（仍手工同步）。

## 3. 动作分级模型（已实现）

### 3.1 核心接口定义

```typescript
// server/src/permissions/catalog.ts
export interface PermissionDomain {
  key: string;           // 域前缀，如 "contract"
  label: string;         // 中文标签
  group: string;         // UI 分组
  actions: PermissionAction[];
  /**
   * 动作等级表（可选）。
   * key = 动作 token，value = 整数等级（越大越强）。
   * 缺省时使用 DEFAULT_ACTION_RANKS。
   */
  actionRank?: Record<string, number>;
}
```

### 3.2 全局默认动作等级

```typescript
export const DEFAULT_ACTION_RANKS: Record<string, number> = {
  view: 10,      // 只读
  edit: 20,      // 数据写（增删改）
  manage: 30,    // 管理操作
  execute: 40,   // 执行类
  audit: 50,     // 审核类
};
```

### 3.3 合同域自定义动作等级（覆盖默认）

```typescript
// catalog.ts 中 contract 域定义：
actionRank: {
  view: 10,     // 查看合同（最低）
  audit: 20,    // 公司级审核：仅 companyScopes 范围内公司的合同
  execute: 30,  // 比赛级执行：本比赛内任意草稿合同
  manage: 40,   // 全权管理：新建/删除/执行/任意改（最高）
}
```

**蕴含关系（偏序）**：

```
manage (rank 40) ⊇ execute (30) ⊇ audit (20) ⊇ view (10)
```

**设计意图**：
- 能删除合同（manage）者必然能执行合同（execute），解决原语义断层问题；
- 能全局执行（execute）者自然能在其范围内审核（audit）；
- `ContractReviewGuard` 只需校验 `contract:execute`，manage 持有者自动通过。

### 3.4 判定算法实现（`hasPermission`）

```typescript
export function hasPermission(
  role: string | undefined,
  permissions: string[] | null | undefined,
  required: string | string[],
): boolean {
  if (role === "SUPER_ADMIN") return true;           // 超管隐式全放行
  const req = Array.isArray(required) ? required : [required];
  if (req.length === 0) return true;
  const perms = permissions ?? [];
  const owned = new Set(perms);
  return req.every((need) => {
    if (owned.has(need)) return true;                 // ① 精确匹配
    const colon = need.lastIndexOf(":");
    if (colon === -1) return false;
    const domain = need.slice(0, colon);
    const action = need.slice(colon + 1);
    const ranks = getDomainActionRank(domain);        // ② 取该域等级表
    const requiredRank = ranks[action];
    if (requiredRank == null) return false;
    return perms.some((p) => {                        // ③ 同域 rank 比对
      const lastColon = p.lastIndexOf(":");
      if (lastColon <= 0) return false;
      const pDomain = p.slice(0, lastColon);
      const pAction = p.slice(lastColon + 1);
      if (pDomain !== domain) return false;
      const pRank = ranks[pAction];
      return pRank != null && pRank >= requiredRank;
    });
  });
}
```

**与旧规则对比**：

| 判定 | 旧规则 | 新规则（已实现） | 变化 |
|------|--------|-----------------|------|
| `contract:manage` → `contract:execute` | ✗ 不蕴含 | ✓ 蕴含 (40≥30) | 变宽（合理） |
| `contract:execute` → `contract:audit` | ✗ 不蕴含 | ✓ 蕴含 (30≥20) | 变宽（合理） |
| `contract:audit` → `contract:view` | ✓ 已蕴含 | ✓ 蕴含 (20≥10) | 不变 |
| `data:*:edit` → `data:*:view` | ✓ 已蕴含 | ✓ 蕴含 (20≥10) | 不变 |
| 任意同域动作 → `view` | ✓ | ✓ (rank≥10) | 不变 |

### 4.3 三角色模板完整定义

代码位置：`server/src/permissions/role-templates.ts`

| 属性 | SUPER_ADMIN | COMPETITION_ADMIN | PLAYER |
|------|-------------|-------------------|--------|
| defaultPermissions | `[]`（隐式全放行，不落库） | baseView(17) + `contract:manage` + `contract:audit` + `contract:execute` + `stock:edit` = **21 key** | baseView(17) = **17 key** |
| grantCeiling | `[]`（不受限） | 同 defaultPermissions（21） | 同 defaultPermissions（17） |
| grantExtras | `[]` | `message:manage`, `contractType:manage`, `industryType:manage`, `company:manage`, `data:region:edit`（5 个，默认不放行，超管可显式放开） | `[]`（无） |
| companyScopes 默认 | null | null（由前端选公司） | `[]`（空=无可审核合同） |
| viewCompanyScopes 默认 | null | null（不限制） | null（不限制） |
| contractViewCompanyScopes 默认 | null | null（不限制） | null（不限制） |
| stockCompanyScopes 默认 | null | null（不限制） | null（不限制） |

> ⚠️ **范围语义说明**：
> - `viewCompanyScopes` / `contractViewCompanyScopes` / `stockCompanyScopes`：**空(null/[]) = 不限制**（向后兼容直觉）。
> - `companyScopes`（合同 `contract:audit` 审核范围）：**空 = 严格无，看不到任何可审核合同**。这是刻意保持的严格语义：PLAYER 角色默认 `companyScopes=[]`，即「默认不给审核权限」，需管理员显式分配公司后才具备审核能力。该差异在 UI 层需做文案区分。

### 4.4 授予上限校验（`assertGrantAllowed`）

```typescript
export function assertGrantAllowed(
  actorRole: string,       // 操作者角色
  targetRole: string,      // 被修改账号的角色
  permissions: string[],   // 要授予的权限列表
): { allowed: boolean; violations: string[] }
```

**校验规则**：
1. **非超管不可写权限**：`actorRole !== "SUPER_ADMIN"` → 直接拒绝。
2. **超管权限不落库**：`targetRole === "SUPER_ADMIN"` 时 permissions 必须为空数组。
3. **超管专属权限拦截**：非超管角色若包含 `SUPER_ADMIN_ONLY_PERMISSIONS` 中任一 → 拒绝。
4. **授予上限拦截**：非超管角色权限超出 `grantCeiling` → 拒绝。
5. **扩展集提示**：超出上限但在 `grantExtras` 内 → 标注「需超管显式放开」（当前版本仍拦截，未来可加开关）。

角色/权限                  viewCompanyScopes=空   viewCompanyScopes=[1,2,3]

### 5.2 公司列表范围过滤（`companyListScopes`）

- `null` → 不施加公司 id 过滤（可见全部公司）
- `number[]` → 仅返回数组内 id 的公司

**触发条件**：仅当「仅持 `company:view`（无 manage/region:edit）且配置了非空 `viewCompanyScopes`」时，返回非空数组。其余情况一律返回 null（无限制）。

## 6. 守卫体系（已实现）

### 6.1 守卫清单

| 守卫 | 作用域 | 语义 |
|------|--------|------|
| `JwtAuthGuard` | 全局（`app.module.ts` APP_GUARD） | 认证：JWT 签名校验 + tokenVersion 单设备互斥 |
| `MustChangePasswordGuard` | 全局（APP_GUARD） | 强制改密拦截：`mustChangePassword=true` 时仅放行改密接口 |
| `CompetitionScopeGuard` | 全局（APP_GUARD） | 多租户：非超管强制收敛查询/写入的 `competitionId` 到本人所属比赛 |
| `OwnershipGuard` | 资源级（按需 `@UseGuards`） | BOLA 防御：路径 id 查资源归属 → 比赛匹配才放行 |
| `PermissionsGuard` | 资源级（按需 `@UseGuards` + `@RequirePermissions`） | RBAC：AND 语义，SUPER_ADMIN 隐式放行 |
| `ContractReviewGuard` | contracts 执行/预检 | 特殊 OR 语义：`contract:execute` OR `contract:audit` 任一满足 |
| `ContractEditGuard` | contracts 改编号 | 合同编号修改的特殊权限校验 |

### 6.2 PermissionsGuard 实现细节

```typescript
// server/src/permissions/permissions.guard.ts
@Injectable()
export class PermissionsGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride<string[]>(
      PERMISSIONS_KEY, [context.getHandler(), context.getClass()]
    );
    if (!required || required.length === 0) return true;   // 未声明则放行
    const { user } = context.switchToHttp().getRequest();
    if (!user) throw new ForbiddenException("未登录或登录已失效");
    const ok = hasPermission(user.role, user.permissions ?? null, required);
    if (!ok) throw new ForbiddenException("权限不足");
    return true;
  }
}
```

关键点：
- **AND 语义**：`@RequirePermissions("a", "b")` 需 a **且** b 同时满足。
- **未声明即放行**：不贴装饰器的路由不做权限拦截（仅受全局认证守卫约束）。
- **SUPER_ADMIN 直通**：`hasPermission` 首行即返回 true。

## 7. 前后端一致性实现

### 7.1 后端权威 → 前端镜像

- **`server/src/permissions/catalog.ts`**：唯一真实源。
- **`client/src/permissions/catalog.ts`**：同结构镜像副本，供前端：
  - 渲染权限勾选 UI（按 group / domain / action 分级）；
  - 本地 `can()` / `canAny()` 判定（与后端 `hasPermission` 算法一致）。

> ⚠️ 维护约束：**修改后端 catalog.ts 时必须手工同步前端 catalog.ts**。当前版本尚未实现「运行时拉取权限目录」接口（可作为后续优化点：`GET /api/permissions/catalog` 公开路由）。

### 7.2 客户端本地判定（`stores/auth.ts`）

```typescript
// 与后端 hasPermission 逻辑保持一致的 can()
can(required: string | string[]): boolean {
  return hasPermission(this.role, this.permissions, required);
}
canAny(options: (string | string[])[]): boolean {
  return options.some(opt => this.can(opt));
}
```

路由守卫、按钮 `v-if="auth.can('...')"` 均调用此方法，与后端判定结果一致（避免 UI 放行后后端 403）。

## 8. 序列化/反序列化工具

权限与范围字段在数据库中以 JSON 字符串存储，在运行时以类型化数组使用：

| 工具函数 | 用途 |
|---------|------|
| `parsePermissions(raw)` | DB JSON 字符串 → `string[]`（权限 key 数组） |
| `serializePermissions(perms)` | `string[]` → DB JSON 字符串（自动去重，空→null） |
| `parseCompanyScopes(raw)` | DB JSON 字符串 → `number[]`（公司 id 数组，自动过滤非法值） |
| `serializeCompanyScopes(scopes)` | `number[]` → DB JSON 字符串（去重+过滤，空→null） |

User 表中对应 5 个 JSON 字段：
- `permissions`（key 数组）
- `companyScopes`、`viewCompanyScopes`、`contractViewCompanyScopes`、`stockCompanyScopes`（公司 id 数组）

## 9. 扩展指南

### 9.1 新增权限 key

步骤（必须全做，否则前后端漂移）：

1. **后端 `server/src/permissions/catalog.ts`**：
   - 若新域：在 `PERMISSION_CATALOG` 新增 `PermissionDomain` 项。
   - 若已有域加动作：在对应域的 `actions` 数组追加。
   - 若动作不遵循默认等级：在该域加 `actionRank` 覆盖。
2. **前端 `client/src/permissions/catalog.ts`**：
   - 手工同步相同结构（可直接拷贝后端对应片段）。
3. **角色授予上限**（如需）：
   - 在 `role-templates.ts` 的对应角色 `grantCeiling` / `grantExtras` 中纳入该 key。
4. **控制器守卫**：
   - 在对应路由贴 `@RequirePermissions("domain:action")`。
5. **单元测试**：
   - `catalog.spec.ts` 增加合法 key 校验用例；
   - `role-templates.spec.ts` 增加授予上限校验用例。

### 9.2 新增角色

1. 在 `role-templates.ts` 的 `ROLE_TEMPLATES` 追加条目：
   - 定义 `defaultPermissions`、`grantCeiling`、`grantExtras`、默认范围。
2. 在 `assertGrantAllowed()` 中确保该角色命中模板（未知角色会直接拒绝）。
3. 在前端账户管理 UI 的角色下拉选项中追加该角色名。
4. 在 `JwtStrategy` / 前端 `derivePermissions` 派生逻辑中确认新角色行为。

### 9.3 动作等级表不满足？

- **同域内新增动作**：直接在 `actionRank` 中加一个 rank 值，插在合适的等级间隙即可（如 `view=10, edit=20` 之间可插入 `preview=15`）。
- **全局默认等级调整**：修改 `DEFAULT_ACTION_RANKS`。注意这会影响所有未自定义 `actionRank` 的域，必须全量回归守卫行为。
