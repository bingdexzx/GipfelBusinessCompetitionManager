## 🔴 严重缺陷（5 个）

### S1: `setValues` 重算在事务外执行，存在竞态条件

**位置**：`company-fields.service.ts:265-283`

基础字段写入包裹在 `prisma.$transaction` 中，但后续的 `recomputeCalculatedFields` 在事务**外部**作为独立操作执行。并发请求（合同执行、其他用户写入、定时器触发）可在两者之间插入，导致重算读取到非本次写入的值，产出错误结果。

**同样的问题存在于**：
- `applyFiscalYearTimer`（定时器写入在事务内，重算在事务外）
- `revertContract`（合同删除时的字段回滚无事务保护）

**影响**：并发写入同一公司字段时，最终值可能丢失某次写入。

**建议**：将重算写入纳入同一个 `$transaction`，或使用 `companyId` 维度的 advisory lock 串行化所有写入。

---

### S2: `revertContract` 和 `remove` 无事务保护

**位置**：`contract.service.ts:317-342`

合同删除流程：
1. `engine.revertContract(item)` — 重写 `CompanyFieldValue`
2. 重算计算字段 + 广播
3. `prisma.contract.delete()` — 级联删除 `ContractFieldEffect`

三步均未包裹在 `$transaction` 中。若进程在步骤 1 和 3 之间崩溃，字段已回滚但合同仍存在，重试删除会**双重回滚**。且步骤 1 内部的多个 DB 操作无行级锁，并发合同执行可交错读写同一字段。

**影响**：数据不一致，字段值可能被错误回滚。

**建议**：将整个删除流程包裹在单一 `$transaction` 中。

---

### S3: 删除字段时未检查是否被计算图引用

**位置**：`industry-type.service.ts:426-438`

`removeField` 仅检查 `CompanyFieldValue` 是否存在，**不检查**同产业类型下其他 `IndustryField.calcGraph` 是否包含引用该 `fieldKey` 的 FIELD 节点。删除后，引用该字段的计算图静默返回 `0`（见 S4），无任何错误或警告。

`getFieldDependencies()` 方法已存在，可直接复用。

**影响**：计算图静默损坏，错误值传播到合同评估、区域总览、仪表盘。

**建议**：删除前解析同类型所有计算图，若存在引用则拒绝删除并提示依赖关系。

---

### S4: FIELD 节点引用不存在的字段时静默返回 0

**位置**：`industry-calc-engine.service.ts:204-206`

```typescript
case "FIELD":
  return Object.prototype.hasOwnProperty.call(scope, d.fieldKey)
    ? scope[d.fieldKey]
    : 0;  // ← 静默零值，无日志无警告
```

当字段被删除、重命名、或属于不同产业类型时，引擎静默返回 `0`。VAR 节点同样如此。

**影响**：计算结果静默错误，难以排查。

**建议**：至少记录警告日志。理想情况下在编辑时做语义校验，验证所有 FIELD 引用是否存在。

---

### S5: `getMapOverview` 无跨比赛边界校验，存在数据泄露风险

**位置**：`region.service.ts:130-176`

`resolveCards` 按 `companyId` 查询公司时**不按 competitionId 过滤**。卡片可引用其他比赛的公司，且值会正确解析返回。`getLocalCompanies` 在 `competitionId` 为 undefined 时加载**所有比赛**的公司。

**影响**：跨比赛数据泄露。

**建议**：在 `resolveCards` 中增加 `company.competitionId === region.competitionId` 校验。

## 🟠 高优先级缺陷（8 个）

### H1: 合同删除前未验证合同状态

**位置**：`contract.service.ts:317-342`

`remove` 检查 `effectCount > 0` 但不检查 `item.status === "EXECUTED"`。若 DRAFT 状态的合同因数据异常有 `ContractFieldEffect` 记录，回滚会在幻影效果上执行。

**建议**：增加 `if (item.status !== "EXECUTED") return` 前置检查。

---

### H2: 字典字段 SUB 在 `applyFieldEffect` 和 `applyOp` 中行为不一致

**位置**：`contract-engine.service.ts:1629-1637` vs `:1489`

- `applyFieldEffect` 的 SUB：`delete after[k]` — 仅删除 base 中存在的 key
- `applyOp` 的 `DICT_SUB`：对仅存在于 subtracted 字典的 key 产生 `-num(db[k])`

同一逻辑操作产生不同结果。

**建议**：统一两处实现，`applyFieldEffect` 应复用 `applyOp` 的逻辑。

---

### H3: 列表字段 ADD 在 `applyFieldEffect` 中不去重

**位置**：`contract-engine.service.ts:1618`

```typescript
after = [...base, ...items];  // 累积重复项
```

而 `applyOp` 的 `LIST_ADD` 明确使用 `deepEqual` 去重。

**建议**：统一去重逻辑。

---

### H4: `publishedOnly` 模式无法看到「已发布但隐藏」的字段

**位置**：`company-fields.service.ts:152-155`

`visibleFields` 过滤在 `publishedOnly` 过滤**之前**执行。若字段 `visible: false` 但已被发布到区域总览，仅持 `company:view` 的用户无法看到它。

**建议**：在 `publishedOnly` 模式下跳过 `visible` 过滤，或将过滤顺序调整为：先取已发布字段集合，再与可见字段取并集。

---

### H5: 消费者需求区域变更时不重算旧区域公司

**位置**：`consumer-demand.service.ts:64-79`

更新 `region` 时只用新区域调用 `recomputeConsumerDemandDependentFields`，旧区域的公司保留陈旧值。

**建议**：更新前读取旧 `region`，新旧区域都触发重算。

---

### H6: `updateField` 的 calcGraph 校验依赖过时的 `isCalculated` 状态

**位置**：`industry-type.service.ts:327-330`

部分更新时若未显式传 `isCalculated: true`，`validateCalcGraph` 被跳过，无效图结构可入库。

**建议**：当 `dto.calcGraph` 存在时，无论 `dto.isCalculated` 是否传值都校验。或取有效值 `dto.isCalculated ?? field.isCalculated`。

---

### H7: `updateField` 使用旧字段类型做配置校验

**位置**：`industry-type.service.ts:381`

`effectiveType` 始终取数据库中的旧类型。若更新将 `NUMBER` 改为 `DICTIONARY`，DICTIONARY 专属的 config 校验不会执行。

**建议**：使用 `dto.fieldType ?? field.fieldType` 作为有效类型。考虑在有已有值时禁止修改类型。

---

### H8: `timerRawValue` 对 null `timerValue` 无防护

**位置**：`company-fields.service.ts:484-499`

- `parseFloat(null)` → `NaN` → 抛出 `BadRequestException("数值非法：NaN")`
- `JSON.parse(null)` → `SyntaxError`
- `String(null)` → `"null"`（语义错误）

虽然 DTO 层有校验，但直接数据库修改或调用代码 bug 可绕过。

**建议**：在 `timerRawValue` 入口增加 null guard。

## 🟡 中等缺陷（16 个）

### M1: `precheck` 不使用事务，与执行时数据可能不一致

**位置**：`contract-engine.service.ts:2428-2486`

`precheck` 用裸 Prisma 客户端读数据，`execute` 在 `$transaction` 内执行。用户看到通过的检查可能在执行时失败（反之亦然）。

---

### M2: `isTruthy` 在合同引擎和安全表达式求值器中不一致

**位置**：`contract-engine.service.ts:272` vs `safe-expression.ts:179`

合同引擎 trims 字符串，安全表达式不 trims。空白字符串 `" "` 在两处产生不同布尔值。

---

### M3: 字典 ADD/SUB 的数值强制转换在两处不一致

**位置**：`contract-engine.service.ts:1637-1642` vs `:1470-1482`

`applyFieldEffect` 不对共享 key 调用 `num()`，`applyOp` 的 `DICT_ADD` 会调用。

---

### M4: 字符串/布尔字段的 GTE/LT 比较使用数值强制转换

**位置**：`contract-engine.service.ts:1793-1806`

`"abc" >= "def"` 变成 `0 >= 0 = true`，语义错误。

---

### M5: `resolveCards` 不检查 `visible` 标志

**位置**：`region.service.ts:126-177`

字段设为 `visible: false` 后，区域总览卡片仍显示其值。与公司详情页行为不一致。

---

### M6: 消费者需求重算使用 `String.includes` 检测 `CONSUMER_DEMAND`

**位置**：`company-fields.service.ts:361`

```typescript
f.calcGraph.includes("CONSUMER_DEMAND")
```

若字段 key 或常量字符串碰巧包含 `"CONSUMER_DEMAND"` 文本，产生误报。

**建议**：解析 JSON 检查 `nodes.some(n => n.data?.kind === "CONSUMER_DEMAND")`。

---

### M7: `resolveCards` 的 blanket catch 吞掉所有异常

**位置**：`region.service.ts:167-173`

数据库连接失败、OOM 等异常也被静默处理为 `valid: false`，无法调试。

**建议**：至少记录错误日志。

---

### M8: IndustryField 删除时不清理引用它的总览卡片

**位置**：`industry-type.service.ts:426-438`

已发布到区域总览的字段可被删除，导致卡片静默失效。

---

### M9: Company 删除时不清理引用它的总览卡片

**位置**：`company.service.ts:74-79`

卡片静默变为 `valid: false`，无清理机制。

---

### M10: `getMapOverview` 性能为 O(R × (C + C×F))

**位置**：`region.service.ts:261-293`

每个区域独立查询公司+解析卡片，无缓存、无分页、无批量。

---

### M11: `getCardValue` 为获取单个卡片值重建整个总览

**位置**：`region.service.ts:299-306`

调用 `getMapOverview(competitionId)` 获取所有区域所有卡片，只为找一个值。股票服务也如此。

---

### M12: `calcGraph` 语义校验缺失

**位置**：`industry-type.service.ts:39-62`

`validateCalcGraph` 仅做结构校验（JSON 有效、有 output 节点），不校验：
- FIELD 节点引用的 `fieldKey` 是否存在
- OP 节点的运算名是否合法
- 边的 source/target 是否引用存在的节点
- assign 节点是否有 `data.name`
- 图是否无环（仅运行时检测）

---

### M13: `FOREACH` 循环中 `ASSIGN` 的作用域隔离脆弱

**位置**：`contract-engine.service.ts:2005-2010`

当前实现正确（浅拷贝），但设计脆弱——未来修改传参顺序即可破坏隔离。

---

### M14: `DICT_INVERT` 在多 key 映射到同 value 时静默丢失数据

**位置**：`contract-engine.service.ts:1466`

`{a: 1, b: 1}` → `{1: "b"}`，key `"a"` 静默丢失。

---

### M15: `assign` 节点拓扑排序使用不动点迭代

**位置**：`industry-calc-engine.service.ts:131-154`

O(n²) 最坏情况，硬限制 10000 次迭代。应使用 Kahn 算法。

---

### M16: `industry-type.service.ts: update()` 未调用 `withParsedFields`

**位置**：`industry-type.service.ts:276-280`

`findOne`/`findAll`/`create` 都调用 `withParsedFields` 解析 config JSON，唯独 `update` 不调用，返回的字段 config 为原始 JSON 字符串。
