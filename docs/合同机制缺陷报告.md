## 一、事务与并发

### 缺陷 T1（严重）：`remove` 的 revert + 重算 + delete 无事务保护

**位置**：[contract.service.ts:317-342](server/src/modules/contracts/contract.service.ts#L317-L342)

```typescript
async remove(id: number, competitionId?: number) {
  // ...
  if (effectCount > 0) {
    await this.engine.revertContract(item);        // ① 重写字段值
    for (const p of affected) {
      await this.companyFields.recomputeCalculatedFieldsForCompany(p.companyId);  // ② 重算
      this.realtime.broadcastToCompetition(...);   // ③ 广播
    }
  }
  return this.prisma.contract.delete({ where: { id } });  // ④ 删除合同
}
```

**问题**：四步均在独立的 DB 操作中执行，无 `$transaction` 包裹。

- 若进程在 ① 和 ④ 之间崩溃，字段已回滚但合同仍存在。重试删除会**双重回滚**。
- ① 内部的多个 `upsert` 也无事务（见 T2）。
- ② 的重算在 ① 之后、④ 之前，期间并发合同执行可交错读写同一字段。

**影响**：数据不一致，字段值可能被错误回滚。

**建议**：将 ①②④ 全部包裹在单一 `$transaction` 中。

### 缺陷 T2（严重）：`revertContract` 内部无事务，多次 upsert 非原子

**位置**：[contract-engine.service.ts:2042-2101](server/src/modules/contracts/contract-engine.service.ts#L2042-L2101)

```typescript
async revertContract(contract) {
  // 1. 查询被删合同的所有效果记录
  // 2. 对每个受影响字段：
  //    a. 查询剩余效果记录
  //    b. 计算基线值
  //    c. 重放其余合同增量
  //    d. upsert CompanyFieldValue  ← 每次都是独立 DB 操作
}
```

**问题**：对每个 `(companyId, industryFieldId)` 的 upsert 是独立的。若 5 个字段受影响，前 3 个成功、第 4 个失败，数据库处于部分回滚状态。

且所有操作使用 `this.prisma`（原始客户端），非事务客户端。并发执行可交错。

**影响**：部分字段回滚、部分未回滚。

**建议**：将整个 revertContract 包裹在 `$transaction` 中，使用事务客户端 `tx`。

### 缺陷 T3（高）：`execute` 在事务内，但 `recomputeCalculatedFieldsForCompany` 在事务外

**位置**：[contract.service.ts:201-212](server/src/modules/contracts/contract.service.ts#L201-L212)

```typescript
const { log, result } = await this.engine.execute(contractForEngine);  // 事务内
// ↑ 事务已提交

// ↓ 事务外
for (const companyId of affectedCompanies) {
  await this.companyFields.recomputeCalculatedFieldsForCompany(companyId);
}
```

**问题**：`engine.execute` 在 `$transaction` 内写入基础字段，但重算在事务**外**。并发请求可在两者之间读到已更新的基础字段但未重算的计算字段。

**影响**：并发读取可能看到不一致状态（基础字段新值 + 计算字段旧值）。

**建议**：将重算纳入 execute 的事务中，或在 execute 事务内标记"待重算"并在事务提交后立即执行。

### 缺陷 F2（高）：DICTIONARY 字段 SUB 在 `applyFieldEffect` 和 `applyOp` 中行为不一致

**位置**：[contract-engine.service.ts:1629-1637](server/src/modules/contracts/contract-engine.service.ts#L1629-L1637) vs `:1489`

- `applyFieldEffect` SUB：`delete after[k]` — 仅删除 base 中存在的 key，忽略仅在 subtracted 中的 key
- `applyOp` `DICT_SUB`：对仅存在于 subtracted 字典的 key 产生 `-num(db[k])`（负值）

**影响**：同一逻辑操作产生不同结果。

### 缺陷 F3（高）：DICTIONARY 字段 ADD 在两处的数值强制转换不一致

**位置**：[contract-engine.service.ts:1637](server/src/modules/contracts/contract-engine.service.ts#L1637) vs `:1470-1482`

- `applyFieldEffect` ADD：`{ ...base, ...obj }` — 不对共享 key 调用 `num()`，保留原始类型
- `applyOp` `DICT_ADD`：对共享 key 调用 `num()`，将字符串/布尔转为数字

**影响**：`{a: "5"}` ADD `{a: 3}` 在 FIELD 效果中结果为 `{a: 3}`（后者覆盖），在 OP 中结果为 `{a: 8}`（数值相加）。

### 缺陷 F4（中）：STRING/BOOLEAN 字段 ADD/SUB 退化为 SET

**位置**：[contract-engine.service.ts:1644-1648](server/src/modules/contracts/contract-engine.service.ts#L1644-L1648)

```typescript
if (ft === "STRING" || ft === "BOOLEAN") {
  // ADD/SUB 对字符串 / 布尔无定义，统一退化为 SET
  after = castScalar(ft, newValue);
}
```

**问题**：对字符串字段执行 ADD 操作不会拼接字符串，而是直接覆盖。用户可能期望 `"abc" + "def" = "abcdef"`。

**影响**：STRING 字段的 ADD/SUB 无实际效果，等同于 SET。

**建议**：文档化此行为，或为 STRING 定义 ADD 语义（拼接）。

### 缺陷 F5（中）：`applyFieldEffect` 的 `castScalar` 不处理 DICTIONARY/LIST 类型

**位置**：[contract-engine.service.ts:315-323](server/src/modules/contracts/contract-engine.service.ts#L315-L323)

```typescript
function castScalar(type: string | undefined, val: any): any {
  const t = (type || "STRING").toUpperCase();
  if (t === "NUMBER") return toNumber(val);
  if (t === "BOOLEAN") return val === true || val === "true" || val === 1 || val === "1" || val === "是";
  if (val == null) return "";
  if (typeof val === "object") return JSON.stringify(val);
  return String(val);
}
```

**问题**：`castScalar` 的 `type` 参数是 `fieldType`（如 "DICTIONARY"），但函数只处理 NUMBER/BOOLEAN，其他类型走 `String(val)`。对 DICTIONARY/LIST 类型调用 `castScalar` 会将对象/数组转为 `"[object Object]"`。

在 `applyFieldEffect` 的字典分支中（第 1639-1641 行），`castScalar` 被用于转换字典的值：
```typescript
after = Object.fromEntries(
  Object.entries(after).map(([k, v]) => [k, castScalar(valueType, v)]),
);
```
这里 `valueType` 是字典值的类型（如 "NUMBER"），所以是正确的。但若 `valueType` 为 "DICTIONARY"（嵌套字典），`castScalar` 会将其转为字符串。

**影响**：嵌套字典/列表值会被错误序列化。

### 缺陷 F6（中）：`compareField` 对标量 STRING/BOOLEAN 使用数值比较

**位置**：[contract-engine.service.ts:1793-1806](server/src/modules/contracts/contract-engine.service.ts#L1793-L1806)

```typescript
default: {
  const ok = (() => {
    switch (op) {
      case "GT": return length > toNumber(expected);
      // ...
    }
  })();
}
```

**问题**：`default` 分支对 LIST/DICTIONARY 使用 `length` 比较，但对标量 STRING/BOOLEAN 也走此分支（因为 `isList` 和 `isDict` 都为 false）。`toNumber(currentRaw)` 将字符串转为数字（通常为 NaN → 0），比较结果无意义。

**影响**：STRING 字段的 GT/LT/GTE/LTE 比较总是返回 `0 >= expected`，语义错误。

**建议**：对标量 STRING 增加字典序比较分支。

## 三、合同回滚机制

### 缺陷 R1（严重）：`revertContract` 基线计算假设 `allForField[0]` 是最早且正确的

**位置**：[contract-engine.service.ts:2073-2084](server/src/modules/contracts/contract-engine.service.ts#L2073-L2084)

```typescript
const allForField = [
  ...remaining.map((r) => ({ ex: r.contract?.executedAt ?? null, row: r })),
  ...deletedRowsForField.map((r) => ({ ex: contract.executedAt ?? null, row: r })),
];
allForField.sort((a, b) => {
  const ta = a.ex ? a.ex.getTime() : 0;  // null → 0（1970-01-01）
  const tb = b.ex ? b.ex.getTime() : 0;
  // ...
});
let value: any = parseJsonValue(allForField[0].row.beforeRaw);
```

**问题**：
1. `contract.executedAt` 为 null 时映射为时间戳 0（1970-01-01），排序后排在最前。若被删合同的 `executedAt` 为 null 但实际不是最早执行的，基线取错。
2. `beforeRaw` 是字段在**该合同执行前**的值，不是 `IndustryField.defaultValue`。若被删合同是第一个执行的，`beforeRaw` 可能是初始默认值或手动设置的值，但若字段在此之前没有 `CompanyFieldValue` 记录，`beforeRaw` 的来源不明。

**影响**：基线值可能不正确，导致回滚后字段值错误。

**建议**：
1. 对 `executedAt === null` 的合同，使用 `createdAt` 作为排序依据。
2. 若所有效果都被删除（无 remaining），使用 `IndustryField.defaultValue` 作为最终值。

## 五、效果执行

### 缺陷 E1（中）：FOREACH 循环中 ASSIGN 的作用域隔离依赖浅拷贝

**位置**：[contract-engine.service.ts:2008-2010](server/src/modules/contracts/contract-engine.service.ts#L2008-L2010)

```typescript
for (const el of list) {
  const childScope = { ...sc, [varName]: el };  // 浅拷贝
  for (const sub of eff.body || []) await applyEffect(sub, childScope);
}
```

**问题**：`{ ...sc }` 是浅拷贝。若 `sc` 中有嵌套对象（如字典），`childScope` 和 `sc` 共享同一引用。ASSIGN 修改嵌套对象时会影响父作用域。

**影响**：FOREACH 中修改嵌套字典可能污染外层作用域。

**建议**：使用深拷贝（如 `JSON.parse(JSON.stringify(sc))`），或在 ASSIGN 时创建新对象。

### 缺陷 E2（中）：FOREACH 的 `items` 求值为非数组时静默跳过

**位置**：[contract-engine.service.ts:2005-2006](server/src/modules/contracts/contract-engine.service.ts#L2005-L2006)

```typescript
const arr = await resolveValue(eff.items, sc);
const list = Array.isArray(arr) ? arr : [];
```

**问题**：若 `items` 求值为非数组（如 null、数字、字符串），静默视为空数组，FOREACH 不执行。无警告。

### 缺陷 E3（低）：`ASSIGN` 的 `sc[eff.name]` 直接修改传入的 scope 对象

**位置**：[contract-engine.service.ts:2013](server/src/modules/contracts/contract-engine.service.ts#L2013)

```typescript
} else if (eff.kind === "ASSIGN") {
```

### 建议修复优先级

**第一批（应立即修复）**：

- **T3**：将重算纳入 execute 事务 — 防止并发读到不一致状态

- **F1 + F2 + F3**：统一 applyFieldEffect 与 applyOp 的行为 — 消除同一操作两种结果
- **R2**：remove 前验证合同状态
- **R3**：从 ContractFieldEffect 提取 companyId 而非 parties
- **P1**：统一 isTruthy 实现
