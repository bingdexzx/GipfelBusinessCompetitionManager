## 一、权限目录与守卫链

### 当前架构

```
请求 → JwtAuthGuard → MustChangePasswordGuard → CompetitionScopeGuard → OwnershipGuard → PermissionsGuard
         │                    │                       │                      │                  │
         │                    │                       │                      │                  └─ @RequirePermissions 校验
         │                    │                       │                      └─ @Ownership 校验（BOLA 防御）
         │                    │                       └─ @NoCompetitionScope 豁免 + competitionId 收敛
         │                    └─ mustChangePassword 拦截
         └─ @Public 豁免 + JWT 验证 + tokenVersion 校验
```

权限 key 格式：`<domain>:<action>`（如 `data:material:edit`）

动作蕴含规则：
- `manage` ⊇ `edit` ⊇ `view`（同域内向下蕴含）
- `execute` / `audit` 需精确持有，不做向下蕴含

## 二、缺陷列表

### 🔴 高优先级（5 个）

#### P1: `hasPermission` 的 `view` 蕴含逻辑过于宽泛

**位置**：[catalog.ts:294-296](server/src/permissions/catalog.ts#L294-L296)

```typescript
if (action === "view") {
  return perms.some((p) => p === domain || p.startsWith(domain + ":"));
}
```

**问题**：`view` 的蕴含检查是 `perms.some(p => p.startsWith(domain + ":"))`。这意味着：

- 拥有 `data:material:edit` → 满足 `data:material:view` ✅（正确）
- 拥有 `data:material:view` → 满足 `data:material:view` ✅（正确）

但考虑嵌套域：
- 拥有 `data:material:view` → 满足 `data:material:edit:view`（假设有此权限）❌
  - `"data:material:view".startsWith("data:material:")` 为 true

实际上当前权限 key 最多两层冒号（`data:material:edit`），不存在三层的情况。但逻辑上 `startsWith` 匹配不够精确——它会匹配所有以 `domain:` 开头的 key，包括不同子域的 key。

**更精确的实现**：
```typescript
if (action === "view") {
  return perms.some((p) => {
    if (p === domain) return true; // 精确匹配无 action 的 key（理论上不存在）
    const lastColon = p.lastIndexOf(":");
    return lastColon > 0 && p.slice(0, lastColon) === domain;
  });
}
```

**影响**：当前实际权限 key 结构下无实际风险，但逻辑不够严谨。

#### P2: `edit` 蕴含仅检查 `manage`，不检查 `execute` / `audit`

**位置**：[catalog.ts:298-300](server/src/permissions/catalog.ts#L298-L300)

```typescript
if (action === "edit") {
  return owned.has(`${domain}:manage`);
}
```

**问题**：若某域有 `execute` 或 `audit` 动作（如 `contract:execute`），拥有这些权限的用户**不被视为**拥有 `contract:edit`。这是正确的——`execute` 和 `audit` 不等于 `edit`。

但反过来：若某域有 `edit` 权限但没有 `manage` 权限（如 `data:material`），拥有 `data:material:edit` 的用户**不被视为**拥有 `data:material:manage`。这也是正确的。

**无实际缺陷**，但需确认设计意图：`edit` 仅由 `manage` 蕴含，不由 `execute` / `audit` 蕴含。

#### P3: JWT payload 不包含 `stockCompanyScopes`

**位置**：[auth.service.ts:48-53](server/src/auth/auth.service.ts#L48-L53)

```typescript
const payload = {
  sub: user.id,
  username: user.username,
  role: user.role,
  tv: updatedUser.tokenVersion,
};
```

**问题**：JWT payload 仅包含 `sub/username/role/tv`，**不包含** `permissions`、`companyScopes`、`viewCompanyScopes`、`contractViewCompanyScopes`、`stockCompanyScopes`。

这些值在 `JwtStrategy.validate()` 中从数据库实时读取（第 41-45 行）。这意味着：

1. **每次请求都查数据库**：`validate()` 对每个请求执行 `prisma.user.findUnique()`，无法利用 JWT 的无状态特性。
2. **权限变更即时生效**：管理员修改用户权限后，下一次请求即生效（正确行为）。
3. **但增加了 DB 负载**：每个 HTTP 请求都有一额外的 DB 查询。

**设计权衡**：将权限放入 JWT 可减少 DB 查询，但权限变更需等到 token 过期才生效。当前设计选择了「即时生效 + 每请求查 DB」，这是安全优先的合理选择。

**非缺陷**，但值得文档化此设计决策。

#### P5: `hasPermission` 对 `edit` 的蕴含不检查 `execute` / `audit`，但 `view` 蕴含检查所有 action

**位置**：[catalog.ts:286-304](server/src/permissions/catalog.ts#L286-L304)

**问题**：`view` 的蕴含逻辑是 `perms.some(p => p.startsWith(domain + ":"))`，即**任何**以 `domain:` 开头的权限都满足 `view`。但 `edit` 的蕴含仅检查 `manage`。

这意味着：
- 拥有 `contract:execute` → 满足 `contract:view` ✅（通过 `startsWith`）
- 拥有 `contract:audit` → 满足 `contract:view` ✅（通过 `startsWith`）
- 拥有 `contract:execute` → 满足 `contract:edit` ❌（仅检查 `manage`）

这是**正确**的行为：`execute` / `audit` 应该可以读取合同（view），但不应该编辑合同（edit）。但逻辑实现依赖 `startsWith` 的副作用而非显式检查，可读性差。

#### P8: `company:view` 的 `viewCompanyScopes` 逻辑在 `canReadCompanyAllFields` 中有边界情况

**位置**：[catalog.ts:362-381](server/src/permissions/catalog.ts#L362-L381)

```typescript
export function canReadCompanyAllFields(
  role, permissions, viewCompanyScopes, companyId,
): boolean {
  if (role === "SUPER_ADMIN") return true;
  const hasManage = hasPermission(role, permissions, "company:manage");
  const hasRegionEdit = hasPermission(role, permissions, "data:region:edit");
  const hasView = hasPermission(role, permissions, "company:view");
  if (hasManage || hasRegionEdit) return true;
  if (hasView) {
    const scopes = viewCompanyScopes && viewCompanyScopes.length > 0 ? viewCompanyScopes : null;
    if (!scopes) return true; // 空范围 = 无限制
    return scopes.includes(companyId);
  }
  return false;
}
```

**问题**：若用户同时拥有 `company:view` 和 `company:manage`，`hasManage` 为 true，直接返回 true，`viewCompanyScopes` 被忽略。这是正确的行为。

但若用户只有 `company:view` 且 `viewCompanyScopes` 为空数组 `[]`，`scopes` 为 null，返回 true（无限制）。这是**向后兼容**的设计——未配置范围即不限制。

**边界情况**：管理员想**限制**某用户只能看特定公司的字段，但配置了空数组，实际上该用户仍可看全部公司。需在 UI 上提示"空数组 = 无限制"。

#### P9: `ContractReviewGuard` 和 `ContractEditGuard` 不检查 `view` 权限

**位置**：`server/src/modules/contracts/contract-review.guard.ts`

```typescript
const canExecute = hasPermission(user.role, user.permissions, "contract:execute");
const canAudit = hasPermission(user.role, user.permissions, "contract:audit");
if (!canExecute && !canAudit) {
  throw new ForbiddenException("无权审核/执行合同");
}
```

**问题**：仅持 `contract:view` 的用户无法通过此守卫（正确）。但若用户同时持有 `contract:view` 和 `contract:audit`，守卫检查 `contract:audit` 通过，允许执行。

然而 `ContractReviewGuard` 用于 `POST /:id/execute` 和 `POST /:id/precheck`。拥有 `contract:audit` 的用户可以**执行**合同（不仅是审核）。这是否是设计意图？

**文档说明**：`contract:audit` 的语义是"可审核范围内公司合同"，`ContractReviewGuard` 允许 `audit` 或 `execute` 任一通过即可进入。service 层进一步按 `companyScopes` 校验范围。

#### P10: `OwnershipGuard` 对 `null` competitionId 的实体放行

**位置**：[ownership.guard.ts:99](server/src/common/guards/ownership.guard.ts#L99)

```typescript
if (entityCompetitionId === own) return true;
```

#### P11: `CompetitionScopeGuard` 对未分配比赛用户的处理

**位置**：[competition-scope.guard.ts:73-77](server/src/common/guards/competition-scope.guard.ts#L73-L77)

```typescript
} else if (own === null) {
  throw new ForbiddenException("账号未归属比赛，无法访问该数据");
}
```

**问题**：未分配比赛（`competitionId === null`）的非超管用户，在未显式传 `competitionId` 时被拒绝。但若显式传了 `competitionId=null`（或空字符串），`resolveCompetitionId` 返回 null，`cid === own`（null === null）为 true，放行。

这意味着未分配比赛的用户可以通过显式传 `competitionId=null` 来访问全局数据（`competitionId` 为 null 的实体）。

**影响**：未分配比赛的用户可访问全局共享字典（如全局原料/零件），但不能访问任何比赛级数据。这是**正确**行为。

#### P13: `PermissionsGuard` 对未声明 `@RequirePermissions` 的路由放行

**位置**：[permissions.guard.ts:20](server/src/permissions/permissions.guard.ts#L20)

```typescript
if (!required || required.length === 0) return true;
```

**问题**：若路由未声明 `@RequirePermissions`，守卫直接放行。这意味着：

## 三、守卫执行顺序分析

### 全局守卫声明顺序（app.module.ts）

```typescript
providers: [
  { provide: APP_GUARD, useClass: JwtAuthGuard },           // ①
  { provide: APP_GUARD, useClass: MustChangePasswordGuard }, // ②
  { provide: APP_GUARD, useClass: CompetitionScopeGuard },   // ③
  { provide: APP_GUARD, useClass: OwnershipGuard },          // ④
  PermissionsGuard,                                           // ⑤（路由级）
]
```

**执行顺序**：① → ② → ③ → ④ → ⑤

**问题**：`APP_GUARD` 的执行顺序由 `providers` 数组顺序决定。NestJS 按声明顺序执行全局守卫。当前顺序是正确的：

1. 先认证（JwtAuthGuard）
2. 再检查强制改密（MustChangePasswordGuard，需要 user）
3. 再检查比赛归属（CompetitionScopeGuard，需要 user）
4. 再检查资源归属（OwnershipGuard，需要 user + competitionId）
5. 最后检查权限（PermissionsGuard，需要 user + permissions）

**无缺陷**。
