# 前端刷新机制重构设计

> 版本：v1
> 状态：设计草案（待确认后实施）
> 关联代码基线：`client/src/realtime/useResourceChanged.ts`、`client/src/realtime/resource-changed.ts`、`client/src/realtime/socket.ts`、`client/src/api/request.ts`、`client/src/api/cache.ts`、`client/src/stores/auth.ts`、`client/src/components/layout/AppLayout.vue`、`client/src/composables/useCompetitionReload.ts`
> 阅读对象：本系统维护者。本文档是《数据同步与实时机制重构设计.md》§4.3「前端刷新机制重构」的**深化专章**，只讨论「数据如何到达界面、界面如何决定重拉」这一件事；存储/增量/实时通道的整体方案以数据同步文档为准（任务编号沿用数据同步文档的 S1–S12，本文档补充 F 系列细化任务）。

## 1. 背景与目标

用户长期反馈「前端界面总是不刷新」：他人改了数据自己的界面不动、断线重连后界面停留在旧状态、管理员加了权限对方看不到。数据同步文档已从**存储与通道**层面给出方案（S1–S12），本文档聚焦**前端一侧的刷新机制**——组件在什么时机、依据什么信号决定重新拉取，以及数据层如何保证「事件之后的读取必然拿到新数据」。

本次重构目标：

1. **事件驱动成为唯一刷新触发源**：组件重拉只由「匹配的实时事件 / 对账完成通知 / 比赛切换 / 写操作成功」触发，删除组件自实现的各种刷新逻辑；
2. **事件精确匹配**：按 `资源 + 比赛` 双层匹配，跨比赛、全局资源事件不误刷、不漏刷；
3. **消灭 memo 时序竞态**：任何「事件晚于请求发起」的场景都不允许 15s 窗口返回旧值；
4. **断线重连必刷新**：对账完成主动通知组件，无需用户手动刷新；
5. **权限等账号级状态实时生效**：加权限 / 改角色 / 禁用账号后，对方菜单、按钮、`can()` 判定在 30 秒内自动更新。

## 2. 现状：刷新链路全景

### 2.1 触发源（4 类）

| # | 触发源 | 实现 | 走向 |
|---|--------|------|------|
| A | 组件主动拉取 | `onMounted` + `useCompetitionReload(reload, clear)`（`useCompetitionReload.ts:17-28`，14 处使用） | 直接调 load 函数 |
| B | 实时事件驱动 | socket `resource:changed` → `resource-changed.ts`（400ms 防抖）→ `window "resource-changed"` → `useResourceChanged` 回调 | 事件 → 组件重拉 |
| C | 写操作成功 | `_mutating` 成功后 `invalidateResource(url)` + `_resetMemo()`（`request.ts:578-586`） | 失效副本+memo → 下次读取全量 |
| D | 周期 / 断线对账 | 5min `FULL_SYNC_INTERVAL_MS`（`request.ts:502`）与断线重连 `reconcileAllIncremental`（`request.ts:601-681`，`resource-changed.ts:83-85`） | 更新副本 → **不通知组件** |

### 2.2 数据层「是否发请求」的判定（memo）

`_cachedGet`（`request.ts:538-564`）：

```
命中条件 = memo 存在 && Date.now() - memo.time < 15s && _lastEventAt[resource] <= memo.time
命中 → 直接返回内存值（不打网络）
未命中 → cachedGetImpl（全量 / 增量 / 离线降级）→ 写回 memo（time = 完成时刻）
```

- `bumpResourceEvent(resource)`（`request.ts:169-172`）在事件到达时把 `_lastEventAt[resource]` 置为当前时间，使该资源 memo 立即失效；
- `_resetMemo()`（`request.ts:175-178`）清空 memo + 事件时间表（写操作 / 登出时调用）；
- `_reqKey`（`request.ts:180-183`）为 `METHOD url params`，**不含账户 / 比赛维度**。

### 2.3 组件接入模式（现状统计）

| 模式 | 数量 | 代表 |
|------|------|------|
| `useResourceChanged(resource, reload)` | 28 处 / 22 文件 | MaterialsManager、PartsManager、ContractManageView 等 |
| `useCompetitionReload(reload, clear)` | 14 处 | 各数据管理页、ContractManageView、MapsManager |
| 自实现防抖 + 单一订阅 | 2 处 | `StockMarketView.vue:627-634`、`StockManageView.vue`（仅订阅 `company-field`，**漏 `stocks`**） |
| 多资源订阅 | 2 处 | `DashboardView.vue:467-470`（4 资源）、`RegionOverviewView.vue:475-480`（4 资源） |

### 2.4 关键缺口（代码事实）

- `useResourceChanged`（`useResourceChanged.ts:12-23`）只按 `detail.resource === resource` 匹配，**不使用事件里的 `competitionId`**（事件 detail 已带 cid，见 `resource-changed.ts:55`）；
- `reconcileAllIncremental`（`request.ts:601-681`）完成后**不派发任何 window 事件**；
- `AppLayout.vue:10` 路由 key 为 `route.path`（同路由 query 变化不重挂载）；`AppLayout.vue:40` 仅挂载时 `fetchProfile()` 一次；
- `AccountManagementView.vue:79` 的 `el-form` 缺 `@submit.prevent`（对比 `CompetitionListView.vue:143` 有）；
- `authStore`（`stores/auth.ts:36-62`）的 `can()/canAny()` 全部基于 `user.value.permissions`，该值只在登录与 `fetchProfile` 时更新，**不消费任何实时事件**。

## 3. 问题清单（R 系列）

> R 编号为本文档内部编号；括号内是数据同步文档的对应 P 编号。

### R1（高）事件不按比赛匹配 → 误刷 / 漏刷（≈P5 前端侧）

- `useResourceChanged` 只看 `resource`：同一资源名（如 `materials`）的事件，无论属于哪个比赛，都会触发当前视图重拉。服务端房间已按比赛隔离（`comp-{cid}`），但全局房间（`industry-types`/`contract-types`/`competitions`）与超管多比赛订阅场景下，**跨比赛事件仍会误触发**；
- 反向缺口：detail 页（如公司详情 `/companies/:id`）若订阅 `companies`，收到列表级事件也会重拉——**粒度是资源级而非实体级**，浪费但无害；
- 后果：多余的网络请求与闪烁；且因 `useResourceChanged` 类型定义（`useResourceChanged.ts:15`）不含 `competitionId`，事件 cid 被丢弃。

### R2（高）memo 时序竞态 → 15s 窗口返回旧值（≈P4）

时序场景（事件到达时已有 in-flight 请求）：

```
t0  组件 A 发起 GET（memo 无缓存）→ 进入 cachedGetImpl（读副本 → 增量请求 in-flight）
t1  事件到达：bumpResourceEvent(resource) → _lastEventAt = t1
t2  in-flight 响应返回：patchFullItems 写回副本，_memo.set(key, {time: t2, value: v_旧})
    —— v_旧 是 t1 之前的数据（不含本次变更）
t3  检查：_lastEventAt(t1) <= memo.time(t2) → 命中 → 15s 窗口内持续返回 v_旧
```

根因：memo 的 `time` 记录的是**完成时刻**而非**数据新鲜点（请求发起时刻）**，事件时间戳与完成时刻比较时被绕过。

### R3（高）断线重连对账不通知组件 → 界面不刷新（=P2）

- `resource-changed.ts:83-85` 在 `connect` 时调 `reconcileAllIncremental`，它只更新 IndexedDB 副本与 memo，**不派发 window 事件**；
- 断线期间他人产生的变更，重连后副本已新、界面依旧旧，直到用户手动切页 / 刷新。

### R4（高）账号级状态（权限/角色/范围/禁用）不实时刷新（=P3 前端侧）

- `AppLayout.vue:40` 挂载时 `fetchProfile()` 一次后不再更新；
- `resource:changed(users)` 只被 `AccountManagementView.vue:442` 消费（刷新账号列表），`authStore` 不感知；
- 后果：菜单显隐、按钮 disabled、`can()` 判定全部停留在旧权限，与「服务端已按新权限放行/拒绝」不一致。

### R5（中）路由复用 → query 变化不重挂载

- `AppLayout.vue:10` `:key="route.path"`：同路由仅 query 变化（如筛选条件放 query 的页面）不重建组件，`onMounted` 不重跑。

### R6（中）表单回车触发原生提交 → 整页重载

- `AccountManagementView.vue:79` 等 `el-form` 缺 `@submit.prevent`；单文本框表单按回车会触发原生提交，路由跳回默认页（表现为「保存后界面重置」）。

### R7（中）股票视图漏订阅 → 他人交易/撮合不可见

- `StockMarketView.vue:634`、`StockManageView.vue:731` 仅订阅 `company-field`；`stocks` 事件（他人下单/成交/轮次推进）不会触发重拉；
- 且组件内自实现 `scheduleAccountReload` 400ms 防抖与全局总线防抖**双重防抖**，模式不统一。

### R8（中）detail 请求无集合副本 → 依赖 memo 过期

- 非列表接口（`/companies/:id` 等 detail）不建集合副本，只按请求键缓存；刷新完全依赖 memo 15s 过期 + 事件。事件到达后 `bumpResourceEvent` 会失效 memo，但 detail 组件若不订阅对应资源事件，则仍不刷新。

### R9（低）对账范围过大（=P9）

- `reconcileAllIncremental` 遍历**本地全部集合**（含已切换离开的比赛、已失去权限的资源），带宽浪费且可能触发无谓的越权请求（被服务端拒绝但产生噪音）。

## 4. 目标设计

### 4.1 事件总线精确匹配（useResourceChanged v2）→ 修 R1

**原则**：组件声明「我关心哪类资源、在哪个比赛下」，事件按 `resource + competitionId` 精确匹配后才触发回调。

```ts
// 新签名（向后兼容：options 缺省时按 resource 匹配，行为同现状）
useResourceChanged(resource, onChanged, options?: {
  scope?: "competition" | "global" | "any"; // 默认 "competition"
});
```

匹配规则（以组件当前比赛 `compStore.competitionId` 为基准）：

| 事件 cid | 组件 scope=competition | scope=global | scope=any |
|----------|------------------------|--------------|-----------|
| `=== 当前比赛` | 触发 | 不触发 | 触发 |
| `null`（全局豁免实体） | 不触发 | 触发 | 触发 |
| `≠ 当前比赛` | 不触发 | 不触发 | 触发（按 resource） |

- 存量改造：全局资源组件（`ContractTypeManageView`→`contract-types`、`IndustryTypeManageView`→`industry-types`、`CompetitionListView`→`competitions`）显式传 `scope: "global"`；其余比赛资源组件不传（默认 competition）即可获得精确匹配；
- `useResourceChanged.ts:15` 的事件 detail 类型补 `competitionId?: number | null`；
- 兼容旧服务端：事件 detail 无 `competitionId` 时按 `scope: "any"` 回退，行为同现状。

### 4.2 memo 时序竞态修复 → 修 R2

**核心一行改动**：写 memo 时 `time` 记录**请求发起时刻**而非完成时刻（`request.ts:562`）：

```ts
const startedAt = Date.now();          // 发起前记录
const p = cachedGetImpl(...);           // 原有 in-flight 合并
const result = await p;
_memo.set(key, { time: startedAt, value: result });  // time = 数据新鲜点
```

这样 `_lastEventAt[resource] <= memo.time` 的比较语义变为「事件是否晚于本数据的请求发起时刻」——任何晚于发起的事件都会使该 memo 失效，**从根上消除 R2 的时序窗口**。配套约束：

1. `_getInflight` 合并（`request.ts:548-549`）时，后续等待者拿到的是同一份结果，memo 只写一次（以首个发起者的 `startedAt` 为准）——保持现状即可；
2. `_reqKey` 增加 `uid|cid|` 前缀（沿用数据同步文档 S3），避免同窗口切账号/比赛串值；
3. `_lastEventAt` 保持全局 Map（事件到达即失效对应资源），不引入按比赛拆分——因为失效是「宁可多失效、不可漏失效」的策略，代价仅是一次额外请求，收益是绝无旧值；
4. 事件到达时**已进入 cachedGetImpl 的请求**仍会正常完成并写回副本（patchFullItems 由 S3 generation 互斥保护），只是 memo 不再缓存旧结果。

### 4.3 对账完成主动通知 → 修 R3

- `reconcileAllIncremental`（`request.ts:601-681`）在 `finally` 中派发 `window "sync:reconciled"`，detail 携带 `{ collections: string[] }`（本次实际对账的集合键列表）；
- 新增 hook `useSyncReconciled(onReconciled)`（或并入 `useResourceChanged` 内部）：监听 `sync:reconciled`，回调当前视图 `reload()`；
- `resource-changed.ts:83-85` 的 connect 处理不变（触发对账），对账完成由新机制通知组件；
- 防抖：对账可能跨越多个集合，`sync:reconciled` 同样走 400ms 防抖，避免一次重连触发多次组件重拉。

### 4.4 账号级状态实时刷新 → 修 R4

前端先行实现（不依赖后端推送也能降级生效）：

1. `socket.ts` 注册 `permissions:changed` 监听（后端推送方案见数据同步文档 S7）：收到即调 `authStore.refreshProfile()`；
2. `authStore` 新增 `refreshProfile()`：调 `GET /auth/me` 更新 `user.value`（Pinia 响应式 → `can()/canAny()`、菜单、按钮自动更新），失败静默（离线保持旧状态）；
3. **降级路径**（后端未升级时）：`resource-changed.ts` 收到 `resource=users` 且 `id === 当前用户 id` 的事件时，也调 `refreshProfile()`——写权限的服务端事件必达，确保旧后端下同样生效；
4. `AppLayout.vue:40` 的挂载逻辑保留（首次初始化），权限变更改由事件驱动刷新。

### 4.5 组件加载模式统一（复合 hook）→ 修 R7/R8

**约定**：所有列表 / 详情组件统一采用「刷新三件套」：

```ts
useListReload({
  resources: ["materials"],          // 订阅的资源（比赛资源默认精确匹配当前比赛）
  globalResources: [],               // 全局豁免资源（如 industry-types）
  reload,                            // onMounted + 事件 + 对账完成 统一入口
  clear,                             // 切比赛时清空旧数据引用（可选）
});
```

- 复合 hook 内部组合 `useResourceChanged`（v2）+ `useSyncReconciled` + `useCompetitionReload`，并做一次统一的 400ms 防抖（替代组件内自实现防抖）；
- 存量改造：
  - `StockMarketView.vue:627-634`、`StockManageView.vue:731`：删除组件内 `scheduleAccountReload` 自实现防抖，改用 `useListReload({ resources: ["stocks", "company-field"], reload: reloadAll })`（**补上 `stocks` 订阅**）；
  - 所有现有 `useResourceChanged` + `useCompetitionReload` 组合调用点，机械替换为 `useListReload`（行为等价，改动低风险）；
- detail 页：订阅父资源事件（如公司详情订阅 `companies`），父资源事件到达即重拉——`bumpResourceEvent` 已保证 memo 失效，重拉必走网络。

### 4.6 路由 / 表单 / 订阅补齐 → 修 R5/R6

| 项 | 改动 |
|----|------|
| 路由复用 | `AppLayout.vue:10` `:key="route.path"` → `:key="route.fullPath"`（query 变化即重挂载） |
| 表单回车 | 全局检索 `el-form`，补 `@submit.prevent`（重点：`AccountManagementView.vue:79`） |
| 事件订阅审计 | 每个视图对照「本页展示的资源集合」逐一核对 `useListReload.resources` 是否覆盖（验收项） |

### 4.7 对账范围收敛 → 修 R9

- `reconcileAllIncremental` 增加过滤：仅对账「当前比赛命名空间（S8 之后的 `c<cid>|` 前缀）+ 已订阅资源」，跳过已离开比赛 / 无权限集合；
- 数据同步文档 S5 的验收口径：对账请求数与当前视图订阅一致（超管除外，超管维持全量以便跨比赛切换即见）。

## 5. 刷新时序（关键场景）

### 5.1 正常事件刷新（他人修改 → 我的界面更新）

```
服务端写库 → $allOperations → emitResourceChanged {resource,id,action,cid,seq}
  → comp-{cid} 房间 → socket → resource-changed.ts
  → bumpResourceEvent(resource)          // memo 立即失效（R2 修复后语义正确）
  → 400ms 防抖 → window resource-changed
  → useListReload 匹配 resource + cid = 当前比赛 → reload()
  → cachedApi.get → memo 未命中（事件已失效）→ 增量请求 → 新数据渲染
```

### 5.2 断线重连

```
reconnect → resource-changed.ts connect 处理 → reconcileAllIncremental()
  → 逐集合增量 + existingIds 复核 → 更新副本 + 基线
  → finally：400ms 防抖 → window sync:reconciled
  → useListReload 回调 reload() → 界面自动刷新（R3 修复后不再需要手动）
```

### 5.3 写操作后立即读取

```
_mutating 成功 → invalidateResource + _resetMemo
  → 同一组件 reload() → memo 空 → 全量同步（首次）或增量（有副本时重建）
  → 在途增量响应（旧基线）由 S3 generation 互斥丢弃 → 副本一致
```

### 5.4 权限变更

```
（新后端）users.service 改权限 → emitToUser(uid, "permissions:changed")
（旧后端降级）resource:changed {resource:"users", id: 我}
  → authStore.refreshProfile() → GET /auth/me → user.value 更新
  → can()/菜单/按钮 响应式刷新（30 秒内）
```

## 7. 兼容与迁移策略

1. **事件总线向后兼容**：`useResourceChanged` 旧调用（不传 options）行为 = `scope:"any"` 回退，等价现状——F1 可全量替换后逐页验收；
2. **memo 改动无迁移成本**：`startedAt` 语义只在运行时生效，无持久化数据；
3. **对账通知新增事件**：`sync:reconciled` 是纯增量事件，旧组件不监听则无感知；
4. **账号刷新降级路径**：F4 不阻塞于后端 S7 是否上线，旧后端靠 `users` 事件降级生效；
5. **回滚**：F1–F3、F5–F8 全部集中在 `client/src` 前端文件，可逐文件 revert；F4 需前后端同发（前端 build + 重启），回滚时两端同步还原。

## 8. 验收基线（用户体验口径）

| 场景 | 现状 | 目标 |
|------|------|------|
| 他人修改同一比赛数据 | 依赖组件订阅覆盖，部分页面不刷新 | 展示该数据的页面 1s 内自动更新 |
| 他人修改其它比赛数据 | 可能误刷当前视图 | 当前视图完全不动 |
| 断线 30s 后重连 | 界面停留在旧数据，需手动刷新 | 自动对账并刷新 |
| 管理员给我加/减权限 | 菜单按钮不更新，直到重启 | 30 秒内自动生效 |
| 同一页面仅 query 变化 | 不重挂载，可能显示旧内容 | 重挂载并拉取 |
| 表单回车 | 整页重载 | 不触发提交 |
