## 一、logsreader（日志可视化读取工具）

### 文件结构

```
tools/logsreader/
├── logsreader.mjs    # Node.js HTTP 服务（450 行）
├── index.html        # 单页前端（922 行）
└── run.bat           # Windows 启动脚本
```

### 功能概述

启动本地 HTTP 服务（默认端口 7799），提供：
- `/api/list` — 列出日志文件
- `/api/query` — 按级别/上下文/操作员/时间/关键词过滤日志
- 统计面板（级别分布、上下文 Top、URL Top、时间线堆叠图）
- 实时跟随模式（2 秒轮询）
- CSV 导出
- 无限滚动分页

### 缺陷

#### L1（中）：`runQuery` 每次查询都全量读取所有选中文件

**位置**：[logsreader.mjs:237-248](tools/logsreader/logsreader.mjs#L237-L248)

```typescript
for (const fname of files) {
  const abs = resolve(LOGS_DIR, fname);
  if (!existsSync(abs)) continue;
  const lines = readLogLines(abs);  // ← 每次都完整读取文件
  for (const ln of lines) {
    ln._file = fname;
    ln.seq = seq++;
    collected.push(ln);
  }
}
```

**问题**：每次查询都完整读取所有选中的日志文件到内存。若日志文件较大（如 100MB+），每次查询都会：
1. 读取整个文件到 Buffer
2. 按行分割
3. 解析每行 JSON
4. 过滤/排序/分页

**影响**：大日志文件时查询缓慢，内存占用高。

**建议**：
- 增加文件大小检查，超过阈值时使用流式读取
- 或在文件级别先按修改时间预过滤

#### L2（中）：`readLogLines` 读取整个文件到内存

**位置**：[logsreader.mjs:87-107](tools/logsreader/logsreader.mjs#L87-L107)

```typescript
function readLogLines(absPath) {
  let buf;
  try {
    buf = readFileSync(absPath);  // ← 整个文件读入内存
  } catch {
    return [];
  }
  // ...
}
```

**问题**：`readFileSync` 将整个文件读入内存。对于 100MB+ 的日志文件，这会消耗大量内存。

**建议**：使用 `createReadStream` 流式读取，逐行处理。

---

#### L3（低）：`matchText` 对每行做 `JSON.stringify` 

**位置**：[logsreader.mjs:174-187](tools/logsreader/logsreader.mjs#L174-L187)

```typescript
function matchText(obj, q) {
  const hay = [
    obj.message, obj.context, obj.operator, obj.requestId, obj.ip,
    JSON.stringify(obj),  // ← 对整个对象序列化
  ].filter(Boolean).join(" ");
  return hay.toLowerCase().includes(q.toLowerCase());
}
```

**问题**：对每行日志都执行 `JSON.stringify(obj)` 来构建搜索文本。对于大量日志行，这会产生大量临时字符串。

**建议**：仅在 `message`/`context`/`operator`/`requestId`/`ip` 不匹配时才 fallback 到 `JSON.stringify`。

---

#### L4（低）：实时跟随模式使用 `setInterval` 轮询，无增量查询

**位置**：[index.html:895](tools/logsreader/index.html#L895)

```javascript
followTimer = setInterval(() => doQuery(true), 2000);
```

**问题**：每 2 秒执行一次完整查询（含全量文件读取+过滤+排序）。虽然有 `afterOffset` 增量游标，但文件读取仍是全量的。

**建议**：使用 `fs.watch` 监听文件变更，仅在文件修改时增量读取新行。

---

#### L5（低）：前端 `PAGE_SIZE = 200` 硬编码

**位置**：[index.html:357](tools/logsreader/index.html#L357)

```javascript
const PAGE_SIZE = 200;
```

**问题**：分页大小硬编码，用户无法调整。对于需要快速浏览大量日志的场景，200 条可能太少。

**建议**：在高级筛选中增加「每页条数」选项。

---

#### L6（信息）：本地访问限制基于 IP 地址检查

**位置**：[logsreader.mjs:378-386](tools/logsreader/logsreader.mjs#L378-L386)

```typescript
if (
  !remote.includes("127.0.0.1") &&
  !remote.includes("::1") &&
  remote !== "::ffff:127.0.0.1"
) {
  res.writeHead(403, ...);
  res.end("only local access allowed");
  return;
}
```

**问题**：仅检查 IP 地址。在某些代理/容器环境中，`remoteAddress` 可能不是 `127.0.0.1`。

**影响**：在 Docker/WSL 等环境中可能无法访问。

---

### 改进建议

1. **流式读取大文件**：用 `createReadStream` + 逐行处理替代 `readFileSync`
2. **增量跟随**：用 `fs.watch` 替代 `setInterval` 轮询
3. **可配置分页**：在 UI 中增加每页条数选项
4. **搜索优化**：`matchText` 先检查简单字段，再 fallback 到 `JSON.stringify`

## 二、updater（发布管理工具）

### 文件结构

```
tools/updater/
├── release-core.mjs  # 发布核心逻辑（280 行）
├── release.mjs       # CLI 入口（206 行）
├── ui.mjs            # HTTP 服务（122 行）
├── index.html        # 可视化界面（395 行）
└── run.bat           # Windows 启动脚本
```

### 功能概述

- CLI 模式：`node tools/updater/release.mjs --version 1.1.0 --notes "修复xxx"`
- 交互模式：不带参数时逐项询问
- 可视化界面：`node tools/updater/ui.mjs` 启动本地 HTTP 服务（端口 7788）
- 功能：更新 `server/package.json` + `client/package.json` 版本号、写入 `announcement.ts` 公告、更新 `CHANGELOG.md`、可选 git 提交

### 缺陷

#### U1（高）：`git add` 使用字符串拼接，存在命令注入风险

**位置**：[release-core.mjs:256-259](tools/updater/release-core.mjs#L256-L259)

```typescript
const files = changes.map((c) => c.file).join(" ");
execSync(`git add ${files}`, { cwd: ROOT, stdio: "pipe" });
execSync(`git commit -m "release: v${opts.version}"`, { cwd: ROOT, stdio: "pipe" });
```

**问题**：
1. `files` 由文件路径拼接而成，若路径含空格或特殊字符，`git add` 会失败或行为异常
2. `opts.version` 直接嵌入 `git commit -m` 命令，若版本号含 shell 特殊字符（如 `; rm -rf /`），存在命令注入风险

虽然 `opts.version` 有 SEMVER 正则校验（`/^\d+\.\d+\.\d+$/`），但 `files` 路径无校验。

**建议**：使用 `execSync` 的数组形式（`execFileSync`）或对参数进行 shell 转义。

---

#### U2（中）：`insertAnnouncement` 使用字符串查找定位插入点

**位置**：[release-core.mjs:106-114](tools/updater/release-core.mjs#L106-L114)

```typescript
function insertAnnouncement(content, entry) {
  const marker = "export const announcements: Announcement[] = [";
  const idx = content.indexOf(marker);
  if (idx === -1) throw new Error("未找到 announcements 数组标记，无法写入。");
  const lineEnd = content.indexOf("\n", idx);
  const before = content.slice(0, lineEnd + 1);
  const after = content.slice(lineEnd + 1);
  return before + entry + after;
}
```

**问题**：依赖固定的字符串标记来定位插入点。若 `announcement.ts` 的格式稍有变化（如 marker 前加了注释、或改为 `export const announcements = [`），插入会失败。

**影响**：代码格式调整可能导致发布工具失效。

**建议**：使用正则匹配或 AST 解析来定位插入点。

---

#### U3（中）：`buildEntry` 使用模板字面量拼接 TypeScript 代码

**位置**：[release-core.mjs:116-129](tools/updater/release-core.mjs#L116-L129)

```typescript
function buildEntry(version, title, date, htmlLines) {
  const inner = htmlLines.join("\n");
  return (
    "  {\n" +
    `    version: ${JSON.stringify(version)},\n` +
    `    title: ${JSON.stringify(title)},\n` +
    `    date: ${JSON.stringify(date)},\n` +
    "    content: `\n" +
    inner +      // ← htmlLines 内容直接嵌入模板字面量
    "\n" +
    "    `,\n" +
    "  },\n"
  );
}
```

**问题**：`htmlLines` 是 `notesToHtml` 生成的 HTML 字符串数组。虽然 `notesToHtml` 对文本做了 `escapeHtml`，但若 `htmlLines` 中碰巧包含反引号 `` ` `` 或 `${`，会导致 TypeScript 语法错误。

**影响**：更新要点中包含反引号时，`announcement.ts` 语法错误，构建失败。

**建议**：对 `inner` 中的反引号和 `${` 进行转义。

## 三、两个工具的共性问题

### 共性 1：本地访问限制仅靠 IP 检查

两个工具都通过检查 `req.socket.remoteAddress` 来限制本地访问。在 Docker/WSL/代理环境中可能失效。

**建议**：绑定 `127.0.0.1`（已做）+ 增加 token 认证（可选）。

### 共性 2：无错误恢复机制

两个工具在文件读写失败时直接抛错，无重试或回滚机制。

**建议**：关键操作（如发布写入）增加原子性保证——先写临时文件，成功后重命名。

### 共性 3：`readBody` 函数重复

两个工具都有相同的 `readBody` 函数（读取 HTTP 请求体）。

**建议**：提取到 `common/` 目录共享。
