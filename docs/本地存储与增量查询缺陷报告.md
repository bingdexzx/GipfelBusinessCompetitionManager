## 一、IndexedDB 缓存层

### 缺陷 C1（高）：`patchFullItems` 在 `existingIds` 为空数组时清空本地副本

**位置**：[cache.ts:186-189](client/src/api/cache.ts#L186-L189)

```typescript
if (existingIds && Array.isArray(existingIds)) {
  const existSet = new Set(existingIds as number[]);
  result = result.filter((it) => it && existSet.has(it.id));
}
```

**问题**：当 `existingIds` 为**空数组 `[]`** 时，`existSet` 为空 Set，所有条目都被过滤掉——本地副本被清空。

虽然 `request.ts` 中已做了保护（新鲜窗口内不传 `existingIds`），但 `patchFullItems` 本身没有防御。任何调用方传入空数组都会清空副本。

**影响**：若服务端返回 `existingIds: []`（如该集合确实为空、或服务端 bug），前端本地副本被清空，下次读取走全量同步。

**建议**：在 `patchFullItems` 中增加判断：`existingIds` 为空数组时跳过过滤（空数组 ≠ "无数据"，而是"服务端未返回"）。

### 缺陷 C2（高）：`removeFullItemByResource` 使用 cursor 遍历，效率为 O(N)

**位置**：[cache.ts:199-230](client/src/api/cache.ts#L199-L230)

```typescript
const req = store.openCursor();
req.onsuccess = () => {
  const cursor = req.result;
  if (cursor) {
    const k = cursor.key as string;
    if (k.startsWith(prefix)) {
      // 读取整个记录 → 过滤 → 写回
    }
    cursor.continue();
  }
};
```

**问题**：每次删除事件都遍历 IndexedDB 中**所有**键，检查前缀匹配。若本地有 100 个集合、每集合 100 条记录，每次删除都要扫描 100 个键。

**影响**：高频删除事件（如批量删除）时性能下降。

**建议**：维护一个内存索引（Map<resource, Set<collectionKey>>），直接定位需要修改的键。

### 缺陷 C3（中）：`openDB` 连接缓存无过期机制

**位置**：[cache.ts:56-82](client/src/api/cache.ts#L56-L82)

```typescript
let _dbPromise: Promise<IDBDatabase> | null = null;
let _dbName: string | null = null;

function openDB(): Promise<IDBDatabase> {
  const name = currentDbName();
  if (_dbPromise && _dbName === name) return _dbPromise;
  // ...
}
```

**问题**：`_dbPromise` 是模块级变量，缓存了 IndexedDB 连接。若连接因浏览器回收、隐私模式切换等原因失效，`_dbPromise` 仍指向旧的 rejected promise，后续所有操作都会失败。

**影响**：长时间运行后缓存操作可能全部失败，但无恢复机制。

**建议**：在 `openDB` 失败时清除 `_dbPromise`，下次调用重新打开。或增加连接健康检查。

### 缺陷 C4（中）：`deleteByPrefixes` 使用 cursor 遍历删除，效率为 O(N×P)

**位置**：[cache.ts:373-394](client/src/api/cache.ts#L373-L394)

```typescript
if (prefixes.some((p) => k.startsWith(p))) store.delete(k);
```

**问题**：对每个键检查所有前缀。若有 3 个前缀、100 个键，每次失效操作执行 300 次字符串比较。

**影响**：写操作后失效本地副本时，若有大量缓存键，可能产生可感知的延迟。

**建议**：IndexedDB 支持 IDBKeyRange 前缀查询，可用 `store.getAll(IDBKeyRange.bound(prefix, prefix + '￿'))` 替代全表扫描。

### 缺陷 C5（低）：`clearCurrentAccountCache` 清空整个 objectStore，含非缓存数据

**位置**：[cache.ts:398-410](client/src/api/cache.ts#L398-L410)

```typescript
tx.objectStore(STORE_NAME).clear();
```

**问题**：`STORE_NAME` 是唯一的 objectStore，所有数据（全量副本、基线、全量同步时间、详情缓存）都在其中。`clear()` 一次性清空所有。

**影响**：当前设计中所有数据都是缓存数据，所以这是正确的。但如果未来增加非缓存的持久化数据，会被误删。

**建议**：当前无实际影响，仅作设计备注。

## 二、增量同步逻辑

### 缺陷 S1（严重）：`cachedGetImpl` 增量请求失败时回退到全量同步，但不更新基线

**位置**：[request.ts:519-521](client/src/api/request.ts#L519-L521)

```typescript
// 服务端未返回增量形态（兜底）：按全量处理
const fv = await fetchFullSync(url, config, params);
return await storeAndReturn(ck, fv, params, url, config);
```

**问题**：当增量请求发出但服务端未返回 `incremental: true`（如服务端版本不支持、或 `updatedAfter` 参数被忽略），代码回退到全量同步。`storeAndReturn` 会更新基线。

但若增量请求**成功**返回了 `incremental: true`，基线在第 514 行更新。若增量请求**失败**（网络错误），catch 块（第 526-533 行）返回本地副本但**不更新基线**。

这意味着：若增量请求超时但服务端实际已处理，下次请求仍用旧基线，可能遗漏变更。

**影响**：网络抖动可能导致增量同步遗漏变更。

**建议**：在 catch 块中，若本地副本存在，仍尝试用 `serverTime` 更新基线（如果响应中有的话）。

### 缺陷 S2（严重）：`syncCompanyFields` 增量模式不带 `requireExistingIds`

**位置**：[request.ts:444-448](client/src/api/request.ts#L444-L448)

```typescript
const v = await (api as any).get(url, {
  ...config,
  params: { ...params, updatedAfter: baseline },
});
```

**问题**：`syncCompanyFields` 的增量请求**不带** `requireExistingIds`，但服务端 `getValues` 始终返回 `existingIds`。这意味着每次增量请求都触发服务端全量 id 扫描。

而通用列表的增量请求在新鲜窗口内**不带** `requireExistingIds`（仅对账时带），减少了服务端开销。

**影响**：公司字段的增量查询每次都触发服务端全量 id 扫描，增加服务端压力。

**建议**：与通用列表对齐：仅在对账模式（基线过期）时带 `requireExistingIds`。

### 缺陷 S3（高）：`collectionKeyFor` 对嵌套路径的处理可能产生键冲突

**位置**：[request.ts:209-224](client/src/api/request.ts#L209-L224)

```typescript
const subPath = parts.slice(1).join("/");
if (subPath) restParts.push(`_p=${subPath}`);
```

**问题**：嵌套路径如 `/competitions/123/fiscal-years` 生成键 `competition|_p=123/fiscal-years`。但 `/competitions/123`（详情）生成键 `competition|_p=123`。

若同一资源既有嵌套列表又有详情，它们的键不同，本地全量副本独立维护。但 `SEG_TO_RESOURCE` 中没有 `competitions` 的子路径映射，`invalidateResource` 按 `competition` 前缀失效时会**同时失效** `competition|_p=123/fiscal-years` 和 `competition|_p=123`。

**影响**：写比赛详情时，财年列表的本地副本也被失效（过度失效）。

**建议**：在 `invalidateResource` 中精确匹配路径，而非仅按资源前缀。

### 缺陷 S4（高）：`fetchFullSync` 的 `LARGE_PAGE_SIZE = 10000` 可能超出服务端限制

**位置**：[request.ts:148](client/src/api/request.ts#L148)

```typescript
const LARGE_PAGE_SIZE = 10000;
```

**问题**：全量同步时用 `pageSize=10000` 请求。若服务端有 `pageSize` 上限（如 1000），请求会被截断，前端拿到不完整的全量副本，后续增量同步基于不完整数据。

**影响**：大数据量场景下本地副本可能不完整。

**建议**：`fetchFullSync` 已有循环分页逻辑，应使用服务端实际返回的 `pageSize` 而非硬编码 10000。或在首次请求后检查 `total` 与实际返回条数是否一致。

---

### 缺陷 S5（高）：`reconstruct` 的分页切片基于本地全量副本，total 可能与服务端不一致

**位置**：[request.ts:240-247](client/src/api/request.ts#L240-L247)

```typescript
function reconstruct(items: any[], shape: "array" | "paged", params: Record<string, any>): any {
  if (shape === "array") return items;
  const total = items.length;  // ← total = 本地副本条数
  const start = (page - 1) * pageSize;
  return { items: items.slice(start, start + pageSize), total, page, pageSize };
}
```

**问题**：`total` 始终等于本地副本的条数。若增量同步遗漏了某些变更（如网络抖动），`total` 可能与服务端实际总数不一致。

**影响**：分页组件可能显示错误的总条数。

**建议**：在增量响应中保留服务端返回的 `total`（如有），而非始终用本地副本长度。

### 缺陷 S6（中）：`_cacheable` 对 `AbortController` signal 的处理有副作用

**位置**：[request.ts:185-192](client/src/api/request.ts#L185-L192)

```typescript
function _cacheable(config?: any): boolean {
  return config?.cache !== false && !config?.signal;
}
```

**问题**：若有 `signal`（AbortController），请求被标记为不可缓存，直接走网络。但 `signal` 的用途是取消请求，与缓存策略无关。

**影响**：带 `signal` 的请求永远不走缓存，即使 `cache` 未设置。这可能导致组件取消旧请求时，新请求也不必要地走网络。

**建议**：将 `signal` 与缓存策略解耦：`return config?.cache !== false;`

### 缺陷 S7（中）：`_getInflight` 去重的 key 包含 silent 配置

**位置**：[request.ts:544-547](client/src/api/request.ts#L544-L547)

```typescript
const silentConfig = { ...config, silent: true };
const key = _reqKey("GET", url, silentConfig);
const pending = _getInflight.get(key);
```

**问题**：`_reqKey` 使用 `JSON.stringify(config.params)` 生成 key。但 `silentConfig` 包含 `silent: true`，而原始 `config` 可能没有 `silent`。这意味着同一个 URL + params 的请求，若一个带 `silent` 一个不带，不会去重。

**影响**：理论上同一请求可能被发送两次（一次 silent，一次非 silent），但实际中 `_cachedGet` 总是加 `silent: true`，所以不会发生。

### 缺陷 S8（中）：`storeAndReturn` 使用 `maxUpdatedAtOf` 作为基线可能不精确

**位置**：[request.ts:292-293](client/src/api/request.ts#L292-L293)

```typescript
const base = v?.serverTime || maxUpdatedAtOf(v);
if (base) await setBaseline(ck, base);
```

**问题**：若服务端不返回 `serverTime`（如旧版本），基线取响应中所有条目的最大 `updatedAt`。但这可能早于服务端当前时间，导致下次增量请求遗漏在此期间的变更。

**影响**：服务端不返回 `serverTime` 时，增量同步可能有微小间隙。

**建议**：优先使用 `serverTime`，仅在无 `serverTime` 时回退到 `maxUpdatedAtOf`。当前代码已是如此，但应确保所有服务端接口都返回 `serverTime`。

### 缺陷 S9（中）：`syncMapFull` 的 `reconcile` 逻辑与通用列表不一致

**位置**：[request.ts:366-387](client/src/api/request.ts#L366-L387)

```typescript
if (needReconcile) {
  await patchFullItems(subs[0], v.nodes || [], v.existingIds?.nodes);
  // ...
} else {
  await patchFullItems(subs[0], v.nodes || []);
  // ...
}
```

**问题**：复合地图的对账逻辑在 `needReconcile` 为 true 时传 `existingIds`，否则不传。这与通用列表的逻辑一致。

但复合地图的 `existingIds` 是嵌套结构 `{ nodes: [], edges: [], ... }`，而 `patchFullItems` 期望的是 `number[]`。若服务端返回 `existingIds: { nodes: [], edges: [], ... }` 但某个子键为空数组，`patchFullItems` 会清空该子资源的本地副本（与 C1 同构）。

**影响**：对账时若服务端某子资源返回空 `existingIds`，该子资源的本地副本被清空。

**建议**：在调用 `patchFullItems` 前检查 `existingIds` 是否为空数组。

## 三、账号隔离

### 缺陷 A1（高）：`setActiveUser(null)` 不清除 IndexedDB 连接缓存

**位置**：[accountStorage.ts:38-43](client/src/utils/accountStorage.ts#L38-L43)

```typescript
export function setActiveUser(id: number | null): void {
  _activeUserId = id;
  _initialized = true;
  if (id == null) localStorage.removeItem(ACTIVE_USER_KEY);
  else localStorage.setItem(ACTIVE_USER_KEY, String(id));
}
```

**问题**：`setActiveUser(null)` 更新了 `_activeUserId` 指针，但 `cache.ts` 的 `_dbPromise` 和 `_dbName` 仍指向旧账号的数据库。下次 `openDB()` 调用时，`currentDbName()` 返回 `gipfel-client-cache-anon`，但 `_dbName` 仍是旧库名，连接被重建。

这是**正确的**行为（库名变化时重建连接）。但若两个账号的 `activeUserId` 相同（理论上不可能，但数据库迁移时可能发生），连接不会重建，数据会串档。

**影响**：正常情况下无影响。极端边界情况可能串档。

## 四、实时事件处理

### 缺陷 R1（高）：`bindResourceChanged` 注册的 `resource:changed` 监听与 `company-field:changed` 监听可能重复触发

**位置**：[resource-changed.ts:37-76](client/src/realtime/resource-changed.ts#L37-L76)

```typescript
// 监听 1：resource:changed
onRealtime("resource:changed", (payload) => {
  // → bumpResourceEvent → scheduleResourceReload
});

// 监听 2：company-field:changed
onRealtime("company-field:changed", (payload) => {
  // → bumpResourceEvent("company-field") + bumpResourceEvent("companyField")
  // → scheduleResourceReload("company-field")
});
```

**问题**：当 `CompanyFieldValue` 被写入时：
1. Prisma 中间件广播 `resource:changed { resource: "company-field" }`
2. Service 手动广播 `company-field:changed { companyId }`

前端两个监听器都被触发，`scheduleResourceReload("company-field")` 被调用两次。由于去抖机制（400ms），两次调用合并为一次。

但 `bumpResourceEvent` 被调用 3 次（`"company-field"` 1 次 + `"companyField"` 1 次 + `"company-field"` 1 次），导致 memo 被多次失效。

**影响**：去抖机制正确合并了重拉，但 memo 失效可能过于激进（同一资源在 400ms 内被标记 3 次）。

**建议**：统一事件源，去掉重复的 `company-field:changed` 监听（依赖 `resource:changed` 即可）。

---

### 缺陷 R2（高）：`scheduleResourceReload` 的去抖仅按 `resource` 分组，不区分 `companyId`

**位置**：[resource-changed.ts:21-31](client/src/realtime/resource-changed.ts#L21-L31)

```typescript
function scheduleResourceReload(resource: string, detail: Record<string, any>): void {
  const existing = _reloadTimers.get(resource);
  if (existing) clearTimeout(existing);
  _reloadTimers.set(
    resource,
    setTimeout(() => {
      window.dispatchEvent(new CustomEvent("resource-changed", { detail }));
    }, RELOAD_DEBOUNCE_MS),
  );
}
```

**问题**：去抖按 `resource` 分组。若短时间内收到两条 `company-field:changed` 事件（分别对应 companyId=1 和 companyId=2），第二次事件覆盖第一次的 `detail`。最终只广播 companyId=2 的事件。

但 `useResourceChanged` 监听的是 `resource` 级别，不关心 `companyId`。所以组件会重拉所有公司字段，覆盖了丢失的 companyId=1。

**影响**：若两个公司的字段同时变更，只有一个公司的 `detail` 被保留。但由于组件按 `resource` 重拉（不按 `companyId`），实际影响有限。

## 五、内存 Memo 与新鲜度窗口

### 缺陷 M1（中）：`_memo` 和 `_lastEventAt` 无大小限制

**位置**：[request.ts:158-160](client/src/api/request.ts#L158-L160)

```typescript
const _memo = new Map<string, { time: number; value: any }>();
const _lastEventAt = new Map<string, number>();
```

**问题**：`_memo` 缓存每个请求键的最近响应。若用户访问大量不同查询参数的页面（如不同公司的详情页），`_memo` 无限增长。

**影响**：长时间运行后内存占用增加。

**建议**：限制 `_memo` 大小（如 LRU 策略，最多 200 个条目）。

---

### 缺陷 M2（中）：`_memo` 的 15 秒窗口可能导致组件看到过时数据

**位置**：[request.ts:553-554](client/src/api/request.ts#L553-L554)

```typescript
if (m && Date.now() - m.time < STALE_WINDOW_MS && lastEvt <= m.time) {
  return m.value as T;
}
```

**问题**：15 秒窗口内，若组件 A 读取了数据（写入 memo），组件 B 在 14 秒后读取同一数据（命中 memo），但此期间服务端数据已变更（无实时事件到达）。

**影响**：组件 B 看到最多 15 秒的过时数据。

**设计意图**：这是 stale-while-revalidate 策略的有意取舍——后台增量请求会在下次读取时更新数据。但用户可能在 15 秒内看到不一致。

---

### 缺陷 M3（低）：`_resetMemo` 清空所有 memo，包括不相关资源

**位置**：[request.ts:175-178](client/src/api/request.ts#L175-L178)

```typescript
function _resetMemo(): void {
  _memo.clear();
  _lastEventAt.clear();
}
```

**问题**：写操作后清空**所有**资源的 memo，而非仅失效被写资源的 memo。若用户编辑原料 A，其他资源（如零件列表）的 memo 也被清空。

**影响**：写操作后首次访问任何资源都 miss memo，多发一次网络请求。

**建议**：仅失效被写资源的 memo（按 `SEG_TO_RESOURCE` 匹配）。
