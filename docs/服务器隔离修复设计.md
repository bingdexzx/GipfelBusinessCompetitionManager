# 服务器隔离修复设计（客户端本地数据按「服务器身份」分桶）

> 配套提交：客户端本地缓存库名与 token 键由「仅按用户 id」升级为「按 服务器身份 realm + 用户 id」双重命名空间，并在切换服务器时清理旧 realm 数据、强制重新登录。

## 1. 问题背景

服务端每台实例是独立的 SQLite 文件（`server/prisma/dev.db`），数据库物理隔离，**服务端数据永远不会跨服务器混合**。所谓「串」，指的是**客户端本地的缓存副本 + 登录会话 token** 这两样东西此前只按「用户 id」隔离，没有按「服务器」隔离。

证据（代码）：

- 客户端缓存库名只含用户 id，不含服务器（`client/src/api/cache.ts:18-22`）：
  ```ts
  const BASE_DB_NAME = "gipfel-client-cache";
  function currentDbName(): string {
    const id = getActiveUserId();
    return id == null ? `${BASE_DB_NAME}-anon` : `${BASE_DB_NAME}-u${id}`;
  }
  ```
- token / 账号键只按 id（`client/src/utils/accountStorage.ts:45-47`）：`acct_u<id>__`，注释明说 *"serverUrl 等保持全局、不加前缀"*。
- `serverUrl` 是单机全局值（`localStorage.serverUrl`），切换只改这一个（`client/src/stores/config.ts:32`）。
- seed 在每台服务器造出完全一样的 admin（`server/prisma/seed.ts`：`username:"admin"` + `SUPER_ADMIN`，autoincrement 第一号 → 两台服务器 admin 都是 id=1）。

把以上拼起来：客户端切换服务器（都指向带 `admin` 的实例）时，缓存桶 `gipfel-client-cache-u1` 与 token `acct_u1__token` **是同一个**。当前靠两道临时护栏兜底——`SettingsView` 改地址时 `clearCurrentAccountCache()` + 收到 401 清缓存——但只要两台服务器的 `JWT_SECRET` 相同（开发/演示常用 `.env.example` 模板默认值），A 的 token 会被 B 直接接受，**一个 admin 会话无感横跨两台服务器、B 的响应又写回同一个 `u1` 桶**，这才是实打实的「串档」。且这两道护栏只在「通过系统设置改地址」这一条路径生效。

## 2. 修复方案：把「服务器身份 realm」并进命名空间

核心思路：用一个确定性指纹 `realm` 标识「当前服务器」，把它编入本地缓存库名和 token 键，使**不同服务器即使 admin 都是 id=1，本地数据也物理隔离，token 不能跨服务器冒用**。

### 2.1 realm 定义

对「归一化后的服务器地址」做确定性短哈希：

- 归一化：补协议（无协议补 `http://`）、去尾部斜杠、转小写 → 形如 `http://host:port`（仅 protocol+host+port，不含路径）。
- 哈希：djb2a（无依赖、稳定、输出小写十六进制），输出作为 `realm`。
- 不同服务器 → 不同 realm；同一服务器地址稳定不变；非法/空地址用固定哨兵 `noserver`。

### 2.2 命名空间改写

| 项目 | 改前 | 改后 |
|---|---|---|
| IndexedDB 缓存库名 | `gipfel-client-cache-u<id>` / `-anon` | `gipfel-client-cache-<realm>-u<id>` / `-<realm>-anon` |
| 账号级 localStorage 键前缀 | `acct_u<id>__` | `acct_<realm>_u<id>__`（token / currentCompetition / announcementSeenVersion 等全部账号键一并隔离） |

`realm` 段为 `[0-9a-f]+`，与 `u<id>` 之间以下划线分隔，模式无歧义，便于按前缀批量清理。

### 2.3 切服务器清理（根治跨服冒用）

`config/index.ts` 新增 `setServerUrl(url)`，在写入新地址**之前**：

1. 按「旧 realm」删除其全部 localStorage 账号键（`acct_<oldRealm>_` 前缀）；
2. 按「旧 realm」删除其全部 IndexedDB 全量副本库（`gipfel-client-cache-<oldRealm>-` 前缀）；
3. `setActiveUser(null)` 重置激活账号指针（旧 token 已删 → 强制重登）；
4. 重置 realm 缓存 + 派发 `server:changed` 事件清空内存 memo，避免旧服务器响应被新服务器命中。

如此，即便两台服务器 `JWT_SECRET` 相同：切换后新 realm 下无 token → 请求不带 `Authorization` → 服务端 401 → 自动跳转登录，从根上杜绝旧 token 跨服务器冒用；两侧本地数据也落在各自的 realm 桶，互不串档。

## 3. 改动文件清单

| 文件 | 改动 |
|---|---|
| `client/src/utils/realm.ts`（新增） | realm 计算（`realmForUrl`）、带缓存的 `getServerRealm()` / `resetServerRealm()`、`clearRealmData(realm)`（按 realm 删 localStorage + IndexedDB） |

## 4. 兼容迁移（升级无损）

- **已登录用户无缝保留**：启动时 `migrateOldAccountKeys` 把升级前的 `acct_u<id>__` 旧账号键整体 re-key 到「当前 realm」命名空间（token / 比赛选择等不丢），无需重新登录。
- **旧格式 IndexedDB**：启动时 `deleteOldAccountDbs()` 删除无 realm 的 `gipfel-client-cache-u<id>` / `-anon` 旧库，下次访问自动建新 realm 库（数据从服务端重新拉取，等价一次「首次进入」）。

## 5. 验收

- `client` `vue-tsc --noEmit` 零错误；
- 行为核对：切到不同地址的服务器，两侧本地缓存 / 会话互不干扰；同一地址的服务器仍共享一份本地数据；升级前已登录用户登录态保留。

## 6. 范围与取舍

- 仅改**客户端本地隔离**；服务端之间本就物理隔离，无需改动。
- realm 以「地址 origin」为粒度。若两个不同服务器刻意复用同一 origin（仅靠路径/租户区分），仍会落在同一 realm——属刻意非常规部署，不在本次范围；如需支持应把 realm 升级为「用户可命名的服务器档案」。
