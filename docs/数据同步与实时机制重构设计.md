# 数据同步与实时机制重构设计

> 版本：v1（草案）
> 状态：仅设计文档，重构待确认后实施
> 关联代码基线：`client/src/api/cache.ts`、`client/src/api/request.ts`、`client/src/realtime/resource-changed.ts`、`client/src/realtime/socket.ts`、`client/src/stores/auth.ts`、`client/src/utils/accountStorage.ts`、`client/src/AppLayout.vue`；`server/src/realtime/*`、`server/prisma/schema.prisma`、`server/src/common/guards/competition-scope.guard.ts`
> 阅读对象：本系统维护者。本文档是「本地存储 / 增量同步 / 前端刷新 / 实时同步 / 数据比赛隔离」五件事的重构蓝图；与《权限分级与重构设计.md》互补（权限分级管"谁能做什么"，本文档管"数据如何到达界面"）。

---

## 1. 背景与目标

当前客户端已有「IndexedDB 全量副本 + updatedAt 增量基线 + WebSocket 实时事件」的雏形，但存在四类被反复反馈的痛点：

1. **本地存储与增量同步内容冲突**：写操作失效缓存与在途增量请求存在竞态，副本可能被旧数据覆盖回写；
2. **前端界面总是不刷新**：断线重连对账不通知组件、15 秒内存新鲜度窗口返回旧值、事件订阅漏配等；
3. **权限变更不同步**：管理员给某账户加权限后，对方界面菜单/按钮不更新（服务端 API 其实已即时生效）；
4. **数据未强制按比赛隔离**：除产业类型、合同类型、系统账户外，仍有 22 个模型的 `competitionId` 可空，可写入跨比赛全局数据。

本次重构目标：

1. **本地存储按「比赛 + 账户」双层隔离**，切换比赛/账户不串档、不残留；
2. **增量同步以服务端为唯一事实源**，消除覆盖冲突与基线回退；
3. **前端刷新机制重构**：事件驱动 + 比赛/资源精确匹配 + 对账完成主动通知；
4. **实时同步机制重设计**：事件携带 `competitionId` 与序号、断线补拉、定向推送；
5. **非数据类信息实时主动同步**（权限 / 消息 / 公告 / 比赛配置），权限变更即时生效，杜绝"我加了权限对方看不到"；
6. **除产业类型、合同类型、系统账户外，所有数据强制关联比赛**，加固多租户隔离。

## 2. 现状盘点（基线）

### 2.1 本地存储现状

| 层 | 实现 | 隔离维度 |
|----|------|---------|
| IndexedDB | 原生 API，库名 `gipfel-client-cache-u<id>`（`cache.ts:18-22`），objectStore `responses`，keyPath `key` | **按账户分库**；比赛靠集合键内 `competitionId=` 参数区分（`FULL|material|competitionId=1`） |
| 缓存键 | `FULL|<资源>|<非分页参数>`、`META|baseline|...`、`META|fullSyncAt|...`（`cache.ts:24-28`） | 22 类资源（`SEG_TO_RESOURCE`，`cache.ts:31-55`） |
| axios 缓存 | 两级：**O3 内存 memo**（15s 新鲜度窗口，`request.ts:157,555`）+ **IndexedDB 全量副本/增量**（`cachedGetImpl`，`request.ts:476-536`） | memo 键 = `GET url params`，**无账户/比赛维度**（`_reqKey`，`request.ts:180-183`） |
| localStorage | `utils/accountStorage.ts` 前缀 `acct_u<id>__`（`accountStorage.ts:45-47`） | 按账户；比赛维度仅 Dashboard 布局键（`DashboardView.vue:270-274`） |

### 2.2 增量同步现状

- 基线 = 服务端返回的最大 `updatedAt`（`maxUpdatedAtOf`）；增量请求带 `updatedAfter=<基线>`；`patchFullItems` 按 id 合并（`cache.ts:175-196`）；
- 删除复核：5 分钟周期（`FULL_SYNC_INTERVAL_MS`）或断线重连（`reconcileAllIncremental`，`request.ts:601-681`）时带 `requireExistingIds`，用 `existingIds` diff 删除；
- 写操作成功后 `invalidateResource` + `_resetMemo`（`request.ts:578-586`）；
- 离线降级：读本地全量副本（`request.ts:530-533`）。**无离线写队列**。

### 2.3 实时推送现状

- 网关 `server/src/realtime/realtime.gateway.ts`：握手 JWT 鉴权 → `join("user-{id}")`；客户端 `subscribe {competitionId}` → `comp-{cid}` 房间（非超管只能订阅自身比赛）；
- 事件清单（`server/src/realtime/realtime.service.ts`）：

| 事件 | 触发点 | 载荷 | 房间 |
|------|--------|------|------|
| `resource:changed` | Prisma `$allOperations` 中间件自动广播（`prisma.service.ts`），`MODEL_TO_RESOURCE` 25 模型 | `{resource, id, action}`——**不含 competitionId**（`realtime.service.ts:103`） | `comp-{cid}` 或全体（cid 为 null 时） |
| `message:new` | `message.service.ts` 定向收件人 | `{id,title,content,senderId,...}`——不含 competitionId | `user-{id}` |
| `company-field:changed` | company-fields / contract service | `{companyId, competitionId}` | `comp-{cid}` |
| `contract:changed` | contract.service | 合同对象 + competitionId | `comp-{cid}` |
| `competition:changed` / `fiscal-year:changed` | competition/files service | 实体 | 全体/房间 |
| `stock:round-advanced` | stock.service | 轮次信息 | `comp-{cid}` |

- **权限变更无定向推送**：`users.service.update()` 改角色/权限/范围后仅写库；Prisma 中间件会广播泛化 `resource:changed(users)`，但前端只把它当账号列表缓存失效（`AccountManagementView.vue:442` 刷新列表），**auth store 不消费** → 被改账户的菜单/按钮仍按旧权限渲染（`AppLayout.vue:40` 仅在挂载时拉一次 `/auth/me`）。服务端 API 层权限**即时生效**（`jwt.strategy.ts` 每次请求从 DB 重载 permissions/scopes），问题纯在前端本地状态。

### 2.4 数据与比赛关联现状（32 模型）

| 归属 | 模型 |
|------|------|
| 强关联（必填） | `Competition`（本体）、`FiscalYear`、`Contract` |
| 豁免（可全局） | `User`（系统账户）、`IndustryType` / `IndustryField`（产业类型）、`ContractType`（合同类型） |
| **弱关联（`competitionId Int?` 可空，不合要求）** | `Material` `Part` `Product` `TechNode` `MapNodeType` `PathType` `MapNode` `MapEdge` `Infrastructure` `Warehouse` `ProductionLine` `Fuel` `Vehicle` `Region` `ConsumerDemand` `Company`（16 个基础数据）+ `Stock` `StockFundsAccount` `StockHolding` `StockOrder` `StockCandle`（5 个股票）+ `Message`（`competitionId Int?` 可空，注释明示不靠它做租户隔离） |
| 间接关联 | `PartMaterial` `PartTechRequirement` `ProductPart` `ProductTechRequirement` `TechPrerequisite` `VehiclePathType`（经父实体；父实体可空 → 间接关联亦弱） |

- `CompetitionScopeGuard`（`server/src/common/guards/competition-scope.guard.ts`）全局注册：超管放行；非超管写强制 `body.competitionId = user.competitionId`、读注入 own cid、`cid ≠ own` 抛 Forbidden。
- **绕过口**：`@NoCompetitionScope()` 豁免 5 个控制器——`files`、`contract-type`、`message`、`competition`、`industry-type`；显式传 `competitionId=null` 且账号 own=null 时也放行（读全局字典，设计如此）。

## 3. 问题分析（问题清单）

### P1（高）写失效与在途增量竞态 → 「本地存储和增量同步内容冲突」

- 写操作成功后 `invalidateResource` 清掉本地副本并 `_resetMemo`；但**在途的增量请求**（如断线重连对账、其他组件的增量 GET）不受影响，其基于**旧基线**返回的变更可能在失效之后 `patchFullItems` 写回副本，并把基线推进到旧 `serverTime` → 副本混入旧数据、后续增量基于错误基线；
- 两个并发 GET（同一集合，一个全量 `storeAndReturn`、一个增量 `patchFullItems`）先后写副本，后写者以旧底本合并，可能覆盖全量的新副本；
- 结论：**本地副本的写方不互斥、无版本校验**，是"老是有冲突"的核心机制。

### P2（高）断线重连对账不通知组件 → 界面不刷新

- `reconcileAllIncremental`（`resource-changed.ts:83-85` 触发）只更新 IndexedDB 副本与 memo，**不派发 window 事件**，已挂载组件不会重载 → 断线期间他人产生的变更，重连后界面依然旧。

### P3（高）权限变更无实时同步 → 「我加权限对方看不到」

- 无 `permissions:changed` 定向事件；泛化 `resource:changed(users)` 不被 auth store 消费；前端权限状态（`can()`/菜单/按钮）只在登录与 `AppLayout` 挂载时初始化（`AppLayout.vue:40`）。
- 影响面：菜单显隐、按钮 disabled、`can()` 判定全部停留在旧权限；**服务端已按新权限拒绝/放行**，前后端判定不一致。

### P4（高）15s memo 与实时事件竞态 + memo 无账户维度

- `_cachedGet`（`request.ts:551-557`）：窗口内且 `_lastEventAt <= m.time` 直接返回内存旧值。**事件先于 memo 写入**（或事件丢失）时，memo 会在窗口内持续返回旧值；
- memo 键（`_reqKey`）**不含账户维度**：同窗口内切换账号，同 url 同 params 可能命中上一账号的缓存（登出路径是否 `_resetMemo` 需核实）；
- `_lastEventAt` 是全局 Map，不区分比赛：A 比赛的股票事件会使 B 比赛同资源 memo 失效（过度失效，浪费）或相反（漏失效）。

### P5（中）`resource:changed` 载荷缺 competitionId、无序号

- 载荷仅 `{resource, id, action}`（`realtime.service.ts:103`），前端无法按比赛过滤；事件丢失**无序号兜底**，只能靠 5 分钟全量对账或重连对账补齐 → 长在线窗口内容易出现"别人改了看不到"。

### P6（中）股票多集合共用 resource=stocks → 删除事件跨集合误伤

- `MODEL_TO_RESOURCE` 把 `Stock/StockFundsAccount/StockOrder/StockHolding/StockCandle` 全部映射为 `stocks`（`realtime.service.ts:31-34`）；
- 前端 `removeFullItemByResource("stocks", id)` 按前缀 `FULL|stocks|` 扫描**所有股票集合**删除同 id（`cache.ts:202-232`）——不同集合（accounts/orders/holdings）的同 id 是**不同实体**，删除一条订单可能误删一条持仓记录。

### P7（中）22 个模型 `competitionId` 可空 → 弱租户隔离

- 16 个基础数据 + 5 个股票 + Message 均可写入 `null` 形成跨比赛全局数据；`@NoCompetitionScope` 豁免 5 个控制器、显式 null 放行，存在数据越比赛写入/读取面。

### P8（低）界面刷新遗漏点

- 路由复用：`AppLayout.vue:10` `:key="route.path"`，同路由仅 query 变化不重挂载；
- 表单回车：`AccountManagementView.vue:79` `el-form` 缺 `@submit.prevent`（对比 `CompetitionListView.vue:143` 有）→ 回车整页重载；
- 事件漏订阅：`StockMarketView.vue:634` 仅订阅 `company-field`，未订阅 `stocks` → 他人交易/撮合不刷新；
- detail 请求无增量：非列表接口仅按请求键缓存，刷新依赖 memo 过期 + 事件。

### P9（低）对账范围过大

- `reconcileAllIncremental` 遍历**本地全部集合**（含已切换离开的比赛、已失去权限的资源）逐一发增量请求——浪费带宽且可能触发越权请求（虽被服务端拒绝，但产生噪音）。

## 4. 目标设计

### 4.1 本地存储按「比赛 + 账户」双层隔离

**原则**：任何缓存键（IDB / localStorage / memo）必须具备完整身份：`账户 × 比赛`；全局豁免数据（产业类型/合同类型）用显式 `global` 命名空间，与比赛数据物理区分。

| 层 | 现状 | 目标 |
|----|------|------|
| IndexedDB 库名 | `gipfel-client-cache-u<id>` | 保持按账户分库（已隔离），**集合键增加显式 `c<cid>|` 前缀**：`FULL|c<cid>|material|...`；全局豁免资源用 `FULL|global|...` |
| 内存 memo | `GET url params` | 键加入 `uid|cid|` 前缀，登出/切换账号必须 `_resetMemo` |
| localStorage | `acct_u<id>__` 前缀 | 比赛相关键统一 `acct_u<id>__c<cid>__`；全局键 `acct_u<id>__global__` |
| 切换比赛 | 仅 `useCompetitionReload` 清空组件数据 | 切换时：切到目标比赛的命名空间 → 立即对账该比赛 → 广播 `sync:reconciled` |
| 清缓存 | 整库 `clear()` | 支持按比赛粒度清理（删除 `FULL|c<cid>|` 前缀），登出按账户整库清理 |

### 4.2 增量同步防冲突（单一事实源）

1. **写方互斥（generation 标记）**：`request.ts` 维护每集合 `generation`，写操作开始时 `generation++` 并记录；在途增量响应返回时校验 `generation` 未变才允许 `patchFullItems` 写回，否则丢弃（数据随后由失效后的全量同步补齐）；
2. **基线单调推进**：`setBaseline` 仅接受 ≥ 本地基线的时间（ISO 字符串比较），服务端 `serverTime` 为准，禁止回退；
3. **副本版本校验**：`patchFullItems` 写入前记录 `savedAt`，与读底本时校验，若期间被其它写方更新则重读合并（或直接放弃本次 patch，交给全量兜底）；
4. **事件驱动优先，对账兜底**：created/updated 事件到达后组件重拉（增量），deleted 事件精确移除；对账（existingIds）仅用于断线补漏，不再作为常规路径；
5. **集合限定删除**：删除事件携带集合标识（见 4.4），`removeFullItemByResource` 支持按 `_p=` 子集合限定，杜绝 P6 跨集合误伤。

### 4.3 前端刷新机制重构

1. **统一事件总线升级**：`resource-changed` 载荷透传 `competitionId` + `seq`；`useResourceChanged` 按 `resource + competitionId` 精确匹配（不匹配当前比赛的事件不触发重载）；
2. **对账完成主动通知**：`reconcileAllIncremental` 完成后派发 `sync:reconciled`（携带涉及的集合），已挂载组件监听后统一重载——直接修复 P2；
3. **组件加载模式统一**：`onMounted 拉取 + 订阅事件重载`，重载统一走 `useResourceChanged`/`useCompetitionReload`，不再各自为政；
4. **路由复用**：`AppLayout.vue` 的 `:key` 改为 `route.fullPath`（含 query），query 变化即重挂载；
5. **表单**：所有 `el-form` 补 `@submit.prevent`（全局检索补齐）；
6. **补订阅**：`StockMarketView` 增加 `stocks` 资源订阅；detail 请求（`/:id`）在所属资源事件到达时一并失效。

### 4.4 实时同步机制重设计

**统一事件格式**（向后兼容：旧字段保留，新增字段可缺省）：

```
resource:changed → { resource, id, action, competitionId, seq, ts }
```

- **房间路由标准化**：`emitResourceChanged` 改为按实体归属自动路由——有 `competitionId` → `comp-{cid}`；全局豁免实体（IndustryType/ContractType/Competition 等）→ 全体房间；用户定向（权限/消息）→ `user-{id}`；
- **事件序号 seq**：服务端维护单调递增全局序号（内存计数，重启归零可接受），事件与增量响应均携带 `seq`；客户端记录 `lastSeq`，重连后发 `sync:replay {afterSeq}`，服务端补发遗漏事件（内存环形缓冲，保留最近 N 条）；
- **心跳与重连**：现有心跳/重连保留；重连成功 → 先 `sync:replay` 补事件 → 再 `reconcileAllIncremental` 对账 → 最后广播 `sync:reconciled`；
- **多 Tab 一致性**：事件广播与 IndexedDB 写入结合 localStorage `BroadcastChannel`（如适用）同步，保证同账户多窗口一致（Electron 单窗口场景可后置）。

### 4.5 非数据类信息实时主动同步（权限 / 消息 / 公告 / 配置）

| 信息 | 现状 | 目标 |
|------|------|------|
| **权限/角色/范围变更** | 无定向推送，前端不刷新（P3） | 后端 `users.service.update/create` 后 `emitToUser(targetUserId, "permissions:changed", {version})`；**前端 auth store 订阅 → 拉取 `/auth/me` → 更新 `can()`/菜单/按钮**（Pinia 响应式自动生效） |
| 消息 | `message:new` 定向已有 | 载荷补 `competitionId`；读状态变更（已读）实时同步 `message:read` |
| 公告 | `announcementSeenVersion` 本地存储 | 公告变更推送 `announcement:changed`，前端刷新版本号 |
| 比赛配置/财年 | `competition:changed` / `fiscal-year:changed` 已有 | 统一走新事件格式（补 seq） |
| 账户被禁用/顶号 | 401 被动登出 | 定向 `account:disabled` 事件主动登出提示 |

> 关键保证：**权限变更的"数据"（permissions 数组）写库即生效（服务端即时判定），实时推送只解决"前端界面状态同步"**。二者解耦后，即使推送丢失，重连对账也会把 `/auth/me` 拉齐。

### 4.6 数据强制关联比赛（多租户强化）

1. **Schema 必填化**：22 个弱关联模型的 `competitionId Int?` → `competitionId Int`（`Message` 一并必填化，按发送者归属比赛）；
2. **存量迁移**：一次脚本把 `competitionId = null` 的行迁移到「默认比赛」（决策点 E3），迁移前备份 `dev.db`；迁移后业务查询不再需要容忍 null；
3. **CompetitionScopeGuard 收口**：
   - `@NoCompetitionScope` 白名单收敛为仅全局字典控制器（contract-type / industry-type / competition 的公开读）；
   - 显式 `competitionId=null` 的非豁免写请求一律拒绝；
   - `Message`/`files` 等控制器改为内部按 sender/业务归属收敛；
4. **关联表随父实体**：`PartMaterial` 等 6 个关联表不直接加字段，查询路径经父实体必填 `competitionId` 自然收敛（服务端 findAll 统一按 `where.competitionId` 注入）；
5. **豁免清单固定**：`User`（系统账户，多比赛共用）、`IndustryType`/`IndustryField`（产业类型，全局字典）、`ContractType`（合同类型，全局字典）——写入代码常量 `GLOBAL_ENTITY`，守卫与前端共用。

## 5. 端点-事件对照（验收基线）

| 资源 | 事件 | 房间 | 前端处理 |
|------|------|------|---------|
| 16 个基础数据 + 5 个股票 + company-field + contract | `resource:changed` | `comp-{cid}` | 精确匹配 cid → 组件重载（增量） |
| industry-type / contract-type / competition | `resource:changed` | 全体 | 全局命名空间刷新 |
| users | `permissions:changed`（定向） | `user-{id}` | auth store 拉 `/auth/me` 刷新权限状态 |
| users | `resource:changed`（泛化） | 房间 | 仅账号管理列表刷新（保留） |
| messages | `message:new` / `message:read` | `user-{id}` | 消息中心增量 |
| announcements | `announcement:changed` | 全体/房间 | 公告横幅/版本号 |

## 7. 兼容与迁移策略

1. **事件载荷向后兼容**：`resource:changed` 新增字段缺省可解析，旧客户端（未升级前端）不受影响；前端升级后自动启用精确匹配；
2. **本地存储键迁移**：S8 键前缀变更通过「检测旧键 → 读取后删除」一次性迁移（启动时执行一次），失败则回退全量同步；
3. **数据库迁移（S10，一次）**：22 模型 `competitionId` 必填化前，先备份 `dev.db`，跑存量归并脚本（null → 默认比赛），再 `db push`；若后端正在运行需先停止（SQLite 写锁）；
4. **灰度顺序**：S1–S2（事件+总线）→ S3–S4–S5（缓存一致性）→ S6–S9（精确删除+界面修复）→ S7（权限实时，联动权限文档 T4/T7/T9）→ S8（存储隔离）→ S10（数据关联迁移）→ S11–S12（收尾）；
5. **回滚**：S1–S6、S9 集中在 request/cache/realtime 层，可整文件 revert；S7 需前后端同发（客户端 build+重启）；S10 迁移前有备份，异常时还原 `dev.db`。

## 8. 决策点（待确认）

| 决策点 | 选项 | 推荐 | 影响 |
|--------|------|------|------|
| E1 本地存储隔离粒度 | A. 保持现有「集合键含 competitionId 参数」+ 补齐 memo/全局命名空间（增量改造）；B. 显式 `c<cid>\|` 命名空间 + 键迁移（彻底） | **B** | B 让「比赛」成为一等隔离维度（切换/清理/对账都按比赛为单位），一次性根治；A 成本低但隔离语义分散在 key 参数里 |
| E2 权限变更推送方案 | A. 定向 `permissions:changed` + 前端自动重拉 `/auth/me`（事件驱动）；B. 前端周期轮询 `/auth/me` | **A** | A 即时且省流量；B 实现简单但有延迟（轮询间隔内不一致） |
| E3 存量 null 比赛数据归属 | A. 迁移到「默认比赛」（第一个比赛）；B. 迁移到当前操作者所属比赛（逐行）；C. 维持可空但禁止新写 null | **A** | A 确定性最高、可脚本化；B 依赖操作者上下文、结果分散；C 治标不治本 |
| E4 事件可靠性 | A. 事件带 seq + 内存环形缓冲 + 重连 `sync:replay` 补拉（低成本）；B. 变更日志表 + 统一 `/api/sync` 增量端点（高成本） | **A** | A 覆盖"断线期间事件丢失"主场景，重启服务端归零可接受；B 更强但引入存储与接口复杂度 |
