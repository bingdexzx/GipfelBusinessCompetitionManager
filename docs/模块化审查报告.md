## 二、代码重复热点

### 🔴 严重重复（19 个文件，23 处）

#### D1: `findAll` 增量同步模板

每个 service 的 `findAll` 方法重复相同的结构：

```typescript
const baseWhere = competitionId ? { competitionId } : {};
const { where, incremental } = applyUpdatedAfter(baseWhere, updatedAfter);
if (incremental) {
  const items = await this.prisma.MODEL.findMany({ where, orderBy: { updatedAt: "desc" } });
  const existingIds = requireExistingIds
    ? (await this.prisma.MODEL.findMany({ where: baseWhere, select: { id: true } })).map(e => e.id)
    : [];
  return buildIncrementalResult(items, existingIds);
}
// ... 分页回退
```

**出现次数**：material / fuel / warehouse / infrastructure / production-line / company / part / product / vehicle / tech-tree / region / competition / contract / industry-type / stock + map.service.ts（5 次）

**每次重复**：~15-20 行

**建议**：提取泛型函数 `withIncrementalSync(prismaModel, baseWhere, include, updatedAfter, requireExistingIds)`

---

#### D2: `create` 唯一性校验模板（13+ 模块）

```typescript
const existing = await this.prisma.MODEL.findFirst({
  where: { competitionId: dto.competitionId, name: dto.name },
});
if (existing) throw new ConflictException("NAME already exists");
```

`update` 中同样重复（加 `NOT: { id }`）。

**建议**：提取 `assertUniqueName(prisma, model, name, competitionId, excludeId?)`

---

#### D3: `findOne` + NotFoundException 模板（每个 service）

```typescript
const item = await this.prisma.MODEL.findUnique({ where: { id } });
if (!item) throw new NotFoundException("ENTITY does not exist");
return item;
```

**建议**：在 BaseCrudService 中统一实现。

---

#### D4: `remove` 模板（14+ 模块）

```typescript
const item = await this.findOne(id);
assertSameCompetition(item.competitionId, competitionId);
await this.prisma.MODEL.delete({ where: { id } });
return { message: "已删除" };
```

**建议**：在 BaseCrudService 中统一实现。

---

#### D5: `getDeleteImpact` 模板（13 模块）

每个模块实现近乎相同的 `getDeleteImpact` 方法，查询子表计数并返回 `{ name, children }`。仅子表查询不同。

**建议**：提取 `buildDeleteImpact(prisma, modelName, id, childQueries[])`

---

#### D6: `parseConfig` 函数重复（2 文件）

**位置**：
- `company-fields.service.ts:75`
- `industry-type.service.ts:15`

两处完全相同的函数：解析字段 config（可能是 JSON 字符串或对象）。

**建议**：移至 `common/json.util.ts`

---

#### D7: `DeleteImpact` 类型导入路径混乱（10 模块）

10 个 service 从 `../materials/material.service` 导入 `DeleteImpact` 和 `DeleteImpactItem` 类型，使 `material.service` 成为意外的"类型宿主"。

类型已移至 `common/types/delete-impact.ts`，但旧导入路径仍在。

**建议**：统一从 `common/types/delete-impact.ts` 导入，移除 `material.service` 中的 re-export。

---

#### D8: 控制器查询参数解析模板（每个控制器）

每个控制器重复相同的查询参数解析：

```typescript
@Query("page") page?: string,
@Query("pageSize") pageSize?: string,
@Query("competitionId") competitionId?: string,
@Query("updatedAfter") updatedAfter?: string,
@Query("requireExistingIds") requireExistingIds?: string,
// + parseInt 调用
```

**建议**：使用自定义装饰器 `@QueryParams()` 一次性解析所有通用参数。

## 三、缺失的抽象

### A1: 无 BaseCrudService 泛型基类

13+ 模块的 `findAll` / `findOne` / `create` / `update` / `remove` / `getDeleteImpact` 遵循相同模板。一个参数化的基类可消除数百行重复代码：

```typescript
// 理想的抽象
@Injectable()
export abstract class BaseCrudService<T> {
  constructor(
    protected prisma: PrismaService,
    protected modelName: Prisma.ModelName,
    protected entityLabel: string,
  ) {}

  async findAll(competitionId?, page?, pageSize?, updatedAfter?, requireExistingIds?) {
    // 通用增量同步逻辑
  }

  async findOne(id: number) {
    // 通用查询 + NotFoundException
  }

  async remove(id: number, competitionId?: number) {
    // 通用删除 + assertSameCompetition
  }
}
```

**收益**：每个新模块从 ~80 行 boilerplate 降至 ~10 行自定义逻辑。

---

### A2: 无共享的增量同步高阶函数

`common/sync.ts` 提供了 `applyUpdatedAfter` 和 `buildIncrementalResult`，但调用模式（prisma 查询 + existingIds 查询 + 条件返回）仍在每个 service 中手动重复。

**建议**：增加 `withIncrementalSync(model, baseWhere, include, opts)` 封装完整流程。

---

### A3: 无共享的唯一性校验器

`findFirst` + `ConflictException` 模式在每个 create/update 中重复。

**建议**：增加 `assertUnique(model, where, label, excludeId?)` 工具函数。

---

### A4: 无共享的控制器 Mixin 或装饰器

控制器重复的查询参数解析、守卫装饰、路由定义可通过 mixin 或自定义装饰器标准化。

## 四、模块间耦合

### 依赖关系图

```
ContractsModule ──→ CompanyFieldsModule ──→ IndustryCalcEngineService
       │                    ↑                          │
       │                    │                          ↓
       ├──→ RealtimeModule  │                    PrismaModule
       │                    │
CompetitionModule ──→ CompanyFieldsModule
       │
       ├──→ RealtimeModule

StockModule ──→ RegionModule
       │
ConsumerDemandsModule ──→ CompanyFieldsModule

MessageModule ──→ RealtimeModule

```

### 被依赖最多的模块

| 模块 | 被依赖次数 | 说明 |
|------|-----------|------|
| **CompanyFieldsService** | 4 | 被 contracts / competitions / consumer-demands / (自身) 依赖 |
| **RealtimeService** | 5 | 被 contracts / competitions / regions / messages / prisma 依赖 |
| **PrismaModule** | 所有模块 | 全局模块 |

### 耦合评估

| 耦合类型 | 状态 | 说明 |
|----------|------|------|
| 直接服务注入 | ✅ 正确 | 通过 NestJS DI 注入，显式声明依赖 |
| 类型耦合 | ⚠️ 有隐患 | 10 模块从 material.service 导入类型 |
| 运行时耦合 | ⚠️ 有隐患 | PrismaService 通过 `getRealtimeService()` 隐式依赖 RealtimeService |
| 隐式耦合 | ⚠️ 有隐患 | ContractEngineService 直接查 Prisma 模型，绕过其他 service |

## 五、循环依赖风险

### R1: PrismaService ↔ RealtimeService（高风险）

**位置**：`server/src/prisma/prisma.service.ts`

`PrismaService` 通过 `getRealtimeService()` 函数调用（非构造函数注入）访问 `RealtimeService`。这避免了 NestJS 的循环依赖检测，但创建了运行时耦合。

若 `RealtimeModule` 依赖 `PrismaModule`（通过任何注入了 Prisma 的 service 间接依赖），则形成模块级循环引用，仅靠延迟函数调用模式解决。

**建议**：将审计/广播逻辑从 Prisma `$extends` 扩展移至 NestJS 拦截器或事件订阅者。

---

### R2: CompanyFieldsService 作为依赖中心

`CompanyFieldsService` 被 4 个模块依赖，且自身依赖 `PrismaService`、`RealtimeService`、`IndustryCalcEngineService`。它是依赖图的中心节点。

**风险**：修改 `CompanyFieldsService` 的接口可能影响 4 个下游模块。

---

### R3: ContractEngineService 的隐式耦合

**位置**：`server/src/modules/contracts/contract-engine.service.ts`（2567 行）

合同引擎直接通过 `this.prisma` 查询 10+ 个模块的 Prisma 模型（material / part / product / techNode / warehouse / productionLine / fuel / vehicle / infrastructure / mapNode / company / industryField / companyFieldValue），不注入任何其他模块的 service。

**好处**：避免了模块间显式依赖。
**风险**：任何这些模型的 schema 变更都可能静默破坏引擎。

## 七、God Object 问题

### contract-engine.service.ts（2567 行）

这是代码库中**最大的单文件**，包含：

| 组件 | 行数（估） | 说明 |
|------|-----------|------|
| `ContractEngineService` 类 | ~400 | 执行、回滚、前置检查 |
| `evalValueSpec` 函数 | ~200 | 核心求值引擎 |
| `applyOp` 函数 | ~300 | 40+ 运算 |
| `applyFieldEffect` 函数 | ~100 | 字段效果应用 |
| `compareField` 函数 | ~100 | 前置检查比较 |
| 聚合计算函数 | ~800 | 20+ 个 compute* 函数 |
| 辅助函数 | ~200 | toNumber, isTruthy, deepEqual 等 |
| Dijkstra 算法 | ~100 | 地图路程计算 |

**建议**：拆分为 4-5 个文件：
1. `contract-engine.service.ts` — 执行/回滚/前置检查编排
2. `contract-eval.service.ts` — evalValueSpec + applyOp
3. `contract-aggregates.ts` — 所有 compute* 聚合函数
4. `contract-field-effect.ts` — applyFieldEffect + compareField
5. `contract-helpers.ts` — toNumber, isTruthy, deepEqual 等
