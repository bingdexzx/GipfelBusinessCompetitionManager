# Gipfel商赛系统 — 软件文档

> **版本**：v1.1（2026-08-13）

---

## 1. 系统概述

### 1.1 项目背景

本系统为商业模拟竞赛（商赛）的办赛方提供一套完整的数据管理工具，用于维护竞赛所需的全量标准化数据，包括原料、零件、产品、地图、基建、科技树、燃料、载具等八大类业务数据，以及系统账户管理。办赛方通过本系统配置竞赛参数，参赛选手通过系统获取竞赛数据。

### 1.2 系统目标

| 目标      | 说明                                                   |
| ------- | ---------------------------------------------------- |
| 标准化数据管理 | 统一管理竞赛所需的全部基础数据，确保数据一致性                              |
| 权限分级    | 超级管理员 + 细粒度权限（基于 `permissions` 数组的 RBAC）             |
| 可视化管理   | 每类数据提供直观的可视化管理界面，地图数据提供图形化编辑器                        |
| 模块化架构   | 服务端与客户端均按功能模块拆分，便于维护与扩展                              |
| 高效执行    | 数据加载懒加载、表格虚拟滚动、按需请求；客户端本地缓存（IndexedDB）减少重复请求、减轻服务器压力 |

### 1.3 核心功能

1. **比赛与财年管理**：创建比赛（租户根），开/关财年；所有业务数据按 `competitionId` 隔离。
2. **数据管理**（含比赛隔离）：原料、零件、产品、地图（节点/边/类型）、基建、科技树、燃料、载具、仓库、生产线、产业类型、公司及其产业字段。
3. **合同系统**：配置驱动的合同类型模板 + 执行引擎（改写公司产业字段 `CompanyFieldValue`），含前置检查。
4. **账户与权限管理**：超级管理员 + 细粒度权限（基于 `permissions` 数组的 RBAC）。
5. **认证授权**：JWT 令牌 + 细粒度权限守卫（`PermissionsGuard` + `@RequirePermissions`）。
6. **服务端日志**：请求日志、操作日志、错误日志、运行日志。
7. **可视化界面**：每类数据配备列表视图、表单编辑、地图图形编辑器、科技树可视化、合同可视化编辑器。
8. **实时广播**：基于 WebSocket（socket.io）的通用广播基建，管理员操作（开/关财年、比赛状态变更、合同执行、公司字段写入）即时同步到所有已登录前端。
9. **消息中心**：办赛方可向指定账号定向发布消息；接收方登录后于收件箱持久留存（含未读红点），在线时另从屏幕右侧滑入弹窗、停留数秒后自动向右滑出关闭。

### 2.3 通信方式

客户端与服务端通过两种方式通信：

1. **HTTP REST API**（主通道）：数据格式为 JSON，基准路径 `/api`。
   - 认证：请求头携带 `Authorization: Bearer <JWT>`
   - 服务器地址：客户端启动时从本地配置读取，支持在设置页修改
   - 错误处理：统一 HTTP 状态码 + `{ code, message, data }` 响应体
2. **WebSocket 实时广播**（辅助通道）：服务端基于 **socket.io** 复用 HTTP 3000 端口，握手携带 JWT 鉴权，按 `comp-{competitionId}` 房间订阅。用于把管理员的强时效操作（开/关财年、比赛状态变更、合同执行/状态变更、公司字段写入）即时推送给所有同比赛的已登录前端。详见 §12.11。

## 3. 环境要求与快速上手

### 3.1 环境要求

- **Node.js**：≥ 18（推荐 20 LTS）
- **npm**：随 Node 安装
- **操作系统**：Windows / macOS / Linux（服务端为跨平台 Node 应用）

### 3.2 安装依赖

分别在两个目录安装依赖（首次需联网拉取 npm 包）：

```bash
# 服务端
cd server
npm install

# 客户端
cd ../client
npm install
```

### 3.3 初始化数据库

服务端使用 SQLite，数据库文件为 `server/prisma/dev.db`。首次运行需同步表结构并创建默认超管：

```bash
cd server

# 方式一：迁移（推荐，会生成迁移记录）
npx prisma migrate dev --name init

# 方式二：仅推送 schema（无需迁移历史）
npx prisma db push

# 创建默认超级管理员（仅显式初始化备用，见 §18.A）
npm run prisma:seed
```

> 默认超管账号：**`admin` / `admin123`**，角色 `SUPER_ADMIN`，`competitionId` 为 null。  
> 首次登录后请务必在「系统设置」中修改密码。

### 3.4 启动开发环境

开两个终端：

```bash
# 终端 1：启动服务端（默认监听 3000 端口，带 watch 热重载）
cd server
npm run start:dev

# 终端 2：启动客户端（Vite 开发服务器 + Electron 窗口）
cd client
npm run dev
```

默认服务端地址为 `http://localhost:3000`。若服务端部署在其他地址，在客户端「登录页 → 服务器设置」或「系统设置」中修改即可（持久化到 `localStorage` 或 Electron 配置文件）。

### 3.5 首次使用流程

1. 用 `admin / admin123` 登录。
2. 进入「比赛管理」创建一场比赛。
3. 选择该比赛后，在「数据管理」中录入原料、零件、产品、科技树、地图、燃料、载具、仓库、生产线、基建等基础数据。
4. 在「公司管理」中创建参赛公司，并维护其产业字段。
5. 所有业务数据均按 `competitionId` 隔离；不选择比赛时界面不展示数据。

### 3.6 构建与打包

**仅构建（校验类型与编译）**：

```bash
# 服务端
cd server && npm run build          # 输出 dist/

# 客户端（含类型检查 vue-tsc + vite 打包）
cd client && npm run build          # 输出 dist/ 与 dist-electron/
```

**生产启动**：

```bash
cd server && npm run start:prod     # node dist/main.js
```

**打包桌面应用（Windows NSIS）**：

```bash
cd client && npm run electron:build # 输出 client/release/
```

产物为 Windows 安装包（NSIS），`appId` 为 `com.gipfel.businesscompetition`。

## 5. 数据模型设计

### 5.1 关联链与多租户隔离约定

系统共 9 大业务实体 + 账户实体，核心关联链：

```
科技树(TechNode) ──引用──┐
                        ├──> 零件(Part) ──配比──> 原料(Material)
                        ├──> 产品(Product) ──配比──> 零件(Part)
燃料(Fuel) ──引用──> 载具(Vehicle) ──可通过──> 路径类型(PathType)
地图节点(MapNode) ──连线──> 地图边(MapEdge) ──类型──> 路径类型(PathType)
                    └── 类型 ──> 节点类型(MapNodeType)
基建(Infrastructure) ── 独立实体
```

> **多租户隔离约定**：除 `User`、`Competition`、`FiscalYear`、`ContractType`、`IndustryType`/`IndustryField`（全局模板，无 `competitionId`）外，其余业务实体均含可选 `competitionId Int?` 字段（`null` 表示全局共享字典）。所有带 `competitionId` 的实体在读取、创建、删除各环节都按当前比赛隔离：
>
> - **读取 / 创建**：查询与创建传 `competitionId`；地图四类子资源（`map-node-types`/`path-types`/`map-nodes`/`map-edges`）与 `getFullMap` 同样按 `competitionId` 过滤。
> - **删除作用域校验**：`remove(id, competitionId?)` 统一 `assertSameCompetition`，目标不属于当前比赛时拒绝（400），防跨比赛误删 / 越权。
> - **级联删除警告**：`GET /:id/impact` 返回将被级联删除的子数据条数，前端二次确认。
> - **名称唯一性**：`name` 改为 `(competitionId, name)` 复合唯一，允许不同比赛同名。

> 以下各实体字段表为要点说明；**权威、完整的字段定义以 `prisma/schema.prisma` 为准**（见 §5.3）。

### 5.2 实体字段摘要

**User（账户）**

| 字段                        | 类型       | 约束                   | 说明                                                                                                                                                                                             |
| ------------------------- | -------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| id                        | Int      | PK, 自增               | 主键                                                                                                                                                                                             |
| username                  | String   | 唯一, 非空               | 用户名                                                                                                                                                                                            |
| passwordHash              | String   | 非空                   | 密码哈希（bcrypt）                                                                                                                                                                                   |
| role                      | String   | 非空, 默认 `PLAYER`      | `SUPER_ADMIN` / `COMPETITION_ADMIN` / `PLAYER`（SQLite 无原生 enum，以字符串存储）                                                                                                                         |
| displayName               | String?  | -                    | 显示名称                                                                                                                                                                                           |
| competitionId             | Int?     | FK→Competition, 级联删除 | 该账号可管理的比赛（超管为 null＝全部）                                                                                                                                                                         |
| permissions               | String?  | JSON 数组              | 细粒度权限 key 列表（如 `["data:material:edit","contract:execute"]`）；为 null 时仅按 `role` 继承；`SUPER_ADMIN` 始终隐式拥有全部权限，不受此字段约束                                                                              |
| companyScopes             | String?  | JSON 数组              | 该账号可审核的合同所属公司 id 范围；仅与 `contract:audit` 配合生效（仅审范围内公司合同）；`SUPER_ADMIN`/合同管理员通常不限；空值=不限制                                                                                                         |
| viewCompanyScopes         | String?  | JSON 数组              | 该账号可读取「全量（含未发布）字段」的公司 id 范围；仅与 `company:view` 配合生效（范围外公司只能读已发布到区域总览的公开字段）；`SUPER_ADMIN`/`company:manage`/`data:region:edit` 不受限；空值=不限制。与 `companyScopes` 相互独立                                  |
| contractViewCompanyScopes | String?  | JSON 数组              | 该账号可查看的**合同**的参与方公司 id 范围；仅与 `contract:view` 配合生效（仅能查看「至少有一个参与方公司在范围内」的合同）；`contract:audit`/`contract:execute`/`contract:manage` 不受限；空值=不限制（可见全部合同）。与 `companyScopes`/`viewCompanyScopes` 相互独立 |
| createdAt / updatedAt     | DateTime | 自动                   | 创建/更新时间                                                                                                                                                                                        |

**Material（原料）**

| 字段                        | 类型     | 约束          | 说明                   |
| ------------------------- | ------ | ----------- | -------------------- |
| id                        | Int    | PK, 自增      | 主键                   |
| name                      | String | 唯一, 非空      | 原料名称                 |
| origin                    | String | 非空          | 原料产地                 |
| price                     | Float  | 非空, ≥0      | 原料价格（元/单位）           |
| carbonEmissionCoefficient | Float  | 非空, ≥0      | 碳排放系数（kgCO2e/单位）     |
| type                      | String | 默认 `NORMAL` | `NORMAL` / `SPECIAL` |
| competitionId             | Int?   | -           | 比赛隔离                 |

**Part（零件）**：`id` / `name`(唯一,非空) / `competitionId?`。  
关联表 `PartMaterial`（零件-原料配比：`partId`,`materialId`,`ratio`）、`PartTechRequirement`（零件-科技树需求：`partId`,`techNodeId`）。

**Product（产品）**：`id` / `name`(唯一,非空) / `competitionId?`。  
关联表 `ProductPart`（`productId`,`partId`,`ratio`）、`ProductTechRequirement`（`productId`,`techNodeId`）。

**Map（地图四实体）**

| 实体          | 关键字段                                                                                                                               |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| MapNodeType | `id`,`name`,`description?`,`color?`                                                                                                |
| PathType    | `id`,`name`,`description?`,`color?`                                                                                                |
| MapNode     | `id`,`name`(非空),`region`(非空,所属区域),`nodeTypeId`(FK),`x`(默认0),`y`(默认0)                                                               |
| MapEdge     | `id`,`fromNodeId`(FK),`toNodeId`(FK),`distance`(≥0),`pathTypeId`(FK)；`@@unique([fromNodeId, toNodeId])`，无向边存储时 `fromId < toId` 规范化 |

**Infrastructure（基建，10 项属性）**：`id`,`name`(唯一,非空),`footprint`(≥0),`employmentRateBonus`,`populationBonus`,`highQualityPopulationBonus`,`price`(≥0),`happinessIndexBonus`,`perCapitaIncomeBonus`,`carbonReductionBonus`,`activationPrice`(≥0),`competitionId?`。

**TechNode（科技树）**：`id`,`name`(唯一,非空),`description?`,`tier`(≥0),`researchCost`(默认0),`competitionId?`。关联表 `TechPrerequisite`（`nodeId`,`prerequisiteNodeId`），构成 DAG 前置依赖。

**Fuel（燃料）**：`id`,`name`(唯一,非空),`pricePerLiter`(≥0),`competitionId?`。

### 5.4 产业计算图引擎（可视化蓝图）与产业字段计算

> 旧版「公式引擎（`IndustryField.formula`，mathjs 单行表达式）」已废弃：自本版起，`isCalculated` 字段统一改用**产业计算图**（`IndustryField.calcGraph`，`GGraph` JSON）配置，复用合同可视化编辑器的节点图能力，可组合单种产业类型的**所有字段**完成任意复杂度的计算（含列表 / 字典 / 控制流）。旧的 `formula` 列保留以支持历史数据兼容，新字段不再写入 `formula`，已存的 `formula` 视为无效、需手动在「产业类型管理」中用新计算图重配。

**核心概念**：每个 `isCalculated` 字段对应一张**蓝图节点图**（与合同类型图同源同构的 `GGraph`），图中用「数值源 / 运算 / 控制流」节点把本产业类型的各字段组合运算，最终汇聚到唯一的「输出」节点——其求值结果即该字段的存储值。

**节点类型**（编辑器 `IndustryFieldGraphEditor.vue`，仅 4 类，无合同参与方 / 输入项 / 检查 / 效果）：

| 节点       | 输入端口                                           | 输出端口  | 数据 / 说明                                                                                                                                                                                                                                                                                                    |
| -------- | ---------------------------------------------- | ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `output` | `value`                                        | —     | 图的最终结果 = 本计算字段的值。每张图恰好一个。                                                                                                                                                                                                                                                                                  |
| `value`  | 依 `kind`：`OP` 时为 `OP_ARG_SPECS[op]` 的各参数端口；其余无 | `out` | 数值来源。`kind ∈ FIELD / CONST / FORMULA / OP / VAR / CONSUMER_DEMAND`：  
• `FIELD`：读取本产业类型某字段现值（按 `fieldKey`，无需参与方）  
• `CONST`：字面量（数字 / 字符串 / `[]` / `{}`）  
• `FORMULA`：mathjs 表达式，作用域 = 本产业类型各字段现值（按 `fieldKey`）+ `EXPR_HELPERS`  
• `OP`：列表 / 字典 / 算术 / 比较运算，参数端口可连线或填字面量（`argLiterals`）  
• `VAR`：读取运行期变量（由 `assign` 节点赋值）  
• `CONSUMER_DEMAND`：按「所在地」取区域消费者需求总数（编辑器显示为「消费者需求总数(按所在地)」）。自动读取本产业实例（公司）「所在地」字段对应的地图节点，取该节点所属区域，汇总**本比赛该区域**下全部消费者需求（`ConsumerDemand.quantity`）之和；无需额外参数。所在地为空 / 找不到区域 / 无需求 → 返回 `0`。 |
| `if`     | `cond` / `then` / `else`                       | `out` | **值返回式条件分支**：求 `cond`（布尔），真则返回 `then` 输入端口的值，假则返回 `else` 输入端口的值。`then`/`else` 各连一个数值源节点。                                                                                                                                                                                                                   |
| `assign` | `value`                                        | —     | 中间变量赋值：求 `value` 输入端口的值，存入运行期变量 `data.name`，供图中 `VAR` 节点复用（**不回写任何字段**）。                                                                                                                                                                                                                                   |

- `OP` 运算与合同引擎**完全一致**（33 个 OP，详见 §10.6 的 `OP_ARG_SPECS` / `OP_LABELS_FULL`）：列表（`LIST_APPEND`/`LIST_CONCAT`/`LIST_LEN`/`LIST_SUM_OF`…）、字典（`DICT_MERGE`/`DICT_GET`/`DICT_ADD`/`DICT_APPEND`…）、算术（`ADD`/`SUB`/`MUL`/`DIV`/`EXP`/`LOG`/`MIN`/`MAX`）、布尔比较（`CMP_EQ`/`CMP_NE`/`CMP_GT`/`CMP_LT`/`CMP_GTE`/`CMP_LTE`，返回布尔可连 `if.cond`）。后端统一走 `applyOp(op, args, scope)`。
- `DICTIONARY`：键值字典，`config` 定义 `entries`（`key`/`label`/`defaultValue`）与 `valueType`；`LIST`：列表，`config` 定义 `itemType`（`STRING`/`NUMBER`/`BOOLEAN`）。
- **作用域**：图的求值作用域 = 该公司当前所有产业字段现值（`fieldKey → 已按字段类型解析的值`）。`value` 节点 `FIELD` 直接按 `fieldKey` 取该作用域中的值；`FORMULA` 表达式中可直接写字段 `fieldKey` 作变量名（如 `revenue - cost`、`tax = revenue * 0.13`）。
- **`CONSUMER_DEMAND` 的区域映射（易错点）**：该数据源依赖一个「区域上下文」`ctx = { competitionId, locationNodeName }`，由级联重算时按公司所属比赛与「所在地」字段现值得知。`所在地`字段以 **JSON 编码字符串**存储地图节点名（如 `"B区节点"`），读取须 `JSON.parse` 还原；随后查 `MapNode.name = 所在地名` 得到其 `region`（区域名），再按 `region` 汇总 `ConsumerDemand.quantity`。为兼容两种数据约定（`ConsumerDemand.region` 既可能是 `MapNode.region`，也可能是节点名本身），匹配条件为 `region IN (节点 region, 节点名)` 且 `competitionId` 收敛到本比赛。若产业类型未定义 `location` 字段或所在地为空，该节点恒返回 `0`。

**编辑界面（全屏蓝图编辑器）**：在「产业类型管理 → 字段」中，点击计算字段的「编辑蓝图」即进入全屏蓝图编辑器——屏幕左上角为「字段细节」面板（字段名称 / 字段键 / 类型 / 默认值 / 排序 / 前台展示 / 是否计算字段），右侧主区为可视化蓝图画布（`IndustryFieldGraphEditor.vue`，含节点库 / 画布 / 属性面板）。保存或关闭后写回字段；未配置图时可从字段对话框点「打开全屏蓝图编辑器」进入。非计算字段仍走原内联编辑表单。

**计算时机 — 写入时级联重算**：

- 公司管理界面通过 `PUT /company-fields` 写入（或修改）任一普通字段后，服务端**同步级联重算**该公司所属产业类型的**全部** `isCalculated` 字段：解析每个计算图的 `FIELD` 依赖 → 在「计算字段之间」按依赖拓扑排序（检测循环依赖，环内字段跳过并报错）→ 按序求值并写回各自的 `CompanyFieldValue`。
- 因采用拓扑排序且每算完一个即用新值刷新作用域，计算字段之间的**传递依赖**（A 依赖 B，B 又依赖普通字段）也能正确重算；读取时直接取存储值，无需实时计算。
- 仅写本字段：每张图的最终输出 = 该图所属字段自身；图内 `assign` 仅产生运行期中间变量，不会改写其它字段。
- 公司字段初始化：创建公司时自动复制产业类型的所有字段默认值到 `CompanyFieldValue`；随后即对 `isCalculated` 字段跑一次级联重算，得到首值。

**旧公式迁移**：存量 `isCalculated` 字段若仍持有 `formula` 而无 `calcGraph`，旧公式引擎不再参与读写；需在「产业类型管理」打开该字段、用新计算图重新配置并保存（保存时 `calcGraph` 写入、`formula` 清空）。

## 6. 认证与权限模型

### 6.1 认证流程（JWT）

1. 客户端发送 `POST /api/auth/login`（username + password）
2. 服务端校验密码（bcrypt.compare），签发 JWT（有效期 24h，payload 含 `sub/username/role/tv`(tokenVersion)/`permissions/companyScopes/viewCompanyScopes/contractViewCompanyScopes`，详见 §6.4）
3. 客户端存储 JWT（Electron 本地安全存储），后续请求携带 `Authorization: Bearer <token>`
4. 服务端 `JwtAuthGuard` 校验令牌，将 User 信息注入请求上下文
5. 需要写操作的路由再经 `PermissionsGuard` 按 `@RequirePermissions(...)` 校验细粒度权限

### 6.2 细粒度 RBAC（permissions 数组）

- 鉴权由 `User.permissions`（JSON 数组）中的**权限 key** 决定，不再仅靠 `role`。守卫为 `PermissionsGuard` + `@RequirePermissions("domain:action")`。
- `SUPER_ADMIN` 隐式拥有全部权限，始终放行；其余角色按 `hasPermission(role, permissions, required)` 校验：
  - **精确匹配**：`permissions` 中含所需 key 即放行。
  - **同域动作蕴含（manage ⊇ edit ⊇ view）**：`required` 为 `domain:view` 时，持有该域任意能力（view/edit/manage/execute/audit 等）即视为可读；`required` 为 `domain:edit` 时，持有 `domain:manage` 即放行。`manage`/`execute`/`audit` 等需精确持有，不做向下蕴含。该规则保证「给某域写/管理权限者天然可读」，给读接口统一加 `view` 守卫时不会令既有的 `edit`/`manage` 授权失效。
- **读权限统一策略**：所有业务数据的 `GET`（列表 / 详情 / 级联影响）均在控制器类级 `@RequirePermissions("domain:view")` 守卫下——读接口继承类级 `view`，写接口（`@Post/@Patch/@Delete`）已有 `edit`/`manage` 覆盖（方法级 `@RequirePermissions` 优先于类级）。即「读 = 有 view（或同域更强权限），写 = 有 edit/manage」。各数据域的 `view` 与 `edit` 权限 key 一一对应（如 `data:material:view`/`data:material:edit`）；`industryType`/`contractType` 亦补齐 `:view`。
- **例外（读接口对全部已登录开放）**：
  - `GET /api/competitions`（列表 / 详情 / 财年）保持仅 `JwtAuthGuard`：比赛列表 / 选择是所有已登录角色都需要的入口，不单独设 view。
  - `GET /api/company-fields/:companyId` 走自定义发布 + 公司可见字段范围（viewCompanyScopes）逻辑（见 §9.9）：已发布到区域总览的字段对任何已登录用户公开；未发布字段对 `SUPER_ADMIN`/`company:manage`/`data:region:edit` 恒可见，对仅持 `company:view` 者仅在其 `viewCompanyScopes` 范围内公司可见，范围外公司只能读已发布字段。
- `dashboard:view` / `settings:view`/`settings:manage` 仅作用于前端菜单可见性（后端无对应数据接口）。
- 权限 key 形如 `domain:action`。常用 key：
  - `competition:manage`

- `User.contractViewCompanyScopes`（JSON 数组，公司 id 列表）用于把账号限制到「仅可查看参与方是这些公司的合同」——配合 `contract:view` 生效：合同只要存在**任一参与方公司**落在 `contractViewCompanyScopes` 内即对该账号可见（按参与方公司匹配，而非按合同归属公司）。`contract:audit`/`contract:execute`/`contract:manage`（更高权限）始终不受 `contractViewCompanyScopes` 约束，可见全部合同；仅持纯 `contract:view` 的角色才受此范围约束。`contractViewCompanyScopes` 为空（null 或 `[]`）与「未配置范围」等价——即不施加任何合同查看限制（可见全部合同）。三项范围（`companyScopes` 审核范围 / `viewCompanyScopes` 字段读范围 / `contractViewCompanyScopes` 合同查看范围）相互独立，账号管理页分别由**三个**多选框配置。
- `User.stockCompanyScopes`（JSON 数组，公司 id 列表）用于把**股票系统「低级管理」（`stock:edit`）**&#x8D26;号限制到「仅可管理这些公司的资金账户 + 自己的用户资金账户」——配合 `stock:edit` 生效：低级管理在「股票管理」界面只能看到 / 操作 `stockCompanyScopes` 内公司的资金账户，以及 `ownerType=USER && userId=自己` 的用户账户；其余公司账户与他人的账户不可见、不可操作。`stock:manage`（高级管理）/`SUPER_ADMIN` 不受 `stockCompanyScopes` 约束，可见并管理全部资金账户，且可增删股票、推进轮次。`stockCompanyScopes` 为空（null 或 `[]`）与「未配置范围」等价——即不施加任何公司级限制。账号管理页由独立的「股票管理范围」多选框配置。

### 6.4 单设备登录互斥（tokenVersion）

为防止同一账号在多处同时登录造成的数据竞争与越权操作，系统实现「单设备登录」：同一账号在一台新设备登录后，旧设备的会话立即失效（被踢出）。

**数据真源**：`User.tokenVersion`（库内会话版本号，整数，默认 0）。

**机制流程**：

1. **登录自增**：`AuthService.login` 在密码校验通过后，对 `User.tokenVersion` 执行 `increment: 1`，并将新值写入 JWT 载荷 `tv`（`payload.tv = updatedUser.tokenVersion`）。
2. **校验比对**：`JwtStrategy.validate` 在每次请求解析令牌时，比对 `payload.tv` 与库内当前 `User.tokenVersion`：
   - `typeof payload.tv === "number" && payload.tv !== u.tokenVersion` → 抛出 `UnauthorizedException("您的账号已在其他设备登录，请重新登录")`，该请求被拒，前端触发登出（见下）。
   - `payload.tv` 为 `undefined`（部署新机制前签发的旧 token 无此字段）→ 为兼容存量会话，**暂不踢出**（仅当存在明确版本号且不一致才判失效）。
3. **踢出表现**：客户端请求拦截器在收到非登录请求的 `401` 时，优先采用后端返回的中文消息——若后端明确返回「您的账号已在其他设备登录，请重新登录」，前端即弹该提示并清除本地 token / 缓存、跳回登录页；其余 `401`（token 过期、用户被删，后端返回通用「Unauthorized」）回退提示「登录已过期，请重新登录」。

**管理端注意**：

- 每次登录都会使旧 token 失效；若管理员在 A 设备登录后又在 B 设备登录，A 设备的下一次请求即被拒并登出。
- `tokenVersion` 仅随**登录动作**自增，修改密码（`changePassword`）不会自增，故改密后旧 token 仍可用直至自然过期或被新登录顶掉。
- 该机制对 `SUPER_ADMIN` 同样生效（无角色豁免）。

### 7.2 日志系统与操作溯源

采用 **winston + nest-winston**，四级：`error / warn / info / debug`。

| 类别   | 内容                                                                          | 级别    |
| ---- | --------------------------------------------------------------------------- | ----- |
| 请求日志 | 每个 HTTP 请求的方法、路径、状态码、耗时、请求/回应包大小（`requestBodySize` / `responseBodySize`，字节） | info  |
| 操作日志 | 数据增删改（谁、改了什么）                                                               | info  |
| 错误日志 | 未捕获异常、数据库错误、认证失败                                                            | error |
| 运行日志 | 服务启动/停止、定时任务                                                                | info  |

- **输出**：控制台彩色格式（开发用）；文件按日轮转、保留 30 天 —— `logs/app-YYYY-MM-DD.log`（info+warn）、`logs/error-YYYY-MM-DD.log`（error），格式为 JSON 行。
- **操作溯源**：每条日志自动带 `operator`（id/用户名/角色）、`requestId`、`ip`。
  - 上下文经 `AsyncLocalStorage` 注入：中间件在最前置阶段解析 JWT 得到操作员，用 `als.run` 包裹整条下游管线（拦截器因 RxJS 懒执行无法传播上下文，故用中间件而非拦截器）。
  - 单条写操作（`create/update/delete` 等）由 `PrismaService` 的 `$use` 审计中间件记录前后值：`create/upsert` 记新记录，`update` 记 `before/after/changes`，`delete` 记被删记录，`*Many` 记数量与脱敏 data/where。
  - 登录成功 / 失败（守卫前无 `request.user`）单独记用户名，便于安全溯源。
- **脱敏**：所有落盘的结构化数据（审计前后值、请求体）经 `sanitize` 处理 —— 密码 / 令牌 / 密钥等键名置 `***(已脱敏)`，长字符串截断、深对象与超大数组限长，敏感信息不进日志文件。
- 按 `operator.username`、`audit:true`、`ip` 即可回溯「谁、从哪、改了哪条数据、改前改后」。

### 7.3 通用拦截器与过滤器

- **ResponseInterceptor**：统一成功响应格式 `{ code: 0, message: "成功", data: T }`（`message` 固定为中文「成功」，不携带业务语义；service 返回 `undefined/null` 时 `data` 为 `null`）。
- **HttpExceptionFilter**：`@Catch()` 捕获一切异常，统一错误响应 `{ code: <HTTP 状态码>, message: <中文错误信息>, data: null }`。要点：
  - 失败响应的 `code` 等于 **HTTP 状态码本身**（400/401/403/404/409/500），并非自定义业务码。
  - 5xx 异常的真实原因**只写 Winston 日志，不向客户端透出**，统一返回 `服务器内部错误`。
  - `class-validator` 的字段级错误数组被折叠为一句 `请输入有效数据`，客户端拿不到具体字段名。
  - 非 `HttpException` 的原生 Error（含 Prisma 唯一约束 `P2002`）不会被转换，仅记日志并以 500 返回。
- **ValidationPipe**：全局启用 `class-validator`，配置 `whitelist + forbidNonWhitelisted + transform`——传入未声明字段会直接拒绝（400）。

### 8.5 API 封装层与本地缓存（IndexedDB）

`request.ts` 创建 Axios 实例，所有 `*Api` 复用，统一处理：

- **请求拦截器**：注入 `Authorization` 头、拼接 `baseURL`
- **响应拦截器**：解包 `{ code, message, data }`，`code≠0` 抛出业务错误
- **401 处理**：令牌过期清空本地令牌与缓存并跳转登录页
- **错误提示**：网络 / 服务器错误统一 `ElMessage` 中文提示

**客户端本地缓存（IndexedDB）**：GET 结果持久化到 IndexedDB，减少重复请求、减轻服务器压力：

- **始终回源 + 离线降级**：GET 一律请求服务器，成功写回缓存；仅当请求失败（网络错误 / 服务端不可达）时回退本地缓存，保证离线可用；404/410 不降级（资源确已删除直接抛错）
- **并发去重**：同一 GET 进行中时复用其 Promise，避免同刻重复请求
- **写失效**：POST/PUT/PATCH/DELETE 成功后按资源分组（URL 首段）失效本地全量副本与基线，保证下次读取走全量同步拿到最新
- **增量查询（网络层，真正降低服务器压力）**：每个「资源集合」（资源名 + 非分页查询参数唯一标识）在本地维护一份**全量副本**。列表刷新时若本地已有全量副本，则携带 `updatedAfter=<基线时间>` 走增量请求，仅取回「`updatedAt` 晚于基线的变更条目」（`patchFullItems` 合并）。**基线过期（默认 5 分钟）不再整表重拉**：改为增量请求并显式带 `requireExistingIds=true`，用服务端回传的 `existingIds`（满足过滤条件的全部 id）diff 出被删除的本地副本并移除；仅在首次 / 写失效 / 401 清缓存（本地无副本）时才走「全量同步」（大 pageSize 一次取回）。离线时以本地全量副本构造响应降级。非列表形态（详情 GET）不做全量副本，仅按原请求键缓存以离线降级。
- **服务端按需计算 `existingIds`（O1）**：`existingIds` 是增量对账的成本项（每请求一次全量 id 扫描 + 大响应体）。服务端现已默认**不下发** `existingIds`（返回空数组），仅当客户端显式传 `requireExistingIds=true`（周期对账 / 断线重连对账）时才计算。新鲜窗口内的增量请求不携带它——删除由实时事件（`removeFullItemByResource` 精确移除）处理，无需全量核对，从而把「每增量请求 2 次 DB 查询 + 巨型响应」降为「1 次变更查询」。
- **跨挂载新鲜度窗口（O3）**：`_cachedGet` 按请求键在内存缓存最近一次成功响应；窗口内（默认 15s）且该资源期间无实时事件时直接返回内存副本，不打网络（含后台增量请求）。任意实时变更（`bumpResourceEvent`）立即使该资源的 memo 失效，写失效 / 401 也会清空全部 memo，保证及时刷新。
- **实时重拉去抖（O4）**：`resource-changed.ts` 对同一资源的多次实时事件做 ≈400ms 去抖后再广播 `window` 事件，避免「批量创建 / 更新」触发一连串组件重拉（每次重拉都打后台增量请求）；删除仍立即精确移除本地副本。
- **跳过与降级**：`AbortController`(`signal`) 或 `config.cache=false` 跳过缓存；IndexedDB 不可用时自动走网络

实现见 `client/src/api/cache.ts`（`cacheGet`/`cacheSet`/`invalidateResource`/`clearCurrentAccountCache`/`getFull`/`setFull`/`getBaseline`/`setBaseline`/`getFullSyncAt`/`setFullSyncAt`/`patchFullItems`/`removeFullItemByResource`/`extractItems`/`inferShape`）与 `client/src/api/request.ts` 的 `_cachedGet`/`cachedGetImpl`/`syncMapFull`（复合地图 `/maps/full` 拆成 nodes/edges/nodeTypes/pathTypes 四个本地全量副本做增量同步）。

#### 8.5.2 本地存储按账号隔离

同一浏览器 / 机器上可能有多个账号交替使用（如超管为不同玩家代操作、或同一台展示机轮换登录）。若不隔离，账号 A 的 `currentCompetition`、已读公告版本、以及 IndexedDB 全量副本会残留并被账号 B 读到，历史上曾导致「玩家账号之间缓存键如 `competitionId=3` 残留 → 账号 B 以 A 的比赛 id 发请求 → 403 串味」。

隔离方案（`client/src/utils/accountStorage.ts` 为唯一真源）：

- **账号级 localStorage 键统一加前缀 `acct_u<id>__`**：覆盖 `token` / `currentCompetition` / `announcementSeenVersion` 三类账号级键；`activeUserId` 为全局指针（同时持久化于 `localStorage["activeUserId"]`），决定当前命名空间。机器级配置（`serverUrl` 等）保持全局、不加前缀。
- **IndexedDB 按账号分库**：库名 `gipfel-client-cache-u<id>`（未登录用 `-anon` 匿名库），`cache.ts` 的 `openDB()` 在 `activeUserId` 变化时丢弃旧连接、按当前账号重新开库，使不同账号的全量副本 / 增量基线物理隔离。
- **登出不清空账号数据**：`logout()` 仅移除本账号的 `token`，保留该账号其余已持久化数据（含 IndexedDB 库），下次登录同一账号可恢复；是否真的「已登录」由「账号命名空间下是否存在 token」决定，`competition.loadFromStorage` 据此守卫，避免登出态残留比赛。
- **升级迁移**：`main.ts` 在 `app.mount` 前调用 `ensureStorageMigration()`，把升级前写在顶层（`localStorage["token"]` 等）的旧键按 JWT `sub` 解码出的用户 id 搬入账号命名空间，并删除遗留的共享库 `gipfel-client-cache`，未显式登出的老用户可无缝保持登录态。
- **清空本地缓存（设置页）**：仅清当前账号的 IndexedDB 库与「当前比赛选择」，不触碰 token（保持登录）也不影响其他账号。

> 历史代码中曾存在三套 HTTP 层，现已**全部收敛到 `client/src/api/request.ts` 的 `api`**。新增请求请统一 `import api from "@/api/request"` 或使用 `client/src/api/index.ts` 中的 `*Api` 封装，不要新建 axios 实例。客户端默认地址常量集中在 `client/src/config/index.ts` 的 `DEFAULT_SERVER_URL`（`http://localhost:3000`），被多文件共用。

#### 8.5.1 实时数据同步（WebSocket 推送，覆盖增 / 删 / 改）

缓存增量同步解决了「下次刷新时剔除已删除项」，但仍是**被动拉取**——别人（如超管）创建 / 修改 / 删除的数据，当前界面要等到你主动刷新才变化。为此新增**实时变更推送**，让任意写操作「及时」反映到所有同比赛客户端。

**链路**：

1. **后端广播**：`PrismaService` 的审计中间件（`registerAuditMiddleware`）在每次写操作成功后，通过 `RealtimeService.emitResourceChanged(resource, id, competitionId, action)` 广播统一的 `resource:changed` 事件，`action` 取值随写类型而定：
   - `create` / `upsert` → `action="created"`（新增）
   - `update` → `action="updated"`（更新）
   - `delete` → `action="deleted"`（删除）
   - `createMany` / `updateMany` / `deleteMany` → `action="bulk"`（批量写，无单条 id，前端整资源失效）
   - `resource` 由 `MODEL_TO_RESOURCE`（Prisma model 名 → URL 首段，如 `Material→materials`、`TechNode→tech-nodes`）映射；不在表中的内部表不触发。
   - `competitionId` 解析优先级：`before.competitionId`（改前记录）> `result.competitionId`（改后记录）；有比赛归属 → 仅向 `comp-{cid}` 房间广播（租户隔离）；全局模板（合同类型 / 产业类型 / 比赛本身）或批量操作无法定位单条归属时 `competitionId` 为 `null` → 向全体广播。
   - 复用现有 `RealtimeService`（`server.to(房间).emit`），与 `fiscal-year:changed` / `competition:changed` 同源同端口，无需新建通道。
2. **前端监听**：`client/src/realtime/resource-changed.ts` 的 `bindResourceChanged()`（在 `stores/competition.ts` 的 `bindRealtime()` 中注册）收到 `resource:changed` 后：
   - **删除**（`action="deleted"`）：调用 `removeFullItemByResource(resource, id)` 精确从本地全量副本中移除该条目，避免触发整表重拉；删除也会在 5 分钟增量对账（带 `existingIds`）或断线重连对账时被再次确认。
   - **创建 / 更新 / 批量变更**：**不再作废本地全量副本**（保留它，使随后组件重拉走「增量模式」仅取变更数据），直接派发 `window` 自定义事件 `resource-changed` 触发组件自动重拉。
   - 组件重拉均经 `cachedApi` → 增量模式（见 §8.5），仅取回变更行，进一步降低服务器压力。
3. **组件刷新**：列表组件在 `setup` 中调用组合式函数 `useResourceChanged("<resource>", 重载函数)`（`client/src/realtime/useResourceChanged.ts`），收到匹配 `resource` 的任意变更事件（增 / 删 / 改）时自动重拉本列表。`onUnmounted` 自动移除监听，无泄漏。
   - 已接入：`MaterialsManager`/`PartsManager`/`ProductsManager`/`WarehousesManager`/`VehiclesManager`/`TechTreeManager`/`ProductionLinesManager`/`MapsManager`(map-nodes+map-edges)/`ContractManageView`(contracts)/`ContractTypeManageView`(contract-types)/`IndustryTypeManageView`(industry-types)/`CompanyListView`(companies)/`AccountManagementView`(users)/`CompetitionListView`(competitions)。

**设计要点**：

- **零遗漏**：广播点统一在 Prisma 中间件，所有经 REST 增删改的实体自动覆盖，无需逐个 service 加代码。
- **幂等无副作用**：自己写时已有「写失效 + 重拉」，实时推送到达后只是再作废一次缓存、重拉一次，不会重复打扰；`bulk` 批量写仅整资源失效一次。
- **与增量查询互补**：推送只负责「更快地触发一次拉取」，拉取内部仍走 §8.5 的增量查询（仅取回变更条目）；即使推送短暂丢失（如断线重连窗口），下次手动刷新也会通过增量对账（5 分钟增量 + existingIds 核对，或断线重连对账）补上变更。
- **断线重连主动对账**：WebSocket 重连成功后（`resource-changed.ts` 监听 `connect` 事件），客户端自动对当前已加载的本地全量副本各发一次增量请求（带各自基线，**显式 `requireExistingIds=true`**，因服务端默认不再下发 `existingIds`），用服务端回传的 `existingIds` 立即清理「断线 / 实时事件丢失期间」被删除的条目，无需等用户手动刷新或 5 分钟强制全量周期。仅对已有基线的集合生效（首次进入尚无副本的集合无脏数据，自动跳过）。实现见 `client/src/api/request.ts` 的 `reconcileAllIncremental` 与 `client/src/api/cache.ts` 的 `listFullCollections` / `listMapSyncKeys`。
- **事件名演进**：早期仅广播删除（`resource:deleted`），后统一升级为 `resource:changed` 并携带 `action`，旧的事件名与 `useResourceDeleted` / `bindResourceDeleted` 已废弃移除。

#### 8.5.2 后端增量查询接口约定（降低服务器压力）

所有列表类接口均支持可选查询参数 `?updatedAfter=<ISO8601>`：

- **不传 `updatedAfter`**（或值非法）：保持原行为——分页接口返回 `{ items, total, page, pageSize }`，非分页接口返回裸数组，复合地图 `/maps/full` 返回 `{ nodes, edges, nodeTypes, pathTypes }`。客户端据此建立本地全量副本。
- **传 `updatedAfter`**（合法 ISO 时间）：进入**增量模式**——服务端忽略分页（`skip/take`），仅返回「`updatedAt` 晚于该基线」的变更条目；**默认不再额外返回 `existingIds`**，以减轻每请求一次全量 id 扫描 + 大响应体的开销。仅当客户端**同时传 `requireExistingIds=true`** 时，才一并返回满足基础过滤条件（如 `competitionId`）的**全部 id 集合 `existingIds`**，供周期 / 重连对账 diff 出被删除的本地副本（新鲜窗口内的普通增量请求不传它，删除由实时事件精确处理）。响应形态：
  - 分页 / 裸数组接口：`{ items, total, existingIds: number[], serverTime: string, incremental: true }`（`existingIds` 仅在 `requireExistingIds=true` 时非空）  
    （`total` 为变更条目数；`serverTime` 为服务端当前时间，客户端作为下一次同步基线，避免增量间隙漏推）
  - 复合地图 `/maps/full`：`{ nodes, edges, nodeTypes, pathTypes, existingIds: { nodes, edges, nodeTypes, pathTypes }, serverTime, incremental: true }`（`existingIds` 各子键同理按需返回）
- **统一工具**：`server/src/common/sync.ts` 的 `applyUpdatedAfter(baseWhere, updatedAfter)`（构造 `updatedAt: { gt: 基线 }` 过滤）与 `buildIncrementalResult(changedItems, existingIds)`（包装增量响应）。各 service 的 `findAll` 在增量分支默认用 `baseWhere` 查空 `existingIds`；仅当 `requireExistingIds` 为真时才用 `baseWhere` 额外查全量 id 集合，用 `where`（带时间过滤）查变更集。
- **已覆盖模块**：materials / parts / products / companies / warehouses / production-lines / vehicles / infrastructures / fuels / competitions / industry-types / contract-types / contracts / users / tech-nodes / map-nodes / map-edges / map-node-types / path-types / maps(`/maps/full`) / **company-fields**(`/company-fields/:companyId`，派生集合，按 `companyId` 维护本地全量副本，见下方说明)。`contracts` 的 `existingIds` 在「公司范围过滤（`companyScopes`）」之后计算，保证审计范围受限账号的增量对账正确。
- **前端消费**：`client/src/api/request.ts` 的 `_cachedGet` 在本地有全量副本时一律带 `updatedAfter` 增量请求并 `patchFullItems`（窗口内且无实时事件时直接返回内存 memo）；基线过期时额外带 `requireExistingIds=true` 做删除核对；仅首次 / 写失效 / 401 清缓存（无副本）才大 pageSize 全量同步；离线用本地全量副本降级。

#### 地图背景图（每比赛一张）

管理端（持有 `data:map:edit` 权限）可在「地图管理」工具栏点击「导入背景」上传一张图片，作为整张地图编辑器的背景图层；「清除背景」可移除。

- **粒度**：每比赛一张，与节点/边的坐标相互独立——上传或清除背景不会改变任何节点的 `x/y` 或边的数据。
- **存储**：图片落盘至服务端 `uploads/map-backgrounds/`（不入库，`.gitignore` 已忽略）；`Competition.mapBackground` 仅保存 `{ url, filename, width, height }` 的 JSON 元信息。
- **渲染**：背景置于最底层图层（`<v-layer listening=false>`），覆盖节点包围盒 + `160px` 留白，随画布平移/缩放，且不拦截任何鼠标交互（不影响节点拖拽/连线/选中）。
- **权限与隔离**：上传/清除走 `POST|DELETE /api/files/map-background`，标记 `@NoCompetitionScope`；服务端 `FilesService.resolveTarget` 按角色强制收敛——超管须显式传 `competitionId`，归属账号（`competitionId` 非空）仅能操作自身比赛，杜绝越权写他人比赛背景；查看走 `GET /api/files/map-background`（仅 JWT 守卫）。
- **实时同步**：背景变更经 `RealtimeService.broadcastToCompetition(cid, "competition:changed", updated)` 广播，所有同比赛前端（含其他标签页）立即刷新背景图层。
- **格式/大小限制**：仅 PNG / JPEG / GIF / WebP / BMP，单文件 ≤ 15MB（由 `FileInterceptor` 的 `fileFilter` 与 `limits.fileSize` 校验）。

**背景编辑模式（位置与缩放）**：工具栏在已设置背景后显示「背景编辑」按钮，点击进入编辑态：

- **移动**：背景图层开启 `listening` 且 `draggable`，可直接拖拽背景图改变其在画布中的世界坐标位置（与节点同坐标系）；拖拽结束自动持久化。
- **缩放**：画布左下角浮动面板提供缩放滑块（`10%–500%`），实时预览并保存；也可一键「重置位置/缩放」回到按节点包围盒自动适配。
- **持久化**：变换以 `{ x, y, scale }` 写入 `Competition.mapBackground` 的 `transform` 字段（服务端 `PATCH /api/files/map-background/transform`，需 `data:map:edit`）；`transform` 为 `null` 时前端按节点包围盒自动适配。变更同样广播 `competition:changed`，跨端实时同步。
- **交互隔离**：编辑态下点击背景图不会触发画布平移（平移仅在点击空白时触发），也不会因为背景图层置于底层而遮挡节点的拖拽/选中（节点图层在其之上）。

### 8.9 版本一致性硬封锁（启动门禁）

**目的**：客户端与服务端必须版本一致，否则禁止任何功能与网络请求，强制用户获取最新版本，避免「新旧客户端混连同一服务端」导致的数据/行为错乱。

**双版本真源**：

| 来源    | 取值位置                                                                                                                                                               | 回退                                |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------- |
| 客户端版本 | Electron 运行时 `app.getVersion()`（取自 `client/package.json` 的 `version`），经 `preload.electronAPI.getAppVersion` 暴露；非 Electron 环境回退常量 `CLIENT_VERSION_FALLBACK="1.0.0"` | `1.0.0`                           |
| 服务端版本 | `GET /api/version`（`@Public()` 免鉴权，响应体 `{ code:0, data:{ version } }`），读取 `server/package.json` 的 `version`                                                        | `SERVER_VERSION_FALLBACK="1.0.0"` |

> 发版由 `tools/updater/release-core.mjs` 的 `runRelease` 统一改写两处 `package.json` 的 `version`，确保二者天然相等；不一致只会出现在「服务端已升级、客户端尚未更新」或反之的过渡期。

**硬封锁语义（不同即锁）**：

- 触发条件：`serverVersion !== clientVersion`（**任一方向不一致都锁**，不再区分谁新谁旧，也不提供「不再提示」）。
- 被锁后：
  1. 全局标志 `versionBlocked`（独立模块 `client/src/version-block.ts` 导出的 `ref`，作为请求拦截器与实时连接的唯一真源，专门规避 `request.ts` ⇄ `stores/version.ts` 的循环依赖）置 `true`；
  2. **请求拦截器**（`api.interceptors.request`）在发出网络前检查：若 `versionBlocked` 且请求未带 `bypassVersionBlock`，直接 `Promise.reject` 并不发任何网络——实现「无法发出任何请求」；
  3. **实时通道**（`realtime/socket.ts` 的 `connectRealtime`）在 `versionBlocked` 时返回 `null` 并断开已有连接——锁定期间无任何后台 WebSocket；
  4. 前端弹出**不可关闭**的提示层 `VersionUpdateDialog.vue`（无关闭按钮、禁 ESC、禁点遮罩），文案「客户端版本与服务端不一致……请联系管理员获取最新版本」，并明确告知「已锁定全部功能并停止一切网络请求」。
- 版本恢复一致（`serverVersion === clientVersion`）时自动解除封锁：`versionBlocked=false`、关闭提示层、实时重连、功能恢复。

**启动门禁与周期复核**：

- `App.vue` `onMounted` 先 `await versionStore.checkVersion()`，仅在**未封锁**时才 `announcementStore.maybeOpen()`（锁定期间不弹公告）；
- 启动后每 5 分钟周期调用 `checkVersion()` 复核，应对「运行中服务端升级导致版本不一致」或「版本恢复一致后自动解锁」；版本校验请求自身携带 `bypassVersionBlock:true`，确保被锁时仍能打 `/api/version` 完成复核。

**容错**：`checkVersion` 的网络/服务端异常**不触发封锁**（避免服务端临时不可达把客户端锁死），也不弹提示，等下次复核再试。

**关键文件**：`client/src/version-block.ts`、`client/src/stores/version.ts`、`client/src/api/request.ts`（请求拦截器）、`client/src/realtime/socket.ts`、`client/src/components/VersionUpdateDialog.vue`、`client/src/App.vue`、`server/src/version.controller.ts`。

### 8.10 更新公告（Announcement）

系统在每次启动（或发版）后，向用户弹出「更新公告」，告知近期变更；用户确认后不再自动弹出，直至出现更高版本（新公告）。

**数据源**：`client/src/data/announcement.ts` 维护一个**按版本倒序**的 `announcements` 数组（最新在最前）。发版时在数组**最前面**插入一条新公告；`currentAnnouncement` 恒指向首条（最新），作为「是否已读」的锚点。正文 `content` 通过 `v-html` 渲染，仅由开发者维护（受信任内容），**切勿渲染任何来自用户或服务端不可信的 HTML**，避免 XSS。

**已读锚点**：`localStorage["announcementSeenVersion"]` 记录用户已确认读过的最高公告 `version`。

**触发与行为**：

- **首启弹出**：`App.vue` 启动门禁中，在版本硬封锁检查通过（`!versionBlocked`）后调用 `announcementStore.maybeOpen()`——仅当 `seenVersion !== currentAnnouncement.version`（该版本未读过）时 `visible=true` 弹窗。
- **不可绕关**：`AnnouncementDialog.vue` 设 `:show-close="false"`、`:close-on-click-modal="false"`、`:close-on-press-escape="false"`，且监听 `update:model-value` 阻止任何非「确认」的关闭；唯一关闭入口为底部「不再显示」按钮，点击即 `confirm()`（写入已读锚点并关闭）。
- **历史查看**：`AnnouncementHistoryDialog.vue` 列出 `announcements` 全量历史更新记录（倒序），由「系统设置 → 关于」中「查看更新记录」打开；`SettingsView.vue` 提供入口。`openFromSettings()` 直接打开当前公告（不自动标记已读），`markSeen()` 可显式「标记为已读」使其不再自动弹出（仍保留打开查看能力）。

**与版本硬封锁的协作**：公告弹出发生在版本一致性检查**之后**，故被版本锁定的客户端不会弹出公告（先锁后公告）；公告与版本提示是两套独立机制——版本锁是「强制禁用」硬阻断，公告是「温和告知」软提示。

## 9. 业务模块说明

各模块服务端为 NestJS 标准 CRUD 同构，客户端为对应 Manager 页面。关键文件与要点如下。

### 9.1 比赛与财年（competitions）

- **服务端**：`src/modules/competitions/competition.controller.ts`、`competition.service.ts`、`dto/competition.dto.ts`
- **客户端**：`CompetitionListView.vue`、`stores/competition.ts`
- `Competition` 是**租户根**：删除比赛会级联删除其下全部关联数据（用户除外）。
- 财年接口：`GET/POST /competitions/:id/fiscal-years`、`PATCH/DELETE /competitions/fiscal-years/:fyId`。**写接口 body 为内联类型，未走 ValidationPipe 校验**。
- 客户端 `stores/competition.ts` 在选择比赛时异步拉取当前进行中财年；`localStorage` 持久化当前比赛；财年变更经 WebSocket 实时广播即时同步（前端直接依据广播 payload 更新，无需回源请求）。

### 9.2 生产链：原料 / 零件 / 产品（materials / parts / products）

- 数据关联：`Material →(PartMaterial 配比)→ Part →(ProductPart 配比)→ Product`；零件/产品均通过 `*TechRequirement` 关联科技树节点。
- 创建零件/产品时 `partMaterials`/`productParts` 为带 `ratio` 的数组（配比），`techRequirements` 为科技节点 id 数组；DTO 使用 `@ValidateNested` + `@Type` 校验嵌套数组。
- **扩展**：新增生产链实体 → 仿照 `parts` 建立模型、连接表（`@@id([aId,bId])`）与三件套文件，并在 DTO 中声明嵌套数组。

### 9.3 科技树（tech-tree）

- `TechNode` 通过 `TechPrerequisite`（`NodePrerequisites`/`NodeRequiredBy` 双命名关系）自引用，构成 **DAG 前置依赖**。
- 创建节点可带 `prerequisites: [{ prerequisiteNodeId }]`。前端用 ECharts 渲染树状/层级结构。

### 9.4 地图（maps）

- 服务端 `src/modules/maps/` 含 **1 个 service + 5 个 controller**：`MapController`(`/maps`，`GET /maps/full` 返回 `{nodes,edges,nodeTypes,pathTypes}` 聚合图)、`MapNodeTypeController`(`/map-node-types`)、`PathTypeController`(`/path-types`)、`MapNodeController`(`/map-nodes`)、`MapEdgeController`(`/map-edges`)。
- 客户端：`MapsManager.vue`（vue-konva 画布编辑）。
- **限制**：地图 4 个子控制器（node-types/path-types/nodes/edges）目前**不支持 `competitionId` 过滤**，但 Prisma 模型含该字段。
- `MapEdge` 有 `@@unique([fromNodeId, toNodeId])`，反向边需单独创建。

### 9.5 燃料与载具（fuels / vehicles）

- `Fuel` 定义单价；`Vehicle` 关联 `fuelId`（消耗燃料）、`pathTypeIds`/`vehiclePathTypes`（可通过的路径类型）。
- 载具两种路径类型入参表达并存，`vehiclePathTypes`（`[{pathTypeId}]`）为权威结构，service 内部归一。
- `Vehicle.fuel` 关系无 `onDelete`（默认 Restrict），删除燃料前需先解绑载具。

### 9.6 仓库与生产线（warehouses / production-lines）

- 这两个模块的 `findAll` **不分页**，直接返回数组（Query 仅支持 `competitionId`）。
- `Warehouse.type` 取值 `MATERIAL/PART/PRODUCT/FUEL`；`ProductionLine.laborCount` 为 int 且 ≥1。

### 9.7 基建（infrastructures）

- 基建为独立主数据实体，含 10 项数值属性，创建时全部必填，由办赛方在「基建管理」页维护。公司不再单独挂载基建子资源。

### 9.8 产业类型（industry-types）

- 产业类型**不再自动播种**，由用户在「产业类型管理」页（需 `industryType:manage`）自行创建维护。
- 路由：`GET/POST /industry-types`、`GET/PATCH/DELETE /industry-types/:id`，写操作需 `industryType:manage`；字段子资源 `GET/POST /industry-types/:id/fields`、`PATCH/DELETE /industry-types/fields/:fieldId` 同样需 `industryType:manage`。
- `IndustryField` 已通过 API 暴露，`fieldType` 取值 `STRING`/`NUMBER`/`BOOLEAN`/`DICTIONARY`/`LIST`。
- **字段展示开关（visible）**：每个产业字段带 `visible` 布尔（默认 `true`），在「产业类型管理」的字段管理对话框内可即时切换。设为 `false` 的字段**仅不在公司管理界面（`CompanyDetailView` 的「字段」卡片）展示**——「隐藏」只作用于公司管理；区域总览「添加数据框」的字段选择**仍会列出隐藏字段**（可将其选中并发布到数据框，发布后照常展示），满足「产业类型管理处关闭显示的字段、区域管理仍可选择」的需求。合同可视化编辑器中 FIELD 效果 / FIELD_COMPARE 检查的字段目标下拉仍过滤隐藏字段隐藏是纯展示层行为：合同引擎仍按 `fieldKey` 正常读写隐藏字段的 `CompanyFieldValue`（即隐藏字段的值仍可被合同改写、只是前端不显示）；隐藏字段也仍计入 `company-fields` 读取的 `existingIds`（未被删除）。
- **增量同步正确性（隐藏 / 重显字段，缺陷 #385）**：`company-fields` 的 `getValues` 增量模式按「值变更（`CompanyFieldValue.updatedAt`）**或**定义变更（`IndustryField.updatedAt`，由 Prisma `@updatedAt` 自动 bump）」回传，并携带真实当前值。因此切换 `visible` 开关（仅 bump 定义表的 `updatedAt`、不碰值表）或新建 / 改名产业字段时，重新展示的字段会正确出现在增量响应中，前端 `patchFullItems` 会增量增删，不会长期缺席。该一致性曾因增量模式仅按「值变更」回传而缺失（记为缺陷 #385，现已修复）；`existingIds` 仍计入隐藏字段（未被删），服务端 `getValues` 已按 `visible !== false` 过滤，前端区域总览与仪表盘另有 `visible === false` 兜底过滤。

### 9.9 公司管理（companies）

- 结构是 `Company`（产业实例）→ `CompanyFieldValue`（产业字段值，按所属产业类型下的 `IndustryField` 定位）。
- 主 CRUD 需 `company:manage` 权限；自定义字段值读接口（`GET /company-fields/:companyId`）按「权限 + 公司可见字段范围（viewCompanyScopes）」区分读权限：
  - **全量可读（含未发布字段）**：`SUPER_ADMIN`，或持有 `company:manage` / `data:region:edit` 的角色（`data:region:edit` 一并放开，因为「区域总览 → 添加数据框」发布动作需先看见全部字段）；此外仅持 `company:view` 且 `viewCompanyScopes` 为空（未配置范围）的角色，也对全部公司全量可读。
  - **范围內全量 / 范围外受限**：仅持 `company:view` 且配置了非空 `viewCompanyScopes` 的角色——`viewCompanyScopes` 内公司可读全量字段，范围外公司只能读「已发布到区域总览」的公开字段。
  - **受限可读**：其余已登录角色（参赛队员 / 主席团 / 经管中心等，无任何 `company:*` 权限）仅可读「已发布到区域总览」的字段——即某 `(companyId, industryFieldId)` 出现在任一 `Region.overviewCards` 中的字段；未上总览的字段对其不可见（返回中既不含该字段值，也不计入 `existingIds`）。
- 公司不再持有分部 / 库存 / 载具 / 科技 / 基建等子资源表；合同仅可改写公司的产业字段（`CompanyFieldValue`），不操作账户或任何子资源。
- 公司「自定义字段」编辑器按所属产业类型下的字段定义渲染（含 STRING/NUMBER/BOOLEAN/DICTIONARY/LIST 类型与可计算字段），字段值经 `/company-fields` 接口写入（仅超管），展示只读。
- **客户端 `CompanyDetailView.vue`**：展示公司基础信息与「字段」卡片。字段按产业类型定义渲染，值为**只读展示**（只能通过合同引擎执行或超管 `PUT /company-fields` 改写）；可计算字段随其它数值字段实时求值。合同执行（`contract:changed`）或字段写入（`company-field:changed`）广播后，同比赛前端自动重载字段显示，无需手动刷新。

### 9.10 合同系统（概述）

后端 `src/modules/contracts/` 提供 `ContractType`（全局模板，`contractType:manage`）与 `Contract`（比赛级，`contract:manage`）两套控制器，并配套 `contract-engine.service.ts` 按 `ContractType` 配置驱动执行。

- 引擎效果：仅 `FIELD`（改写公司产业字段 `CompanyFieldValue`，按 `fieldKey` 定位所属产业类型下的 `IndustryField`）；数值支持 `CONST`/`INPUT`/`ENTITY`/`FORMULA`/`OP`/`VAR`，控制流 `IF`/`FOREACH`/`ASSIGN`。合同不再操作公司子资源表（分部 / 库存 / 载具 / 科技 / 基建），这些子资源的可见性由公司所属产业类型的 `modules` 字段控制。
- 前置检查（conditions）共 5 类——`FIELD_COMPARE`（产业字段比较）/ `VALUE_COMPARE`（两自由数值源比较）/ `INDUSTRY_IS`（产业类型判定）/ `DICT_COMPARE`（两个字典互相比较）/ `LIST_COMPARE`（两个列表互相比较），`precheck` 仅评估不落账。
- **客户端**：
  - `ContractTypeManageView.vue`：合同类型管理页（全局模板，`contractType:manage`，无条件加载），内置**图编辑器**可视化配置 `partyRoles`/`inputSchema`/`effects`/`conditions`/`graph`。
  - `ContractManageView.vue`：合同实例管理页（`contract:manage`），按 `inputSchema`/`partyRoles` 动态生成建单表单；支持详情查看、执行（DRAFT→EXECUTED）、删除、执行前 `precheck` 检查清单展示；编号分步补全由各参与方管理员在详情页内联补全；列表「执行」按钮仅 DRAFT 且有权限时启用。
- 设计细节详见 §10（合同引擎详细设计）与 §11（合同需求与字段清单）。

### 9.11 区域系统（regions）

- **背景与目标**：比赛方需要一张「区域总览」看板——每创建一个**区域**就以一条**横向带状区域**呈现；每个区域内可添加多个**数据框**，每个数据框可单独（1）绑定到「该区域内的某家公司」的「某个产业字段」作为数据来源，（2）设置展示名称。数据框实时显示所绑字段的当前值。
- **与地图 `MapNode.region` 的区别**：地图节点的 `region` 仍是自由文本（地理区域标签），与本模块的业务 `Region` 实体**解耦**，区域系统不读取地图节点的 `region` 字段。

#### 9.11.1 数据模型（Prisma）

- 新增独立 `Region` 实体：
  - `id Int @id @default(autoincrement())`
  - `name String`
  - `description String?`
  - `competitionId Int?`（比赛级，复用 `CompetitionScopeGuard` 隔离；`onDelete: Cascade`）
  - `overviewCards String @default("[]")` —— 总览卡片配置（JSON 字符串，结构见 §9.11.2）
  - `companies Company[]`（反向关系，由公司 `regionId` 指向）
  - `@@unique([competitionId, name])`
- `Company` 增加归属字段：`regionId Int?` + `region Region? @relation(fields: [regionId], references: [id], onDelete: SetNull)`。**一个公司仅属一个区域**；删除区域时将其下公司的 `regionId` 置空（不级联删公司）。
- `Competition` 增加 `regions Region[]` 反向关系（便于级联删除）。

#### 9.11.2 区域总览卡片模型（overviewCards）

`overviewCards` 为 JSON 数组，每个元素结构：

```json
{
  "id": "c-1700000000000-1",   // 前端生成的卡片本地 id（用于排序/编辑，后端无需持久化）
  "displayName": "本月产量",     // 展示名称（用户自定义）
  "companyId": 5,               // 数据来源公司 id（限定本区域内的公司）
  "industryFieldId": 12         // 该公司所属产业类型下的产业字段 id
}
```

- 前端「添加数据框」流程：先选「本区域公司」（`companyId` 下拉只列当前区域的公司）→ 再选该公司的某个产业字段（`industryFieldId`）→ 最后填「展示名称」（`displayName`）。
- **卡片实时值**：按 `(companyId, industryFieldId)` 调 `GET /api/company-fields/:companyId` 取该字段当前值并展示；值随 `company-field:changed` 广播自动刷新。
- `overviewCards` 仅由后端以 JSON 原样存储，**不校验字段是否存在**（字段可能随产业类型变更而失效）；前端渲染时若该字段已失效，显示「字段已失效」占位而非报错。

#### 9.11.3 接口清单

类级守卫：`JwtAuthGuard, PermissionsGuard` + `@RequirePermissions("data:region:view")`：读接口（列表 / 详情 / companies / overview / map-overview）继承类级 view；写接口（POST/PATCH/DELETE）与保存卡片（PUT overview-cards / `by-name`/:name/overview-cards）方法级覆盖为 `data:region:edit` 或 `data:map:edit`（方法级优先于类级，见 §6.2）。

| 方法     | 路径                                | 守卫/权限              | 说明                                                                |
| ------ | --------------------------------- | ------------------ | ----------------------------------------------------------------- |
| GET    | `/api/regions`                    | 登录                 | 区域列表（Query: `competitionId`；未传则由 `CompetitionScopeGuard` 收窄到所属比赛） |
| GET    | `/api/regions/:id`                | 登录                 | 区域详情（含 `companies`）                                               |
| POST   | `/api/regions`                    | `data:region:edit` | 创建区域（`CreateRegionDto`）                                           |
| PATCH  | `/api/regions/:id`                | `data:region:edit` | 更新区域（`UpdateRegionDto`）                                           |
| DELETE | `/api/regions/:id`                | `data:region:edit` | 删除区域（其下公司 `regionId` 置空；Query 可带 `competitionId` 做越权校验）           |
| GET    | `/api/regions/:id/companies`      | 登录                 | 该区域下的公司列表（用于总览卡片下拉与区域管理）                                          |
| GET    | `/api/regions/:id/overview`       | 登录                 | 返回 `overviewCards` 解析结果 + 每张卡片的实时字段值（聚合 `company-fields`）         |
| PUT    | `/api/regions/:id/overview-cards` | `data:region:edit` | 保存总览卡片配置（`{ cards: [...] }`，覆盖写 `overviewCards` JSON）             |

- **公司归属管理**：通过既有的 `PATCH /api/companies/:id` 增加 `regionId?` 字段完成；`GET /api/companies` 支持 `?regionId=` 过滤，便于按区域枚举公司（`UpdateCompanyDto` 与 `company.service.findAll` 需相应扩展，见 §15.1「公司」）。
- DTO：
  - `CreateRegionDto`：`name`(必填,string)、`description?`(string)、`competitionId?`(int)、`overviewCards?`(array，可选初始卡片)。
  - `UpdateRegionDto`：`name?`、`description?`、`overviewCards?`(array)。

#### 9.11.4 前后端职责

#### 9.11.6 消费者需求（consumer-demands）

「消费者需求」是区域系统的附属数据：办赛方可按**区域**登记各**产品**的市场需求（数量 / 备注），用于区域总览中展示该区域对各产品的消费体量，辅助选手决策。

**数据模型**：`ConsumerDemand`（`consumerDemand` 表）核心字段：`competitionId`(比赛归属，可空)、`region`(区域名，字符串)、`productId`(关联产品主数据 id，必填)、`productType`(产品名称**冗余写入**，便于产品被删后需求仍可读)、`quantity`(需求量，默认 0，≥0)、`note`(备注)。

**API 与权限**（控制器 `consumer-demands.controller.ts`，沿用区域权限域 `data:region`）：

| 方法     | 路径                          | 权限                 | 说明                                                                                     |
| ------ | --------------------------- | ------------------ | -------------------------------------------------------------------------------------- |
| GET    | `/api/consumer-demands`     | `data:region:view` | 列出需求，支持 `?competitionId=` / `?region=` 过滤                                              |
| POST   | `/api/consumer-demands`     | `data:region:edit` | 新建（校验 `productId` 对应产品存在，否则 404）；并按 `Ownership` 归属当前比赛                                 |
| PATCH  | `/api/consumer-demands/:id` | `data:region:edit` | 更新（任一字段可选；改 `productId` 时重算 `productType`）；`@Ownership({model:"consumerDemand"})` 越权校验 |
| DELETE | `/api/consumer-demands/:id` | `data:region:edit` | 删除（`assertSameCompetition` 越权校验）                                                       |

**行为要点**：

- 产品名称 `productType` 由后端按 `productId` 冗余写入——`create`/`update` 改产品时自动解析并刷新，即使原产品后续被删除，该需求记录仍可正常显示产品名。
- 写操作（增/改/删）均通过 `realtime.emitResourceChanged("consumer-demand", ...)` 广播 `consumer-demand:changed`，区域总览前端监听该事件自动重载需求列表，无需手动刷新。
- 客户端 `consumerDemandsApi` 的 `list` 返回**直接数组**（非 `{items,total}` 包裹），与区域总览其余接口一致；区域总览页 `RegionOverviewView.vue` 内嵌需求编辑（按区域分组、增/改/删）。

### 9.12 消息中心（messages）

办赛方向指定账号定向发布消息，接收方在客户端「消息中心」页面查看收件箱与已发布记录，并在线时收到实时滑入弹窗。

#### 9.12.1 数据模型（Prisma）

- `Message`：消息主体。`title`/`content`（文本）、`senderId`（发布者）、`competitionId`（发布者所属比赛，仅作元数据，检索不依赖它）、`targetsAll`（是否向范围内全部账号发送）、`targetUserIds`（JSON 字符串，显式选中的接收人 id 列表）、`images`（JSON 字符串，消息附带图片元信息列表 `[{url, filename}]`；`url` 为 `/uploads/message-images/...` 相对路径，落盘于 `server/uploads/message-images/`，删除消息时由服务端一并清理）。
- `MessageRecipient`：收件人结算行。`messageId` + `userId` 唯一约束；`read`/`readAt` 记录已读状态。**发布时一次性结算**（`targetsAll` 与显式选人取并集去重），收件箱与未读以该表为权威来源，与比赛隔离解耦——离线用户登录后也能在收件箱看到未读。

#### 9.12.2 权限与隔离

- 权限域 `message`：`message:view`（查看收件箱 / 接收弹窗）、`message:manage`（发布 / 删除消息）。账号管理页权限编辑器自动出现该域（见 §6.2）。
- 收件箱 / 未读 / 已读以当前用户（`userId`）为过滤维度，不依赖 `competitionId`，故控制器整体豁免 `CompetitionScopeGuard`（`@NoCompetitionScope`）。
- 发布范围：非超管仅能向其**所属比赛**的账号发布；`SUPER_ADMIN` 可向全部账号发布（前端「按比赛筛选」下拉可缩小接收范围）。发布目标 = **账号多选 + 本比赛全体**（`targetsAll` 开关）取并集去重；二者均为空则拒绝（`BadRequest`）。
- 删除：仅发布者或 `SUPER_ADMIN` 可删（`message:manage`），级联删除收件人记录。

#### 9.12.3 接口清单

| 方法     | 路径                               | 权限               | 说明                                                                                           |
| ------ | -------------------------------- | ---------------- | -------------------------------------------------------------------------------------------- |
| GET    | `/api/messages/selectable-users` | `message:manage` | 可选收件人（超管可附 `?competitionId=` 过滤）                                                             |
| POST   | `/api/messages/upload-image`     | `message:manage` | 上传单张消息图片（multipart 字段名 `file`，≤15MB，仅图片格式），返回 `{url, filename}`                              |

#### 9.12.4 实时弹窗与前端职责

- 后端 `RealtimeService.emitToUsers(ids, "message:new", {...})` 向每位在线收件人私有房间（`user-${id}`）推送新消息；`RealtimeGateway.handleConnection` 已让每个 socket 加入自身 `user-${id}` 房间。

### 9.13 股票系统（stock）

模拟股票交易系统，作为商赛子系统集成于现有后端 / 前端 / 权限体系，数据按比赛隔离。所有股票相关接口路径前缀均为 `/stocks`（见 §9.13.6），前端缓存资源名统一为 `stocks`，使实时广播正确触发增量刷新。

#### 9.13.1 数据模型

五个模型（均含 `competitionId` + `competition` 关联 + `createdAt/updatedAt`，按比赛隔离）：

- **Stock（股票）**：`code`（按比赛唯一）、`name`、`totalShares`（总股本，万股）、`initNetProfit`（初始净利润，万）、`industryPE`（行业 PE）、`currentCarbon` / `industryAvgCarbon`（当前碳排 / 行业碳排均值）、`happiness`（幸福度）、`carbonFieldRef?` / `happinessFieldRef?`（绑定区域总览卡片的实时引用，JSON `{region, cardId}`；为空 = 不绑定，使用上述手动值）、`initPrice`（初始价，公式自动算）、`currentPrice`（当前价）、`round`（轮次，默认 0）、`companyId?`（关联商赛公司）。`@@unique([competitionId, code])`。
- **StockFundsAccount（资金账户）**：`name`（按比赛唯一）、`ownerType`（`COMPANY` / `USER`）、`companyId?`、`userId?`、`cashBalance`（默认 1,000,000）。`@@unique([competitionId, name])`。
- **StockOrder（订单）**：`stockId`、`fundsAccountId`、`side`（`BUY` / `SELL`）、`price`、`quantity`、`amount`(=price×quantity)、`status`（`PENDING` / `FILLED` / `CANCELLED`，默认 PENDING）、`round`（下单时股票轮次）。`@@index([competitionId, stockId, round, status])`。
- **StockHolding（持仓）**：`fundsAccountId`、`stockId`、`shares`、`costPrice`（加权平均成本）。`@@unique([fundsAccountId, stockId])`。
- **StockCandle（K线）**：`stockId`、`round`、`open`、`high`、`low`、`close`、`changePct`。`@@unique([stockId, round])`。

`User.stockCompanyScopes`（JSON 公司 id 数组，nullable）：仅 `stock:edit` 低级管理使用，限定其可管的公司资金账户范围（详见 §9.13.3）。

#### 9.13.2 权限分级

新增 `stock` 权限域（`server/src/permissions/catalog.ts` 与 `client/src/permissions/catalog.ts` 镜像）：

| 权限 key | 含义 | 界面可见性 |
| ------ | ---- | ---- |
| `stock:view` | 查看行情、选购、下单买卖 | 显示「股票行情」菜单与交易面板 |
| `stock:edit` | 低级管理：管理「所选公司 + 自己」的资金账户 | 显示「股票管理」中的资金账户表（仅范围内账户） |
| `stock:manage` | 高级管理：看全部账户、增删股票、推进轮次 | 额外显示股票增删表 +「推进一轮」按钮 |

权限蕴含与后端 `hasPermission` 一致：`view` 可由同域任意能力满足（持 `stock:edit` / `stock:manage` 即视为有 `stock:view`）；`edit` 由 `stock:manage` 满足；超管隐式全放行。菜单显隐：「股票行情」需 `stock:view`；「股票管理」需 `stock:edit` 或 `stock:manage`。

#### 9.13.3 范围约束（stockCompanyScopes）

- **超管 / 持 `stock:manage`**：可见全部资金账户，可增删任何股票、代任意账户下单、推进轮次。
- **仅持 `stock:edit`（低级管理）**：仅能操作「自己名下的 USER 账户」+「`stockCompanyScopes` 内公司的 COMPANY 账户」。创建公司账户时公司不在范围内则拒绝；订单 / 持仓 / 资金账户读列表按可操作集合收敛。
- **仅持 `stock:view`**：只能操作自己名下的 USER 账户（买卖自己的股票账户）。

#### 9.13.4 撮合与定价引擎

逻辑严格对齐用户提供的 Excel「模拟股票系统.xlsx」（引擎为纯函数 `server/src/modules/stock/engine.ts`）：

- **初始价**：`ROUND(initNetProfit × 10000 / totalShares / industryPE, 2)`，创建股票或修改股本 / 净利润 / 行业 PE 时自动重算。
- **撮合**（推进一轮时汇总本轮 `PENDING` 订单）：最高买价 = `MAX(买入价)`，最低卖价 = `MIN(卖出价)`，成交价 = `(最高买 + 最低卖) / 2`，是否成交 = 最高买 ≥ 最低卖。实际成交采用贪心配对（买价 ≥ 卖价，按价 / 时间排序，现金与持仓实时扣减；现金不足或持仓不足的单被部分 / 全部取消）。
- **实时价格**：买盘总额 = `Σ买入金额`，卖盘总额 = `Σ卖出金额`；幸福因子 = `1 + 0.2 × (幸福度 − 50) / 50`；碳因子 = `1 − 0.5 × (当前碳排 − 行业碳排均值) / 行业碳排均值`；理论价 = 上轮价 × 买盘总额 / 卖盘总额 × 幸福因子 × 碳因子；最终价 = 限幅(理论价, 上轮价 × 0.9, 上轮价 × 1.1)，保留 2 位小数。
- **K线**：开盘 = 上轮收盘；收盘 = 最终价；盘高 = `MAX(开盘, 收盘)`；盘低 = `MIN(开盘, 收盘)`；涨跌幅 = `(收盘 − 开盘) / 开盘 × 100`。

#### 9.13.4.1 绑定区域总览字段（碳排 / 幸福度实时引用）

「当前碳排」与「当前幸福度」除手动输入外，还可**绑定到区域总览的某张卡片**（区域总览 → 某区域 → 数据框），实现实时引用：股票不存储具体数值，而是存储对卡片的引用 `{region, cardId}`；引擎每次定价时，由 `StockService` 通过 `RegionService.getMapOverview` 实时解析该卡片的当前字段值作为有效值。

- **绑定方式（实时引用）**：`Stock.carbonFieldRef` / `happinessFieldRef` 存 JSON `{region, cardId}`；列表接口与推进轮次时统一解析为 `effectiveCurrentCarbon` / `effectiveHappiness` 参与幸福因子 / 碳因子计算。
- **未绑定**：直接使用手动输入的 `currentCarbon` / `happiness`。
- **回退**：若引用卡片失效（字段被删 / 公司产业类型变更）或值为非数字，则回退到手动输入值，保证引擎稳定。
- **字段来源为「区域卡片」**：卡片底层仍绑定「某区域内某公司」的「某个产业字段」，区域总览变更时股票侧实时联动，无需手工同步。
- **前端**：股票管理对话框中「碳排绑定字段 / 幸福度绑定字段」下拉列出所有区域的可用卡片（失效卡片禁用）；绑定后显示卡片实时值（只读），隐藏手动输入框；股票列表「碳排 / 幸福度」列展示有效值并以「绑」标签标注已绑定股票。

#### 9.13.5 手动推进轮次流程

1. 玩家在「股票行情」界面对自己可操作的资金账户下单（`POST /stocks/orders`，`status=PENDING`，`round` = 当前轮次）。
2. 高级管理点击「推进一轮」（`POST /stocks/advance-round`）→ 后端逐股在事务内：撮合本轮订单 → 更新现金 / 持仓（加权成本）→ 写入 K 线 → 更新股价与 `round+1` → 广播。未成交订单置 `CANCELLED`。
3. 行情界面实时刷新股价与 K 线（ECharts 蜡烛图，红涨绿跌中国习惯）。

## 10. 合同引擎详细设计

### 10.1 设计原则

1. **配置驱动**：每种合同是一个 `ContractType` 模板，含 `partyRoles`（参与方）、`inputSchema`（需填写的输入字段）、`effects`（签署后效果）、`conditions`（前置检查）。新增合同类型只需加一条数据，无需改代码。
2. **只改产业字段**：合同效果唯一允许改写的目标是公司在其产业类型下的「自定义产业字段」（`CompanyFieldValue`，对应 `IndustryField.fieldKey`）。公司未设置产业类型、或该产业下无对应字段时，引擎直接报错（合同不应静默跳过字段操作）。
3. **数值取自数据管理实体（ENTITY）**：如 `MATERIAL.price × 数量`、`FUEL.pricePerLiter × 升数`、`TECH_NODE.researchCost`、`WAREHOUSE.price` 等，在执行时按用户所选实体实时读取，作为 FIELD 效果的 `value`。无实体的合同用 `INPUT` 手动填写。
4. **事务一致**：所有效果在一个 `prisma.$transaction` 内执行，失败整体回滚，并写 `executionLog` 审计。

### 10.2 数据模型

- `ContractType`：`key`(唯一编码) / `name` / `category` / `partyCount` / `partyRoles`(JSON) / `inputSchema`(JSON) / `effects`(JSON) / `conditions`(JSON) / `graph`(JSON 可视化节点图) / `enabled`。
- `Contract`：`competitionId` / `contractTypeId` / `name` / `status`(DRAFT/EXECUTED/TERMINATED) / `parties`(JSON) / `inputs`(JSON) / `executionLog`(JSON) / `executionResult`(JSON) / `signedAt` / `executedAt`。
- `CompanyFieldValue`（既有）：公司产业字段值，`@@unique([companyId, industryFieldId])`。FIELD 效果按 `(companyId, fieldKey→industryFieldId)` upsert 此表。

### 10.3 效果（effects）类型

```ts
// 唯一允许的叶子效果：改写公司的产业字段
// value：第一数值来源（ValueSpec）；value2 + valueOp：可选第二数值来源与组合方式，最终写入量 = value <valueOp> value2
{ kind:"FIELD", party:"A"|"B"|"C", fieldKey:"<IndustryField.fieldKey>",
  op:"ADD"|"SUB"|"SET", value: ValueSpec,
  valueOp?:"ADD"|"SUB"|"MUL", value2?: ValueSpec }

// 数值来源 ValueSpec
type ValueSpec =
  | { type:"ENTITY", entityType:"MATERIAL"|"PART"|"PRODUCT"|"TECH_NODE"|"WAREHOUSE"|"PRODUCTION_LINE"|"FUEL"|"VEHICLE"|"INFRASTRUCTURE"|"MAP_NODE", entityRef:"<id字段>", attribute:"price"|"researchCost"|"pricePerLiter"|..., multiplyByInput?:"<数量字段>" }
  | { type:"INPUT", key:"<字段>" }                 // 取值为原始类型：数字→number，列表/字典→数组/对象
  | { type:"CONST", value:number|string|any[]|object }  // JSON 字符串会自动解析
  | { type:"FORMULA", expr:"mathjs 表达式，作用域=inputs + scope" }
  | { type:"OP", op:"OP名称", args: ValueSpec[] }   // 列表/字典运算，args 递归为子 ValueSpec
  | { type:"VAR", name:"<运行期变量名>" }          // 引用 scope（FOREACH 循环变量 / ASSIGN 赋值结果），回退 inputs
  | { type:"ROUTE", routeRef:"<输入项字段 key>"}   // 地图路程（输入源）：求相邻节点最短路距离之和
  | { type:"FIELD", party:"A"|"B"|..., fieldKey:"<IndustryField.fieldKey>" }  // 产业字段现值（数据源）
  | { type:"INDUSTRY_IS", party:"A"|"B"|..., industryTypeId:number }  // 产业类型判断（布尔值源，返回 company.industryTypeId === industryTypeId，可连 IF.cond）
```

- **ENTITY**：引擎按 `entityType` 找到对应数据管理模型，用 `entityRef` 指向的 id 读取 `attribute` 真实属性，再用 `multiplyByInput` 相乘（如燃料购销：`{type:"ENTITY", entityType:"FUEL", entityRef:"fuelId", attribute:"pricePerLiter", multiplyByInput:"liters"}`）。
- **编辑器数值源来源（下拉项）**：目前提供 `实体(ENTITY)` / `产业字段现值(FIELD)` / `常量(CONST)` / `公式(FORMULA)` / `产业类型判断(INDUSTRY_IS)` 五种。原 `输入项(INPUT)` 与 `变量(VAR)` 两类已**从编辑器源下拉框移除**（不再可新建）；引擎仍保留对它们的求值能力，已保存的旧合同图若含这两类数值源，载入后照常执行，仅无法在 UI 重新选择。
- **ROUTE（地图路程）**：`ROUTE` 是**输入源**——设计合同类型时不固定节点，而是声明「节点路径」取自某个输入项（该输入项 `type` 为 `nodeRoute`，创建合同时签约方在表单里逐个选择地图节点组成有序路径）。执行时引擎按 `competitionId` 读取该比赛地图边（无向图，边权 `distance`），从 `inputs[routeRef]` 取出节点 id 列表，对相邻节点逐对求最短路（Dijkstra），求和得到「路程」；相邻两节点不可达则报错中止。节点数 < 2 时路程为 0。
- **FIELD（产业字段现值）**：`FIELD` 让数值源可以**读取公司当前的产业字段值**，与 `FIELD` 效果（写）互为读写两端。执行时按该参与方的 `companyId` → `industryTypeId` → `IndustryField(fieldKey)` → `CompanyFieldValue` 取现值，并按字段类型解析：`NUMBER` 数字（无记录回落 `defaultValue`，再无则 0）；`LIST`/`DICTIONARY` 数组/对象；`STRING`/`BOOLEAN` 字符串/布尔。参与方为主席团/经管中心（`isHost=true`）或未绑定公司时返回 0；公司未设产业类型或该产业下无此字段时报错中止。
- **INDUSTRY_IS（产业类型判断，布尔值源）**：`INDUSTRY_IS` 让数值源可以**输出一个布尔值**——判断某参与方公司所属产业类型是否等于指定产业类型（即 `company.industryTypeId === industryTypeId`）。**编辑器中以「产业类型」下拉框按名称直接选择**，由系统自动映射到对应 `industryTypeId`，无需手填 ID（下拉项来自「产业类型管理」）。执行时按该参与方的 `companyId` 取 `industryTypeId` 比对；参与方为主席团/经管中心（`isHost=true`）或未绑定公司、或找不到参与方、或未设产业类型时返回 `false`。该值源**输出端口类型为「布尔」**，可直接连到「条件(IF)」节点的「条件」端口，驱动真/假分支（例如「若甲方属于矿业，则走优惠条款，否则走标准条款」）。注意它与「前置检查 INDUSTRY_IS」同名但用途不同：前置检查在合同执行前整体核验（不过则中止落账），而此处是图内可组合的布尔表达式，喂给 `IF` 做分支。
- **效果双值组合（`value` + `value2` + `valueOp`）**：写入的「量」可由两个数值来源组合，二者都来自数值源节点，不写死常量。`valueOp`：`ADD`(加)/`SUB`(减)/`MUL`(乘)；仅接 `value` 时退化为写入 `value`。标量字段按数字运算；列表字段 ADD/SUB 为拼接/移除元素；字典字段 ADD/SUB 为合并/删键；MUL 对集合退化为仅用 `value`。

### 10.4 前置检查（conditions）类型

合同执行前可声明一组「对公司状态的核验」，任一不过则中止执行（事务回滚，不落账）。共五类：

```ts
// 产业字段比较
{ kind:"FIELD_COMPARE", party:"A", fieldKey:"<fieldKey>", op:"GTE"|"LTE"|"GT"|"LT"|"EQ"|"CONTAINS"|"HAS_KEY"|"LEN_GTE"|"LEN_LTE"|"LEN_EQ", value: ValueSpec }
// 数值互相比较（推荐，更灵活）
{ kind:"VALUE_COMPARE", op:"GTE"|"LTE"|"GT"|"LT"|"EQ"|"CONTAINS"|"HAS_KEY", value1: ValueSpec, value2: ValueSpec }
// 产业类型判定
{ kind:"INDUSTRY_IS", party:"A", industryTypeId:number }
// 两个字典互相比较：前提——值一的每个键都必须存在于值二的键集合中；满足后逐键比较
{ kind:"DICT_COMPARE", op:"GTE"|"GT"|"EQ", value1: ValueSpec, value2: ValueSpec }
// 两个列表互相比较（按元素集合的包含关系，非长度）：元素相等(ELEMENT_EQ)/被包含(CONTAINS)/大于(GT,值一真包含值二)/大于等于(GTE,值一包含值二)/等于(EQ,集合相同)
{ kind:"LIST_COMPARE", op:"ELEMENT_EQ"|"CONTAINS"|"GT"|"GTE"|"EQ", value1: ValueSpec, value2: ValueSpec }
```

- `FIELD_COMPARE`：按字段类型施加比较。NUMBER 用 `GTE/LTE/GT/LT/EQ`；LIST/DICTIONARY 用 `CONTAINS`/`HAS_KEY`/`LEN_*`。
- `VALUE_COMPARE`：两个操作数都是自由数值源，均可接数值源节点（FIELD/ENTITY/INPUT/FORMULA/OP…）。`op` 支持 `GTE/LTE/GT/LT/EQ`（数字比较）、`EQ`（结构相等）、`CONTAINS`（列表含元素/字典含值）、`HAS_KEY`（字典含键）。
- `INDUSTRY_IS`：核验参与方公司所属产业类型是否等于 `industryTypeId`，常用于「准入类合同」。
- `DICT_COMPARE`：两个操作数都是自由**字典**源（均可接数值源节点，无需参与方）。执行时先校验**前提**——`Object.keys(value1)` 必须是 `Object.keys(value2)` 的子集（即值一的每个键都在值二中存在），否则该检查直接判不过，并在详情中列出缺失的键。前提满足后，对两个字典的**共有键**逐一执行 `toNumber(value1[k]) op toNumber(value2[k])`（`op` 仅限 `GTE`/`GT`/`EQ` 三种），任一键不满足即判不过。常用于「需逐项达标」类核对（如公司各分部指标均不低于标准值）。
- `LIST_COMPARE`：两个操作数都是自由**列表**源（均可接数值源节点，无需参与方）。比较的是**元素集合的包含关系**（非长度）。`op` 支持五种：
  - `ELEMENT_EQ`（元素相等）：两列表长度相同且对应位置元素相等（有序结构相等，`deepEqual` 逐元素比对）；
  - `CONTAINS`（被包含）：值一的每个元素都存在于值二中（值一 ⊆ 值二，集合包含），任一缺失即判不过；
  - `GT`（大于）：值一**真包含**值二（值一 ⊃ 值二，即值二 ⊆ 值一 且二者集合不等）；
  - `GTE`（大于等于）：值一**包含**值二（值一 ⊇ 值二，即值二 ⊆ 值一，含相等）；
  - `EQ`（等于）：两列表**元素集合完全相同**（值一 ⊆ 值二 且 值二 ⊆ 值一）。  
    两个操作数均须为数组，否则该检查直接判不过。常用于「清单齐备性」类核对（如公司采购清单是否包含全部必需原料、某清单是否被另一清单完整包含）。
- 主办方（主席团，`isHost=true`）不是公司账户，检查到其名下时视为不可检查、直接判不过。经济管理中心为普通参与方（`isHost=false`），绑定公司后可正常检查。
- `POST /contracts/:id/precheck` 仅评估不落账，便于前端执行前展示检查清单。

#### 10.4.1 检查挂在 IF 分支（按条件执行检查）

检查（condition）节点与输入项（input）节点一样，新增了「上级」控制流输入端口：把某个 **IF 条件节点**的「真分支 / 假分支」输出端口连到该检查的「上级」端口后，该检查即「隶属于」那个 IF 分支。

- **含义**：该检查是否执行，取决于所属 IF 分支的条件在执行时是否成立。
  - 挂在「真分支」下：仅当 IF 条件为真时才执行该检查；条件为假时**跳过**（不计过、不阻塞）。
  - 挂在「假分支」下：仅当 IF 条件为假时才执行该检查；条件为真时跳过。
- **与输入项的区别**：输入项分支是「前端创建表单按条件显隐」（前端求值、不提交隐藏字段）；检查分支是**引擎执行期按条件短路**（服务端 `runConditions` 内求值，分支不激活则该检查直接跳过）。两者共享同一套 IF 条件定义（`branch.cond`）。
- **序列化**：`ConditionSpec` 新增可选字段 `branch?: { when: "then" | "else"; cond: ValueSpec }`；可视化编辑器经 `graphToFlat` 写入，经 `flatToGraph` 按 `cond` 同构匹配回连 `IF.then/else → condition.parent`。
- **引擎短路逻辑**：`runConditions` 在遍历每条检查时，若 `c.branch` 存在，先求值 `branch.cond`；按 `when` 取真值（`then`）或反值（`else`），未激活则跳过该检查（结果记为 `skipped=true`、`passed=true`，不阻塞执行）。`execute` 与 `precheck` 均经 `runConditions`，自动生效。
- **注意**：若某检查依赖某个输入项的值，且该输入项本身挂在某个 IF 分支下，则二者应挂在同一 IF 分支（连线即可保证），否则该输入项被隐藏、检查取值会取不到。

### 10.5 列表 / 字典与表达式能力

- `resolveValue` 返回值类型从 `number` 放宽为 `any`：数字场景用 `toNumber` 兜底；列表/字典场景直接返回数组/对象。统一的模块级 `evalValueSpec(spec, inputs, prisma, scope?)` 取代原先重复的两份求值实现。
- `CONST` 的 `value` 支持数字、字符串，以及 JSON 数组/对象字符串（如 `[1,2,3]`、`{"a":1}`），引擎自动解析为数组/对象。编辑器 CONST 数值源面板提供两个快捷按钮「空字典 {}」「空数组 []」，一键将 `value` 设为 `{}` / `[]`，用于输出空字典或空数组（如作为 `DICT_ADD`/`LIST_APPEND` 的初始容器、或作为清空某字段的写入值）。
- FORMULA 表达式作用域注入 `EXPR_HELPERS`，配合 mathjs 原生数组能力（`[1,2,3]`、`sum()`、`map()`、`filter()`、`concat()`、`[1]` 为 **1-based** 索引）：

| 函数                                                | 作用                  |
| ------------------------------------------------- | ------------------- |
| `len(x)`                                          | 数组长度 / 对象键数 / 字符串长度 |
| `push(arr, ...items)`                             | 数组追加元素              |
| `concat(a, b)`                                    | 拼接两个数组              |
| `contains(c, x)`                                  | 列表含元素 / 字典含键或含值     |
| `indexIn(arr, x)`                                 | 元素首次出现下标            |
| `keys(o)` / `values(o)`                           | 字典键 / 值列表           |
| `get(o, k)` / `has(o, k)` / `hasKey(o, k)`        | 取键值 / 是否含键          |
| `merge(...objs)`                                  | 合并多个字典              |
| `unique(arr)` / `flatten(arr)` / `join(arr, sep)` | 去重 / 拍平 / 拼接        |
| `sumOf(arr)`                                      | 列表元素求和              |

- `inputSchema` 的输入项 `type` 新增 `list` / `dict`（可选 `elementType`：number/string/boolean）：可视化编辑器「输入项」节点类型下拉新增列表/字典；合同实例填写页为 list 渲染可增删的元素编辑器，为 dict 渲染键值对编辑器。

**FIELD 效果对结构化字段的语义**：

- **LIST**：`ADD` 追加元素（可传数组批量）；`SUB` 移除首次匹配的元素；`SET` 整体替换为数组。元素按 `itemType` 强制标量类型。
- **DICTIONARY**：`ADD`/`SET` 合并键值（SET 整体替换）；`SUB` 删除指定键（可传键名、键名数组或 `{键:任意}` 删其键）。值按 `valueType` 强制标量类型。
- **NUMBER**：保持原 `ADD`/`SUB`/`SET` 数值运算。

**FIELD_COMPARE 的结构化算子**：在数值算子 `GTE/LTE/GT/LT/EQ` 之外新增 `CONTAINS`（列表含元素/字典含键或值）、`HAS_KEY`（字典含指定键）、`LEN_GTE`/`LEN_LTE`/`LEN_EQ`（列表长度/字典键数比较；数字算子对结构化字段退化为长度比较）。

| 字典 | `DICT_FROM_PAIRS`                                                 | 由键值对列表造字典                                                                                         | pairs                                                             |
| 字典 | `DICT_FROM_KEYS`                                                  | 由键列表造字典（值统一填）                                                                                     | keys, value                                                       |
| 字典 | `DICT_INVERT`                                                     | 键值互换                                                                                              | dict                                                              |
| 字典 | `DICT_ADD`                                                        | 字典相加：共有键值相加，仅 a 的键保留原值，仅 b 的键加入其原值                                                                | a, b                                                              |
| 字典 | `DICT_SUB`                                                        | 字典相减：共有键值相减（a−b），仅 a 的键保留原值，仅 b 的键加入其值的负数                                                         | a, b                                                              |
| 字典 | `DICT_APPEND`                                                     | 字典追加元素：在原字典基础上追加一个键值对（等价于 `{...dict, [key]: value}`，key 已存在则覆盖）                                   | dict, key, value                                                  |
| 字典 | `DICT_SUM`                                                        | 字典求和：把字典所有键对应的值相加，输出单个数字（非数字值按 0 计，不递归嵌套）                                                         | dict                                                              |
| 通用 | `LEN` / `CONTAINS` / `SUM_OF`                                     | 长度 / 包含 / 求和（单参）                                                                                  | x / coll,item / list                                              |
| 算术 | `ADD` / `SUB` / `MUL` / `DIV`                                     | 加 / 减 / 乘 / 除（除数为 0 时返回 0）                                                                        | left, right                                                       |
| 算术 | `EXP` / `LOG` / `MIN` / `MAX`                                     | 指数 / 对数 / 取最小 / 取最大                                                                               | EXP: operand；LOG: operand, base（底数缺省按自然对数 e）；MIN/MAX: left, right |
| 比较 | `CMP_EQ` / `CMP_NE` / `CMP_GT` / `CMP_LT` / `CMP_GTE` / `CMP_LTE` | 等式 / 不等式比较，**返回布尔**（= ≠ > < ≥ ≤）；数值按 `toNumber` 比较，`CMP_EQ`/`CMP_NE` 用结构相等（`deepEqual`，列表 / 字典亦可） | left, right                                                       |

- 每个参数端口可连线到另一个"数值源"或填**字面量**（`argLiterals[handle] = {type:"CONST", value:...}`）。未连线取字面量，字面量缺失时回退 `CONST 0`。
- 后端 `applyOp(op, args, scope?)` 为**纯函数**；未知 op 抛 `BadRequestException`。前端 `opCategory(op)` 决定渲染：`op.startsWith("DICT_")` → 字典；`op ∈ {ADD,SUB,MUL,DIV,EXP,LOG,MIN,MAX}` → 计算节点；`op.startsWith("CMP_")` → 布尔比较节点；其余 → 列表。
- **计算节点（calc）**：暴露 `ADD/SUB/MUL/DIV/EXP/LOG/MIN/MAX`，输入端口连数值源，输出端口连入任意数值输入端口，序列化形态同样是 `OP` 类型。
  - `EXP(operand)`：`e^operand`（自然指数）。
  - `LOG(operand, base?)`：对数；`base` 缺省（未连线 / ≤ 0）时按自然对数 `ln(operand)` 计算，指定 `base > 0` 时按 `ln(operand)/ln(base)`（如 base=10 即常用对数）。
  - `MIN(left, right)` / `MAX(left, right)`：两个数值（值A / 值B）的最小值 / 最大值。
- **布尔比较节点（compare）**：新增的「输出布尔值的条件式」节点，两个输入端口「值A/值B」连数值源，输出端口输出**布尔**。可选 op 为 `CMP_EQ`/`CMP_NE`/`CMP_GT`/`CMP_LT`/`CMP_GTE`/`CMP_LTE`（= / ≠ / > / < / ≥ / ≤）。数值比较走 `toNumber`；`CMP_EQ`/`CMP_NE` 对列表 / 字典也按结构相等（`deepEqual`）判定。序列化形态为 `{type:"OP", op:"CMP_*", args:[值A,值B]}`，即一个普通的 `ValueSpec`——因此它的输出可直接连到 **IF 节点的「条件」端口**（`if.cond`），驱动真 / 假分支，实现「等式或不等式 → 布尔 → if 语句」的完整逻辑。

**变量引用（VAR 类型）**：

```ts
{ type:"VAR", name:"x" }   // 取 scope["x"]；不在 scope 则回退 inputs["x"]
```

变量的来源有三：`FOREACH` 的循环变量、`ASSIGN` 的赋值结果、`inputs` 中的字段（回退）。

> 编辑器变更：`FOREACH`/`ASSIGN` 控制流节点已**从可视化编辑器的「控制流」面板移除**（不再可拖拽新建）；当前面板仅保留「条件(IF)」。二者仍保留在引擎与图序列化层，旧合同图若含 `foreach`/`assign` 节点，载入后照常渲染与执行。相应地，「数值源」中的 `变量(VAR)` 也已移除，故运行期变量目前仅能由 `inputs` 回退提供。

**控制流（Effect 递归结构）**：

```ts
{ kind:"IF", cond: ValueSpec, then: Effect[], else?: Effect[] }
{ kind:"FOREACH", items: ValueSpec, var:string, body: Effect[] }
{ kind:"ASSIGN", name:string, value: ValueSpec }
```

**引擎执行（递归分发）**：

```ts
const scope: Record<string, any> = {};
const applyEffect = async (eff, sc = scope): Promise<void> => {
  if (eff.kind === "IF") {
    const cond = await resolveValue(eff.cond, sc);
    const branch = isTruthy(cond) ? eff.then || [] : eff.else || [];
    for (const sub of branch) await applyEffect(sub, sc);
  } else if (eff.kind === "FOREACH") {
    const arr = await resolveValue(eff.items, sc);
    for (const el of Array.isArray(arr) ? arr : []) {
      const childScope = { ...sc, [eff.var || "item"]: el };
      for (const sub of eff.body || []) await applyEffect(sub, childScope);
    }
  } else if (eff.kind === "ASSIGN") {
    sc[eff.name] = await resolveValue(eff.value, sc);
  } else {
    await applyLeaf(eff, sc);   // 仅 FIELD：改写公司产业字段
  }
};
for (const eff of effects) await applyEffect(eff, scope);
```

- `scope` 贯穿 `evalValueSpec`：OP 的 `args`、FORMULA 作用域、VAR 取值、前置检查 `runConditions` 均共享同一变量表。
- `isTruthy`：非 null、非空字符串、非零数字、非空数组 / 非空对象均视为真。
- 控制流与叶子效果**可任意嵌套**。

**输入项挂在 IF 分支（创建表单条件显隐）**：

输入项（`input` 节点）新增一个「上级(parent)」控制流输入端口。把它连到某个 `IF` 节点的「真分支(then)」或「假分支(else)」输出端口后，该输入项即**隶属于这个条件分支**：在「创建合同」表单中，前端按 IF 条件实时求值，仅当条件成立（挂真分支）或不成立（挂假分支）时才显示并要求填写该输入项；不满足条件时该字段隐藏且不参与提交。

- **端口**：`input` 节点的输入端口增加 `parent`（类型=控制流），与 `party` / `infraList` / `vehList` 等已有输入端口并存；只能连到 `IF` 节点的 `then` / `else` 输出（控制流→控制流，类型校验放行，其他连线画红色警告）。`input.out` 数据输出端口照常工作，可继续连到效果 / 检查 / 公式。
- **序列化**：`inputSchema[].branch = { when: "then" | "else", cond: ValueSpec }`（`cond` 即所属 IF 节点的条件值源，与 `effects` 中该 IF 的 `cond` 同源同构）。未挂分支的输入项不写 `branch` 字段，行为不变（始终显示）。
- **前端轻量求值器**：`graph-model.ts` 导出 `evalFormCondition(condSpec, ctx)`，依据已填输入项（`ctx.inputs`）与各参与方所绑公司的 `industryTypeId`（`ctx.industryTypeOf(role)`）求值布尔结果；`INDUSTRY_IS` / `CMP_*`(OP) 可判定，`INPUT` / `CONST` 可参与比较；无法判定（如依赖尚未填写的字段、公司字段未知）时返回 `null`，调用方按 **fail-open** 显示该字段，避免误隐藏。
- **引擎侧无改动**：隐藏的输入项在 `execute` 时不提交、不落账；若某效果依赖该输入项，设计上应把该效果同样置于同一 IF 分支下（编辑器通过端口连线即可保证）。详细见 §10.7 与 ContractManageView 的 `isFieldVisible`。

**服务端引擎接口（`ContractEngineService`）**：

```ts
async execute(contractId: number, dto?: ExecuteContractDto, user?: any): Promise<Contract>  // 事务内按 effects 改写公司产业字段，写 executionLog，广播 contract:changed
async precheck(contractId: number, user?: any): Promise<{ ok: boolean; results: ConditionResult[] }>  // 仅评估前置检查，不落账
async setStatus(contractId: number, status: string): Promise<Contract>  // 如 TERMINATED
```

### 10.7 前端序列化（节点图 Graph ↔ flat 嵌套效果树）

可视化编辑器为**蓝图拖拽式（节点图）**：参与方 / 输入项 / 数值源 / 效果 / 检查 / 控制流都是带坐标与端口的节点，节点间用边（端口连线）连接。组件 `client/src/components/contracts/ContractTypeGraphEditor.vue`，数据层 `client/src/contracts/graph-model.ts` 的 `GGraph`（`{ nodes, edges }`）。

- 节点：`{ id, type, x, y, data }`；`type` ∈ `party`/`input`/`value`/`effect`/`condition`/`if`/`foreach`/`assign`/`list-op`/`dict-op`（`root` 仅作标题）。其中 `foreach`/`assign` 已**从编辑器控制流面板移除**（不可再新建），但 `GNodeType` 联合与 `NODE_PORTS`/`NODE_META` 仍保留，载入含这两类节点的旧图时照常渲染与执行。
- 端口：`NODE_PORTS` 定义每类节点的输入/输出端口；连线 `GEdge { source, sourceHandle, target, targetHandle }`。控制流子节点通过其 `parent` 输入端口连到父节点的 `then`/`else`/`body` 输出端口。
- `if` 节点：`cond` 输入 + `then`/`else` 输出；`foreach` 节点：`items` 输入 + `body` 输出（数据 `var` 记录循环变量名）；`assign` 节点：`value` 输入 + `name` 数据。
- **序列化（`graphToFlat`）**：遍历 `GGraph`，按节点类型与端口连线把每个数值输入解析为 `ValueSpec`（`OP` 递归解析 `args`），控制流节点递归收集 `parent` 连线指向的子节点，最终产出 `partyRoles`/`inputSchema`/`effects`/`conditions`，整张 `GGraph` 同时存入 `ContractType.graph` 以便原样回载。
- **反序列化（`flatToGraph`）**：从 `effects`/`conditions` 经 `buildEffectNode`/`buildValueNode` 重建节点与 `parent` 连线，从 `partyRoles`/`inputSchema` 重建参与方/输入项节点；输入项若带 `branch`（`when`+`cond`），在 IF 节点建好后按 `cond` 同构匹配对应 IF，再连 `IF.then/else → 输入.parent`（控制流），实现分支归属的回载。
- **向后兼容**：旧版积木树 `graph`、旧 Konva 节点图 `graph` 直接作为 `GGraph` 使用；库中存在历史数据时其 `flat` 字段会被 `flatToGraph` 用来重建节点图，无需手动迁移。
- **往返一致性**：`graph→flat→graph` 经 `canon` 规范化比对需一致；已覆盖 IF / FOREACH+VAR / ASSIGN+IF(VAR 条件) / 多层嵌套四类结构。

### 10.9 清单输入源与端口体系

合同类型编辑器有一类**清单输入源**节点：建单时用户多选实体并填数量，存为 `{名称: 数量}` 字典（按比赛隔离）。每个节点左侧可有 0~1 个「过滤端口」（限定前端下拉范围），右侧一个 `out`（原始字典）+ 若干**聚合端点**（按比赛按名查实体字段，`Σ(字段 × 数量)`；找不到按 0，仅数量 > 0 参与）。

**聚合端点一览**（统一 `Σ(字段 × 数量)` 浮点）：

| 节点                        | 过滤端口             | 主要聚合端点                                                                                                                                                                                                                                                                                                                                                |
| ------------------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `materialList` 原料清单       | `party`（按所在地取价）  | `carbon` 碳排放合计、`price` 总价格、`materialQty` 总数量                                                                                                                                                                                                                                                                                                          |
| `partList` 零件清单           | —                | `materials` 所需原料字典、`techNodes` 科技节点列表、`partQty` 总件数                                                                                                                                                                                                                                                                                                   |
| `productList` 产品清单        | —                | `parts` 所需零件字典、`techNodes`、`productQty` 总件数                                                                                                                                                                                                                                                                                                           |
| `fuelList` 燃料清单           | —                | `fuelQty` 总数量、`fuelPrice` 总价格                                                                                                                                                                                                                                                                                                                         |
| `vehicleList` 载具清单        | `vehList` 载具列表   | `vehiclePrice` 总价、`vehicleCargo` 总载货量、`vehicleFuelPerKm` 总每公里油耗、`vehicleCarbon` 总碳排数（**不乘**每公里油耗，= Σ(carbonEmission × 数量)）                                                                                                                                                                                                                            |

- **过滤输入端口**：`infraList`/`vehList` 连入实体名数组后，前端建单下拉仅展示列表内实体（未连则全部）；序列化经 `allowedInfrastructures`/`allowedVehicles` 字段存库。
- **引擎范围校验**：`execute` 与 `precheck` 对挂了过滤端口的清单强制校验，拒绝绕过前端直传的列表外实体（`validateInfraListFilters`/`validateVehicleListFilters`）；失败则 `execute` 整体中止、`precheck` 以未通过项展示。旧合同类型（`allowedXxx` 为空）不受影响。
- **`materialList` 的 `party` 端口（按所在地过滤 / 取价）**：原料清单输入源连上某参与方后，前端建单时按该参与方产业类型的「所在地」节点过滤可选原料（仅展示「产地 `origin`（节点名数组）包含该节点」的原料）；`price` 聚合端点按该所在地节点取对应地点价（`computeMaterialListPrice`）。**存储约定（易错点）**：公司 `所在地` 字段（`CompanyFieldValue.value`，`fieldKey=location`）以 JSON 编码字符串存节点名（如 `北京` 存为 `"\"北京\""`），读取时须 `JSON.parse` 回普通字符串再与原料 `origin` 比较；若漏解析，引号会导致过滤下拉全空、按地区取价失效。相关读取点：`client/src/views/data-management/ContractManageView.vue` 的 `getCompanyLocation` 与 `server/src/modules/contracts/contract-engine.service.ts` 的 `resolvePartyLocationNodeId` 均已做安全解析（兼容纯字符串与 JSON 编码两种存储）。

### 10.10 合同生命周期与编号

合同状态：`DRAFT`（草稿）/ `EXECUTED`（已执行）/ `TERMINATED`（已终止）。

- **创建即存草稿**：`POST /contracts` 仅建 `DRAFT`，不执行、不落账；至少需一个实际公司参与方。
- **编号分步补全**：合同编号是各方私有信息，不能由一方代填。需要的编号数量 = 合同中**非主办方角色**数；主办方（主席团，`isHost=true`）永免编号、不计数量；经济管理中心是普通参与方（`isHost=false`），同样需编号。新建表单透出主办方一行（只读「无需编号」），非主办方需选公司并填编号；发起人建单时只填自己那方，其余留空（"未编号"），各方管理员在详情页内联补填（权限隔离：只能补自己 `companyScopes` 内的公司那方，经 `PATCH /contracts/:id/party-numbers`）。
- **执行落账**：所有非主办方编号齐全后，`execute` 从 `parties` 逐个校验编号非空，任一为空则拒绝（400，提示具体角色）；齐全则跑 `precheck` + `execute` 落账、置 `EXECUTED`。已执行合同不可改编号、不可重复执行。
- **检查错误窗口**：执行 / 创建后若前置检查（`conditions`）未通过，事务回滚、不落账，并弹出窗口逐条列出未通过项与原因（具体值 / 期望值 / 产业类型不符等）；创建后若当前用户有审核权限还会自动预检提示草稿问题。
- **删除即复原字段（不影响后续合同）**：执行合同会按效果改写公司产业字段（`CompanyFieldValue`），每次叶子效果落账一条不可变记录 `ContractFieldEffect`（含 `op` / 增量 `valueRaw` / 改写前 `beforeRaw`）。删除**已执行**合同时，引擎以「全部效果中按 `(executedAt,id)` 最早者的 `beforeRaw`」为基线，按 `executedAt` 顺序重放**其余**已执行合同的增量、写回 `CompanyFieldValue`，从而精确撤销本合同造成的字段变化；后续合同已落账的字段值完全不受影响（ADD / SUB / SET 语义均成立）。DRAFT / 无字段改写的合同删除不触发复原。

> 存量 `DRAFT` 数据仍可展示 / 终止，不会被自动执行。

### 11.1 合同类型全量提取（按产业/业务环节）

- **公司基础运行**：办公室拍卖交易合同、选址合同、薪资结算合同（本次赛事由《购销合同》代替）、借款合同（金融+借款+担保+主席团，一式四份）、股权投资协议（金融+被投+双方主席团）。
- **原料开采产业**：生产资料购买合同·矿点、生产资料购买合同·仓库/生产线/劳动力、原料开采合同、原料购销合同（原料↔加工，一式四份）、三方物流合同·原料运输（原料+加工+物流，一式六份）。
- **零件加工产业**：购销合同·原料采购、三方物流合同·零件运输、购销合同·仓库购置、购销合同·生产线购置、专利技术人才招募合同。
- **产品经销产业**：购销合同·仓库购置、生产设备购买合同、产成品等级评定合同、产成品加工合同、产成品购销合同、技术研发合同。
- **物流运输产业**：生产资料购买合同·运输工具购置、购销合同·物流节点购置、三方物流合同·物流。
- **金融服务产业**：证券承销与保荐协议（融资额、承销费率含超额配售分成）。
- **经济管理中心**：定向拨款协议（拨款金额、使用范围、绩效目标）、公共物品采购合同。

> 每份合同均标注参与方与「一式 N 份 / 谁持有 / 备案」等流程信息——软件可记录为字段（`copies`/`holders`），但不必实现物理份数。

**通用字段（所有合同）**：

### 11.3 已实现结论

1. **实现深度**：已实现配置驱动的执行引擎——效果可改写公司产业字段，执行前可检查公司状态（资金/产业字段等）。详见 §10。
2. **覆盖范围**：合同类型不再预置固定清单，改由用户在「合同类型管理」页按需自建（动态字段 `inputSchema`）。本清单的字段定义可作自建类型的模板参考；seed 不再预置任何合同类型。
3. **参数来源**：创建时手动填写 + 模板/配置带入，数值支持常量、输入引用、公式（`mathjs`），不写死。

**实现建议（数据结构草图）**：`ContractType`(id, name, defaultCopies, partyRoles[], fieldSchema) / `Contract`(id, contractTypeId, competitionId, fiscalYear, title, code, status, parties, fields, createdAt) / 参与方 `companyId` 引用 Company；其中主办方（主席团）用 `isHost=true` 枚举表示、不单独建实体、免合同编号且引擎跳过账户操作；经济管理中心为普通参与方（`isHost=false`），需绑定公司、填合同编号、引擎正常做账。

## 12. API 接口文档

> 基准路径：所有接口均以 `/api` 为全局前缀；下列路径已含前缀。

### 12.0 通用约定

**认证方式**：除明确标注「公开」的接口外，所有请求须在请求头携带 JWT：`Authorization: Bearer <token>`。Token 由 `POST /api/auth/login` 获取。登录后可调用 `GET /api/auth/me` 取回当前用户信息。

**统一响应结构**：成功响应统一为 `{ "code": 0, "message": "成功", "data": <业务数据> }`。失败（异常）时返回同样的 `{ code, message, data }` 形状，但 `code` 等于 **HTTP 状态码本身**（如 400/401/403/404/409/500），`data` 为 `null`。成功时 `message` 恒为 `"成功"`；失败时为中文错误信息。

> 客户端 `src/api/request.ts` 的响应拦截器已对成功响应做**解包**：组件通过 `api.get(...)` 直接拿到 `data` 字段内的业务数据。请求层另含**并发去重**与**本地持久化缓存**（IndexedDB，`cache.ts`）。

**分页与列表返回**：多数列表接口返回分页结构 `{ "items": [...], "total": 100, "page": 1, "pageSize": 50 }`。查询参数：`page`（默认 1）、`pageSize`（默认 50）。**注意例外**：`/warehouses`、`/production-lines` 不分页直接返回数组；`/companies`、`/competitions`、`/industry-types`、`/maps/full` 亦返回数组或对象。

**校验与错误**：全局 `ValidationPipe` 配置 `whitelist + forbidNonWhitelisted + transform`——传入 DTO 未声明的字段会被直接拒绝并返回 400（字段级错误数组折叠为一句 `"请输入有效数据"`）。状态码 → 中文 `message`：`400 请输入有效数据` / `401 未登录或令牌已过期`或`用户名或密码错误` / `403 权限不足` / `404 <资源>不存在` / `409 <名称>已存在` / `500 服务器内部错误`（原因仅入日志，不透出）。

**权限模型（细粒度 RBAC）**：见 §6.2。读接口需持 `domain:view`（或由同域 edit/manage 蕴含，见 §6.2）；写接口按 `@RequirePermissions` 校验；`SUPER_ADMIN` 隐式放行；合同审核/执行走 `ContractReviewGuard`（`contract:execute` 或 `contract:audit`）。

**多租户（比赛隔离）**：业务数据均带 `competitionId`（可空），`null` 视为全局共享字典。服务端 `request.user` 不含 `competitionId`，租户隔离依赖客户端在查询参数传入。四个地图接口（`/map-node-types`、`/path-types`、`/map-nodes`、`/map-edges`）的列表与删除均已支持 `competitionId` 过滤与归属校验，与 §5.1 一致。

### 12.1 认证与账户

**登录（公开）** `POST /api/auth/login`

请求体（`LoginDto`）：`username`(string, ≥2)、`password`(string, ≥4)。响应 `data`：`{ "token": "<jwt>", "user": { "id", "username", "role", "displayName" } }`。失败（401）：`用户名或密码错误`。

**获取当前用户** `GET /api/auth/me`：守卫登录。响应 `data`：`{ id, username, role, displayName }`。用户不存在返回 401 `用户不存在`。

**用户管理**（类级守卫 `JwtAuthGuard + PermissionsGuard + @RequirePermissions("account:manage")`）：

| 方法     | 路径                        | 说明                                                                       | 请求体                                      |
| ------ | ------------------------- | ------------------------------------------------------------------------ | ---------------------------------------- |
| GET    | `/api/users`              | 分页列表，Query：`page`(1)/`pageSize`(20)/`competitionId`（支持 `null`/`""` 查未分配） | —                                        |
| GET    | `/api/users/:id`          | 详情                                                                       | —                                        |
| POST   | `/api/users`              | 创建                                                                       | `CreateUserDto`                          |
| PATCH  | `/api/users/:id`          | 更新（不可改 username / competitionId）                                         | `UpdateUserDto`                          |
| PATCH  | `/api/users/:id/password` | 改密                                                                       | `UpdatePasswordDto { password: string }` |
| DELETE | `/api/users/:id`          | 删除                                                                       | —                                        |

`CreateUserDto`：`username`(≥2)、`password`(≥4)、`role?`(`IsIn` 三选一，默认 PLAYER)、`displayName?`、`competitionId?`(int)。`UpdateUserDto`：`role?`、`displayName?`。

### 12.3 通用数据字典（CRUD 同构）

以下模块控制器结构完全同构：

- 读操作：控制器类级 `@RequirePermissions("data:<module>:view")`（持有该域 view 或 edit/manage 即可，见 §6.2 蕴含规则）；地图相关模块（map-nodes/map-edges/map-node-types/path-types/maps/full）同属 `data:map:view`，科技树为 `data:tech:view`，区域为 `data:region:view`。
- 写操作（POST/PATCH/DELETE）：方法级追加 `PermissionsGuard + @RequirePermissions("data:<module>:edit")`（覆盖类级 view）。
- 编辑权限 key 映射：materials→`data:material:edit`、parts→`data:part:edit`、products→`data:product:edit`、tech-nodes→`data:tech:edit`、infrastructures→`data:infrastructure:edit`、fuels→`data:fuel:edit`、vehicles→`data:vehicle:edit`、warehouses→`data:warehouse:edit`、production-lines→`data:productionLine:edit`；对应只读权限均为 `data:<module>:view`。

| 方法     | 路径                | 说明               | 请求体                                     |
| ------ | ----------------- | ---------------- | --------------------------------------- |
| GET    | `/api/{base}`     | 分页列表（见 §12.0 例外） | Query：`page`/`pageSize`/`competitionId` |
| GET    | `/api/{base}/:id` | 详情               | —                                       |
| POST   | `/api/{base}`     | 创建（超管）           | `Create{X}Dto`                          |
| PATCH  | `/api/{base}/:id` | 更新（超管）           | `Update{X}Dto`                          |
| DELETE | `/api/{base}/:id` | 删除（超管）           | —                                       |

各模块 base 与关键字段：

- **原料** `/api/materials`：`CreateMaterialDto`（均必填）`name`(string)、`origin`(string)、`price`(number, ≥0)、`carbonEmissionCoefficient`(number, ≥0)；可选 `type`(`NORMAL`/`SPECIAL`)、`competitionId`(int)。
- **零件** `/api/parts`：`CreatePartDto`：`name`(必填)；`partMaterials`(必填, `[{ materialId:number, ratio:number }]`)；`techRequirements`(必填, `[{ techNodeId:number }]`)；可选 `competitionId`。
- **产品** `/api/products`：`CreateProductDto`：`name`(必填)；`productParts`(必填, `[{ partId:number, ratio:number }]`)；`techRequirements`(必填, `[{ techNodeId:number }]`)；可选 `competitionId`。
- **科技树节点** `/api/tech-nodes`：`CreateTechNodeDto`：`name`(必填)、`tier`(number 必填)、`researchCost`(number 必填)；可选 `description`、`prerequisites`(`[{ prerequisiteNodeId:number }]`)、`competitionId`。
- **基建** `/api/infrastructures`：`CreateInfrastructureDto`（10 项属性均必填且 ≥0）：`name`、`footprint`、`employmentRateBonus`、`populationBonus`、`highQualityPopulationBonus`、`price`、`happinessIndexBonus`、`perCapitaIncomeBonus`、`carbonReductionBonus`、`activationPrice`；可选 `competitionId`。
- **燃料** `/api/fuels`：`CreateFuelDto`：`name`(必填)、`pricePerLiter`(number ≥0 必填)；可选 `competitionId`。
- **载具** `/api/vehicles`：`CreateVehicleDto`（均必填）：`name`、`fuelId`(int)、`fuelConsumptionPerKm`(≥0)、`maxCargo`(≥0)、`price`(≥0)、`carbonEmission`(≥0)；可选 `pathTypeIds`(number[])、`vehiclePathTypes`(`[{pathTypeId:number}]`)、`competitionId`。
- **仓库** `/api/warehouses`（不分页）：`CreateWarehouseDto`（均必填）：`name`、`capacity`(number)、`price`(number)、`type`(`MATERIAL`/`PART`/`PRODUCT`/`FUEL`)；可选 `competitionId`。
- **生产线** `/api/production-lines`（不分页）：`CreateProductionLineDto`（均必填）：`name`、`price`(≥0)、`laborCount`(int, ≥1)、`maxPerYear`(≥0)；可选 `competitionId`。

### 12.5 公司管理

类级守卫：`JwtAuthGuard, PermissionsGuard` + `@RequirePermissions("company:view")`：读接口（列表 / 详情 / impact）继承类级 view（可由 `company:manage` 蕴含）。**公司可见字段范围（viewCompanyScopes）约束**：`SUPER_ADMIN`/`company:manage`/`data:region:edit` 可见全部公司；仅持 `company:view` 者按 `viewCompanyScopes` 过滤列表、范围外公司 `GET /:id` 与 `/:id/impact` 返回 403、其全量字段读也受同一范围约束（见 §9.9）；`viewCompanyScopes` 为空则不限制。主 CRUD（POST/PATCH/DELETE）方法级覆盖为 `company:manage`。公司产业字段值读接口（`GET /company-fields/:companyId`）走自定义发布 + 范围逻辑（详见 §9.9），写接口（`PUT /company-fields/:companyId`）需 `company:manage`。

### 12.9 已知限制与不一致（对接前必读）

1. **非 `SUPER_ADMIN` 角色的能力完全取决于其 `permissions` 数组**：`COMPETITION_ADMIN` / `PLAYER` 仅是 `role` 值，不含任何隐含权限。`permissions` 为空数组时，该账号对业务数据既无读（需 `*:view`，可由同域 edit/manage 蕴含，见 §6.2）也无写权限——即「无任何数据访问」，而非「只读」。如需让某账号只读某域数据，应显式授予该域 `*:view`。
2. **公司子资源写接口已有 `company:manage` 权限校验，但无 DTO 校验**（body 为 `any`），写入结构由调用方保证。
3. **财年 3 个写接口 body 为内联类型**，绕过 `ValidationPipe` 校验。
4. **地图四类子资源与 `getFullMap` 已按 `competitionId` 过滤**，删除经 `assertSameCompetition` 作用域校验 + `GET /:id/impact` 级联警告（见 §5.1）。
5. **列表返回形状不统一**：多数为 `{items,total,page,pageSize}`；`warehouses`/`production-lines`/`companies`/`competitions`/`industry-types`/`maps/full` 为裸数组或对象。
6. **删除返回不统一**：多数返回 `{message:"已删除"}`；`competitions` 删除返回被删实体对象。
7. **`request.user` 不含 `competitionId`**，租户隔离依赖客户端 Query 传参。
8. **合同系统已完整实现并暴露 API**：`/api/contract-types`、`/api/contracts` 均可调用（合同执行/预检经 `ContractReviewGuard`：`contract:execute` 或 `contract:audit`）。引擎按 `ContractType` 配置驱动，效果仅 `FIELD`（改写公司产业字段），前置检查共 5 类（`FIELD_COMPARE`/`VALUE_COMPARE`/`INDUSTRY_IS`/`DICT_COMPARE`/`LIST_COMPARE`）。
9. **命名不一致**：`parts` 模块 404 称"部件"、409 称"零件"；`vehicles` 模块 404 称"车辆"、409 称"载具"。

### 12.11 实时广播（WebSocket / Socket.IO）

服务端复用 HTTP 端口（默认 3000）提供 Socket.IO 实时通道，用于比赛 / 财年 / 合同状态 / 公司字段变更的即时同步，避免前端轮询。

- **鉴权**：握手时通过 `client.handshake.auth.token`（或 `?token=`）携带 JWT，校验失败直接断开连接。
- **房间模型**：客户端连接后发送 `{ competitionId }` 的 `subscribe` 事件加入 `comp-{competitionId}` 房间；`unsubscribe` 退出。仅同比赛的客户端收到对应广播。
- **广播事件**（均为比赛房间级，payload 为变更后的实体 / 状态）：
  - `fiscal-year:changed` —— 开 / 关财年、财年状态变更（payload 携带 `fiscalYear{status,year}`，前端直接据此更新，无需回源请求）。
  - `competition:changed` —— 比赛信息或状态变更。
  - `contract:changed` —— 合同新建 / 执行 / 状态变更。
  - `company-field:changed` —— 公司产业字段写入（payload 携带 `companyId` / `competitionId`）。前端 `resource-changed.ts` 将其统一转译为 `resource-changed` 窗口事件（`resource="company-field"`），公司详情页据此在本地全量副本上做**增量刷新**；该集合已接入 §8.5 增量同步（本地全量副本 + `updatedAfter` + 5 分钟强制全量 + 断线重连主动对账），因此参赛队员等所有同比赛前端都能可靠拿到最新产业字段值，不再依赖单一组件自行订阅。
- **客户端接入**：客户端启动后建立 Socket.IO 连接，监听上述事件以驱动相关界面即时刷新。

### 13.2 全局守卫执行顺序

`APP_GUARD` 注册顺序即拦截链：`JwtAuthGuard`（鉴权，放行 `@Public`）→ `MustChangePasswordGuard`（强制改密）→ `CompetitionScopeGuard`（比赛归属）→ `PermissionsGuard`（路由级 RBAC）。认证失败、需改密、越权访问均返回标准化错误，不向客户端泄露细节。

### 13.3 强制改密流程

默认超管 `admin / admin123` 首次登录后标记 `mustChangePassword = true`，除「改密 / 查看自身」外所有业务接口被守卫拦截，前端登录页弹出不可关闭的改密对话框；提交成功后清除标记并进入系统。生产环境必须首次登录即改密，再投入运营。

### 13.4 生产硬性检查项

- `JWT_SECRET` 必须替换为 ≥ 32 字节强随机值（`openssl rand -base64 48`），并保持跨重启稳定。
- `CORS_ORIGIN` 指定可信域名（桌面客户端直连可留本地默认值）；**不再允许通配 `*` 与凭证同用**。
- 默认超管务必首次登录即改密；如需更严，可在 seed 中关闭默认创建，改为运维手动建超管。
- 密码策略：最小长度 8 位且需同时包含字母与数字（前后端一致）；管理员通过界面新建的账号默认强制「首次登录改密」，不可永久使用初始密码。

### 13.6 按 ID 直查越权读闭环（BOLA）

对「按 ID 直查」的系统性越权读（整体逻辑复查发现，初版加固未覆盖）做闭环：

- **问题**：约 17 个比赛级业务模块的 `GET /:id`（详情）与 `GET /:id/impact`（级联影响）按主键直查，既不携带也不读取 `competitionId`，`CompetitionScopeGuard` 只校验列表/删除的 `competitionId` 参数，无法约束直查。一个比赛的玩家可用顺序 ID 枚举读走任意比赛数据——尤其 `company-fields`（现金 / 库存 / 所在地等核心商业机密）与 `users`（用户名 / 角色 / 权限）。
- **整改**：新增 `common/guards/ownership.guard.ts` 与 `@Ownership` 装饰器。守卫仅对标注了 `@Ownership` 且路由含对应 id 参数的接口生效，用**请求者真实归属比赛**（`user.competitionId`，非前端可伪造的查询参数）校验被查实体归属：超管豁免；其余角色实体 `competitionId` 必须等于本人所属比赛；实体不存在返回 404。
- **标注范围**：`User` / `Company` / `Contract` / `Product` / `Material` / `TechNode` / `Part` / `Warehouse` / `Vehicle` / `Fuel` / `ProductionLine` / `MapNode` / `MapEdge` / `MapNodeType` / `PathType` / `Infrastructure` 直接持有 `competitionId`，用 `@Ownership({ model })`；`CompanyField` 经 `companyId` 关联 Company，用 `@Ownership({ viaCompany: true, param: "companyId" })`。列表接口（无 id 参数）自动放行，不影响既有数据流。
- **豁免**：全局模板 `ContractType` / `IndustryType` 与比赛实体 `CompetitionController` 已用 `@NoCompetitionScope()` 豁免，对所有角色可见（含选比赛流程）；其 `findOne` 不标注 `@Ownership`。

### 13.7 两处设计语义澄清（非缺陷）

- **`company-fields` 写权限**：写接口要求 `company:manage`（仅超管）。这是设计预期——公司产业字段（现金 / 库存 / 所在地等）由合同引擎计算或有意由超管独占管理，比赛管理员不开放写；如需放开，应在 `company-fields.controller` 调整 `@RequirePermissions`。
- **`company-fields` 读权限（按总览公开区分）**：读接口 `GET /company-fields/:companyId` 现已区分读权限——`SUPER_ADMIN` 或持有 `company:view` / `company:manage` / `data:region:edit` 的角色可读该公司全部（visible）字段；其余已登录角色仅可读已发布到区域总览（`Region.overviewCards` 中的 `(companyId, industryFieldId)` 对）的字段，未上总览的产业字段对其不可见。判定由服务端 `CompanyFieldsService.getPublishedFieldIds` 解析该比赛全部 Region 的 `overviewCards` 实现。
- **`compareField` 结构化字段数值比较**：合同条件 `FIELD_COMPARE` 对 `LIST` / `DICTIONARY` 类型字段使用数值算子（`==` `>=` `<=` `>` `<`）时，比较的是**元素个数 / 键数量**（引擎报错 `detail` 会显示 `长度=…`），并非字段内容。合同设计者配置时需注意此语义。

### 13.8 删除前级联影响提示审计与多层删除确认

删除是高风险操作：多数实体存在 `onDelete: Cascade` 子表，点「确认」会静默连带删除大量数据。为降低误删风险，系统提供两道互补防线——**后端级联影响提示端点**与**前端多层确认弹窗**。本节记录对该机制的一次一致性审计与修复结果。

#### 13.8.1 审计方法（权威事实源）

- 本仓库用 `prisma db push` 同步结构，**线上库以 `server/prisma/schema.prisma` 为权威事实源**。
- 对 schema 中**未显式声明** `onDelete` 的关系，以迁移 SQL（`prisma/migrations/*_init`）的实际动作判定——例如 `Vehicle.fuelId` 在迁移中为 `ON DELETE RESTRICT`（非 Cascade）。
- 前端 `utils/deleteConfirm.ts` 的 `confirmDeleteWithImpact` 仅渲染后端返回的 `children`，自身不判定级联，故**任何前后端不一致均为用户可见**。

#### 13.8.2 端点一览与命名约定

后端为 15 个实体提供 `GET /:resource/:id/impact` 端点，返回 `{ name, children: [{ label, count }] }`：

- `materials` / `parts` / `products` 三个服务的方法名为 `getDeleteImpact`；
- 其余 12 个实体（`warehouse` / `infrastructure` / `vehicle` / `production-line` / `company` / `tech-tree` / `fuel` / `contract` / `map-edge` / `map-node` / `path-type` / `map-node-type`）使用同名 `*Impact`（如 `getCompanyImpact` / `getFuelImpact` / `getContractImpact` / `getTechNodeImpact`）。

审计以 schema + 迁移 SQL 为基准逐项核对，**12 个正确，3 个不符（已修复，纯后端语义修复，前端无需改动）**：

| # | 实体              | 问题                                                                                                                                                                                   | 修复                                                                                                                                                                   |
| - | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | **TechNode** 漏报 | `TechPrerequisite` 的 `nodeId` 与 `prerequisiteNodeId` 两外键**均** Cascade，但 `getTechNodeImpact` 只统计了 `prerequisiteNodeId`（「以该节点为前提的科技关系」），漏掉 `nodeId`（「该节点的前提依赖关系」）——删除科技节点会静默级联删掉前者而不预警 | 新增 `techPrerequisite.count({ where: { nodeId: id } })` 并 push「该节点的前提依赖关系」，与既有 `requiredBy` 共同覆盖两个 Cascade 方向                                                         |
| 2 | **Contract** 漏报 | `getContractImpact` 直接返回空 `children`；但 `ContractFieldEffect.contractId` 是 `onDelete: Cascade`——删合同会级联删字段效果行，弹窗无任何警告                                                                  | 删除空返回，新增 `contractFieldEffect.count({ where: { contractId: id } })` 并 push「合同字段效果」                                                                                   |
| 3 | **Fuel** 误报     | `getFuelImpact` 报告「使用该燃料的载具将被级联删除」，前端据此弹「将级联删除 N 条载具」；但 `Vehicle.fuelId` 无 `onDelete`（迁移 RESTRICT），载具**不会被级联删**、反而**删除会被外键阻止并报 500**——提示与真实行为相反                                      | `getFuelImpact` 不再谎报、返回空 `children`；并给 `remove` 加前置校验——若 `vehicle.count({ fuelId: id }) > 0` 抛 `ConflictException("该燃料正被 N 个载具使用，无法删除（请先为这些载具更换燃料）")`，避免点确认后 500 硬报错 |

> 修复后**后端须重启 NestJS 进程**才生效（运行中的进程仍加载旧逻辑）；前端仅消费既有 `children`，无需改动。

#### 13.8.4 多层删除确认弹窗（UI 防线）

对于**无 impact 端点**但删除破坏力大的实体，改用前端多层 `ElMessageBox.confirm` 顺序确认（对标 `CompetitionListView` 模式，纯前端、无需后端改动）：

| 实体                     | 确认层数                             | 说明                                                                                     |
| ---------------------- | -------------------------------- | -------------------------------------------------------------------------------------- |
| **比赛（Competition）**    | **3 层**（warning → error → error） | 删除比赛会清空大半数据库，破坏力最大，故配三层顺序确认；比赛本身已有 `@NoCompetitionScope` 豁免且无需 impact 端点               |
| **产业类型（IndustryType）** | **2 层**（warning → error）         | 其下 `IndustryField` 已由 schema `onDelete: Cascade` 随删，无需后端端点；两层确认文案明确「其下的产业字段会一并删除且不可恢复」 |
| **合同（Contract）**       | **2 层**（warning → error）         | 已执行合同删除会触发字段复原（见 §10.10），两层确认防止误删已落账合同                                                 |

设计约定：`confirmDeleteWithImpact`（带级联子表的实体）与「纯多层 `ElMessageBox` 确认」（无端点的大破坏力实体）二者择一，确保任何删除都有明确、如实的二次及以上劝阻；`IndustryType` / `Competition` 的 impact 端点缺口**未补**，由多层确认替代（用户确认比赛删除已有三层确认、无需补端点）。

## 14. 部署与运维

本文档面向将系统部署到生产/竞赛现场环境的运维与开发人员，覆盖服务端部署、反向代理、客户端分发、备份与故障排查。

### 14.1 环境变量

服务端所有可配置项均通过 `server/.env` 提供（项目已内置一份开发用 `.env`，生产环境务必逐项核对并修改）。

| 变量               | 默认值                                             | 说明                                                                    | 生产建议                                       |
| ---------------- | ----------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------ |
| `PORT`           | `3000`                                          | HTTP 监听端口                                                             | 按部署规划设定                                    |
| `DATABASE_URL`   | `"file:./dev.db"`                               | SQLite 文件路径，**相对于 `server/prisma/` 目录**，即实际文件为 `server/prisma/dev.db` | 保持相对路径；备份时连同该文件一起备份                        |
| `JWT_SECRET`     | 无（未配置则启动失败）                                     | JWT 签名密钥；代码已 fail-closed，缺失直接拒绝启动                                     | **必须设为 ≥ 32 字节强随机值**（见 §13.4），否则服务无法启动     |
| `JWT_EXPIRES_IN` | `"24h"`                                         | Token 有效期                                                             | 按安全策略调整（如 `12h`）                           |
| `CORS_ORIGIN`    | `"http://localhost:5173,http://localhost:3000"` | 允许跨域的来源（逗号分隔）                                                         | 桌面客户端直连可留默认；若有 Web 管理端，应限制为具体域名；不再支持通配 `*` |

| `LOG_DIR`        | `"./logs"`                                      | 日志目录，**相对于服务端工作目录**                                                   | 确保该目录可写；建议挂载到持久卷                           |

> 客户端默认连接 `http://localhost:3000`，该地址已抽取为 `client/src/config/index.ts` 中的 `DEFAULT_SERVER_URL` 常量，用户可在登录页/设置页修改，无需改代码。

桌面客户端通常直连 `http://localhost:3000`，无需反向代理。远程访问 / HTTPS / 限制 CORS 场景建议 Nginx：

### 14.7 备份与数据迁移

SQLite 是单文件数据库，备份极简：

1. **停止写入**（或短暂停服）：`pm2 stop gipfel-server` 或 `systemctl stop gipfel-server`。
2. **复制数据库文件**：`server/prisma/dev.db`（以及可能的 `-journal` 文件）。
3. **重启服务**。


## 15. 模块开发指南（面向二次开发者）

服务端：NestJS（Controller / Service / Module / DTO）。客户端：Electron + Vue 3。

### 15.0 通用开发约定

**服务端「标准 CRUD 模块」骨架**：

```
src/modules/<name>/
├── <name>.module.ts        # @Module({ controller, provider })
├── <name>.controller.ts    # 路由 + 守卫
├── <name>.service.ts       # 业务逻辑 + Prisma 调用
└── dto/
    ├── <name>.dto.ts       # Create/Update DTO（class-validator）
```

- 控制器守卫模板：类级 `@UseGuards(JwtAuthGuard)`；写操作追加 `@UseGuards(PermissionsGuard)` + `@RequirePermissions("domain:action")`。`SUPER_ADMIN` 隐式拥有全部权限；其余角色能力取决于其 `permissions` 数组。
- 服务返回约定：列表分页接口返回 `{ items, total, page, pageSize }`；需 `competitionId` 过滤时从 Query 读取，`null` 视为全局共享。
- 统一响应：成功由 `ResponseInterceptor` 包装为 `{ code:0, message:"成功", data }`，开发者只管返回业务数据。
- 错误处理：在 service 中 `throw new NotFoundException("xxx不存在")` / `ConflictException("xxx名称已存在")` 等，过滤器会统一为中文 `message`。

**客户端「标准数据管理页」骨架**：

- 通过 `client/src/api/index.ts` 的 `*Api` 对象调用接口（底层统一走 `client/src/api/request.ts` 的 `api`）。
- 读取器直接使用 `api.get(...)` 返回值（已解包为业务数据）。
- 写操作前校验，失败由 `request.ts` 响应拦截器统一 `ElMessage.error`，组件内一般无需重复弹窗（仅保留 `console.error`）。
- 请求经 `request.ts` 统一拦截，含**并发去重**与**本地持久化缓存**（IndexedDB）。

> 历史代码中曾存在三套 HTTP 层，现已**全部收敛到 `client/src/api/request.ts` 的 `api`**。新增请求请统一 `import api from "@/api/request"` 或使用 `client/src/api/index.ts` 中的 `*Api` 封装，不要新建 axios 实例。

**默认服务地址**：客户端默认地址常量集中在 `client/src/config/index.ts` 的 `DEFAULT_SERVER_URL`（`http://localhost:3000`），被 `request.ts`、`stores/config.ts`、`stores/competition.ts`、`LoginView.vue`、`SettingsView.vue` 共用。修改默认值只改这一处。

### 15.1 各模块关键文件

| 模块     | 服务端关键文件                                                                    | 客户端关键文件                                                                                          |
| ------ | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 认证/账户  | `src/auth/*`、`src/users/*`、`src/common/guards/*`、`src/common/decorators/*` | `stores/auth.ts`、`views/login/LoginView.vue`                                                     |
| 比赛与财年  | `src/modules/competitions/*`                                               | `views/competitions/CompetitionListView.vue`、`stores/competition.ts`                             |
| 生产链    | `src/modules/materials/`、`parts/`、`products/`                              | `views/data-management/{Materials,Parts,Products}Manager.vue`                                    |
| 科技树    | `src/modules/tech-tree/*`                                                  | `views/data-management/TechTreeManager.vue`                                                      |
| 地图     | `src/modules/maps/*`（1 service + 5 controller）                             | `views/data-management/MapsManager.vue`                                                          |
| 燃料/载具  | `src/modules/fuels/`、`vehicles/`                                           | `views/data-management/{Fuels,Vehicles}Manager.vue`                                              |
| 仓库/生产线 | `src/modules/warehouses/`、`production-lines/`                              | `views/data-management/{Warehouses,ProductionLines}Manager.vue`                                  |
| 基建     | `src/modules/infrastructures/*`                                            | `views/data-management/InfrastructureManager.vue`                                                |
| 公司     | `src/modules/companies/*`                                                  | `views/companies/CompanyListView.vue`、`views/companies/CompanyDetailView.vue`                    |
| 产业类型   | `src/modules/industry-types/*`                                             | 产业类型管理页（需 `industryType:manage`）                                                                 |
| 合同     | `src/modules/contracts/*`（含 `contract-engine.service.ts`）                  | `ContractTypeManageView`、`ContractManageView`、`components/contracts/ContractTypeGraphEditor.vue` |
| 区域     | `src/modules/regions/*`                                                    | `views/regions/RegionManageView.vue`、`views/regions/RegionOverviewView.vue`                      |

要点：

- **认证**：`auth.service` 用 `bcryptjs` 比对密码，签发 JWT（payload 含 `sub/username/role`）。`JwtAuthGuard`（401）、`PermissionsGuard`（403）。用户管理整控制器需 `account:manage`。创建用户时 `role` 默认 `PLAYER`，并可于 `permissions` 中赋予细粒度 key。
- **比赛**：`Competition` 是租户根，删除级联关联数据。财年写接口 body 为内联类型、未走 DTO 校验。
- **生产链**：`Material →(PartMaterial)→ Part →(ProductPart)→ Product`；零件/产品通过 `*TechRequirement` 关联科技树。DTO 用 `@ValidateNested` + `@Type` 校验嵌套数组。
- **地图**：`MapController`(`/maps`) 的 `GET /maps/full` 返回聚合图；4 个子控制器（`/map-node-types`、`/path-types`、`/map-nodes`、`/map-edges`）均已支持 `competitionId` 过滤与归属校验；`MapEdge` `@@unique([fromNodeId, toNodeId])`。
- **燃料/载具**：`Vehicle.fuel` 关系无 `onDelete`，删除燃料前需先解绑载具；`vehiclePathTypes` 为权威结构。
- **公司**：主 CRUD 需 `company:manage`；公司不再持有分部/库存/载具/科技/基建子资源，合同仅改写 `CompanyFieldValue`。
- **产业类型**：不再自动播种，由用户在「产业类型管理」页自建；`fieldType` 取值 `STRING`/`NUMBER`/`BOOLEAN`/`DICTIONARY`/`LIST`。
- **合同**：`ContractType`（全局模板）与 `Contract`（比赛级）两套控制器 + `contract-engine.service.ts`；效果仅 `FIELD`，前置检查 5 类；设计详见 §10。

### 15.4 构建、迁移与工具链注意事项

> 本条整合自项目长期记忆中的「构建环境坑」，供二次开发者与 CI 排障参考。

- **改 Schema 后的强制三步（通用、必读）**：任何 `schema.prisma` 变更（新增 / 删除模型或字段、改动关系）都必须依次执行：`npx prisma generate`（重新生成 Prisma Client）→ `npx prisma db push`（同步线上库结构）→ **重启后端 NestJS 进程**。运行中的进程加载的是旧 Client，若未重启会因「新模型在 Client 中不存在」而在运行时抛 `Cannot read properties of undefined`（例如 `prisma.contractFieldEffect` 为 `undefined`）导致 500。前端若改动了 `client/src` 也需重新构建 / 刷新。
- **全量类型检查在受限环境可能挂起**：服务端 `nest build`（`tsc` 全量）与客户端 `npm run build`（含 `vue-tsc --noEmit`）在部分受限 / 沙箱构建环境下可能长时间无输出而挂起；**最终验证请在本地开发机执行** `npm run build` / `vue-tsc --noEmit`，勿以沙箱内挂起结果判定编译是否通过。
- **受限环境下的文件操作拦截（仅特定自动化沙箱）**：个别沙箱会注入「回收站」shim 拦截 `fs.rmSync` 等删除 / 重命名调用，导致 `prisma generate` 在最后一步重命名引擎 dll（`query_engine-*.dll.node`）时受阻。绕法：执行前清除会话环境变量后再跑生成命令；若仍残留 `*.tmp*` 引擎文件，直接用底层 `rm -f` 删除残留 `.tmp` 文件即可（其 `index.d.ts` / `index.js` 通常已生成完毕，正式引擎 dll 也已存在且内容相同，仅 `.tmp` 残留）。
- **迁移文件为历史存档**：`prisma/migrations/` 下早期迁移含 `CompanyBranch` / `CompanyVehicle` / `CompanyInventory` / `CompanyTech` 等陈旧表，但当前 `schema.prisma` 已无这些模型，`db push` 后线上不包含，仅作历史存档、不影响结构验证（权威事实源始终是 `schema.prisma`）。

## 17. 仪表盘（新版网格画布）

仪表盘已从「统计卡片 + 快捷操作」重构为**可自由编排的网格画布**：

- **圆点网格背景**：20px 间距圆点网格，铺满仪表盘**画布区域**（不含顶部标题栏）；控件可吸附网格自由拖动、自由放大缩小（方形控件，宽高独立，最小 100 / 最大 480）。**拖动 / 缩放过程中实时跟随指针自由变化，松开后位置与宽高均自动吸附到最近的网格线**（宽高各自吸附到 20px 的整数倍，最小不小于 100 / 最大不超过 480）；缩放采用右下角手柄，**宽度随横向拖动、高度随纵向拖动，支持非等比（自由宽高比）缩放**。
- **右下角圆形 ＋ 按钮**：点击弹出菜单，添加三类控件——`文字控件`（直接展示文字内容或绑定字段值）、`仪表控件`（SVG 圆环，底部留缺口，中心偏下显示百分比，并标注剩余百分比）、`表格控件`（新增）。仪表的**总量与展示量均可选择**：既可手动填写数值，也可各自绑定一个「可查看字段」（取值实时跟随字段当前值）；绑定时对应数值输入框隐藏并提示来源。
- **表格控件**：把一个**字典（键值对）**&#x6E32;染成两列表格（左列键 / 右列值），内容区**可滚动**（控件内部 overflow:auto）；数据来源既可绑定一个「可查看字段」（该字段当前值须为字典），也可在编辑中直接填写静态 JSON 字典（如 `{"项目A":10,"项目B":20}`）；可选标题显示在表格上方。绑定字段值随实时广播自动刷新。**注意**：产业字段（公司字段）的字典值由后端以 **JSON 字符串** 形式存储（`CompanyFieldValue.value` 为 String 列），前端 `tableEntries` 渲染时会自动 `JSON.parse` 该字符串；若字段值为字符串形式的数组（`[[k,v],...]` 或 `[{key,value},...]`）也支持，会展开为键值行。
- **控件外形均为方形带圆角**，选中后浮出编辑/删除工具条与右下角缩放柄；**右键点击控件**会弹出上下文菜单，可快捷选择「编辑」或「删除」。
- **字段绑定（可查看字段）**：编辑控件时可从「自己可查看的所有字段」中选择绑定来源，包括：
  - **区域总览字段**：地图区域总览中已发布的数据框（公开可读，需有 `data:region:view`/`edit` 权限或超管）。
  - **公司字段**：服务端 `companiesApi.list` 已按 `viewCompanyScopes` 过滤后的可见公司，逐个拉取其产业字段（范围外公司不在列表内，不会触发降级 403）。
  - 字段值经实时广播（`company-field` / `region` / `map-node`）自动刷新。
- **纯本地保存**：控件布局（位置、大小、绑定字段、文字/总量等配置）仅存浏览器 `localStorage`，按**当前比赛**隔离（`dashboard.widgets.v1.<competitionId>`），不上传云端；刷新或下次进入自动还原。无网络时静态文字 / 手动数值控件仍可用。
