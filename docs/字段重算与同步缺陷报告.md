## 一、字段重算机制

### 当前架构

```
普通字段写入 → $transaction(基础字段 upsert)
                    ↓（事务外）
              recomputeCalculatedFields
                    ↓
              1. 查询全部字段当前值 → 构建 scope
              2. 计算字段间依赖分析 → 拓扑排序
              3. 按序求值每个计算图 → serializeFieldValue
                    ↓
              $transaction(计算字段 upsert)
                    ↓
              broadcastToCompetition("company-field:changed")
```

---

### 缺陷 R1（严重）：基础字段写入与计算字段重算之间存在竞态窗口

**位置**：[company-fields.service.ts:265-283](server/src/modules/company-fields/company-fields.service.ts#L265-L283)

```typescript
// 第 265 行：基础字段写入 —— 在事务内
await this.prisma.$transaction(upserts);

// 第 283 行：重算 —— 在事务外，独立操作
await this.recomputeCalculatedFields(companyId, company.industryType.fields);
```

**问题**：两个操作之间存在时间窗口。并发请求（合同执行、其他用户写入、定时器触发）可在此窗口内修改同一公司的字段值。重算读取到的 scope 可能包含非本次写入的值。

**具体场景**：
1. 用户 A 写入 `revenue = 100`（事务提交）
2. 用户 B 写入 `cost = 30`（事务提交）
3. A 的重算开始，读取 scope = `{revenue: 100, cost: 30}`（包含了 B 的写入）
4. B 的重算开始，读取 scope = `{revenue: 100, cost: 30}`
5. 两次重算都计算 `profit = revenue - cost = 70`，但实际应分别重算

更严重的是，如果两次重算并发写入同一 `CompanyFieldValue` 行，后写入者覆盖前者，最终值取决于写入顺序而非因果关系。

**影响**：并发写入时计算字段最终值可能不正确。

**建议**：将重算纳入同一个 `$transaction`，或使用 `SELECT ... FOR UPDATE` 锁定 `CompanyFieldValue` 行。

### 缺陷 R3（严重）：重算的 scope 读取与写入不是原子操作

**位置**：[company-fields.service.ts:549-619](server/src/modules/company-fields/company-fields.service.ts#L549-L619)

```typescript
// 第 556 行：读取全部字段值构建 scope
const vals = await this.prisma.companyFieldValue.findMany({ where: { companyId } });

// ... 拓扑排序、逐个求值 ...

// 第 611 行：写入计算结果
await this.prisma.$transaction(upserts);
```

**问题**：从读取 scope 到写入结果之间，有多个 `await` 点（`calcEngine.evaluate` 内部可能查数据库求 `CONSUMER_DEMAND`）。在此期间并发写入可修改 scope 中的值，导致写入的计算结果基于过时数据。

**影响**：计算字段值可能基于陈旧的输入值。

**建议**：整个重算过程应在单一事务内完成（读 + 算 + 写），或使用乐观锁（version 字段）检测并发冲突后重试。

### 缺陷 R4（高）：CONSUMER_DEMAND 节点每次求值都查数据库

**位置**：[industry-calc-engine.service.ts:250-267](server/src/modules/industry-types/industry-calc-engine.service.ts#L250-L267)

```typescript
private async resolveConsumerDemandTotal(ctx?): Promise<number> {
  // 每次求值都执行：
  // 1. findFirst MapNode（查区域）
  // 2. aggregate ConsumerDemand（求和）
}
```

**问题**：一个计算图中若有多个 `CONSUMER_DEMAND` 节点，或多个公司的重算串行执行，每个节点/公司都会独立查询数据库。重算 50 个公司 × 每公司 2 个 CONSUMER_DEMAND 节点 = 200 次 DB 查询。

**影响**：重算性能随公司数和节点数线性增长。

**建议**：
1. 在 `recomputeCalculatedFields` 入口处预查询并缓存 `CONSUMER_DEMAND` 结果
2. 或在 `evaluate` 时传入预计算的 `consumerDemandCache`

### 缺陷 R5（高）：消费者需求变更触发重算时逐公司查询，无批量优化

**位置**：[company-fields.service.ts:343-346](server/src/modules/company-fields/company-fields.service.ts#L343-L346)

```typescript
const companies = await this.prisma.company.findMany({
  where: { competitionId },
  include: { industryType: { include: { fields: true } } },  // 加载全部字段定义
});
```

**问题**：加载**所有**公司及其完整产业类型和字段定义，然后在内存中逐个检查 `calcGraph.includes("CONSUMER_DEMAND")`。

**影响**：若比赛有 100 家公司、每公司 20 个字段，每次消费者需求变更都加载 2000 个字段定义。

**建议**：
1. 先查 `IndustryField` 找出含 `CONSUMER_DEMAND` 的产业类型 id 列表
2. 再查 `Company WHERE industryTypeId IN (...) AND competitionId = ?`
3. 只加载匹配的公司

### 缺陷 R12（低）：`recomputeCalculatedFields` 每次都重新查询 CompanyFieldValue

**位置**：[company-fields.service.ts:556-559](server/src/modules/company-fields/company-fields.service.ts#L556-L559)

### 缺陷 R13（低）：`topoSortCalcFields` 使用 O(n²) 的 Kahn 实现

**位置**：[company-fields.service.ts:668-688](server/src/modules/company-fields/company-fields.service.ts#L668-L688)

```typescript
for (const g of calcFields) {           // O(n) 外层
  if (deps[g.fieldKey]?.has(f.fieldKey)) {  // O(n) 内层

  }

```

**问题**：对每个出队节点，遍历所有计算字段检查依赖。若有 k 个计算字段，复杂度 O(k²)。

**建议**：构建反向邻接表，将复杂度降至 O(k + e)。

## 二、字段同步机制

### 当前架构

```
写操作完成
    ↓
PrismaService $allOperations 审计中间件
    ↓
RealtimeService.emitResourceChanged("company-field", id, competitionId, "updated")
    ↓
Socket.IO → comp-{competitionId} 房间
    ↓
前端 resource-changed.ts 监听
    ↓
useResourceChanged("company-field", reloadFn) → 组件重拉
    ↓
GET /company-fields/:companyId?updatedAfter=xxx（增量模式）
    ↓
getValues() → 返回变更字段 + existingIds + serverTime
    ↓
前端 patchFullItems 合并到本地 IndexedDB 全量副本
```

---

### 缺陷 S1（严重）：`company-field:changed` 广播不经过 Prisma 审计中间件

**位置**：[company-fields.service.ts:291-294](server/src/modules/company-fields/company-fields.service.ts#L291-L294)

```typescript
this.realtime.broadcastToCompetition(company.competitionId, "company-field:changed", {
  companyId,
  competitionId: company.competitionId,
});
```

**问题**：`company-field:changed` 是由 service 层**手动**调用 `broadcastToCompetition` 发出的，不经过 Prisma 的 `$allOperations` 审计中间件。而 `CompanyFieldValue` 的写入（upsert）会触发中间件广播 `resource:changed { resource: "company-field", action: "updated" }`。

这意味着前端会收到**两种**不同的事件：
1. `resource:changed { resource: "company-field" }` — 来自 Prisma 中间件
2. `company-field:changed` — 来自 service 手动广播

**影响**：前端可能收到重复通知，触发两次重拉。

**建议**：统一为一种事件。要么 service 层不手动广播（依赖 Prisma 中间件），要么中间件排除 `CompanyFieldValue` 模型。

---

### 缺陷 S2（严重）：合同执行后广播时序可能导致前端读到中间状态

**位置**：合同执行流程

```
1. contractEngine.execute() — 直写 CompanyFieldValue（多条）
2. companyFieldsService.recomputeCalculatedFieldsForCompany() — 重算计算字段
3. realtime.broadcastToCompetition("contract:changed")
4. realtime.broadcastToCompetition("company-field:changed")
```

**问题**：步骤 1 的每次 `CompanyFieldValue.upsert` 都会触发 Prisma 中间件广播 `resource:changed`。前端在步骤 1 完成后立即收到通知并重拉字段值，但此时步骤 2（重算）尚未执行。前端读到的是**重算前**的值（基础字段已更新但计算字段还是旧值）。

**影响**：前端短暂显示不一致状态（基础字段新值 + 计算字段旧值）。

**建议**：
1. 合同执行期间抑制 Prisma 中间件对 `CompanyFieldValue` 的广播
2. 在重算完成后统一广播一次 `company-field:changed`

---

### 缺陷 S3（高）：增量模式下 `existingIds` 不含隐藏字段，但隐藏字段可能有值

**位置**：[company-fields.service.ts:167-169](server/src/modules/company-fields/company-fields.service.ts#L167-L169)

```typescript
const existingIds = visibleFields
  .filter((f: any) => isPublished(companyId, f.id))
  .map((f: any) => f.id);
```

**问题**：`existingIds` 仅包含可见且已发布的字段定义 id。若字段被隐藏（`visible: false`），其 id 不在 `existingIds` 中。前端 diff 逻辑会认为该字段被**删除**，从本地副本中移除。

但实际上 `CompanyFieldValue` 记录仍然存在（隐藏只是展示层行为）。若字段后来重新可见，前端需要重新全量同步才能恢复。

**影响**：频繁切换 `visible` 标志时，前端本地副本可能不稳定。

**建议**：`existingIds` 应包含所有有 `CompanyFieldValue` 记录的字段（含隐藏），前端根据 `visible` 字段自行过滤显示。

### 缺陷 S6（中）：`broadcastToCompetition` 使用的房间名与前端订阅不匹配

**位置**：`realtime.service.ts`

前端 `subscribeCompetition(competitionId)` 订阅房间 `comp-{competitionId}`。
`broadcastToCompetition(competitionId, event, data)` 向 `comp-{competitionId}` 广播。

但 `company-field:changed` 的 payload 中包含 `companyId`，前端需要根据这个 `companyId` 判断是否需要重拉。若前端监听的是通用 `resource:changed` 事件，它按 `resource` 过滤而非 `companyId`。

**问题**：两种事件（`resource:changed` 和 `company-field:changed`）的过滤逻辑不同，前端可能遗漏其中一种。

**建议**：统一事件格式，确保前端 `useResourceChanged` 能正确处理。

### 缺陷 S7（中）：增量基线过期后 `requireExistingIds=true` 但 `getValues` 的 existingIds 不含已删除字段的 id

**位置**：[company-fields.service.ts:167-169](server/src/modules/company-fields/company-fields.service.ts#L167-L169)

```typescript
const existingIds = visibleFields.map((f: any) => f.id);
```

**问题**：`existingIds` 基于当前 `IndustryField` 定义。若字段定义被删除，其 id 不在 `existingIds` 中。前端 diff 出"字段已删除"并从本地副本移除——这是正确的。

但若字段定义存在但 `CompanyFieldValue` 被删除（如合同回滚），`existingIds` 仍包含该字段 id，前端不会移除它，但值为 null。这可能导致前端显示空值而非"未初始化"。

**影响**：边界情况下前端可能显示空值。

### 缺陷 S8（中）：`getValues` 的 `publishedOnly` 过滤与 `visible` 过滤顺序不当

**位置**：[company-fields.service.ts:152-178](server/src/modules/company-fields/company-fields.service.ts#L152-L178)

```typescript

  ? baseFields
  : baseFields.filter((f: any) => f.visible !== false);

// 第 178 行：再过滤 published
.filter((f: any) => isPublished(companyId, f.id))
```

**问题**：若字段 `visible: false` 但已发布到区域总览，`visibleFields` 先将其过滤掉，`publishedOnly` 用户永远看不到它。

但文档 §9.8 说：「隐藏字段仍可在区域总览被选中并发布（仅公司管理界面不展示）」。

**影响**：隐藏但已发布的字段对受限用户不可见，与文档描述矛盾。

**建议**：在 `publishedOnly` 模式下，将过滤顺序改为：先取已发布字段集合，再与可见字段取并集（已发布字段不受 `visible` 限制）。

### 缺陷 S9（低）：`serverNowIso()` 在增量响应中作为 `serverTime` 返回

**位置**：[company-fields.service.ts:208](server/src/modules/company-fields/company-fields.service.ts#L208)

```typescript

```

**问题**：`serverNowIso()` 在查询**之后**调用。若查询耗时较长，`serverTime` 可能晚于实际数据的 `updatedAt`，导致下次增量请求的基线略晚于最后一条记录的更新时间，理论上可能漏掉极短时间内的并发写入。

**影响**：极端竞态下增量同步可能遗漏最近的变更（概率极低）。

**建议**：在查询**之前**记录 `serverTime`，或使用数据库的 `CURRENT_TIMESTAMP`。
